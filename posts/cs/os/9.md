# Unit 9: Disk and Storage

> **How to use this page.** Section IDs (`OS-9.2`) match the tags on practice questions. Arrows like **→ OS-10.2** point to where an idea is developed further; **← OS-8.5** points back to something this section depends on.

Unit 8 treated storage as an array of numbered blocks. This unit looks inside the devices behind that abstraction. A hard disk is a mechanical device where *where* data sits determines how long it takes to reach it; an SSD is an electronic device with strange rules about overwriting. Both shape how the OS schedules requests and lays out data. Then RAID combines many devices into one that is faster, larger, and survives failures, and swap space ties storage back to virtual memory.

---

## OS-9.1 · Hard Disk Drives

### Physical structure

```
        spindle
          |
   ===============   <- platter (two surfaces, both used)
          |      \___ arm with read/write head (one per surface)
   ===============
          |
   ===============

 Top view of one surface:
        _______________
      /   ___________   \      track: one ring on a surface
     |   /   _____   \   |     sector: a slice of a track (512 B or 4 KB)
     |  |   /     \   |  |     cylinder: the set of tracks at the same
     |  |  |   o   |  |  |               arm position on all surfaces
     |  |   \_____/   |  |
     |   \___________/   |
      \_______________ /
```

- **Platters** coated with magnetic material spin on a **spindle** at a constant speed: 5,400, 7,200, 10,000, or 15,000 RPM.
- Each surface is divided into concentric **tracks**, each divided into **sectors**, the smallest unit the drive reads or writes (traditionally 512 bytes; modern "Advanced Format" drives use 4 KB physical sectors).
- A **disk arm** moves all the **heads** together across the surfaces. The tracks under the heads at one arm position form a **cylinder**.
- Outer tracks are longer than inner ones, so modern drives put **more sectors on outer tracks** (zoned bit recording). Since the rotation speed is constant, outer tracks transfer data faster.

The drive presents itself to the OS as a linear array of **logical block addresses (LBA)** 0 to n−1. The drive's firmware maps each LBA to a physical location, roughly filling one track, then the next track on the same cylinder, then the next cylinder. The old cylinder/head/sector (CHS) addressing is obsolete, but the principle remains: **nearby LBAs are physically close**, so the OS can still reason about locality.

### Access time

Reading or writing a sector requires three steps:

```
 T_I/O = T_seek + T_rotation + T_transfer
```

1. **Seek time:** move the arm to the correct track. It includes acceleration, coasting, deceleration, and **settling** (fine positioning). A full-stroke seek might take 15 to 20 ms; the **average** seek is commonly quoted at roughly a third of the full stroke, typically **4 to 9 ms**. Short seeks to nearby tracks are much cheaper, which is what disk scheduling exploits (→ OS-9.2).
2. **Rotational latency:** wait for the desired sector to rotate under the head. The **average is half a rotation**:

```
 one rotation = 60,000 ms / RPM          average rotational latency = half of that
 7,200 RPM:  8.33 ms per rotation   ->   4.17 ms average
 15,000 RPM: 4 ms per rotation      ->   2 ms average
```

3. **Transfer time:** the data passes under the head: `size / transfer rate`. At 100 to 250 MB/s, 4 KB takes only about 0.02 to 0.04 ms.

**For small random requests, seek and rotation dominate completely.** OSTEP's comparison of two drives:

| | "Cheetah" (15,000 RPM, server) | "Barracuda" (7,200 RPM, capacity) |
|---|---|---|
| Average seek | 4 ms | 9 ms |
| Max transfer | 125 MB/s | 105 MB/s |
| Random 4 KB read | 4 + 2 + 0.03 ≈ **6 ms** → 0.66 MB/s | 9 + 4.2 + 0.04 ≈ **13.2 ms** → 0.31 MB/s |
| Sequential 100 MB read | ≈ 800 ms → 125 MB/s | ≈ 950 ms → 105 MB/s |

Random I/O is **100 to 300 times slower** than sequential I/O on the same disk. This single fact drives file-system design (FFS block groups, extents, LFS ← OS-8.4, OS-8.6) and disk scheduling. The number of random operations a device can do per second (**IOPS**) is 1 / T_I/O: about 75 to 200 for hard disks.

### Other details

- **Disk cache (track buffer):** a few hundred MB of RAM in the drive. On reads, the drive may cache the whole track. On writes, it can report completion as soon as the data is in its cache (**write-back** caching: fast, but data can be lost on power failure, and the drive may reorder writes, which is why file systems issue cache-flush or FUA commands at commit points ← OS-8.6) or only after the data is on the platter (**write-through**).
- **Track skew:** when reading across a track boundary, the next track's first sector is offset slightly, so that it has not already passed under the head by the time the (short) head switch or seek completes.
- **Interfaces:** SATA and SAS for disks; NVMe over PCIe for SSDs (→ OS-9.3).
- **Shingled magnetic recording (SMR)** drives overlap tracks like roof shingles to increase density; writing a track damages the next one, so they must be written sequentially in zones (random writes are very slow). They behave a little like SSDs.

## OS-9.2 · Disk Scheduling

When many requests are pending, the OS (or the drive itself) can choose the **order** in which to serve them to reduce seek time. Rotational latency is hard for the OS to optimize, since it does not know the head's angular position; drives do that internally.

Throughout this section: cylinders **0 to 199**, head currently at **53**, pending requests (in arrival order):

```
 98, 183, 37, 122, 14, 124, 65, 67
```

The measure is **total head movement** (number of cylinders crossed). Traces and totals are summarized in N3.

### FCFS

Serve requests in arrival order. Fair and simple, with no starvation, but no attempt to reduce seeks.

```
 53 -> 98 -> 183 -> 37 -> 122 -> 14 -> 124 -> 65 -> 67
 movement: 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = 640 cylinders
```

Note the wild swings (183 → 37 → 122 → 14).

### SSTF (shortest seek time first)

Always serve the pending request **closest** to the current head position (like SJF ← OS-3.3).

```
 53 -> 65 -> 67 -> 37 -> 14 -> 98 -> 122 -> 124 -> 183
 movement: 12 + 2 + 30 + 23 + 84 + 24 + 2 + 59 = 236 cylinders
```

- Much better than FCFS.
- **Starvation:** under heavy load, a steady stream of requests near the head can keep a far-away request waiting indefinitely.
- Not optimal: here, going 53 → 37 → 14 first and then sweeping up to 183 gives 39 + 169 = 208.

**SPTF / SATF** (shortest positioning/access time first): like SSTF but also accounts for rotational delay. Only the drive knows the rotational position, so this is done inside the drive (native command queuing, NCQ), with the OS passing it a batch of requests.

### SCAN (elevator)

The head moves in one direction, serving every request on the way, **all the way to the end** of the disk, then reverses. Like an elevator going up and then down.

With the head moving **toward 0**:

```
 53 -> 37 -> 14 -> [0] -> 65 -> 67 -> 98 -> 122 -> 124 -> 183
 movement: 53 (down to 0) + 183 (up to 183) = 236 cylinders
```

- No starvation: every request is served within two sweeps.
- **Uneven waiting:** when the head reverses at one end, the requests just behind it were only just served, while the heaviest backlog is at the **far end**, which waits longest. Requests in the middle of the disk get served more often than requests at the edges.

### C-SCAN (circular SCAN)

Serve requests in **one direction only**; on reaching the end, return immediately to the other end **without serving** anything on the way back, and sweep again. It treats the cylinders as a circular list.

With the head moving **toward 199**:

```
 53 -> 65 -> 67 -> 98 -> 122 -> 124 -> 183 -> [199] => [0] -> 14 -> 37
 movement: 146 (to 199) + 199 (return) + 37 = 382 cylinders   (183 if the return is not counted)
```

More **uniform waiting time** than SCAN: every position waits about one full cycle. The return trip is a single long seek, which is faster per cylinder than many short seeks, so some texts do not count it. **State your convention** in answers.

### LOOK and C-LOOK

Practical versions of SCAN and C-SCAN: the arm goes only **as far as the last request** in each direction, not to the physical end of the disk.

**LOOK**, head moving toward 199:

```
 53 -> 65 -> 67 -> 98 -> 122 -> 124 -> 183 -> 37 -> 14
 movement: 130 + 169 = 299 cylinders
```

(LOOK moving toward 0 instead: 53 → 37 → 14 → 65 → ... → 183 = 39 + 169 = **208**.)

**C-LOOK**, head moving toward 199:

```
 53 -> 65 -> 67 -> 98 -> 122 -> 124 -> 183 => 14 -> 37
 movement: 130 + 169 (jump back) + 23 = 322 cylinders   (153 without the jump)
```

### Choosing an algorithm

- Performance depends heavily on the **number and pattern** of requests. With only one request pending, every algorithm behaves the same.
- **SSTF** is a natural default; **SCAN/C-SCAN** (LOOK/C-LOOK) perform better under heavy load and avoid starvation.
- File allocation affects scheduling: a contiguously allocated file generates nearby requests; scattered metadata (directories, inodes) generates long seeks, which is why file systems place metadata near data.
- **The drive knows more than the OS** (exact geometry, rotational position, remapped sectors), so modern OSes send several requests at once and let the drive reorder (NCQ holds up to 32 commands).

### Linux I/O schedulers

The block layer (in multi-queue form, blk-mq) offers several schedulers per device:

| Scheduler | Idea | Best for |
|---|---|---|
| `none` | No reordering; just merge adjacent requests | Fast NVMe SSDs (→ S3) |
| `mq-deadline` | Sorted by sector (elevator-like), but each request has a **deadline** (reads ~500 ms, writes ~5 s) so none starves; favours reads | HDDs, SATA SSDs, general use |
| `bfq` | Budget Fair Queueing: proportional share of disk time per process (like CFS for disks ← OS-3.7), good interactivity | Desktops with slow disks |
| `kyber` | Token-based, targets latency goals | Fast multi-queue devices |

The older CFQ (completely fair queueing) and the *anticipatory* scheduler (which briefly **waited** after a read, betting that the same process would soon issue another nearby read, avoiding a seek away and back) were removed when Linux moved to blk-mq.

Two general techniques in every scheduler: **merging** (combine requests for adjacent blocks into one larger request) and **plugging** (hold requests briefly to collect a batch before dispatching).

## OS-9.3 · Solid-State Drives

### NAND flash basics

An SSD stores data in **NAND flash** memory: transistors that trap electric charge. Cells store 1 bit (**SLC**), 2 (**MLC**), 3 (**TLC**), or 4 (**QLC**) bits by distinguishing charge levels. More bits per cell means more capacity per chip, but slower writes and fewer write cycles.

Flash is organized in a strict hierarchy with **asymmetric operations**:

```
 chip -> planes -> blocks (erase unit: e.g., 128 to 256+ pages, several MB)
                     -> pages (read/program unit: e.g., 4 to 16 KB)
```

| Operation | Unit | Typical time |
|---|---|---|
| **Read** | Page | ~25 to 100 µs |
| **Program** (write) | Page, only if it is **erased** | ~200 µs to 1.5 ms |
| **Erase** | **Whole block** | ~1.5 to 5 ms |

The key constraints:

1. **No in-place overwrite.** A page can be programmed only once after its block has been erased. To change a page, you must write the new data somewhere else (or erase the whole block, destroying all other pages in it).
2. **Erase is by block**, which is much larger than a page and slow.
3. **Wear out:** each block survives a limited number of program/erase (P/E) cycles, roughly 100,000 for SLC, about 10,000 for MLC, about 3,000 for TLC, and about 1,000 for QLC. After that, cells no longer hold charge reliably.

### The flash translation layer (FTL)

The SSD's controller runs firmware, the **FTL**, which hides these constraints and presents the same interface as a disk: an array of logical blocks that can be read and written in any order (OSTEP Chapter 44).

- **Log-structured writing:** every write goes to the **next free (erased) page**, never to the old location, like LFS (← OS-8.6). The old page is marked **invalid**.
- **Mapping table:** the FTL maintains a **logical-to-physical** map (logical block → physical page), usually held in the SSD's DRAM. With page-level mapping, 1 TB of 4 KB pages with 4-byte entries needs a 1 GB table: SSDs carry roughly 1 GB of DRAM per TB for this reason (N5). DRAM-less SSDs use host memory or cache only part of the map. (Older designs used block-level or hybrid mappings to shrink the table, at the cost of slow small writes.)
- **Garbage collection (GC):** blocks gradually fill with a mix of valid and invalid pages. To reclaim space, the FTL picks a block with many invalid pages, **copies its remaining valid pages** elsewhere, updates the map, and **erases** the block.
- **Write amplification (WA):**

```
                physical writes to flash
 WA  =  -----------------------------------
          logical writes from the host
```

GC copying makes WA greater than 1: the host writes 1 page, but the SSD may write several internally. High WA reduces performance and wears the flash faster (N5).

- **Over-provisioning:** SSDs contain more flash than they advertise (for example, 7% to 28% extra), giving GC free blocks to work with and lowering WA.
- **Wear leveling:** spread P/E cycles evenly across all blocks. *Dynamic* wear leveling directs new writes to less-worn free blocks. *Static* wear leveling also occasionally moves **cold** data (written once, rarely changed) off low-wear blocks so those blocks can take their share of writes.
- **TRIM:** as explained in ← OS-8.5, the file system tells the SSD which logical blocks are no longer used, so GC does not waste effort copying dead data.
- **Power-loss protection:** the mapping table must survive crashes; enterprise SSDs have capacitors to flush the DRAM on power loss.

### Consequences for the OS

- **No seek or rotational delay:** random reads are nearly as fast as sequential reads. Seek-optimizing schedulers are pointless; Linux uses `none` or `mq-deadline` (S3).
- **Parallelism:** an SSD contains many flash chips that work in parallel, so it performs best with **many outstanding requests**. **NVMe** exposes up to 65,535 queues, each up to 65,536 commands deep, typically one submission/completion queue pair per CPU core, avoiding locks between cores.
- **Writes** are more expensive than reads, and small random overwrites are the worst case (high GC load). Sequential writes are friendliest.
- The file system's own layout decisions (FFS-style placement) matter less; flash-aware file systems (F2FS) write sequentially to cooperate with the FTL.
- **Deleted data is really gone** after TRIM and GC, which complicates forensic recovery (S5); conversely, "overwriting" a file does not reliably destroy the old data on an SSD (the old pages may survive until erased), so secure deletion requires the drive's secure-erase command or encryption.

### HDD vs SSD

| | HDD (7,200 RPM) | SATA SSD | NVMe SSD |
|---|---|---|---|
| Random 4 KB read latency | ~5 to 15 ms | ~50 to 100 µs | ~10 to 100 µs |
| Random read IOPS | ~75 to 200 | ~50,000 to 100,000 | 500,000 to 1,000,000+ |
| Sequential throughput | ~100 to 250 MB/s | ~550 MB/s (SATA limit) | 3 to 14 GB/s |
| Cost per TB | Lowest | Higher | Higher |
| Wear | Mechanical failure, no write limit | Limited P/E cycles | Limited P/E cycles |
| Scheduler relevance | High | Low | Minimal |

## OS-9.4 · Formatting, Partitions, Boot Blocks, and Bad Blocks

### Low-level (physical) formatting

Before a disk can store data, it is divided into sectors that the controller can read and write. Each sector has a **header** (sector number), a **data area** (512 bytes or 4 KB), and a **trailer** containing an **error-correcting code (ECC)**. On every write, the controller computes the ECC; on every read, it recomputes and compares. If a few bits are wrong, ECC **corrects** them (a *soft error*); if too many are wrong, the read fails. This formatting is done at the factory.

**Advanced Format:** 4 KB physical sectors (less space lost to headers and gaps, stronger ECC). For compatibility, many drives present 512-byte logical sectors ("512e"). A write that does not cover a whole 4 KB physical sector forces the drive to read, modify, and write the physical sector, so partitions must be **aligned** to 4 KB boundaries (modern tools align at 1 MiB → S11).

### Partitioning and logical formatting

1. **Partitioning:** divide the device into one or more partitions, recorded in a partition table (**MBR** or **GPT** ← OS-1.7). Each partition is treated as a separate device (`/dev/sda1`, `/dev/nvme0n1p2`).
2. **Volume management** (optional): LVM on Linux combines partitions or disks into flexible logical volumes that can be resized, spanned, or snapshotted.
3. **Logical formatting:** create a file system on the partition (`mkfs.ext4`): superblock, bitmaps, inode tables, root directory, journal (← OS-8.7).

Some applications use a partition **raw**, without a file system: some databases (to control exactly where data goes and avoid double buffering), and historically swap space (→ OS-9.6).

### The boot block

At power-on, firmware must find and start the OS (← OS-1.7). A small bootstrap program in firmware (ROM/flash on the motherboard) loads a **boot block** from a known location:

- **BIOS:** sector 0 of the boot disk, the **MBR**, containing 446 bytes of boot code plus the partition table; it loads a larger bootloader from the **boot partition**.
- **UEFI:** reads a bootloader file from the EFI System Partition (a FAT file system).

A disk containing a boot partition is a **boot disk** or system disk.

### Bad blocks

Disks have moving parts and small tolerances, so sectors can fail (a head crash destroys the whole disk; more often, individual sectors go bad).

- **Old approach (IDE):** bad blocks were found during formatting or by fsck, and marked unusable in the file system's own structures.
- **Modern drives:** the controller maintains a list of bad sectors and keeps **spare sectors** (on each cylinder and in reserved areas).
  - **Sector sparing (forwarding):** when a sector goes bad, the controller transparently remaps its LBA to a spare. The OS sees nothing, but the remapped block may now be physically far away, so an OS scheduling decision based on LBA order may cause an unexpected seek.
  - **Sector slipping:** instead of jumping to a distant spare, shift every sector after the bad one down by one, so the spare immediately follows; this keeps logically adjacent blocks physically adjacent but requires moving data.
- A soft error (corrected by ECC, or succeeding on retry) may trigger remapping preventively. A hard error loses data: it must be restored from backups (or redundancy such as RAID).
- **SMART** (self-monitoring, analysis, and reporting technology) exposes counters such as *reallocated sector count* and *pending sectors*; a rising count is a strong warning that the drive is failing (S10). `smartctl -a /dev/sda` shows them.
- SSDs handle bad blocks inside the FTL: worn or defective blocks are retired and replaced from spare capacity.

## OS-9.5 · RAID

**RAID** (Redundant Array of Independent, originally "Inexpensive," Disks: Patterson, Gibson, Katz, 1988) combines several disks into one logical disk to gain:

- **Performance:** requests spread over several disks run in parallel.
- **Capacity:** one large volume.
- **Reliability:** data survives the failure of one (or more) disks.

It is transparent: to the file system, a RAID looks like a single large disk. It can be implemented in a **hardware** controller (often with a battery-backed write cache) or in **software** (Linux `md`/`mdadm`, ZFS, Btrfs).

### Why reliability needs redundancy

With many disks, **some** disk fails often. If one disk's mean time to failure (MTTF) is 100,000 hours, an array of 100 disks has, on average, a failure every 100,000 / 100 = **1,000 hours** (about 42 days). Without redundancy, each failure loses data.

With **mirroring**, data is lost only if the second copy fails **before the first is replaced and rebuilt** (the mean time to repair, MTTR). For independent failures:

```
 mean time to data loss (mirrored pair) ≈ MTTF² / (2 × MTTR)
 = 100,000² / (2 × 10 h) = 5 × 10⁸ hours ≈ 57,000 years
```

Real failures are **not** independent (same batch of disks, same power surge, same heat, same age), so real reliability is much lower (N8).

### Striping and chunk size

**Striping** spreads consecutive blocks across disks. With N disks and a chunk of one block:

```
          Disk 0   Disk 1   Disk 2   Disk 3
 stripe 0:   0        1        2        3
 stripe 1:   4        5        6        7
 stripe 2:   8        9       10       11
 logical block A -> disk (A mod N), offset (A div N)
```

The **chunk size** is how many consecutive blocks go to one disk before moving to the next. Small chunks spread a single file across many disks (high parallelism for one large request, but every disk must seek for it); large chunks keep each small request on one disk (less parallelism within a request, but more independent requests in parallel).

### RAID levels

**RAID 0: striping, no redundancy.** Full capacity and the best performance, but **any single disk failure loses the array** (reliability is worse than a single disk). Used for scratch data.

**RAID 1: mirroring.** Every block is written to two (or more) disks. Reads can be served by either copy; writes must go to both (in parallel). Capacity is halved. Survives one failure per mirrored pair. Rebuild is a simple copy.

**RAID 2 and 3** (bit- or byte-level striping with Hamming codes or dedicated parity) are obsolete: drives have their own ECC, and fine-grained striping forces every disk to participate in every request.

**RAID 4: block striping with a dedicated parity disk.** For each stripe, the parity disk stores the **XOR** of the data blocks:

```
 P = D0 ⊕ D1 ⊕ D2 ⊕ D3
```

If any one disk fails, each lost block is reconstructed as the XOR of all the surviving blocks in its stripe (XOR is its own inverse). See N7.

- **Small writes** (updating one block): the new parity can be computed without reading the whole stripe, by **subtractive parity**:

```
 P_new = P_old ⊕ D_old ⊕ D_new
```

  This takes **4 I/Os**: read old data, read old parity, write new data, write new parity.
- **Bottleneck:** every write in the array must update the **single parity disk**, so random writes are serialized on it: the array does only about R/2 small writes per second, however many disks it has.

**RAID 5: block striping with distributed parity.** Like RAID 4, but the parity block **rotates** among the disks from stripe to stripe:

```
          Disk 0   Disk 1   Disk 2   Disk 3   Disk 4
 stripe 0:  D0       D1       D2       D3       P0
 stripe 1:  D5       D6       D7       P1       D4
 stripe 2:  D10      D11      P2       D8       D9
 stripe 3:  D15      P3       D12      D13      D14
```

Small writes to different stripes now use different parity disks and proceed in parallel. Each small write still costs 4 I/Os (the **RAID 5 write penalty**), so random-write throughput is N × R / 4. Capacity: N − 1 disks. Survives one failure.

**RAID 6: double parity (P + Q).** Two independent parity blocks per stripe (P is XOR; Q uses Reed-Solomon coding over a Galois field), distributed like RAID 5. Survives **any two** simultaneous failures. Capacity N − 2; a small write costs **6 I/Os**. Increasingly necessary with large disks, because rebuilding takes many hours, and a second failure or an unreadable sector during the rebuild would otherwise lose data (N8, S7).

**RAID 10 (1+0): a stripe of mirrors.** Pair disks into mirrors, then stripe across the pairs. Excellent performance (no parity computation, small write = 2 I/Os), fast rebuilds (copy one disk), survives one failure per pair. Capacity halved. The usual choice for databases.

**RAID 01 (0+1): a mirror of stripes** (two RAID 0 arrays mirrored). A single failure kills a whole stripe set, leaving the array with no redundancy, so RAID 10 is preferred.

### Comparison (OSTEP's analysis)

N disks, each with B blocks, sequential bandwidth S, random I/O rate R:

| | RAID 0 | RAID 1 (mirror pairs) | RAID 4 | RAID 5 |
|---|---|---|---|---|
| Capacity | N·B | N·B / 2 | (N − 1)·B | (N − 1)·B |
| Failures tolerated | 0 | 1 (up to N/2 if lucky) | 1 | 1 |
| Sequential read | N·S | (N/2)·S | (N − 1)·S | (N − 1)·S |
| Sequential write | N·S | (N/2)·S | (N − 1)·S | (N − 1)·S |
| Random read | N·R | N·R | (N − 1)·R | N·R |
| Random write | N·R | (N/2)·R | R / 2 | (N/4)·R |
| Write latency | T | T | 2T | 2T |

(Mirrored sequential reads are listed at (N/2)·S because each disk skips over the blocks read by its partner; smarter controllers do better. RAID 6 behaves like RAID 5 with capacity (N − 2)·B and random writes about (N/6)·R.)

### Practical issues

- **Hot spares:** idle disks that automatically replace a failed disk so the rebuild starts immediately, shrinking MTTR.
- **Rebuild:** reconstructing a failed disk means reading **every** surviving disk completely; with multi-terabyte disks this takes hours to days, during which performance drops and another failure is fatal (for RAID 5).
- **The write hole:** in RAID 5/6, if power fails after writing the data but before writing the parity, the stripe's parity is silently wrong; if a disk then fails, reconstruction produces garbage. Remedies: battery- or flash-backed controller caches, a journal of in-flight stripe updates (Linux md's write journal), or ZFS's RAID-Z, which writes full, variable-width stripes copy-on-write so partial stripes never exist (S9).
- **RAID is not a backup:** it protects against disk failure, not against deletion, corruption by software, ransomware, or a fire (S8).

## OS-9.6 · Swap-Space Management

**Swap space** is the backing store for anonymous pages (heap, stack, COW copies) evicted by virtual memory (← OS-7.1). File-backed pages do not need swap: clean ones are re-read from their file, and dirty ones are written back to their file.

### Where swap lives

- **Swap partition:** a raw partition with a special format, managed by a dedicated swap-space manager optimized for speed rather than for storage efficiency (swap data is short-lived and never needs to survive a reboot).
- **Swap file:** an ordinary file in a file system. Historically slower (going through the file system's structures); modern Linux maps the file's block locations once at `swapon` and then does I/O directly to those blocks, so performance is essentially the same as a partition. Easier to resize.

Linux can use several swap areas at once, with **priorities** (use the faster device first; equal priorities are striped).

### How Linux manages swap

- Each swap area is divided into **page slots** (4 KB).
- A **swap map** is an array of counters, one per slot: 0 = free; a positive value = the number of processes whose page tables point to that slot (a shared anonymous page swapped out once counts once per sharer).
- When a page is swapped out, its PTE (marked not-present) stores the **swap area and slot number**, so the page fault handler knows where to read it from.
- `vm.swappiness` (0 to 200, default 60) tunes the balance between reclaiming file-backed pages and swapping anonymous pages.
- Swap space is allocated only when a page is actually evicted (not when memory is allocated), as in Solaris and most modern systems.

### How much swap?

Old rules of thumb ("twice the RAM") come from systems with little memory. Today:

- Servers with plenty of RAM often use a small amount of swap (a few GB), mainly so that cold anonymous pages can be moved out, leaving RAM for the page cache and active data, and to absorb short spikes.
- **Hibernation** (suspend to disk) writes the contents of RAM into swap, so it needs swap at least as large as the memory in use (S12).
- **Compressed memory** alternatives: **zram** (a compressed block device in RAM used as swap, common on Android and ChromeOS) and **zswap** (a compressed cache in front of a real swap device). Compressing pages is much faster than writing them to disk and avoids flash wear.
- Too much swap on a busy system can mean long periods of thrashing before the OOM killer acts (← OS-7.6).

## Quick Revision Sheet

- HDD: platters, tracks, sectors, cylinders; drive exposes LBAs; nearby LBAs are physically close.
- T_I/O = seek + rotational latency + transfer. Average rotation = half a revolution (7,200 RPM → 4.17 ms).
- Random small I/O is dominated by seek + rotation; random is 100× or more slower than sequential. HDD IOPS ≈ 75 to 200.
- Disk cache: write-back is fast but needs explicit flushes for durability.
- FCFS (fair, slow), SSTF (good, starvation), SCAN (elevator, to the end), C-SCAN (one direction, uniform wait), LOOK / C-LOOK (only to the last request).
- Classic queue (head 53): FCFS 640, SSTF 236, SCAN toward 0 236, C-SCAN up 382 (183 without return), LOOK up 299, C-LOOK up 322 (153 without jump).
- Linux: `none` for NVMe, `mq-deadline` (sorted + deadlines), `bfq` (fair share). Merging and plugging.
- Flash: read/program per page, erase per block, no overwrite in place, limited P/E cycles (SLC > MLC > TLC > QLC).
- FTL: log-structured writes, logical→physical map (~1 GB DRAM per TB), garbage collection, write amplification, over-provisioning, wear leveling, TRIM.
- NVMe: many deep queues, one pair per core; scheduling mostly irrelevant.
- Low-level formatting: sector header + data + ECC trailer. 4K Advanced Format needs aligned partitions.
- Partition (MBR/GPT) → optional LVM → logical format (mkfs). Raw partitions for some databases.
- Bad blocks: ECC, spare sectors (sparing, slipping); SMART reallocated counts warn of failure.
- RAID 0 striping (no redundancy), RAID 1 mirroring, RAID 4 dedicated parity (parity-disk bottleneck), RAID 5 distributed parity (small write = 4 I/Os), RAID 6 P+Q (6 I/Os, two failures), RAID 10 stripe of mirrors.
- Parity = XOR; lost block = XOR of the rest; P_new = P_old ⊕ D_old ⊕ D_new.
- Array MTTF = disk MTTF / N; mirrored MTTDL ≈ MTTF² / (2·MTTR). Rebuild windows and correlated failures matter.
- Write hole; hot spares; RAID is not a backup.
- Swap: partition or file; swap map counters per slot; PTE stores swap location; swappiness; zram/zswap; hibernation needs swap.

## Worked Numerical Problems

### N1 · Disk access time and IOPS (OS-9.1)

**Question.** A 7,200 RPM disk has an average seek time of 9 ms and a transfer rate of 100 MB/s. (a) Average time to read a random 4 KB block? (b) Random-read IOPS and throughput? (c) Time to read a 400 MB file stored contiguously vs as 100,000 random 4 KB blocks? (d) Repeat (a) and (b) for a 15,000 RPM disk with a 4 ms seek and 125 MB/s.

**Answer.**

(a) Rotation = 60,000 / 7,200 = 8.33 ms → average rotational latency **4.17 ms**. Transfer = 4 KB / 100 MB/s ≈ **0.04 ms**. Total ≈ 9 + 4.17 + 0.04 = **13.2 ms**.

(b) IOPS = 1 / 13.2 ms ≈ **76**. Throughput = 76 × 4 KB ≈ **0.31 MB/s**.

(c) Contiguous: one seek + rotation (≈ 13 ms) + 400 MB / 100 MB/s = 4 s → **≈ 4.01 s**. Random: 100,000 × 13.2 ms = **1,320 s = 22 minutes**. The same data takes 330 times longer when scattered.

(d) Rotation = 4 ms → average **2 ms**. Transfer ≈ 0.03 ms. Total ≈ 4 + 2 + 0.03 = **6.03 ms** → **≈ 166 IOPS**, ≈ **0.66 MB/s**. A faster, more expensive disk only doubles random performance.

### N2 · Disk geometry and capacity (OS-9.1)

**Question.** A disk has 4 platters (both surfaces used), 100,000 tracks per surface, an average of 1,000 sectors per track, and 512-byte sectors, spinning at 7,200 RPM. (a) Capacity? (b) How many bits are needed for an LBA? (c) Maximum sustained transfer rate from a track with 1,000 sectors? (d) What does zoned recording do to this rate on outer tracks with 1,500 sectors?

**Answer.**

(a) Surfaces = 8. Sectors = 8 × 100,000 × 1,000 = 8 × 10⁸. Capacity = 8 × 10⁸ × 512 B = **409.6 GB**.

(b) 8 × 10⁸ < 2³⁰ (≈ 1.07 × 10⁹), so **30 bits**.

(c) One track passes under the head per rotation: 1,000 × 512 B = 512,000 B every 8.33 ms → **≈ 61.4 MB/s**.

(d) 1,500 × 512 B per 8.33 ms → **≈ 92 MB/s**. Outer tracks are faster at the same RPM, which is why the start of a disk (low LBAs, mapped to outer tracks) usually benchmarks faster than the end.

### N3 · Disk scheduling totals (OS-9.2)

**Question.** Cylinders 0 to 199, head at 53, queue: 98, 183, 37, 122, 14, 124, 65, 67. Find total head movement for FCFS, SSTF, SCAN (moving toward 0), SCAN (moving toward 199), C-SCAN (toward 199), LOOK (toward 199), and C-LOOK (toward 199).

**Answer.**

| Algorithm | Order served | Total movement |
|---|---|---|
| FCFS | 98, 183, 37, 122, 14, 124, 65, 67 | **640** |
| SSTF | 65, 67, 37, 14, 98, 122, 124, 183 | **236** |
| SCAN (toward 0) | 37, 14, [0], 65, 67, 98, 122, 124, 183 | 53 + 183 = **236** |
| SCAN (toward 199) | 65, 67, 98, 122, 124, 183, [199], 37, 14 | 146 + 185 = **331** |
| C-SCAN (toward 199) | 65 ... 183, [199], jump to [0], 14, 37 | 146 + 199 + 37 = **382** (183 without the return) |
| LOOK (toward 199) | 65 ... 183, then 37, 14 | 130 + 169 = **299** |
| C-LOOK (toward 199) | 65 ... 183, jump to 14, 37 | 130 + 169 + 23 = **322** (153 without the jump) |

Direction matters: SCAN toward 0 happens to cost 236 here (going down first is cheap, since the low requests are close), but 331 toward 199.

### N4 · A second scheduling problem, with time (OS-9.2)

**Question.** Cylinders 0 to 199, head at 50, moving toward higher cylinders. Queue: 82, 170, 43, 140, 24, 16, 190. (a) Total movement for FCFS, SSTF, SCAN, C-SCAN, LOOK, C-LOOK. (b) If moving the head costs 0.1 ms per cylinder, plus 5 ms per request for rotation and transfer, how long does SSTF take to serve all requests, compared with FCFS?

**Answer.**

(a)
- **FCFS:** 50→82 (32) →170 (88) →43 (127) →140 (97) →24 (116) →16 (8) →190 (174) = **642**.
- **SSTF:** 50→43 (7) →24 (19) →16 (8) →82 (66) →140 (58) →170 (30) →190 (20) = **208**.
- **SCAN:** 50 → 82, 140, 170, 190 → 199 (149), then 199 → 43, 24, 16 (183) = **332**.
- **C-SCAN:** 50 → 199 (149), return to 0 (199), 0 → 16, 24, 43 (43) = **391** (192 without the return).
- **LOOK:** 50 → 190 (140), 190 → 16 (174) = **314**.
- **C-LOOK:** 50 → 190 (140), jump to 16 (174), 16 → 43 (27) = **341** (167 without the jump).

(b) Rotation + transfer for 7 requests = 35 ms in all cases.
- SSTF: 208 × 0.1 = 20.8 ms + 35 = **55.8 ms**.
- FCFS: 642 × 0.1 = 64.2 ms + 35 = **99.2 ms**.

(Real seek time is not linear in distance: short seeks are dominated by settling time, so the actual gain is smaller than the cylinder counts suggest.)

### N5 · SSD mapping table and write amplification (OS-9.3)

**Question.** (a) A 2 TB SSD uses page-level mapping with 4 KB pages and 4-byte entries. How large is the mapping table? (b) A flash block has 256 pages. When garbage collection picks a block, 192 of its pages are still valid. How many page writes does the SSD perform per page of new free space, and what is the write amplification? (c) What if GC can find blocks with only 64 valid pages (because of more over-provisioning or TRIM)? (d) The SSD's TLC flash tolerates 3,000 P/E cycles. Estimate the total host data that can be written at WA = 4 and at WA = 1.33.

**Answer.**

(a) 2 TB / 4 KB = 2⁴¹ / 2¹² = 2²⁹ pages × 4 B = 2³¹ B = **2 GB** of DRAM.

(b) GC copies 192 valid pages to reclaim 256 − 192 = 64 free pages. For every 64 host pages written into that space, the SSD writes 64 + 192 = 256 pages. **WA = 256 / 64 = 4**.

(c) 64 valid, 192 reclaimed: WA = (192 + 64) / 192 ≈ **1.33**.

(d) Raw flash write capacity = 2 TB × 3,000 = 6,000 TB. Host data ≈ 6,000 / WA: at WA = 4, **1,500 TB**; at WA = 1.33, **≈ 4,500 TB**. Keeping free space available (TRIM, over-provisioning, not filling the drive to 100%) triples the drive's life and improves write speed.

### N6 · RAID capacity and performance (OS-9.5)

**Question.** Eight 4 TB disks, each capable of R = 200 random IOPS and S = 150 MB/s sequential. Using OSTEP's model, compute usable capacity, random read IOPS, random write IOPS, and sequential read bandwidth for RAID 0, RAID 10 (four mirrored pairs), RAID 5, and RAID 6.

**Answer.**

| | Capacity | Random read | Random write | Sequential read |
|---|---|---|---|---|
| RAID 0 | 8 × 4 = **32 TB** | 8 × 200 = **1,600** | **1,600** | 8 × 150 = **1,200 MB/s** |
| RAID 10 | **16 TB** | **1,600** (either copy can serve) | 8 × 200 / 2 = **800** | (8/2) × 150 = **600 MB/s** (model) |
| RAID 5 | 7 × 4 = **28 TB** | **1,600** | 8 × 200 / 4 = **400** | 7 × 150 = **1,050 MB/s** |
| RAID 6 | 6 × 4 = **24 TB** | **1,600** | 8 × 200 / 6 ≈ **267** | 6 × 150 = **900 MB/s** |

RAID 5 and 6 are space-efficient and read well, but random writes are 2 to 3 times slower than RAID 10. That is why write-heavy databases use RAID 10 and archives use RAID 6.

### N7 · Parity: compute, reconstruct, update (OS-9.5)

**Question.** A RAID 4/5 stripe has four data blocks (shown as single bytes): D0 = 10110011, D1 = 01011100, D2 = 11100001, D3 = 00001111. (a) Compute the parity P. (b) The disk holding D2 fails. Reconstruct D2. (c) D1 is updated to 11111111. Compute the new parity using only D1_old, D1_new, and P_old, and verify it.

**Answer.**

(a)
```
 D0        10110011
 D1   XOR  01011100  = 11101111
 D2   XOR  11100001  = 00001110
 D3   XOR  00001111  = 00000001
 P = 00000001
```

(b) D2 = D0 ⊕ D1 ⊕ D3 ⊕ P:
```
 10110011 ⊕ 01011100 = 11101111
 ⊕ 00001111          = 11100000
 ⊕ 00000001          = 11100001   = D2 ✓
```

(c) P_new = P_old ⊕ D1_old ⊕ D1_new:
```
 00000001 ⊕ 01011100 = 01011101
 ⊕ 11111111          = 10100010   = P_new
```
Check: D0 ⊕ D1_new ⊕ D2 ⊕ D3 = 10110011 ⊕ 11111111 = 01001100; ⊕ 11100001 = 10101101; ⊕ 00001111 = **10100010** ✓.

This update needed only 2 reads (D1_old, P_old) and 2 writes (D1_new, P_new), regardless of stripe width: the 4-I/O small write.

### N8 · RAID reliability (OS-9.5)

**Question.** Disks have an MTTF of 100,000 hours. (a) How often does some disk fail in an array of 100 disks? (b) Mean time to data loss for a mirrored pair with a 10-hour repair time? (c) For an 8-disk RAID 5 with a 24-hour rebuild, using MTTDL ≈ MTTF² / (N(N − 1) × MTTR)? (d) Each disk is 4 TB and has an unrecoverable read error (URE) rate of 1 per 10¹⁴ bits read. When one disk in the 8-disk RAID 5 fails, the rebuild reads the other 7 disks entirely. What is the probability the rebuild hits at least one URE?

**Answer.**

(a) 100,000 / 100 = **1,000 hours** (about 6 weeks).

(b) 100,000² / (2 × 10) = 10¹⁰ / 20 = **5 × 10⁸ hours** (about 57,000 years), assuming independent failures.

(c) 10¹⁰ / (8 × 7 × 24) = 10¹⁰ / 1,344 ≈ **7.4 × 10⁶ hours** (about 850 years).

(d) Data read = 7 × 4 TB = 28 TB = 28 × 10¹² × 8 bits = 2.24 × 10¹⁴ bits. Expected UREs = 2.24. Probability of **none** ≈ e^(−2.24) ≈ 0.106. So there is roughly an **89% chance** the rebuild encounters an unreadable sector, which on RAID 5 (with no redundancy left) means lost data in that stripe, or a failed rebuild.

(Vendor URE specifications are conservative and real rates are usually lower, but the trend is real: as disks grow, single-parity RAID becomes risky. RAID 6 can correct a URE during a single-disk rebuild.)

## Scenario Questions (Test Your Understanding)

### S1 · 200 MB/s on the box, 1 MB/s in production (OS-9.1)

A database server uses a single 7,200 RPM disk advertised at "200 MB/s." A benchmark of the database's workload (random 8 KB page reads) shows barely 1 MB/s. Is the disk faulty?

<details><summary>Answer</summary>

No. The 200 MB/s figure is the **sequential** transfer rate. Each random 8 KB read costs an average seek (~8 ms) plus half a rotation (~4.2 ms) plus a negligible transfer: about 12 ms, so about 80 reads per second × 8 KB ≈ **0.65 to 1 MB/s**. The disk spends almost all its time moving the arm and waiting for rotation.

Remedies: more RAM for caching (avoid the reads entirely), an SSD (random reads in ~0.1 ms), several disks in RAID 10 to parallelize, or restructuring the data for more sequential access.

</details>

### S2 · The request at cylinder 190 (OS-9.2)

A file server uses SSTF. Most activity is on files in cylinders 20 to 60. A user whose files are around cylinder 190 complains that opening a file sometimes takes seconds. Explain, and suggest a scheduler change.

<details><summary>Answer</summary>

**Starvation under SSTF.** While requests keep arriving for cylinders 20 to 60, there is always a pending request closer to the head than 190, so the far request keeps getting postponed. Only a lull lets the head travel out.

Use an algorithm with bounded waiting: **LOOK/C-LOOK** (the head eventually sweeps out to 190 on every pass) or a **deadline** scheduler (sorted order normally, but any request older than its deadline is served first). Linux's `mq-deadline` does exactly this.

</details>

### S3 · No scheduler for NVMe (OS-9.2, OS-9.3)

Linux uses the `none` I/O scheduler by default for NVMe SSDs, and the elevator-style `mq-deadline` for hard disks. Why would "no scheduling" be the better choice for the faster device?

<details><summary>Answer</summary>

Elevator scheduling exists to reduce **seek distance**, which does not exist on an SSD: any block can be read in about the same time. Reordering therefore gains nothing, and the scheduler's bookkeeping (sorting, locking a shared queue) adds CPU overhead and latency, which matters when each I/O takes only 10 to 100 µs. An NVMe SSD also has many internal parallel units and its own deep hardware queues, one per CPU core, so it is better to pass requests straight down and let the device's controller manage them. Merging adjacent requests is still done.

</details>

### S4 · The SSD that got slow when full (OS-9.3)

A new SSD writes at 2 GB/s. After months of use, with the drive 97% full, sustained random writes drop to 150 MB/s, and the drive's wear indicator is dropping faster than expected. Explain and suggest fixes.

<details><summary>Answer</summary>

With almost no free space, garbage collection struggles: most blocks it could reclaim still contain many valid pages, which must be copied before each erase. **Write amplification** rises sharply (each host write triggers several internal writes), which both slows writes (the drive is busy copying) and wears the flash faster. If the file system does not send **TRIM**, the SSD also keeps copying data from files that were deleted long ago.

Fixes: keep more free space (don't fill past ~80 to 90%), enable TRIM (`fstrim` timer or `discard`), and for heavy-write workloads choose a drive with more **over-provisioning** (or leave part of it unpartitioned).

</details>

### S5 · Undelete on SSD vs HDD (OS-9.3, OS-8.5)

A forensic analyst recovers deleted files easily from an old hard disk, but finds nothing but zeros where deleted files were on a laptop's SSD. Conversely, a user who "securely" overwrote a sensitive file several times on an SSD learns that the old contents might still be recoverable. Explain both.

<details><summary>Answer</summary>

On an **HDD**, deleting a file only updates file-system metadata (directory entry, bitmap); the data stays in its sectors until overwritten by something else, so recovery tools can find it.

On an **SSD**, the file system sends **TRIM** for the freed blocks; the FTL removes them from its map (reads of unmapped blocks return zeros) and garbage collection soon erases the physical pages. The data is really gone.

But **overwriting** a file on an SSD does not write to the same physical pages: the FTL writes the new data to fresh pages and merely marks the old pages invalid. Until GC erases them, the old contents physically remain in flash (inaccessible through the normal interface, but readable by chip-level analysis). Reliable erasure on SSDs requires the drive's **secure erase** / sanitize command, or full-disk **encryption** with the key destroyed.

</details>

### S6 · RAID 5 for the order database (OS-9.5)

A company puts its transaction database (many small random writes) on an 8-disk RAID 5 to maximize capacity. Write latency is poor and throughput is far below what 8 disks should provide. Why? What layout would you recommend?

<details><summary>Answer</summary>

Every small write on RAID 5 requires **4 I/Os**: read old data, read old parity, write new data, write new parity. Random-write throughput is about N × R / 4, a quarter of the raw disk capability, and each write's latency includes a read before the write. Database logs and index updates are exactly this pattern.

**RAID 10** needs only 2 writes per small write (one to each mirror), with no reads, giving about twice the random-write throughput and lower latency, at the cost of capacity (50% instead of 87.5%). Common practice: RAID 10 (or SSDs) for the database and its log, RAID 6 for bulk archives and backups.

</details>

### S7 · The second failure during rebuild (OS-9.5)

A NAS with six 12 TB disks in RAID 5 loses a disk. During the 30-hour rebuild, it reports read errors on another disk, and the volume fails. The admin says, "RAID 5 should survive a disk failure." What went wrong, and what should have been used?

<details><summary>Answer</summary>

RAID 5 survives **one** failure. After the first failure, there is no redundancy left, and the rebuild must read every sector of the other five disks, about 60 TB. At a typical specified URE rate (1 per 10¹⁴ bits ≈ 12.5 TB), hitting at least one unreadable sector during that read is very likely (← N8). Disks from the same batch, of the same age, under the heavy rebuild load are also more likely to fail together. Any of these events during the rebuild window is fatal.

For large disks, use **RAID 6** (tolerates a second failure or UREs during rebuild), RAID 10, or erasure-coded storage; keep hot spares to start rebuilds immediately; scrub regularly (read everything periodically to find bad sectors early); and keep **backups**.

</details>

### S8 · RAID 1 did not save the files (OS-9.5)

A developer accidentally runs `rm -rf` on a project directory stored on a RAID 1 mirror. They are surprised that the mirror did not preserve a copy. Explain, and describe what does protect against this.

<details><summary>Answer</summary>

RAID 1 mirrors **every write**, including the metadata changes that delete files. Both disks were updated within milliseconds, so both copies of the directory are gone. RAID protects against **hardware failure** of a disk, not against deletion, software bugs, file-system corruption, or ransomware, all of which are faithfully replicated.

Protection comes from **backups** (ideally following 3-2-1: three copies, two media types, one off-site) and **snapshots** (for example, ZFS or Btrfs snapshots ← OS-8.6, or LVM snapshots), from which deleted files can be restored.

</details>

### S9 · Power failure in the middle of a stripe (OS-9.5)

A software RAID 5 (no battery-backed cache) loses power while updating one block in a stripe: the new data reached the disk, but the new parity did not. After reboot, everything seems fine. Months later a disk fails, and one file is corrupted after the rebuild. Connect the two events.

<details><summary>Answer</summary>

This is the **RAID 5 write hole**. After the power loss, the stripe's parity no longer matched its data, but nothing reads parity during normal operation, so the inconsistency went unnoticed. When a disk failed, the blocks of that stripe on the failed disk were reconstructed from the other blocks **and the stale parity**, producing wrong data.

Defenses: a battery- or flash-backed write cache (hardware RAID), a write-intent journal for stripe updates (Linux md `--write-journal`), resynchronizing parity after every unclean shutdown (md does this using a write-intent bitmap), periodic scrubbing, or a copy-on-write design like ZFS RAID-Z that never writes partial stripes in place.

</details>

### S10 · Warning signs (OS-9.4)

`smartctl` on a server's disk shows "Reallocated_Sector_Ct: 8" last month and "Reallocated_Sector_Ct: 412, Current_Pending_Sector: 37" today. Performance for some files has also become erratic. What do these numbers mean, and why might performance change?

<details><summary>Answer</summary>

**Reallocated sectors** are sectors the drive found bad and remapped to spares; **pending sectors** are sectors that failed to read and are waiting to be remapped (their data may be lost). A rapidly rising count means the surface or head is degrading: the drive is likely to fail soon. Back up the data and replace it now.

Performance becomes erratic because remapped sectors live in spare areas that may be far from their logical neighbours: reading a file sequentially now involves seeks to the spare area and back, which the OS cannot anticipate (← sector sparing). Reads of weak sectors also trigger internal retries that take seconds.

</details>

### S11 · Half speed on a new drive (OS-9.4)

A new 4K Advanced Format disk (presented as 512-byte logical sectors) is partitioned with an old tool that starts the first partition at sector 63. Small random writes run at about half the expected speed. After re-partitioning to start at sector 2048, performance is normal. Explain.

<details><summary>Answer</summary>

Sector 63 × 512 B = 32,256 bytes, which is not a multiple of 4,096. Every 4 KB file-system block therefore straddles **two** physical 4 KB sectors. Writing one block requires the drive to **read** both physical sectors, merge in the new data, and **write** both back: a read-modify-write that doubles (or worse) the work and adds a rotation of latency. Starting at sector 2048 (1 MiB) aligns every file-system block with exactly one physical sector, so writes go straight to disk. Modern partitioning tools align to 1 MiB by default for this reason (it also suits SSD page and RAID chunk boundaries).

</details>

### S12 · The laptop that will not hibernate (OS-9.6)

A laptop with 32 GB of RAM and a 4 GB swap partition fails to hibernate when many applications are open, though suspend-to-RAM works. Explain, and give two fixes.

<details><summary>Answer</summary>

**Hibernation** writes an image of memory into **swap space**, powers off completely, and restores the image at boot. With 20+ GB of memory in use and only 4 GB of swap (minus whatever is already swapped), the image does not fit, even though the kernel compresses it and drops clean page-cache pages first. Suspend-to-RAM keeps memory powered and needs no disk space.

Fixes: enlarge swap (a swap file is easy to resize) to at least the typical amount of memory in use; or close applications before hibernating; or configure the kernel to free more page cache before creating the image (`/sys/power/image_size`).

</details>
