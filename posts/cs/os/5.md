# Unit 5: Deadlocks

> **How to use this page.** Section IDs (`OS-5.4`) match the tags on practice questions. Arrows like **→ OS-6.4** point to where an idea is developed further; **← OS-4.7** points back to something this section depends on.

Unit 4 gave us locks and semaphores, and along the way we met situations where threads wait for each other forever: two semaphores acquired in opposite orders, five philosophers each holding one chopstick. This unit studies that failure systematically: exactly when it can happen, and the four strategies for dealing with it (prevent it, avoid it, detect and recover from it, or ignore it).

---

## OS-5.1 · System Model and the Four Necessary Conditions

### Resources

A system has a finite number of **resource types** R₁, R₂, ..., Rₘ (CPU cycles, memory space, files, I/O devices, locks, semaphores). Each type has one or more identical **instances** (a system with two identical printers has one resource type with two instances). If a process requesting an instance of a type can be satisfied by **any** instance, the instances are identical; otherwise they are really different types.

A process uses a resource in three steps:

1. **Request.** If the request cannot be granted immediately, the process waits.
2. **Use.**
3. **Release.**

Request and release are system calls (`open`/`close`, `malloc`/`free`) or synchronization operations (`lock`/`unlock`, `wait`/`signal`).

Resources come in two kinds:

- **Reusable:** used by one process at a time and not used up (CPU, memory, devices, locks, files). Most deadlock theory is about these.
- **Consumable:** created and destroyed (messages, signals, interrupts). A process waiting to receive a message that is never sent is also stuck; communication deadlocks belong here (→ S2).

### Definition

A set of processes is **deadlocked** when every process in the set is waiting for an event (typically the release of a resource) that can be caused only by another process in the set. None of them can ever proceed.

The simplest example, with two mutexes:

```c
pthread_mutex_t A = PTHREAD_MUTEX_INITIALIZER, B = PTHREAD_MUTEX_INITIALIZER;

void *t1(void *arg) {                 void *t2(void *arg) {
    pthread_mutex_lock(&A);               pthread_mutex_lock(&B);
    /* ... */                             /* ... */
    pthread_mutex_lock(&B);               pthread_mutex_lock(&A);
    /* use A and B */                     /* use A and B */
    pthread_mutex_unlock(&B);             pthread_mutex_unlock(&A);
    pthread_mutex_unlock(&A);             pthread_mutex_unlock(&B);
    return NULL;                          return NULL;
}                                     }
```

If t1 acquires A and t2 acquires B before either reaches its second lock, t1 waits for B (held by t2) and t2 waits for A (held by t1). Forever. Note that deadlock is **possible**, not certain: most runs may interleave harmlessly, which is exactly why these bugs survive testing.

### The four necessary conditions (Coffman et al., 1971)

A deadlock can arise only if **all four** of these hold simultaneously:

| Condition | Meaning | In the two-mutex example |
|---|---|---|
| **1. Mutual exclusion** | At least one resource is non-sharable: only one process can use it at a time | A mutex is held by one thread |
| **2. Hold and wait** | A process holds at least one resource while waiting for others | t1 holds A while waiting for B |
| **3. No preemption** | A resource cannot be taken from a process; it is released only voluntarily | The OS cannot take A away from t1 |
| **4. Circular wait** | There is a cycle P₀ → P₁ → ... → Pₙ → P₀, where each waits for a resource held by the next | t1 waits for t2, t2 waits for t1 |

Important points:

- The conditions are **necessary**: if any one is false, deadlock is impossible. That is the whole basis of **prevention** (→ OS-5.3).
- They are not fully independent: circular wait implies hold and wait.
- For resources with a **single instance** each, the four conditions together are also **sufficient**: a cycle means a deadlock. With multiple instances, a cycle does not guarantee deadlock (→ OS-5.2).

### Where deadlocks actually appear

- **Multithreaded programs** acquiring several locks (the most common case; see ← OS-4.8 for what real bug studies found).
- **Operating system kernels**, which contain thousands of locks. Linux uses a runtime validator, **lockdep**, that records the order in which locks are taken and warns when two code paths could acquire them in conflicting orders, even if the deadlock never actually happened.
- **Databases:** transactions lock rows; two transactions updating the same two rows in opposite order deadlock. Databases detect this and abort one transaction (→ OS-5.5).
- **Distributed systems**, where no single node sees the whole wait-for graph.

## OS-5.2 · Resource-Allocation Graph and Wait-for Graph

### The resource-allocation graph (RAG)

A directed graph with two kinds of nodes:

- **Process nodes** P₁, P₂, ... drawn as circles.
- **Resource nodes** R₁, R₂, ... drawn as rectangles, with one dot per instance.

And two kinds of edges:

- **Request edge** Pᵢ → Rⱼ: Pᵢ has requested an instance of Rⱼ and is waiting.
- **Assignment edge** Rⱼ → Pᵢ: an instance of Rⱼ has been allocated to Pᵢ (drawn from a specific dot).

When a request is granted, the request edge is replaced by an assignment edge; on release, the assignment edge is deleted.

Two small examples, written as edge lists:

```
 Example A: deadlock (single instances)
   R1 (1 instance) --> P1        P1 holds R1
   R2 (1 instance) --> P2        P2 holds R2
   P1 --> R2                     P1 waits for R2
   P2 --> R1                     P2 waits for R1

   Cycle: P1 -> R2 -> P2 -> R1 -> P1.  Every resource in it has one
   instance, so P1 and P2 are deadlocked.

 Example B: cycle but NO deadlock (multiple instances)
   R1 (2 instances) --> P2, P3   R1's two instances held by P2 and P3
   R2 (2 instances) --> P1, P4   R2's two instances held by P1 and P4
   P1 --> R1                     P1 waits for R1
   P3 --> R2                     P3 waits for R2

   Cycle: P1 -> R1 -> P3 -> R2 -> P1 exists.
   But P4 is waiting for nothing: it finishes and releases its R2,
   which goes to P3. P3 finishes and releases R1, which goes to P1.
   (P2 also finishes on its own.) Everyone completes.
```

**Rules for reading a RAG:**

1. **No cycle → no deadlock.** Always.
2. **Cycle, and every resource in it has a single instance → deadlock.** The processes in the cycle are deadlocked.
3. **Cycle with multiple-instance resources → deadlock is possible but not certain.** A process outside the cycle (or holding a spare instance) may release what the cycle needs. You have to run the detection algorithm (→ OS-5.5).

In short: with single instances, a cycle is necessary and sufficient; with multiple instances, a cycle is necessary but not sufficient.

### The wait-for graph

When every resource has a single instance, collapse the RAG: remove the resource nodes and draw an edge Pᵢ → Pⱼ whenever Pᵢ is waiting for a resource that Pⱼ holds.

```
 RAG:  P1 -> R1 -> P2 -> R3 -> P3 -> R2 -> P1        Wait-for graph:  P1 -> P2 -> P3 -> P1
```

A deadlock exists **if and only if** the wait-for graph has a cycle. Detecting a cycle with depth-first search takes O(V + E) time; textbooks often quote O(n²) for n processes, since there can be up to n² edges. This is how databases detect deadlocks between transactions. The wait-for graph does **not** work for multiple-instance resources.

### Claim edges

For deadlock avoidance with single-instance resources (→ OS-5.4), a third edge type is added: a **claim edge** Pᵢ ⇢ Rⱼ (dashed) means Pᵢ **may** request Rⱼ at some point in the future. When the request is made, it becomes a request edge; on release, the assignment edge turns back into a claim edge.

## OS-5.3 · Deadlock Prevention

**Prevention** makes deadlock structurally impossible by ensuring that at least one of the four necessary conditions can **never** hold. Each condition, in turn:

### 1. Breaking mutual exclusion

Make resources sharable where possible: read-only files can be read by any number of processes simultaneously; nobody waits for them. Printers can be **spooled**: processes write output to a spool file on disk (sharable), and only a single printer daemon ever talks to the printer.

**Limit:** many resources are **intrinsically non-sharable** (a mutex exists precisely to be exclusive, as does write access to a data structure). So this condition generally cannot be eliminated. Lock-free data structures (← OS-4.8) are the closest practical example: they avoid the lock entirely.

### 2. Breaking hold and wait

Guarantee that a process never holds some resources while waiting for others:

- **Protocol 1:** request **all** resources at once, before starting (or atomically, all-or-nothing).
- **Protocol 2:** a process may request resources only when it holds **none**; before requesting more, it must release everything it holds.

Example: a process copies data from a DVD drive to a disk file, then sorts the file, then prints the result. Under protocol 1 it must hold the printer for the entire run, though it prints only at the end. Under protocol 2 it requests DVD + file, releases both, then requests file + printer.

**Costs:**

- **Low resource utilization:** resources are allocated long before they are used (→ N7).
- **Starvation:** a process that needs several popular resources may wait indefinitely, because at least one is always in use by someone.
- Processes must know their needs in advance, which is often impossible.

In code, a common version is "acquire all the locks up front, inside one global lock" (OSTEP mentions this), which works but reduces concurrency.

### 3. Breaking no preemption

Allow resources to be taken away:

- **Protocol:** if a process holding resources requests another that cannot be granted immediately, it **releases everything it holds** (they are implicitly preempted). It restarts only when it can regain the old resources plus the new one.
- **Alternative:** when a process requests a resource held by a process that is itself **waiting**, take it from the waiting process.

This works only for resources whose state can be **saved and restored**: CPU registers (a context switch is exactly this), memory pages (swap them out ← OS-2.2). It does not work for printers (half a printout cannot be taken back), and it cannot be applied transparently to mutexes (a half-finished critical section would leave data inconsistent).

In code, the "release and retry" protocol uses **trylock**:

```c
top:
    pthread_mutex_lock(&A);
    if (pthread_mutex_trylock(&B) != 0) {   // could not get B
        pthread_mutex_unlock(&A);            // give up A as well
        /* optionally sleep for a random time */
        goto top;                            // retry
    }
    /* holding A and B */
```

Because the thread gives up A instead of waiting while holding it, no deadlock can form. The new risk is **livelock**: two threads can keep grabbing their first lock, failing on the second, releasing, and retrying in lockstep forever. A **random backoff** before retrying makes that astronomically unlikely (OSTEP).

### 4. Breaking circular wait (the practical one)

Impose a **total order** on all resource types (assign each a number with a function F), and require every process to request resources in **increasing order**. A process holding Rⱼ may request Rₖ only if F(Rₖ) > F(Rⱼ); if it needs a lower-numbered one, it must first release the higher ones.

**Why it works (proof by contradiction):** suppose a circular wait P₀ → P₁ → ... → Pₙ → P₀ exists, where Pᵢ waits for Rᵢ held by Pᵢ₊₁. Pᵢ₊₁ holds Rᵢ and is requesting Rᵢ₊₁, so F(Rᵢ) < F(Rᵢ₊₁). Going around the cycle: F(R₀) < F(R₁) < ... < F(Rₙ) < F(R₀). A number cannot be less than itself. Contradiction.

This is the most widely used prevention technique in real software:

- **Documented lock hierarchies:** Linux's memory-management code has a comment at the top of `mm/filemap.c` (and `mm/rmap.c`) listing the order in which its locks must be taken.
- **Ordering by address or ID** when locks are created dynamically: to lock two objects, always lock the one with the lower address (or lower ID) first.

```c
void transfer(Account *from, Account *to, int amount) {
    Account *first  = (from->id < to->id) ? from : to;
    Account *second = (from->id < to->id) ? to : from;
    pthread_mutex_lock(&first->lock);
    pthread_mutex_lock(&second->lock);
    from->balance -= amount;
    to->balance   += amount;
    pthread_mutex_unlock(&second->lock);
    pthread_mutex_unlock(&first->lock);
}
```

Without the ordering, `transfer(a, b)` and `transfer(b, a)` running concurrently could deadlock (→ S1).

**Limits:** the order must be followed by **every** piece of code, including code written years later by other people, and it may force a process to acquire a lock earlier than it needs it. Encapsulation makes this hard: a library function may take locks internally that the caller does not know about. Tools like lockdep exist to check the ordering automatically.

### Timestamp-based schemes (databases)

Databases often prevent deadlock by giving each transaction a timestamp when it starts (older = smaller timestamp) and deciding, on every conflict, whether to wait or abort:

| Scheme | Older transaction requests a lock held by younger | Younger requests a lock held by older |
|---|---|---|
| **Wait-die** (non-preemptive) | Older **waits** | Younger **dies** (aborts, restarts later with the **same** timestamp) |
| **Wound-wait** (preemptive) | Older **wounds** the younger (forces it to abort) | Younger **waits** |

In both, waiting happens in only one direction of age, so a cycle is impossible. Because an aborted transaction keeps its original timestamp, it eventually becomes the oldest and cannot starve.

## OS-5.4 · Deadlock Avoidance

Prevention restricts **how** requests are made, which often wastes resources. **Avoidance** allows the general request pattern but decides, **for each request at run time**, whether granting it could lead to a deadlock. This requires advance information: each process declares the **maximum** number of instances of each resource type it may ever need.

### Safe and unsafe states

- A **safe sequence** is an ordering ⟨P₁, P₂, ..., Pₙ⟩ of all processes such that, for each Pᵢ, its remaining needs can be satisfied by the currently available resources **plus** the resources held by all Pⱼ with j < i. So P₁ can finish with what is available now; then P₂ can finish using what is available plus what P₁ released; and so on.
- A state is **safe** if at least one safe sequence exists.
- A state is **unsafe** if none exists.

```
 +--------------------------------------------+
 |                 all states                  |
 |   +--------------------+                    |
 |   |       safe         |    unsafe          |
 |   |                    |    +------------+  |
 |   |                    |    |  deadlock  |  |
 |   +--------------------+    +------------+  |
 +--------------------------------------------+
```

- Safe ⇒ no deadlock (the OS can always schedule everyone to completion).
- **Unsafe does not mean deadlocked.** It means the OS can no longer *guarantee* avoiding deadlock: if processes actually request their declared maximums, a deadlock may follow. Processes might in fact release resources early or never request their maximum, and no deadlock would happen (→ S3).
- Deadlocked states are a subset of unsafe states.

The avoidance rule: **grant a request only if the resulting state is still safe.** Otherwise the process waits, even if the resources are available right now. The system starts in a safe state and never leaves it.

**Example (single resource type).** 12 tape drives, three processes:

| Process | Maximum need | Currently holds | Still needs |
|---|---|---|---|
| P0 | 10 | 5 | 5 |
| P1 | 4 | 2 | 2 |
| P2 | 9 | 2 | 7 |

Available = 12 − 9 = 3. Is it safe? P1 needs 2 ≤ 3: it can finish and release its 4, making 5 available. P0 needs 5 ≤ 5: finishes, now 10 available. P2 needs 7 ≤ 10. Safe sequence ⟨P1, P0, P2⟩: **safe**.

Now P2 requests 1 more drive and it is granted: available = 2, P2 holds 3 and still needs 6. Only P1 can finish (needs 2), which leaves 4 available; P0 needs 5, P2 needs 6. No safe sequence: **unsafe**. The avoidance algorithm would therefore make P2 wait, although a drive is free.

### Resource-allocation-graph algorithm (single instances)

With one instance of each resource type, use the RAG with **claim edges**. When Pᵢ requests Rⱼ, grant it only if converting the request edge Pᵢ → Rⱼ into the assignment edge Rⱼ → Pᵢ does **not create a cycle** (counting claim edges). A cycle would mean an unsafe state. Cycle detection costs O(n²).

### Banker's algorithm (multiple instances)

Dijkstra's algorithm, named after a banker who never lends money in a way that could leave him unable to satisfy all his customers' credit lines.

**Data structures** (n processes, m resource types):

| Name | Size | Meaning |
|---|---|---|
| `Available` | m | Number of free instances of each type |
| `Max` | n × m | Maximum demand of each process |
| `Allocation` | n × m | Instances currently allocated to each process |
| `Need` | n × m | Remaining need: `Need[i][j] = Max[i][j] − Allocation[i][j]` |

Vector comparison: X ≤ Y means X[j] ≤ Y[j] for **every** j.

**Safety algorithm** (is the current state safe?):

```
 1. Work = Available;  Finish[i] = false for all i.
 2. Find an i such that Finish[i] == false and Need[i] <= Work.
    If no such i exists, go to step 4.
 3. Work = Work + Allocation[i];   // Pi finishes and returns everything it holds
    Finish[i] = true;
    go to step 2.
 4. If Finish[i] == true for all i, the state is SAFE
    (the order in which processes were picked is a safe sequence);
    otherwise it is UNSAFE.
```

Complexity: O(m × n²).

**Resource-request algorithm** (process Pᵢ requests vector `Request`):

```
 1. If Request > Need[i]: error (process exceeded its declared maximum).
 2. If Request > Available: Pi must wait (resources not available).
 3. Pretend to grant it:
        Available     = Available - Request
        Allocation[i] = Allocation[i] + Request
        Need[i]       = Need[i] - Request
    Run the safety algorithm on this new state.
    If SAFE: the allocation is made.
    If UNSAFE: restore the old state; Pi must wait.
```

N1 works through a complete example with five processes and three resource types.

### Limitations of avoidance

- Each process must declare its **maximum needs in advance**, which most real programs cannot do.
- The number of processes and resources is assumed **fixed**; processes must eventually release everything they hold; resources must not fail (a broken tape drive invalidates the computation).
- It is **conservative:** requests are refused in unsafe states that might never have deadlocked, lowering utilization.
- Running the safety check on every request costs O(m n²).

For these reasons, general-purpose operating systems do not use the banker's algorithm. It still matters in exams, and the same safe-state reasoning appears in some specialized systems (for example, certain embedded or batch resource managers).

## OS-5.5 · Deadlock Detection and Recovery

If a system neither prevents nor avoids deadlock, it can let deadlocks happen, **detect** them, and **recover**.

### Detection with single instances

Maintain the **wait-for graph** (← OS-5.2) and periodically search it for cycles. Every process in a cycle is deadlocked.

### Detection with multiple instances

An algorithm very similar to the safety algorithm, but it uses the **current outstanding requests** instead of the maximum needs, because it asks "can the processes finish given what they are actually waiting for right now?" rather than "is it safe in the worst case?"

| Name | Meaning |
|---|---|
| `Available` | Free instances of each type |
| `Allocation` | n × m currently allocated |
| `Request` | n × m current outstanding requests (what each process is blocked on) |

```
 1. Work = Available.
    For each i: if Allocation[i] == 0 (holds nothing), Finish[i] = true;
                otherwise Finish[i] = false.
 2. Find an i with Finish[i] == false and Request[i] <= Work.
    If none, go to step 4.
 3. Work = Work + Allocation[i];  Finish[i] = true;  go to step 2.
    (Optimistic assumption: if Pi's request can be met, it will finish
     and release its resources. If it later requests more, the next
     run of the algorithm will catch any deadlock.)
 4. If some Finish[i] == false, the system is DEADLOCKED,
    and exactly those processes Pi are deadlocked.
```

Complexity: O(m × n²). See N3.

**Avoidance vs detection, side by side:**

| | Banker's safety algorithm (avoidance) | Detection algorithm |
|---|---|---|
| Uses | `Need = Max − Allocation` | `Request` (current outstanding) |
| Question | Could a deadlock *ever* occur if everyone asks for their maximum? | Is there a deadlock *now*? |
| Requires advance knowledge | Yes (Max) | No |
| When run | On every request | Periodically, or on some trigger |

### When to run detection

- **On every request that cannot be granted immediately:** detects a deadlock the moment it forms, and identifies the request that "caused" it. But this is expensive.
- **Periodically** (for example, once an hour) or **when CPU utilization drops** below some threshold (say 40%), since deadlocked processes stop doing work. Cheaper, but a deadlock may persist unnoticed for a while, and the resulting graph may contain many cycles, making it hard to tell which process caused it.

### Recovery by process termination

- **Abort all deadlocked processes:** definitely breaks the deadlock, at great expense: all their partial computations are lost.
- **Abort one process at a time** until the cycle is broken, re-running detection after each abort. Less work lost, but detection overhead after each step.

Aborting a process can leave things inconsistent: a process killed while updating a file, or while holding a printer mid-job. Choosing a **victim** is a policy decision, considering:

- Priority of the process
- How long it has computed, and how much longer it needs
- How many and which kinds of resources it holds (easy to preempt?)
- How many more resources it needs to complete
- How many processes would need to be terminated
- Interactive or batch

### Recovery by resource preemption

Take resources away from some processes and give them to others until the deadlock is broken. Three issues:

1. **Selecting a victim:** which resources from which processes, minimizing cost (number of resources held, time already consumed).
2. **Rollback:** the preempted process cannot continue normally. Roll it back to a safe state and restart from there. The simplest is **total rollback** (abort and restart); better is rolling back to a **checkpoint**, which requires the system to have saved state periodically. Databases do this naturally with transaction logs: a deadlocked transaction is aborted, its changes undone, and it is retried.
3. **Starvation:** if cost-based selection always picks the same process, it may be rolled back forever. Include the **number of rollbacks** in the cost so a process is chosen as victim only a bounded number of times.

## OS-5.6 · The Ostrich Approach, and Deadlock vs Livelock vs Starvation

### Ignoring the problem

The fourth strategy is to **pretend deadlocks never occur**. It is named after the (false) legend that ostriches bury their heads in the sand. Most general-purpose operating systems, including **Linux and Windows**, take this approach for deadlocks among user processes and user-level locks.

Why this is reasonable engineering, not negligence:

- Deadlocks among user processes are **rare** compared with other failures (hardware faults, crashes, plain bugs).
- The alternatives are **expensive:** prevention restricts every program, avoidance needs maximum claims nobody can provide, detection costs CPU time on every request or periodically.
- Correctness is left to the **application developer**, who knows the program's lock structure (and has tools such as lock ordering, `trylock`, thread sanitizers, and debuggers that show where threads are blocked).
- When a deadlock happens anyway, users or watchdogs kill and restart the affected process (or, in the worst case, reboot).

Inside the kernel, developers do care: kernel deadlocks hang the whole machine, so Linux uses strict lock-ordering rules checked by lockdep, a hung-task detector, and soft/hard lockup watchdogs. Databases, which cannot tolerate hung transactions, **do** detect deadlocks and recover.

Summary of the four strategies:

| Strategy | Idea | Cost | Used by |
|---|---|---|---|
| Prevention | Make one condition impossible (usually circular wait, via lock ordering) | Restricts how resources are requested | Kernels, careful application code |
| Avoidance | Grant only requests that keep the state safe | Needs Max in advance; conservative; O(mn²) per request | Rare; exams |
| Detection + recovery | Let it happen, find cycles, abort or roll back | Detection overhead; lost work | Databases |
| Ignore | Do nothing | Occasional hangs, fixed manually | Linux, Windows (user level) |

### Deadlock vs livelock vs starvation

| | Deadlock | Livelock | Starvation |
|---|---|---|---|
| Threads' state | **Blocked** (waiting) | **Running** (busy, changing state) | Some run; the victim waits (ready or blocked) |
| Progress | None of the involved threads | None of the involved threads | Others progress; the victim does not |
| Resolves by itself? | Never | Possibly by chance (timing change) | Possibly, if load drops |
| CPU usage | Near zero for those threads | High (wasted) | Normal |
| Cause | Cycle of waiting on held resources | Threads repeatedly react to each other (e.g., retry in lockstep) | Unfair scheduling or locking policy |
| Fix | Break one Coffman condition | Randomized backoff, asymmetry | Aging, fair (FIFO) queues |
| Example | Two threads, two locks, opposite order | Two `trylock`-and-release threads in lockstep | Low-priority process under strict priority scheduling; writer under reader-preference locking |

Every deadlock involves starvation of the deadlocked processes, but starvation does not require a deadlock.

A deadlock can even involve **a single thread**: a thread that locks a non-recursive mutex it already holds waits for itself forever (a cycle of length one → S9).

## Quick Revision Sheet

- Deadlock: every process in a set waits for an event only another process in the set can cause.
- Four necessary conditions: mutual exclusion, hold and wait, no preemption, circular wait. All four must hold.
- RAG: request edge P → R, assignment edge R → P. No cycle → no deadlock. Cycle + single instances → deadlock. Cycle + multiple instances → maybe.
- Wait-for graph (single instances only): deadlock ⇔ cycle.
- Prevention: mutual exclusion (spooling, rarely possible); hold and wait (request all up front: poor utilization, starvation); no preemption (release all on failure / trylock: works for CPU and memory, livelock risk); circular wait (global resource order; most practical).
- Lock ordering by ID/address for dynamic objects (`transfer(a, b)`).
- Wait-die: old waits, young dies. Wound-wait: old wounds young, young waits.
- Safe state: a safe sequence exists. Unsafe ≠ deadlock. Deadlock ⊂ unsafe.
- Banker's: Need = Max − Allocation; safety algorithm finds a process with Need ≤ Work, adds its Allocation to Work; request algorithm: Request ≤ Need, Request ≤ Available, pretend, check safety.
- Detection algorithm: like safety but uses current Request; processes with zero allocation start finished.
- Recovery: abort all, abort one at a time, or preempt resources with rollback; avoid starving the same victim.
- n processes each needing up to k instances: n(k − 1) + 1 instances guarantee no deadlock.
- Linux and Windows: ostrich for user-level deadlocks; lockdep inside the kernel; databases detect and abort.

## Worked Numerical Problems

### N1 · Banker's algorithm, complete example (OS-5.4)

**Question.** Five processes P0 to P4 and three resource types A, B, C with 10, 5, and 7 instances in total. At time T0:

| | Allocation (A B C) | Max (A B C) |
|---|---|---|
| P0 | 0 1 0 | 7 5 3 |
| P1 | 2 0 0 | 3 2 2 |
| P2 | 3 0 2 | 9 0 2 |
| P3 | 2 1 1 | 2 2 2 |
| P4 | 0 0 2 | 4 3 3 |

(a) Compute Available and Need. (b) Is the state safe? (c) P1 requests (1, 0, 2). Can it be granted? (d) After (c) is granted, P4 requests (3, 3, 0). (e) After (c), P0 instead requests (0, 2, 0).

**Answer.**

(a) Total allocated = (7, 2, 5), so **Available = (10, 5, 7) − (7, 2, 5) = (3, 3, 2)**.

| | Need = Max − Allocation |
|---|---|
| P0 | 7 4 3 |
| P1 | 1 2 2 |
| P2 | 6 0 0 |
| P3 | 0 1 1 |
| P4 | 4 3 1 |

(b) Safety algorithm, Work = (3, 3, 2):

| Step | Pick | Need ≤ Work? | Work after (+ Allocation) |
|---|---|---|---|
| 1 | P1 | (1,2,2) ≤ (3,3,2) ✓ | (5, 3, 2) |
| 2 | P3 | (0,1,1) ≤ (5,3,2) ✓ | (7, 4, 3) |
| 3 | P4 | (4,3,1) ≤ (7,4,3) ✓ | (7, 4, 5) |
| 4 | P2 | (6,0,0) ≤ (7,4,5) ✓ | (10, 4, 7) |
| 5 | P0 | (7,4,3) ≤ (10,4,7) ✓ | (10, 5, 7) |

All finish: **safe**, with safe sequence ⟨P1, P3, P4, P2, P0⟩. (Other safe sequences exist, such as ⟨P1, P3, P4, P0, P2⟩; any one suffices. At step 1, P0 was not possible because its Need (7,4,3) exceeds (3,3,2).)

(c) Request = (1, 0, 2). Check: ≤ Need₁ (1, 2, 2) ✓; ≤ Available (3, 3, 2) ✓. Pretend to grant:

- Available = (2, 3, 0)
- Allocation₁ = (3, 0, 2), Need₁ = (0, 2, 0)

Safety check from Work = (2, 3, 0): P1 (0,2,0) ✓ → (5, 3, 2); P3 (0,1,1) ✓ → (7, 4, 3); P4 (4,3,1) ✓ → (7, 4, 5); P0 (7,4,3) ✓ → (7, 5, 5); P2 (6,0,0) ✓ → (10, 5, 7). **Safe** (⟨P1, P3, P4, P0, P2⟩), so the request is **granted**.

(d) P4 requests (3, 3, 0): it is ≤ Need₄ (4, 3, 1), but Available is (2, 3, 0), and 3 > 2 for A. The resources are **not available**, so P4 **waits** (no safety check needed).

(e) P0 requests (0, 2, 0): ≤ Need₀ ✓, ≤ Available (2, 3, 0) ✓. Pretend: Available = (2, 1, 0), Need₀ = (7, 2, 3). Safety from Work = (2, 1, 0):

- P0 (7,2,3): no. P1 (0,2,0): no, B needs 2 > 1. P2 (6,0,0): no. P3 (0,1,1): no, C needs 1 > 0. P4 (4,3,1): no.

No process can proceed: **unsafe**. The request is **denied**; P0 waits, even though the resources are physically available.

### N2 · Minimum resources for guaranteed freedom from deadlock (OS-5.1)

**Question.** (a) 4 processes share a resource type; each needs at most 3 instances. What is the minimum number of instances that guarantees deadlock cannot occur? (b) Three processes need at most 3, 4, and 5 instances respectively. Minimum instances? (c) A system has 6 instances and each process needs at most 3. What is the maximum number of processes for which deadlock is impossible?

**Answer.** Worst case: every process holds one less than its maximum and waits for one more. If there is one additional instance beyond that, some process can complete, release everything, and let the others finish.

(a) 4 × (3 − 1) + 1 = **9**. With 8, all four could hold 2 each and wait forever.

(b) (3 − 1) + (4 − 1) + (5 − 1) + 1 = 2 + 3 + 4 + 1 = **10**.

(c) Need n(3 − 1) + 1 ≤ 6, so 2n ≤ 5, n ≤ 2.5: **2 processes**. (With 3 processes, each could hold 2, using all 6, and all wait.)

General formula: deadlock is impossible if **Σ (maxᵢ − 1) + 1 ≤ total instances**, that is, Σ maxᵢ < total + n.

### N3 · Detection algorithm (OS-5.5)

**Question.** Five processes, resource types A, B, C with 7, 2, 6 instances. Current state:

| | Allocation (A B C) | Request (A B C) |
|---|---|---|
| P0 | 0 1 0 | 0 0 0 |
| P1 | 2 0 0 | 2 0 2 |
| P2 | 3 0 3 | 0 0 0 |
| P3 | 2 1 1 | 1 0 0 |
| P4 | 0 0 2 | 0 0 2 |

(a) Is the system deadlocked? (b) P2 now makes an additional request for one instance of C. Is the system deadlocked now, and which processes are involved?

**Answer.**

(a) Allocated = (7, 2, 6), so Available = (0, 0, 0). No process has zero allocation. Work = (0, 0, 0):

- P0: Request (0,0,0) ≤ Work ✓ → Work = (0, 1, 0)
- P2: (0,0,0) ✓ → (3, 1, 3)
- P3: (1,0,0) ✓ → (5, 2, 4)
- P1: (2,0,2) ✓ → (7, 2, 4)
- P4: (0,0,2) ✓ → (7, 2, 6)

All finish: **not deadlocked** (sequence ⟨P0, P2, P3, P1, P4⟩), even though nothing is currently available.

(b) Request₂ = (0, 0, 1). Work = (0, 0, 0): only P0 can finish → (0, 1, 0). Then P1 (2,0,2), P2 (0,0,1), P3 (1,0,0), P4 (0,0,2) all exceed (0, 1, 0). **Deadlocked: P1, P2, P3, P4.** P0's released resources are not enough to satisfy anyone else.

### N4 · Reading resource-allocation graphs (OS-5.2)

**Question.** For each situation, is there a deadlock?

(a) R1, R2, R3 each have one instance. R1 → P1, R2 → P2, R3 → P3 (assignments). P1 → R2, P2 → R3, P3 → R1 (requests). Also draw the wait-for graph.

(b) Same as (a), except R3 has **two** instances, one assigned to P3 and one to P4. P4 requests nothing.

(c) Same as (b), except P4 now requests R1.

**Answer.**

(a) Cycle P1 → R2 → P2 → R3 → P3 → R1 → P1 with single instances: **deadlock** among P1, P2, P3. Wait-for graph: P1 → P2 → P3 → P1.

(b) The same cycle exists, but P4 holds an instance of R3 and waits for nothing. P4 finishes and releases its R3 instance, which is given to P2. P2 finishes and releases R2 to P1; P1 finishes and releases R1 to P3. **No deadlock.** (A cycle is necessary but not sufficient with multiple instances.)

(c) Now P4 waits for R1 (held by P1). Nobody can finish: P1 waits for P2, P2 waits for R3 (both instances held by P3 and P4, who are both waiting), P3 and P4 wait for R1 (held by P1). Available is empty. **Deadlock involving all four.** Running the detection algorithm confirms it: no process has a request satisfiable with Work = 0.

### N5 · Safe or unsafe, single resource type (OS-5.4)

**Question.** A system has 12 instances of one resource. For the state below, (a) is it safe? (b) If P2 requests 1 more instance, should it be granted? (c) If P1 requests 2 instead, should it be granted?

| | Max | Allocated |
|---|---|---|
| P0 | 10 | 5 |
| P1 | 4 | 2 |
| P2 | 9 | 2 |

**Answer.** Available = 12 − 9 = 3. Needs: P0 5, P1 2, P2 7.

(a) P1 (2 ≤ 3) → available 5; P0 (5 ≤ 5) → 10; P2 (7 ≤ 10) → 12. **Safe**: ⟨P1, P0, P2⟩.

(b) Pretend: available 2, P2 needs 6. P1 (2 ≤ 2) → 4; then P0 needs 5 > 4, P2 needs 6 > 4. **Unsafe → do not grant**; P2 waits.

(c) Pretend: available 1, P1 holds 4, needs 0. P1 finishes → 5; P0 (5 ≤ 5) → 10; P2 (7 ≤ 10). **Safe → grant.** Giving resources to the process that is closest to finishing tends to keep the state safe.

### N6 · Cost of detection frequency (OS-5.5)

**Question.** The detection algorithm needs about m × n² basic operations, with m = 5 resource types and n = 200 processes. Each operation takes 10 ns. Requests that cannot be granted immediately occur 2,000 times per second. (a) What fraction of CPU time goes to detection if it runs on every such request? (b) If it runs once per second? (c) What does running less often cost?

**Answer.**

One run: 5 × 200² = 200,000 operations × 10 ns = **2 ms**.

(a) 2,000 runs/s × 2 ms = 4 s of work per second: more than **400%** of one CPU. Impossible to sustain.

(b) 2 ms per second = **0.2%**.

(c) A deadlock can go unnoticed for up to 1 second, with those processes and their resources idle; and when it is found, there may be several cycles, making it harder to tell which request caused it. This is why systems run detection periodically or when CPU utilization drops, not on every request.

### N7 · The price of hold-and-wait prevention (OS-5.3)

**Question.** A job reads from a scanner for 50 minutes, computes for 20 minutes, then prints for 5 minutes. Under the "request everything at the start" protocol, it holds the scanner and the printer for its entire run. (a) What is printer utilization if only this job exists and runs back to back? (b) With protocol 2 (release everything before requesting again), how long does it hold each device? (c) If 4 such jobs run back to back, how long does the whole batch take under protocol 1, assuming the scanner and printer have one instance each and the CPU is not a bottleneck?

**Answer.**

(a) The printer is held for 75 minutes and used for 5: 5 / 75 ≈ **6.7%**.

(b) Scanner held 50 minutes (released when scanning is done); printer held only for its final 5 minutes. Each device is held only while in use.

(c) Under protocol 1, each job holds both devices for 75 minutes, so jobs cannot overlap at all: 4 × 75 = **300 minutes**. (Under protocol 2, job 2 can scan while job 1 computes and prints, so jobs overlap and the batch finishes much sooner: scanning is the bottleneck at 4 × 50 = 200 minutes, plus the last job's 25 minutes of compute and print, about **225 minutes**.)

### N8 · Largest request that can be granted (OS-5.4)

**Question.** One resource type with 10 instances.

| | Max | Allocated |
|---|---|---|
| P1 | 7 | 3 |
| P2 | 4 | 2 |
| P3 | 6 | 2 |

(a) Is the state safe? (b) P3 requests r instances. What is the largest r for which the banker's algorithm grants the request immediately?

**Answer.** Available = 10 − 7 = 3. Needs: P1 4, P2 2, P3 4.

(a) P2 (2 ≤ 3) → 5; P1 (4 ≤ 5) → 8; P3 (4 ≤ 8) → 10. **Safe**.

(b) Try each r ≤ min(Need₃, Available) = 3:

- r = 1: available 2, P3 needs 3. P2 (2 ≤ 2) → 4; P1 (4 ≤ 4) → 7; P3 (3 ≤ 7). **Safe.**
- r = 2: available 1. P1 needs 4, P2 needs 2, P3 needs 2. Nobody fits: **unsafe.**
- r = 3: available 0: **unsafe.**

Largest grantable request: **r = 1**.

## Scenario Questions (Test Your Understanding)

### S1 · The bank that froze (OS-5.3)

A banking service implements `transfer(from, to, amt)` by locking `from->lock`, then `to->lock`. Under load, a few server threads occasionally hang forever. Logs show one hang happened while Alice sent money to Bob and Bob sent money to Alice at the same moment. Explain, and give a fix that does not use a single global lock.

<details><summary>Answer</summary>

Thread 1 runs `transfer(Alice, Bob)`: locks Alice, then waits for Bob. Thread 2 runs `transfer(Bob, Alice)`: locks Bob, then waits for Alice. Circular wait with mutual exclusion, hold and wait, and no preemption: a deadlock.

Fix: break circular wait by ordering. Always lock the account with the **smaller ID** (or address) first, regardless of transfer direction (code in OS-5.3). Every thread then acquires locks in the same global order and no cycle can form. (Alternatives: `trylock` with release and random backoff, which risks livelock without the backoff.)

</details>

### S2 · Deadlock without any locks (OS-5.1, OS-2.4)

A parent program creates two pipes to a child running `tr a-z A-Z` (which writes output as it reads input): the parent writes the entire input to the child's stdin, and only then reads the child's stdout. It works on small inputs. On a 10 MB input, both processes hang. Neither holds a mutex. Is this a deadlock? Which resources are involved?

<details><summary>Answer</summary>

Yes. The child converts input as it goes, so on a large input it fills its stdout pipe (64 KB buffer) and blocks in `write()` waiting for the parent to read. The parent is still blocked in `write()` on the child's stdin pipe, which is full because the child stopped reading. Each waits for the other to drain a buffer: a circular wait on **pipe buffer space** (a resource with limited capacity). Mutual exclusion (buffer space used by one side), hold and wait, no preemption, and circular wait all hold.

Fixes: read and write concurrently (two threads, or non-blocking I/O with `poll`), or write the input to a temporary file. (A child like `sort` would not hang here, because it reads all input before writing anything.)

</details>

### S3 · Unsafe, yet nothing happened (OS-5.4)

A student runs a banker's simulation, forces the system into an unsafe state, lets it run, and all processes finish normally. They conclude the textbook is wrong. What is the misunderstanding?

<details><summary>Answer</summary>

Unsafe means the OS **cannot guarantee** that deadlock will be avoided if processes request up to their declared maximums. It does not mean deadlock is inevitable. In the student's run, processes probably released resources before requesting their full maximum, or never needed their maximum at all, so the worst case never materialized. Deadlocked states are a subset of unsafe states. The banker's algorithm is conservative: it stays in safe states so that the worst case is always survivable.

</details>

### S4 · A cycle, but no problem (OS-5.2)

A monitoring tool builds a resource-allocation graph for a server that has a pool of 8 identical database connections. It reports a cycle and raises a "deadlock" alarm, but the server is clearly processing requests. Why was the alarm wrong, and what should the tool do instead?

<details><summary>Answer</summary>

The connections are a **multiple-instance** resource. A cycle in a RAG proves deadlock only when every resource in the cycle has a single instance. Here, other connection holders outside the cycle can finish and release connections, breaking the cycle. The tool should run the **detection algorithm** (Work/Finish with current requests) for multi-instance resources, and use cycle detection only for single-instance resources such as individual locks.

</details>

### S5 · Why not preempt locks? (OS-5.3)

The OS preempts the CPU all the time and even takes memory away from processes (swapping). Why can it not simply preempt a mutex from a thread to break a deadlock?

<details><summary>Answer</summary>

CPU state and memory contents can be **saved and restored** exactly: a preempted thread resumes as if nothing happened. A mutex protects an invariant over shared data. A thread holding it may be halfway through an update (a linked list with one pointer changed, an account debited but not yet credited). Taking the mutex away lets another thread see the data in that broken state, and when the original thread resumes, it continues as if it still had exclusive access. Correctness would require rolling back the partial update, which only systems with transactions and undo logs (databases) can do. Hence databases *can* preempt locks (by aborting a transaction), but general code cannot.

</details>

### S6 · The polite threads (OS-5.3, OS-5.6)

To avoid deadlock, two threads each run: lock their first lock; `trylock` the second; if that fails, unlock the first and immediately retry. Monitoring shows both threads at 100% CPU for long stretches with no work done. Name the problem and the fix.

<details><summary>Answer</summary>

**Livelock.** The threads are not blocked; they repeatedly acquire, fail, release, and retry in lockstep, each causing the other's failure. Deadlock is prevented (no hold and wait while blocked) but progress is not guaranteed. Fix: add a **random backoff** before retrying (as in Ethernet collision handling), or better, acquire the locks in a **fixed global order**, which removes the need for trylock at all.

</details>

### S7 · Which transaction dies? (OS-5.5, OS-5.3)

A database detects a deadlock between transactions T1 (started an hour ago, has updated 10,000 rows) and T2 (started a second ago, updated 2 rows). Which should it abort, and what could go wrong if it always uses that rule? How do wait-die and wound-wait avoid that problem?

<details><summary>Answer</summary>

Abort **T2**: much less work is lost (cheaper rollback, cheaper retry). The cost function should consider work done, locks held, and time to completion.

If the rule always chooses the youngest or cheapest transaction, a short transaction that keeps conflicting could be aborted every time it retries, and **starve**. Including the number of previous rollbacks in the cost prevents that.

Wait-die and wound-wait abort the younger transaction but let it **restart with its original timestamp**. As time passes it becomes relatively older than newer transactions, and eventually it is the oldest one in any conflict, so it will not be aborted again.

</details>

### S8 · Why Linux does not run the banker's algorithm (OS-5.6)

An interviewer asks: "If the banker's algorithm prevents deadlock, why doesn't Linux use it for user processes?" Give three concrete reasons.

<details><summary>Answer</summary>

(1) Processes cannot declare their **maximum needs** in advance: a program does not know how many files, locks, or memory pages it will need. (2) The process set and resource set change constantly (processes created and destroyed thousands of times per second), while the algorithm assumes fixed n and m. (3) Cost: O(m × n²) on every request, with thousands of processes and resource types, would be enormous. Also, it would refuse requests in unsafe-but-harmless states, reducing throughput. Since user-level deadlocks are rare and usually confined to one application, Linux leaves them to the programmer (the ostrich approach) and restarts hung processes if needed.

</details>

### S9 · Deadlock with one thread (OS-5.1, OS-4.4)

A function `update()` locks `m`, then calls `log_change()`, which also locks `m` (a default, non-recursive pthread mutex). The program hangs whenever `update()` is called. There is only one thread. Is this a deadlock? How can it be fixed?

<details><summary>Answer</summary>

Yes: the thread holds `m` and waits for `m`, which can only be released by itself. It is a circular wait of length one. (A default pthread mutex has undefined behaviour on relock; in practice it blocks forever. An error-checking mutex returns `EDEADLK`.)

Fixes: restructure so the lock is taken only at the outer level (have `log_change_locked()` that assumes the caller holds `m`), or use a **recursive mutex** (`PTHREAD_MUTEX_RECURSIVE`), which lets the owner re-acquire it. Many consider recursive mutexes a design smell, because they hide unclear lock ownership.

</details>

### S10 · Ordering locks you did not create (OS-5.3)

In a file system, `rename("/a/x", "/b/y")` must lock both parent directories `/a` and `/b`. At the same time, another thread renames `/b/p` to `/a/q`. Directory objects are created and destroyed dynamically, so there is no fixed numbering. How can the kernel order these locks?

<details><summary>Answer</summary>

Use an ordering computable at run time: for example, lock the directory with the **lower memory address** (or inode number) first. Both renames then lock the same directory first, and no cycle forms. Real kernels add rules for special cases: Linux's rename locks the **ancestor first** if one directory contains the other, and serializes cross-directory renames with a per-file-system rename lock, because the hierarchy itself can change during the operation. The general idea is the same: every code path must agree on one order.

</details>

### S11 · The thread pool that waits for itself (OS-5.1)

A server uses a fixed pool of 4 worker threads. Each incoming request submits a sub-task to the **same** pool and waits for its result. With 3 simultaneous requests it works; with 4 or more, all requests hang forever. Explain in terms of the four conditions.

<details><summary>Answer</summary>

The resource is **worker threads** (4 instances). With 4 requests, all 4 workers are busy running requests, each waiting for its sub-task. The sub-tasks sit in the queue waiting for a free worker, which can only come from a request finishing, which waits for a sub-task. Mutual exclusion (a worker runs one task at a time), hold and wait (a request holds its worker while waiting), no preemption (a blocked task cannot be moved off its worker), circular wait (requests wait for sub-tasks, which wait for workers held by requests). With 3 requests, one worker is free to run sub-tasks.

Fixes: run sub-tasks in a separate pool; use a work-stealing / fork-join pool where a waiting worker runs queued tasks itself; or make the request asynchronous (don't block a worker while waiting). This is the n(k − 1) + 1 bound in disguise: each request needs 2 workers.

</details>

### S12 · Name the liveness failure (OS-5.6)

Classify each: (a) Two processes, each holding one tape drive and waiting for the other's. (b) Under strict priority scheduling, a nightly backup job has not run for a week because interactive jobs keep arriving. (c) Two network nodes detect a collision, both wait exactly 1 ms, and retransmit, forever colliding. (d) Five philosophers, each holding the left chopstick.

<details><summary>Answer</summary>

(a) **Deadlock**: circular wait on held resources; both blocked. (b) **Starvation**: others progress, the backup never gets the CPU; fix with aging. (c) **Livelock**: both are active and reacting to each other in lockstep; fix with random backoff (as Ethernet does). (d) **Deadlock**: a circular wait of length 5.

</details>
