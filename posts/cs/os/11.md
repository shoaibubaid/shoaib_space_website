# Unit 11: Protection and Security

> **How to use this page.** Section IDs (`OS-11.2`) match the tags on practice questions. Arrows like **→ OS-12.2** point to where an idea is developed further; **← OS-1.4** points back to something this section depends on.

Every unit so far has quietly relied on protection: privileged instructions and dual mode (Unit 1), separate address spaces and page permissions (Units 6 and 7), file permission checks on `open` (Unit 8), privileged I/O (Unit 10). This unit makes protection the main topic. **Protection** is about the mechanisms that control which processes and users may access which resources. **Security** is broader: keeping the system trustworthy against deliberate attackers, who will look for any gap between what the mechanisms were meant to allow and what they actually allow. The treatment here is at the concept level expected in OS courses and interviews.

---

## OS-11.1 · Goals and Principles of Protection

### Protection vs security

| | Protection | Security |
|---|---|---|
| Question | *How* does the system control access to resources? | Is the system safe from **attackers**, and does it stay trustworthy? |
| Threat | Mistakes and faulty programs, as well as misuse | Deliberate, intelligent adversaries |
| Scope | Internal mechanisms: modes, page tables, permissions, ACLs | Also authentication, cryptography, networks, people, physical access |
| Example | The kernel refuses `open("/etc/shadow")` for a normal user | An attacker exploits a bug in a root-owned program to read `/etc/shadow` anyway |

Security goals are often summarized as **CIA**: **confidentiality** (no unauthorized reading), **integrity** (no unauthorized modification), **availability** (no unauthorized denial of service). Others add authenticity and accountability.

### Why protection is needed

- Prevent **malicious** misuse by users and programs.
- Contain the damage from **faulty** programs: a bug in one process must not corrupt another's memory or the kernel (← OS-1.4, OS-6.1).
- Enforce the **policies** of the system's owners (who may read the payroll file?).
- Keep **mechanism separate from policy** (← OS-1.1): the OS provides general mechanisms (permission bits, ACLs, capabilities); administrators and users set the policies.

### Design principles

Saltzer and Schroeder's classic principles (1975) remain the standard vocabulary:

| Principle | Meaning | Example |
|---|---|---|
| **Least privilege** | Give each program and user only the privileges needed for its task, for only as long as needed | A web server binds port 80 then drops root (S9) |
| **Fail-safe defaults** | Default to *no* access; grant explicitly | New files are not world-writable (umask) |
| **Complete mediation** | Check **every** access, not just the first | (UNIX checks at `open` only, so revocation is weaker → S8) |
| **Economy of mechanism** | Keep security mechanisms small and simple, so they can be verified | Small kernels (microkernels, seL4 ← OS-1.6) |
| **Open design** | Security must not depend on keeping the design secret | Published crypto algorithms |
| **Separation of privilege** | Require multiple conditions to grant access | Two-factor authentication |
| **Least common mechanism** | Minimize mechanisms shared between users | Separate address spaces |
| **Psychological acceptability** | Mechanisms must be easy to use correctly, or people bypass them | Sensible defaults |

Also: **defense in depth** (several independent layers, so one failure is not fatal) and **compartmentalization** (divide the system so a breach in one part is contained).

### Protection rings

Hardware provides privilege levels (← OS-1.4): x86 has rings 0 to 3, of which mainstream OSes use ring 0 (kernel) and ring 3 (user). Virtualization adds a level below ring 0 for the hypervisor (→ OS-12.1), and ARM has exception levels EL0 (user), EL1 (kernel), EL2 (hypervisor), EL3 (secure monitor). Code in an inner ring can do everything the outer rings can, and more. Rings give only coarse protection (user vs kernel); finer control comes from the mechanisms below.

### Protection domains

A computer system has **objects**: hardware (CPU, memory segments, printers, disks) and software (files, programs, semaphores, sockets). Each object has a set of **operations** (a file: read, write, execute; a semaphore: wait, signal).

A **protection domain** specifies a set of objects and the operations allowed on each:

```
 domain = { <object, rights-set>, ... }
 D1 = { <file F1, {read}>, <file F2, {read, write}> }
 D2 = { <file F2, {read}>, <printer P, {print}> }
```

A process executes **within a domain**, which determines what it may access. Domains can overlap (share access rights).

- **Static association:** a process's domain is fixed for its lifetime. To follow least privilege, the domain must then include everything the process will *ever* need.
- **Dynamic association:** the process can **switch domains** as it runs, so it holds each privilege only while needed.

In **UNIX**:

- The domain is essentially the **user ID** (plus group IDs and, on Linux, capabilities).
- Switching domains happens through **setuid** programs: when a user runs a program whose file has the setuid bit, the process's effective user ID becomes the file's **owner** (for example, root) while running it (→ OS-11.2).
- Each process also runs in a larger domain boundary given by user mode vs kernel mode.

## OS-11.2 · Access Matrix, ACLs, Capabilities, and UNIX Permissions

### The access matrix

A general model of protection (Lampson, 1971): rows are **domains**, columns are **objects**, and each entry `access(i, j)` lists the operations a process in domain Dᵢ may perform on object Oⱼ.

| | F1 | F2 | F3 | Printer | D1 | D2 |
|---|---|---|---|---|---|---|
| **D1** | read | | read | | | switch |
| **D2** | | | | print | | |
| **D3** | | read | execute | | | |
| **D4** | read, write | | read, write | | switch | |

- Domains themselves can be objects: `switch` in entry (D1, D2) means a process in D1 may switch to D2.
- Special rights control changes to the matrix itself:
  - **Copy** (written `read*`): a domain holding `read*` on an object may grant `read` (or `read*`) to other domains for that object (in the same column).
  - **Owner:** the owner of an object may add or remove any right in that object's column.
  - **Control:** applies to domain objects; a domain with control over D2 may remove rights from D2's row.
- The matrix separates mechanism (the kernel checks every access against the matrix) from policy (who fills in which entries).

The matrix is huge and **sparse** (most domains have no rights to most objects), so it is never stored directly. Implementations:

### Implementation 1: global table

A list of triples `<domain, object, rights-set>`. Simple, but large and slow to search, and hard to express "everyone may read this."

### Implementation 2: access control lists (ACLs)

Store each **column** with its object: each object has a list of `<domain, rights>` pairs.

```
 F1:  alice: read, write;  bob: read;  group staff: read
```

- Easy to answer "**who** can access this object?" and easy to **revoke** a right (edit one list).
- Hard to answer "what can this domain access?" (search every object).
- The check happens on each access (or, in UNIX, at `open` time).
- Default entries handle domains not listed ("everyone else").
- Used by UNIX (the 9 permission bits are a very compressed ACL), POSIX ACLs, NTFS, NFSv4, and most file systems.

### Implementation 3: capability lists

Store each **row** with its domain: each domain has a list of `<object, rights>` pairs. A **capability** is an unforgeable token (like a key or a ticket) naming an object and the operations allowed on it. Possessing the capability **is** the authorization.

- Capabilities must be **protected** from forgery: kept in kernel memory (the process refers to them by index), or tagged in hardware, or cryptographically signed.
- Easy to answer "what can this domain do?" and to **delegate** (pass the capability to another process).
- Hard to answer "who can access this object?" and hard to **revoke**: the capabilities may have been copied anywhere.
- **UNIX file descriptors are capabilities:** after `open()` checks the ACL once, the descriptor itself grants access, and it can be passed to other processes (inherited through `fork` ← OS-2.3, or sent over a UNIX-domain socket with `SCM_RIGHTS`). This is why changing a file's permissions does not affect processes that already have it open (→ S8).
- Pure capability systems: Hydra, CAP, KeyKOS, seL4, Fuchsia (Zircon handles); FreeBSD's **Capsicum** adds capability mode to UNIX.

### Implementation 4: lock–key

Each object has a list of **locks** (bit patterns), each domain a list of **keys**; access is allowed if a domain's key matches one of the object's locks. A compromise between ACLs and capabilities: revocation is easy (change the lock), and keys can be passed around.

### Comparison

| | ACL (per object) | Capability list (per domain) |
|---|---|---|
| "Who can access object X?" | Easy | Hard |
| "What can domain D access?" | Hard | Easy |
| Revocation | Easy (edit the list) | Hard (capabilities may be copied) |
| Delegation | Needs the owner to edit the ACL | Easy (pass the capability) |
| Check cost | Search the list on access | Just validate the token |
| Real systems | UNIX permissions, NTFS, POSIX ACLs | File descriptors, Capsicum, seL4, Android Binder handles |

Real systems **combine** them: an ACL is checked on the first access (`open`), which produces a capability (the file descriptor) used for later accesses.

**Revoking capabilities** is possible with extra mechanisms: *reacquisition* (capabilities are periodically deleted and must be requested again), *back-pointers* (the object keeps pointers to all its capabilities), *indirection* (capabilities point into a global table entry that can be deleted), or *keys* (each capability includes a key compared against a master key that the owner can change). Revocation can be immediate or delayed, selective (some users) or general (everyone), partial (some rights) or total, temporary or permanent.

### UNIX file permissions

Each file has an **owner** (user ID), a **group** (group ID), and 9 permission bits in three classes:

```
 -rwxr-x---   1 alice  staff   ...  report.sh
 |\_/\_/\_/
 | |  |  +-- others: ---   (nothing)
 | |  +----- group:  r-x   (read, execute)
 | +-------- owner:  rwx   (read, write, execute)
 +---------- type: - file, d directory, l symlink, c/b devices, p pipe, s socket
```

In octal, r = 4, w = 2, x = 1 per class: `rwxr-x---` = **0750**.

**How the kernel checks** (using the process's *effective* IDs):

1. If the effective UID is **0 (root)**: access granted (except that execute requires at least one x bit to be set).
2. Else if the process's effective UID equals the file's **owner**: use the **owner** bits, and only them.
3. Else if the file's group matches the process's effective GID or one of its supplementary groups: use the **group** bits.
4. Otherwise: use the **other** bits.

Only **one** class applies; they are not combined. So an owner whose owner bits are empty cannot read the file even if "others" can (→ S3, N2).

**Permissions on directories** mean something different:

| Bit | On a directory |
|---|---|
| **r** | List the names in the directory (`ls`) |
| **w** | Create, delete, or rename entries (requires x as well) |
| **x** | **Search** (traverse): use the directory in a path, access entries by name, `cd` into it |

Consequences: deleting a file needs **w + x on the directory**, not any permission on the file itself; a directory with `x` but not `r` lets people open files whose names they already know, without listing them.

**Special bits** (a fourth octal digit):

| Bit | Octal | On an executable file | On a directory |
|---|---|---|---|
| **setuid** | 4000 | Process runs with the **file owner's** effective UID (shown as `s` in the owner's x position: `-rwsr-xr-x`) | (ignored on Linux) |
| **setgid** | 2000 | Process runs with the file's group as effective GID | New files inherit the directory's **group** (shared project directories) |
| **sticky** | 1000 | (historical; ignored today) | Only a file's **owner** (or the directory owner, or root) may delete or rename it, even if others have w on the directory: `/tmp` is `drwxrwxrwt` (1777 → S4) |

**umask:** a per-process mask of permission bits to **remove** from newly created files. A program creating a file typically requests 0666 (files) or 0777 (directories); the result is `requested & ~umask`. With umask 022, new files get 0644 and directories 0755; with 077, 0600 and 0700 (N1). It implements fail-safe defaults.

### Real, effective, and saved user IDs

Each process has several user IDs (TLPI Chapter 9):

- **Real UID (ruid):** who started the process (the user who ran it).
- **Effective UID (euid):** used for **permission checks**.
- **Saved set-user-ID (suid):** a copy of the euid saved when a setuid program starts, so the program can drop privileges temporarily and regain them later.

When a user (UID 1000) runs a **setuid-root** program such as `passwd` (`-rwsr-xr-x root`), the process starts with ruid = 1000, euid = 0, suid = 0. `passwd` needs root to modify `/etc/shadow`, but uses the real UID to know **whose** password to change and to restrict what the user may do.

- `seteuid(1000)`: drop to the user's privileges temporarily (euid = 1000; suid still 0), so it can later `seteuid(0)` again.
- `setuid(1000)` **as root**: sets ruid, euid, and suid all to 1000: privileges are dropped **permanently** (N7).

setuid programs are powerful and dangerous: any bug in them (a buffer overflow, a race condition, an unexpected environment variable) may let the user run code as root. This is **privilege escalation** (→ OS-11.4), and minimizing setuid programs is a basic hardening step.

### Beyond UNIX bits

- **POSIX ACLs** extend the 9 bits with entries for specific users and groups (`setfacl -m u:bob:r file`, `getfacl`). NTFS uses rich ACLs with allow and deny entries and inheritance.
- **Linux capabilities** split root's all-or-nothing power into about 40 separate privileges: `CAP_NET_BIND_SERVICE` (bind ports below 1024), `CAP_SYS_ADMIN` (many administrative operations), `CAP_KILL`, `CAP_CHOWN`, `CAP_SYS_NICE` (← OS-3.6)... A program can be given just one (`setcap cap_net_bind_service=+ep /usr/bin/server`) instead of being setuid root. (Unrelated to capabilities in the access-matrix sense, despite the name.)
- **Discretionary vs mandatory access control:**
  - **DAC:** the **owner** decides who may access their objects (UNIX permissions, ACLs).
  - **MAC:** a **system-wide policy** that owners cannot override, enforced by the kernel for every access. Linux Security Modules: **SELinux** (labels every process and file with a security context; policy rules say which contexts may interact; used by Android and Red Hat) and **AppArmor** (path-based profiles per program; used by Ubuntu). Classic military MAC models: **Bell–LaPadula** for confidentiality ("no read up, no write down") and **Biba** for integrity (the reverse).
- **Role-based access control (RBAC):** privileges are assigned to **roles** (administrator, auditor, backup operator), and users are assigned roles. Easier to manage in organizations. Solaris RBAC and `sudo` rules approximate it.
- **Windows:** each process has an **access token** (user SID, group SIDs, privileges, integrity level); each object has a **security descriptor** with an ACL. The Security Reference Monitor compares them on access. **Mandatory integrity levels** (low, medium, high, system) keep low-integrity processes (like a sandboxed browser tab) from writing to higher-integrity objects.

## OS-11.3 · Authentication

Protection decides what a *user* may do; **authentication** establishes *who* the user is. It is based on:

- **Something you know:** a password or PIN.
- **Something you have:** a phone (one-time codes), a hardware security key, a smart card.
- **Something you are:** fingerprint, face, iris (biometrics).

**Multi-factor authentication (MFA)** combines two or more categories.

### Storing passwords: hashing

The system must verify passwords without storing them in a form an attacker could read.

- Store a **one-way hash** H(password), never the password itself. At login, compute H(entered password) and compare. Even administrators cannot recover the password, and a stolen hash database does not directly reveal passwords.
- On Linux, hashes live in **`/etc/shadow`**, readable only by root (the world-readable `/etc/passwd` historically held them and now holds only `x`). A shadow entry looks like `alice:$6$<salt>$<hash>:...`, where `$6$` identifies the algorithm (SHA-512-crypt; `$y$` is yescrypt, `$2b$` bcrypt).

Attackers who obtain the hashes can still try guesses offline:

- **Brute force:** try every possible password.
- **Dictionary attack:** try common passwords and variations.
- **Precomputed tables (rainbow tables):** compute hashes of billions of candidate passwords once, and look up stolen hashes instantly.

### Salt

A **salt** is a random value, unique per user, stored alongside the hash; the system stores `salt` and `H(salt + password)`.

- The same password produces **different hashes** for different users, so an attacker cannot tell which users share a password.
- **Precomputed tables become useless**: a table would have to be built for every possible salt.
- An attacker must attack **each hash separately**: the work for a dictionary attack multiplies by the number of users (N3).

A salt is not secret; its value comes from being unique.

### Slow hashes

General-purpose hash functions (MD5, SHA-256) are designed to be **fast**: a GPU can compute billions per second, which helps attackers. Password hashing uses deliberately **slow**, tunable functions: **bcrypt**, **scrypt**, **Argon2** (memory-hard, which also defeats GPUs and custom chips), and SHA-512-crypt with many rounds. A legitimate login computing one hash in 100 ms is unnoticeable; an attacker needing billions of them is slowed by orders of magnitude (N3).

### Other mechanisms

- **Password policies:** length matters more than complexity rules; check new passwords against lists of breached passwords; limit online guessing with rate limiting or lockout.
- **One-time passwords:** TOTP codes (an authenticator app computes a code from a shared secret and the current time) or hardware tokens.
- **Public-key authentication:** SSH keys, FIDO2/WebAuthn security keys and passkeys: the server stores only a public key, and the client proves possession of the private key by signing a challenge. Nothing reusable crosses the network, and phishing is much harder.
- **Biometrics:** convenient, but cannot be changed if compromised, and are usually used to unlock a local key rather than sent to a server.
- **PAM** (pluggable authentication modules) lets Linux programs (`login`, `sshd`, `sudo`) use configurable authentication methods without changing their code.

### From login to shell

On a Linux console: `getty` opens the terminal and runs `login`, which (running as root) authenticates the user via PAM against `/etc/shadow`, then calls `setgid`, `initgroups`, and **`setuid(uid)`** to permanently drop to the user's identity (← OS-11.2), and finally `exec`s the user's shell (← OS-2.3). Every process the user starts inherits those IDs.

## OS-11.4 · Threats: Buffer Overflows, Privilege Escalation, and Others

### Categories of threats

- **Breach of confidentiality** (reading data), **integrity** (modifying data), **availability** (denial of service), **theft of service** (unauthorized use of resources).
- **Program threats:**
  - **Trojan horse:** a program that does something useful (or seems to) but also does something malicious. Classic example: a fake login program that records passwords. A path containing `.` before system directories lets an attacker plant a trojan `ls` in a directory.
  - **Trap door (backdoor):** a hidden way to bypass authentication, left by a programmer. Ken Thompson's "Reflections on Trusting Trust" (1984) showed a compiler could insert a backdoor into the login program and into future compilers, invisible in all source code (→ S11).
  - **Logic bomb:** code that triggers malicious behaviour under a certain condition (a date, a missing name on the payroll).
  - **Virus:** code that attaches itself to other programs or documents and spreads when they run.
  - **Worm:** a standalone program that spreads itself over the network by exploiting vulnerabilities. The **Morris worm** (1988) infected a large share of the Internet using a **buffer overflow** in `fingerd` (which used `gets()`), a debug mode in `sendmail`, and password guessing plus trusted-host `rsh` logins.
  - **Ransomware:** encrypts the victim's files and demands payment for the key.
- **Denial of service:** exhausting resources: a **fork bomb** (N8), filling the disk, network floods (SYN floods, amplification attacks). Resource limits (`ulimit`, cgroups ← OS-7.5) and rate limiting are the defenses.
- **Side channels:** leaking secrets through timing, caches, or power. **Spectre** and **Meltdown** (2018) used speculative execution and cache timing to read memory across protection boundaries (← OS-6 S12). **Rowhammer**: repeatedly accessing DRAM rows flips bits in neighbouring rows, which has been used to corrupt page tables.

### Buffer overflow (stack smashing)

The most famous class of vulnerability, and the one to understand in detail.

Consider:

```c
void greet(const char *input) {
    char name[64];
    strcpy(name, input);      // no bounds check: copies until the terminating '\0'
    printf("Hello, %s\n", name);
}
```

The stack frame of `greet` on x86-64 (the stack grows toward lower addresses ← OS-2.1):

```
 higher addresses
 +----------------------------+
 |  caller's frame            |
 +----------------------------+
 |  return address            |  <- where greet() returns to
 +----------------------------+
 |  saved frame pointer (rbp) |
 +----------------------------+
 |  name[63]                  |
 |  ...                       |  <- strcpy writes upward from name[0]
 |  name[0]                   |
 +----------------------------+
 lower addresses
```

`strcpy` writes from `name[0]` **upward**. If `input` is longer than 64 bytes, it overwrites the saved frame pointer and then the **return address**. When `greet` returns, the CPU jumps to whatever address the attacker placed there.

The classic attack (as in Aleph One's 1996 article "Smashing the Stack for Fun and Profit"):

1. Put machine code (**shellcode**, for example code that runs `/bin/sh`) into the input itself, in the buffer.
2. Overwrite the return address with the address of that code on the stack.
3. When the function returns, the shellcode runs **with the privileges of the process**. If the program is setuid root, or a network daemon running as root, the attacker gets a root shell.

Other memory-corruption bugs follow the same pattern: **heap overflows** (overwrite adjacent heap objects or allocator metadata ← OS-6 S2), **use-after-free** (use memory after it has been freed and reallocated for something else), **format-string bugs** (`printf(user_input)` lets `%n` write to memory), and **integer overflows** (a size calculation wraps around, so a buffer is allocated too small). They are possible because C and C++ do not check bounds.

### Time-of-check to time-of-use (TOCTOU)

A **race condition** between checking a condition and acting on it (← OS-4.1, applied to security). A classic setuid-root program:

```c
if (access("/tmp/userfile", W_OK) == 0) {     // check: may the REAL user write it?
    /* window: attacker replaces /tmp/userfile with a symlink to /etc/passwd */
    int fd = open("/tmp/userfile", O_WRONLY); // use: opened with ROOT's effective ID
    write(fd, data, len);                     // overwrites /etc/passwd
}
```

The file checked is not the file used. Fixes: do not separate check and use: temporarily drop privileges (`seteuid(getuid())`) and let `open()` itself do the check; open with `O_NOFOLLOW` or `O_EXCL`; operate on file descriptors (`fstat`, `openat`) instead of path names; and avoid shared world-writable directories (→ S2).

### Privilege escalation

Gaining privileges beyond those granted:

- **Vertical escalation:** normal user → root (or user mode → kernel mode): exploiting a setuid program, a root daemon, or a **kernel** vulnerability (a bug in a system call or driver lets user code write kernel memory, for example to overwrite its own credentials structure).
- **Horizontal escalation:** accessing another user's data at the same privilege level.

Real attacks chain steps: remote code execution in a network service (running as an unprivileged user), then a local privilege escalation to root, then persistence (a backdoor), then movement to other machines.

## OS-11.5 · Defenses

No single defense stops everything; systems stack many (**defense in depth**).

### Non-executable memory: DEP / NX / W^X

The classic stack-smashing attack executes code **on the stack**. Page tables can mark pages **non-executable** (the **NX / XD bit** in the PTE ← OS-6.4; Windows calls the feature **DEP**, data execution prevention). Stacks and heaps are mapped writable but **not** executable; code pages are executable but **not** writable: the **W^X** (write XOR execute) policy. Jumping into injected shellcode now causes a fault.

### Stack canaries

The compiler (`-fstack-protector`) places a random value, the **canary**, between local buffers and the saved frame pointer / return address, and checks it before the function returns:

```
 | return address |
 | saved rbp      |
 | CANARY         |  <- random per process, checked on return
 | name[64]       |
```

A linear overflow that reaches the return address must overwrite the canary first; the check fails and the program aborts ("stack smashing detected") instead of returning to the attacker's address. Canaries do not stop overwrites of other local variables or targeted (non-linear) writes, and a canary that leaks (or can be guessed byte by byte in a forking server) can be bypassed (N6).

### Address space layout randomization (ASLR)

Attacks need to know **addresses**: where the stack, the shellcode, library functions, or gadgets are. ASLR places the stack, heap, `mmap` region, shared libraries, and (for **position-independent executables**, PIE) the program itself at **random** addresses each time a program runs. The kernel does the same for itself (**KASLR**).

- Effectiveness depends on the **entropy**: the number of random bits. 32-bit systems had so little (around 16 bits for some regions) that brute force was practical; 64-bit systems have far more (N5).
- Defeated by **information leaks**: a bug that reveals one pointer reveals the randomized base of that region, since everything within it moves together.

### Return-oriented programming (ROP), and defenses against it

With NX, attackers stopped injecting code and started **reusing existing code**. **Return-to-libc:** overwrite the return address with the address of `system()` in libc and arrange the argument `"/bin/sh"`. **ROP** generalizes this: chain many short instruction sequences ending in `ret` (**gadgets**) found in existing code, with the stack holding a list of gadget addresses, to perform arbitrary computation, all without writing a single executable byte.

Defenses: ASLR (the attacker must know where gadgets are), **control-flow integrity** (CFI: restrict indirect jumps and calls to valid targets), hardware **shadow stacks** (Intel CET, ARM PAC and BTI: the CPU keeps a protected copy of return addresses and faults if they do not match), and reducing the attack surface.

### Kernel-specific hardening

- **SMEP / SMAP** (x86; PAN/PXN on ARM): the kernel may not **execute** user-space pages (SMEP), and may not **access** user-space pages except through explicit, audited copy functions (SMAP ← OS-1.5 `copy_from_user`). This blocks attacks that trick the kernel into jumping to or reading attacker-controlled user memory.
- KASLR, kernel stack canaries, read-only kernel data after boot, and restrictions on who can load kernel modules.
- **Secure Boot** (UEFI verifies signatures of the bootloader and kernel ← OS-1.7) and **measured boot** with a **TPM** (a chip that records hashes of each boot stage and can refuse to release disk-encryption keys if the boot chain was tampered with).

### Safer code

- Memory-safe languages (Rust, Go, Java, Python) eliminate most buffer overflows and use-after-free bugs by construction; parts of Linux, Windows, and Android are now written in Rust.
- Safer C APIs: `fgets` instead of `gets` (removed from C11), `snprintf`, `strlcpy`; `-D_FORTIFY_SOURCE` adds checks to common functions; compiler warnings, fuzzing, and sanitizers (AddressSanitizer ← OS-6 S2).

### Sandboxing and least privilege

Assume some code **will** be compromised, and limit what it can do afterwards:

- **Privilege separation and dropping:** split a program into a small privileged part and a large unprivileged part (OpenSSH's design); drop root after the privileged setup (S9).
- **`chroot`:** change a process's root directory so it sees only a subtree of the file system. Useful but weak: it does not restrict other resources, and a root process can escape (S10).
- **seccomp / seccomp-BPF:** restrict which **system calls** a process may make (and with which arguments). Every system call is a possible entry point into kernel bugs, so a renderer that only needs `read`, `write`, `mmap`, and a few others blocks the rest. Chrome's renderer sandbox, Docker's default profile, and systemd service hardening use it. OpenBSD's `pledge` and `unveil` are simpler equivalents.
- **Namespaces and cgroups:** give a process its own view of PIDs, mounts, network, users, and resource limits: the basis of containers (→ OS-12.2).
- **Mandatory access control:** SELinux or AppArmor profiles confine what a daemon can touch, even if it runs as root (← OS-11.2).
- **Mobile sandboxes:** Android runs each app as a separate Linux **UID** with SELinux policies and permission prompts; iOS apps run in sandbox containers with entitlements.
- Virtual machines provide an even stronger boundary (→ OS-12.1).

### Protecting data

- **Encryption at rest:** full-disk encryption (Linux dm-crypt/LUKS, Windows BitLocker, macOS FileVault) protects data if the device is stolen, when file permissions are useless because the attacker boots another OS (→ S12).
- **Encryption in transit:** TLS, SSH.
- **Auditing and logging:** record security-relevant events (logins, privilege changes, access denials) for detection and investigation; Linux `auditd`.
- **Patching:** most real compromises exploit known vulnerabilities whose fixes were already available.

| Attack step | Defenses |
|---|---|
| Overflow a buffer | Bounds checking, safe languages, fortify, fuzzing |
| Overwrite the return address | Stack canaries, shadow stacks |
| Execute injected code | NX / W^X |
| Find code and data to reuse | ASLR / KASLR, PIE |
| Chain existing code (ROP) | CFI, shadow stacks, PAC/BTI |
| Use the compromised process's privileges | Least privilege, capabilities, sandboxing, seccomp, MAC |
| Escalate to kernel | SMEP/SMAP, seccomp (less kernel exposure), patching |

## Quick Revision Sheet

- Protection = mechanisms controlling access; security = defending against attackers (confidentiality, integrity, availability).
- Principles: least privilege, fail-safe defaults, complete mediation, economy of mechanism, open design, separation of privilege; defense in depth.
- Domain = set of <object, rights>. UNIX domain = user ID; setuid switches domains.
- Access matrix: domains × objects. Copy (*), owner, control rights; `switch` for domains.
- ACL = column per object (easy revocation, "who can access?"). Capability list = row per domain (easy delegation, hard revocation). File descriptors are capabilities.
- UNIX check uses only one class: root → owner → group → others. Directory r = list, w = create/delete (with x), x = traverse.
- setuid 4000 (run as owner), setgid 2000 (run as group; directories inherit group), sticky 1000 (only owner deletes in shared dirs, /tmp = 1777).
- New file mode = requested & ~umask (umask 022: files 0644, dirs 0755).
- Real UID (who), effective UID (checks), saved set-UID (regain). `seteuid` is temporary; `setuid` as root is permanent.
- Linux capabilities split root; DAC vs MAC (SELinux, AppArmor); RBAC; Windows tokens + security descriptors.
- Authentication: know / have / are; MFA. Store salted, slow hashes (bcrypt, scrypt, Argon2); salt defeats precomputed tables and forces per-user attacks.
- Threats: trojan, backdoor, logic bomb, virus, worm (Morris: fingerd `gets` overflow), ransomware, DoS (fork bomb), side channels (Spectre/Meltdown, Rowhammer).
- Stack overflow: overwrite return address → jump to attacker code. TOCTOU: check then use a different object.
- Defenses: NX/W^X, canaries, ASLR (entropy, info leaks), CFI and shadow stacks against ROP, SMEP/SMAP, secure boot + TPM, safe languages, sandboxing (seccomp, namespaces, MAC, chroot's limits), encryption at rest, patching.

## Worked Numerical Problems

### N1 · Permission bits and umask (OS-11.2)

**Question.** (a) Write the `ls -l` permission string for modes 0754, 0640, 4755, 2750, 1777, and 4644. (b) With umask 022, 027, and 077, what modes do new files (requested 0666) and directories (requested 0777) get?

**Answer.**

(a)
| Octal | String | Notes |
|---|---|---|
| 0754 | `rwxr-xr--` | |
| 0640 | `rw-r-----` | |
| 4755 | `rwsr-xr-x` | setuid, owner has x → lowercase `s` |
| 2750 | `rwxr-s---` | setgid, group has x → `s` in the group position |
| 1777 | `rwxrwxrwt` | sticky → `t` in the others position (/tmp) |
| 4644 | `rwSr--r--` | setuid but owner **lacks** x → capital `S` (setuid has no effect) |

(b) Result = requested & ~umask:

| umask | New file (0666) | New directory (0777) |
|---|---|---|
| 022 | 0644 `rw-r--r--` | 0755 `rwxr-xr-x` |
| 027 | 0640 `rw-r-----` | 0750 `rwxr-x---` |
| 077 | 0600 `rw-------` | 0700 `rwx------` |

(For 027: 0666 & ~0027 = 0666 & 0750 = 0640.) Note umask only removes bits; it never adds execute permission to files.

### N2 · Who can do what? (OS-11.2)

**Question.** Directory `/proj` is owned by alice, group `dev`, mode 0730. Inside it, `data.txt` is owned by alice, group `dev`, mode 0467. Users: alice (member of `dev`), bob (member of `dev`), carol (not in `dev`). For each user: can they list `/proj`? Read `data.txt`? Write `data.txt`? Delete `data.txt`?

**Answer.** `/proj` 0730 = `rwx-wx---`; `data.txt` 0467 = `r--rw-rwx`.

| | List `/proj` | Read `data.txt` | Write `data.txt` | Delete `data.txt` |
|---|---|---|---|---|
| **alice** (owner: dir `rwx`, file `r--`) | Yes | Yes | **No**: owner bits are `r--`, and the group and other bits are never consulted for the owner | Yes (w + x on the directory) |
| **bob** (group: dir `-wx`, file `rw-`) | **No** (no r on the directory) | Yes, if he knows the name (x lets him traverse) | Yes | **Yes**: deletion depends on the directory (w + x), not on the file; no sticky bit |
| **carol** (others: dir `---`) | No | **No**: even though the file says `rwx` for others, she cannot traverse `/proj` | No | No |

Two traps: the owner is **less** privileged than others on this file (only one class applies), and file permissions are irrelevant if the path cannot be traversed.

### N3 · Password cracking and salts (OS-11.3)

**Question.** An attacker has stolen a password-hash database. (a) Passwords are 8 lowercase letters, hashed with a fast hash at 10¹⁰ guesses per second on a GPU cluster. How long does an exhaustive search take? (b) 8 characters from 94 printable ASCII characters? (c) The same as (b), but with bcrypt tuned so the attacker manages only 10⁴ guesses per second? (d) The attacker wants to test a dictionary of 10⁷ common passwords against 10⁶ users. How many hash computations are needed without salts and with per-user salts?

**Answer.**

(a) 26⁸ ≈ 2.09 × 10¹¹ candidates ÷ 10¹⁰/s ≈ **21 seconds**.

(b) 94⁸ ≈ 6.1 × 10¹⁵ ÷ 10¹⁰/s ≈ 6.1 × 10⁵ s ≈ **7 days**.

(c) 6.1 × 10¹⁵ ÷ 10⁴/s ≈ 6.1 × 10¹¹ s ≈ **19,000 years**. The slow hash matters more than the character set.

(d) **Without salts:** hash each dictionary word once, **10⁷** computations, then look up all 10⁶ stolen hashes (or use a precomputed table: zero new work). Users with the same password are also revealed as a group. **With salts:** each user's hash must be attacked separately: 10⁷ × 10⁶ = **10¹³** computations (and no precomputation is possible). Salting does not make one weak password harder to crack, but it multiplies the cost of cracking many.

### N4 · From access matrix to ACLs and capabilities (OS-11.2)

**Question.** Given the access matrix:

| | F1 | F2 | F3 |
|---|---|---|---|
| **D1** | read, write | read | |
| **D2** | | read* | execute |
| **D3** | read | | read, write |

(a) Write the ACLs and the capability lists. (b) What does `read*` allow D2 to do? (c) A system has 1,000 domains and 100,000 objects, and on average each object has 5 non-empty entries. Compare the size of a dense matrix (1 byte per entry) with ACLs (5 bytes per entry: 4-byte domain ID plus 1 byte of rights).

**Answer.**

(a) ACLs (per object): F1: {D1: read, write; D3: read}. F2: {D1: read; D2: read*}. F3: {D2: execute; D3: read, write}.

Capability lists (per domain): D1: {F1: read, write; F2: read}. D2: {F2: read*; F3: execute}. D3: {F1: read; F3: read, write}.

(b) The copy flag lets D2 **grant** `read` on F2 to other domains (for example, add `read` to D3's entry for F2), and possibly `read*` itself depending on the variant (transfer vs limited copy).

(c) Dense: 1,000 × 100,000 = 10⁸ entries = **100 MB**, almost all empty. ACLs: 100,000 × 5 entries × 5 bytes = **2.5 MB**. The matrix is always stored sparsely.

### N5 · ASLR entropy (OS-11.5)

**Question.** An attacker can guess the randomized base address of a library and try an exploit; a wrong guess crashes the target, which (like a forking server) is restarted with the **same** randomization, allowing 100 attempts per second. (a) With 16 bits of entropy (as on some 32-bit systems), how long on average until success? (b) With 28 bits? (c) What if each crash re-randomizes the layout? (d) Why can one information leak defeat ASLR entirely?

**Answer.**

(a) 2¹⁶ = 65,536 possibilities; on average half must be tried: 32,768 ÷ 100/s ≈ **5.5 minutes**. (Researchers demonstrated attacks on 32-bit ASLR in minutes in 2004.)

(b) 2²⁸ ≈ 2.7 × 10⁸; half is 1.3 × 10⁸ ÷ 100/s ≈ 1.3 × 10⁶ s ≈ **15.5 days**, and thousands of crashes per second would be noticed long before.

(c) If the layout changes after every crash, each attempt succeeds independently with probability 2⁻¹⁶; the expected number of attempts becomes 2¹⁶ (twice as many as (a)), since guesses cannot be eliminated. Forking servers that do **not** re-randomize child processes are the easy case for attackers.

(d) All addresses within a region move **together**: learning a single pointer (say, a return address into libc leaked through a format-string bug) reveals the base of the whole library, and every gadget in it. Entropy then drops to zero for that region.

### N6 · Overflow offsets and canaries (OS-11.4, OS-11.5)

**Question.** A function has `char buf[64]`, followed on the stack (toward higher addresses) by an 8-byte saved frame pointer and then the return address. (a) How many bytes of input reach the start of the return address? (b) With a stack protector, an 8-byte canary is placed between `buf` and the saved frame pointer. How many bytes now, and what happens if the attacker simply overwrites everything? (c) The canary's lowest byte is always 0x00 (to stop string copies), and the rest are random. What is the chance of guessing it in one try? (d) A server forks a child per connection, and each child inherits the same canary. Overwriting just one byte of the canary at a time, how many attempts are needed at most to learn it?

**Answer.**

(a) 64 (buffer) + 8 (saved rbp) = **72 bytes** of filler, then the next 8 bytes overwrite the return address. (Real compilers may add padding or reorder locals; attackers measure the exact offset.)

(b) 64 + 8 (canary) + 8 (saved rbp) = **80 bytes** before the return address. Overwriting everything changes the canary, the check before `ret` fails, and the program aborts with "stack smashing detected" instead of jumping to the attacker's address.

(c) 7 random bytes = 56 bits: 1 in 2⁵⁶ ≈ **1.4 × 10⁻¹⁷**.

(d) Overwrite only the first unknown byte: if the child crashes, the guess was wrong; if it does not, the byte is correct. At most 256 guesses per byte × 7 bytes = **1,792 attempts** (about 900 on average). This is why a canary (and ASLR) that does not change across `fork()` is weak against forking servers, and why some servers re-exec their workers.

### N7 · Tracing user IDs (OS-11.2)

**Question.** (a) User 1000 runs a setuid-root program. Give (real, effective, saved) UIDs after each call and whether it succeeds: `seteuid(1000)`; `open("/etc/shadow", O_RDONLY)`; `seteuid(0)`; `setuid(1000)`; `seteuid(0)`. (b) User bob (UID 1001) runs a program that is setuid **alice** (UID 1000, not root). The program calls `setuid(1001)`. What are the IDs, and can it get back alice's identity?

**Answer.**

(a)
| Call | (real, effective, saved) | Result |
|---|---|---|
| start | (1000, 0, 0) | euid = file owner (root) |
| `seteuid(1000)` | (1000, 1000, 0) | OK: temporarily unprivileged |
| `open("/etc/shadow")` | (1000, 1000, 0) | **Fails** (`EACCES`): checks use euid 1000 |
| `seteuid(0)` | (1000, 0, 0) | OK: 0 is the saved set-UID |
| `setuid(1000)` | (1000, 1000, 1000) | OK: with euid 0, `setuid` sets **all three** |
| `seteuid(0)` | (1000, 1000, 1000) | **Fails** (`EPERM`): 0 is neither the real nor the saved UID; root is gone for good |

(b) Start: (1001, 1000, 1000). An **unprivileged** process calling `setuid(1001)` changes only the effective UID: (1001, 1001, 1000). The saved UID is still 1000, so a later `seteuid(1000)` **succeeds**: the program can regain alice's identity. `setuid()` drops privileges permanently only when called by a privileged process; to drop permanently here, use `setresuid(1001, 1001, 1001)`. Confusion about exactly this behaviour has caused real vulnerabilities (TLPI Chapter 9).

### N8 · Fork bomb (OS-11.4)

**Question.** The shell fork bomb `:(){ :|:& };:` defines a function that runs two copies of itself (connected by a pipe) in the background, forever. (a) Ignoring limits, how many processes exist after k generations? (b) With a PID limit of 32,768 (the traditional `pid_max`), after about how many generations is the system full? If each generation takes 1 ms, how long is that? (c) With `ulimit -u 4096` for the user, what happens, and why does the machine still become sluggish? (d) How is this contained on modern systems?

**Answer.**

(a) Each process starts two, so generation k has 2ᵏ new processes; the total spawned is 1 + 2 + ... + 2ᵏ = 2ᵏ⁺¹ − 1 (though finished ones exit, the tree grows about exponentially).

(b) 2¹⁵ = 32,768: about **15 generations**, which takes only **tens of milliseconds**. Then every `fork()` in the system fails (`EAGAIN`), including the administrator's attempts to start `kill` or a shell.

(c) The user's processes stop at 4,096, so other users and root can still fork. But the 4,096 processes keep running, retrying `fork` in tight loops, consuming CPU and scheduler time, so the machine is slow. The fix is to stop all of them at once (for example, `kill -STOP` then `kill -9` for the user's processes, or `pkill -9 -u user`), since killing one at a time lets the rest refill the slots.

(d) Per-user limits (`RLIMIT_NPROC`) and, more robustly, **cgroups** with `pids.max` for each user session, service, or container (systemd sets `TasksMax` by default), so a fork bomb can only exhaust its own group's quota (→ OS-12.2).

## Scenario Questions (Test Your Understanding)

### S1 · How passwd edits a root-only file (OS-11.2)

`/etc/shadow` is readable and writable only by root, yet any user can run `passwd` to change their own password. How? Why is this mechanism also a security risk, and what limits the risk?

<details><summary>Answer</summary>

`/usr/bin/passwd` is owned by root with the **setuid** bit (`-rwsr-xr-x`). When a user runs it, the process's **effective UID is 0**, so the kernel allows it to open `/etc/shadow`. The program itself enforces the policy, using the **real UID** to determine whose entry may be changed and requiring the old password.

The risk: the program runs with full root privileges on input controlled by an untrusted user (arguments, environment variables, terminal input). Any bug (a buffer overflow, a TOCTOU race, trusting `PATH` or `LD_PRELOAD`) becomes a root exploit. Limits: the kernel ignores `LD_PRELOAD` and similar variables for setuid programs ("secure execution mode"); programs are written carefully, drop privileges when not needed, and are kept small; systems minimize the number of setuid binaries (or replace them with Linux capabilities or a privileged daemon reached over IPC, as with polkit).

</details>

### S2 · The race in /tmp (OS-11.4)

A setuid-root utility writes a report for the calling user. It checks `access("/tmp/report", W_OK)` to make sure the real user may write the file, then opens and writes it. An attacker makes the utility overwrite `/etc/passwd`. Explain the attack and at least two fixes.

<details><summary>Answer</summary>

**TOCTOU.** `access()` checks permissions using the **real** UID, but `open()` uses the **effective** UID (root). Between the two calls, the attacker (who controls `/tmp/report`, since `/tmp` is world-writable) replaces it with a **symbolic link** to `/etc/passwd`. The check was done on a harmless file; the open follows the symlink with root's privileges. Running the attack in a loop wins the race eventually.

Fixes: (1) drop privileges (`seteuid(getuid())`) and just call `open()`, letting the kernel check atomically as the user; (2) open with `O_NOFOLLOW` (refuse symlinks) and `O_CREAT | O_EXCL` for new files (fail if anything already exists); (3) create files in a private directory, not a shared one, or use `mkstemp()`; (4) after opening, check with `fstat()` on the descriptor (not the path) that the file is what was expected. Linux's `protected_symlinks` setting also blocks following other users' symlinks in sticky directories.

</details>

### S3 · The owner who cannot read (OS-11.2)

A user runs `chmod 077 secret.txt` intending to "hide it from the group and others," then finds they themselves cannot read it, while everyone else can. Explain.

<details><summary>Answer</summary>

`chmod 077` sets the mode to `----rwxrwx`: **no** permissions for the owner and full permissions for the group and others. They intended `700` (`rwx------`). And because UNIX applies exactly **one** class, the owner is checked against the owner bits only (`---`); the fact that "others" have `rwx` does not help the owner. The owner can still `chmod` the file back, since changing the mode requires ownership, not permissions. (Root would be able to read it regardless.)

</details>

### S4 · Deleting other people's files in /tmp (OS-11.2)

`/tmp` must be writable by everyone so that any program can create temporary files there. Why can user mallory not simply delete or rename the files that alice creates in `/tmp`?

<details><summary>Answer</summary>

Deleting or renaming a file requires **write + execute permission on the directory**, which everyone has for `/tmp` (mode 777). Without anything else, mallory could delete alice's files, or replace them (for example, with a symlink, enabling attacks like S2).

`/tmp` has the **sticky bit** (mode 1777, `drwxrwxrwt`): in a sticky directory, a file can be deleted or renamed only by the file's **owner**, the directory's owner, or root. Everyone can create files, but only owners can remove them.

</details>

### S5 · The leaked password database (OS-11.3)

Two websites have their user databases stolen. Site A stored unsalted MD5 hashes; site B stored bcrypt hashes with per-user salts (cost factor 12). Describe what the attackers can do with each, within a day.

<details><summary>Answer</summary>

**Site A:** MD5 is extremely fast (GPUs compute tens of billions per second), and without salts, attackers can use precomputed tables and crack each common password once for all users who share it. Within hours, most real-world passwords (dictionary words, common patterns, short passwords) are recovered, and identical hashes reveal groups of users with the same password. Since people reuse passwords, attackers then try these credentials on other sites (credential stuffing).

**Site B:** each guess takes a significant fraction of a second of compute per user, and each user must be attacked separately because of the salts. The attacker can afford to test only the most common passwords against a few accounts; strong, unique passwords are effectively safe. Site B should still force a password reset, but the damage is far smaller.

</details>

### S6 · Exploiting gets() (OS-11.4, OS-11.5)

A network daemon running as root reads a request line with `gets(buf)` into `char buf[128]`. Describe how an attacker could get a root shell on a system with no defenses, and which defense stops each step on a modern system.

<details><summary>Answer</summary>

Attack: send a line longer than 128 bytes containing shellcode, padding, and an overwritten return address pointing back into the buffer. `gets()` has no length limit, so it overwrites the saved frame pointer and return address. When the function returns, it jumps into the shellcode, which runs `/bin/sh` as root with its input and output connected to the attacker's socket. (This is essentially how the Morris worm exploited `fingerd`.)

Modern defenses, step by step: the compiler **warns** about `gets` and C11 removed it (use `fgets`); **stack canaries** detect the overwrite before the return; **NX** makes the stack non-executable, so shellcode on the stack cannot run; **ASLR** makes the buffer's and libraries' addresses unpredictable; the daemon should not run as root at all (**least privilege**), and a **seccomp** filter or **SELinux** profile would stop a compromised daemon from executing a shell.

</details>

### S7 · NX is on, but the exploit still works (OS-11.5)

A security team confirms NX is enabled on a server, yet a published exploit for one of its services still achieves code execution without injecting any executable code. How? What additional defenses help?

<details><summary>Answer</summary>

**Return-oriented programming.** The exploit overwrites the stack with a chain of return addresses, each pointing to a short sequence of existing instructions ending in `ret` (gadgets) inside the program or libc. Each `ret` jumps to the next gadget. Combined, they can call `mprotect` to make memory executable, or directly call `execve("/bin/sh")`. No new code is written, so NX is irrelevant.

To build the chain, the attacker must know where the gadgets are: typically obtained through an **information leak** that defeats ASLR, or because the binary was not built as PIE (so its code is at a fixed address). Additional defenses: build everything as PIE with full ASLR, fix info leaks, **control-flow integrity**, hardware **shadow stacks** (Intel CET) or pointer authentication (ARM PAC) that detect corrupted return addresses, and least-privilege sandboxing to limit the damage.

</details>

### S8 · Revoked, but still reading (OS-11.2)

An employee's access to a confidential file is revoked with `chmod` and `setfacl`, but monitoring shows a program running under their account continues to read the file for hours. How? What would stop it?

<details><summary>Answer</summary>

UNIX checks permissions when the file is **opened**. The long-running program opened the file before the change and holds a **file descriptor**, which acts as a **capability**: reads through it are not re-checked against the ACL (UNIX does not do complete mediation on every read). This is the classic revocation weakness of capabilities.

To stop it: terminate the processes holding the file open (`lsof` / `fuser` show them), or revoke at a different level (kill the user's sessions, lock the account, rotate encryption keys). Some systems (like NFSv4 with delegations recalled, or MAC systems that revalidate on access) can enforce revocation more directly, at a cost in performance.

</details>

### S9 · Port 80 without root (OS-11.2, OS-11.5)

On Linux, binding to ports below 1024 traditionally requires root. A web server needs port 80. Give three ways to run it without keeping full root privileges during normal operation.

<details><summary>Answer</summary>

(1) **Bind, then drop privileges:** start as root, create and bind the listening socket, then call `setgid`/`setgroups`/`setuid` to a dedicated unprivileged user (like `www-data`) before handling any request. The socket (a capability) keeps working. Nginx and Apache work this way.

(2) **Linux capabilities:** grant only `CAP_NET_BIND_SERVICE` to the binary (`setcap cap_net_bind_service=+ep /usr/sbin/server`) or the service (`AmbientCapabilities=` in systemd), so it never has root at all.

(3) **Let something else own the port:** systemd socket activation passes an already bound socket to the service; or a firewall rule redirects port 80 to an unprivileged port (such as 8080); or set `net.ipv4.ip_unprivileged_port_start`. Containers often map host port 80 to an unprivileged port inside.

</details>

### S10 · Escaping the chroot (OS-11.5)

A service runs as **root** inside a `chroot` jail. An attacker who compromises it breaks out to the real root file system. How is that possible, and what do containers use instead?

<details><summary>Answer</summary>

`chroot` only changes where **path resolution** starts; it was never designed as a security boundary against root. A root process can, for example, create a directory, `chroot` into it while keeping a descriptor to a directory outside (its current directory), and walk `..` from there up to the real root; or `mknod` a disk device and read it directly; or `mount` file systems; or `ptrace` processes outside the jail; or load a kernel module. chroot restricts nothing except the file-system view.

Containers combine **namespaces** (separate views of mounts with `pivot_root`, PIDs, network, users, IPC, host name), **user namespaces** (root inside maps to an unprivileged user outside), **dropped capabilities**, **seccomp** filters (blocking `mount`, `kexec`, module loading...), cgroups for resource limits, and often SELinux/AppArmor profiles (→ OS-12.2). Even then they share the host kernel; untrusted workloads may need VMs (→ OS-12 S4).

</details>

### S11 · The compiler that lies (OS-11.4)

Ken Thompson described a compiler that inserts a backdoor into the `login` program, and also inserts the backdoor-inserting code into any new compiler it compiles, after which the backdoor is removed from the compiler's source. Why can't a careful source-code audit find it? What partial defenses exist?

<details><summary>Answer</summary>

The backdoor lives only in the **compiled binary** of the compiler. The compiler's source and `login`'s source are both clean. Compiling the clean compiler source with the infected compiler binary produces a new infected compiler binary, and compiling `login` produces a backdoored `login`. Audit all the source you like: the tool you use to turn source into binaries is lying. The lesson: you can only trust code you (or someone you trust) built entirely, including the tools.

Partial defenses: **reproducible builds** (independent parties build the same source and compare binaries bit for bit), **diverse double-compiling** (David A. Wheeler's technique: compile the compiler with a different, independent compiler and compare results), bootstrapping compilers from minimal auditable seeds, code signing, and supply-chain security practices.

</details>

### S12 · Stolen laptop (OS-11.5)

A laptop with sensitive files is stolen. The files were readable only by their owner (`chmod 600`), and the user had a strong login password. Does that protect the data? What does, and what attack remains?

<details><summary>Answer</summary>

No. Permissions are enforced by the **running OS**. The thief can boot another OS from a USB stick (or remove the drive and attach it to another computer) and read every block directly; the file-system permission bits are just data to that OS. The login password protects only the running system.

**Full-disk encryption** (LUKS, BitLocker, FileVault) protects it: without the key (derived from a passphrase, or released by the **TPM** only if the boot chain is unmodified and the user authenticates), the disk is unreadable. Remaining risks: a laptop stolen while **running or asleep** has keys in RAM (cold-boot and DMA attacks, mitigated by IOMMU protection and shutting down or hibernating); an "evil maid" who tampers with the boot loader to capture the passphrase, which Secure Boot and TPM-measured boot are designed to prevent.

</details>
