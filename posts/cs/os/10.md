# Unit 10: I/O Systems

> **How to use this page.** Section IDs (`OS-10.4`) match the tags on practice questions. Arrows like **→ OS-12.1** point to where an idea is developed further; **← OS-1.3** points back to something this section depends on.

A computer is useless without I/O, and I/O devices are wildly diverse: keyboards producing a few bytes per second, NVMe drives moving gigabytes per second, network cards receiving millions of packets per second, GPUs, timers, sensors. Unit 1 introduced interrupts and DMA; Unit 9 looked at storage devices. This unit is about the whole I/O stack: how the CPU talks to device hardware, how the kernel organizes that into a uniform interface of drivers and system calls, and how programs can handle thousands of simultaneous I/O streams efficiently.

---

## OS-10.1 · I/O Hardware

### Buses, ports, and controllers

- A **port** is a connection point for a device (a USB port, a serial port).
- A **bus** is a set of wires plus a protocol shared by several devices. **PCI Express (PCIe)** is the main expansion bus in modern PCs: really a set of point-to-point **lanes** (a link has 1 to 16 lanes) through switches. Other buses and interfaces: USB, SATA, SAS, Thunderbolt, and on-chip interconnects.
- A **controller** is the electronics that operates a port, bus, or device. Simple ones (a serial-port controller) are a single chip; complex ones (a SATA host adapter, an NVMe SSD's controller, a network card) have their own processor, memory, and firmware.

OSTEP's **canonical device** has two parts:

```
 +----------------------------------------------------+
 |  Interface:   [ STATUS ] [ COMMAND ] [ DATA ]      |  <- what the OS sees
 +----------------------------------------------------+
 |  Internals:  micro-controller, memory (DRAM/SRAM), |  <- implementation-specific
 |              firmware, other chips                 |
 +----------------------------------------------------+
```

### Device registers

A controller typically exposes a few registers:

| Register | Direction | Purpose |
|---|---|---|
| **Status** | Read by host | Current state: busy, done, error, data available |
| **Control / command** | Written by host | Start a command, change mode |
| **Data-in** | Read by host | Data coming from the device |
| **Data-out** | Written by host | Data going to the device |

OSTEP's **canonical protocol** for talking to such a device:

```c
while (STATUS == BUSY)
    ;                       // 1. wait until the device is not busy (polling)
write data to DATA register;   // 2. give it the data (programmed I/O)
write command to COMMAND register;  // 3. start the operation
while (STATUS == BUSY)
    ;                       // 4. wait until the device finishes (polling)
```

It works, but wastes CPU time in both polling loops, and uses the CPU to move every data word (**programmed I/O**, PIO). Interrupts fix the first problem and DMA fixes the second (→ OS-10.2).

### How the CPU reaches device registers

**Port-mapped I/O (isolated I/O):** devices live in a separate **I/O address space**, accessed with special instructions. On x86 this space has 64K ports, used with `in` and `out` (e.g., the legacy keyboard controller at port 0x60, the classic IDE disk at 0x1F0 to 0x1F7).

**Memory-mapped I/O (MMIO):** device registers are assigned **physical memory addresses**. Ordinary load and store instructions read and write them; the memory system routes those addresses to the device instead of RAM. PCIe devices are assigned address ranges through their **BARs** (base address registers) at boot. A graphics card's frame buffer is also memory-mapped.

| | Port-mapped I/O | Memory-mapped I/O |
|---|---|---|
| Instructions | Special (`in`, `out`) | Ordinary loads and stores |
| Address space | Separate, small (64K ports on x86) | Part of the physical address space |
| Protection | `in`/`out` are privileged (or permitted per port via a bitmap) | Page tables control access; a device page can even be mapped into a user process |
| Usability from C | Needs inline assembly or helper functions | Plain pointers (declared `volatile`) |
| Caching | Never cached | The mapping must be marked **uncacheable** (← OS-6.4 PTE cache-disable bit) |
| Used by | Legacy x86 devices | Almost all modern devices, and all non-x86 architectures |

Two practical rules for memory-mapped registers (→ S1):

- Mark the pages **uncached**, or the CPU might read a stale cached copy of a status register, or delay a command write in its cache.
- In C, access them through **`volatile`** pointers so the compiler does not remove "redundant" reads of a register whose value changes on its own, or reorder or merge writes. (Here `volatile` is exactly the right tool, unlike for thread synchronization ← OS-4.3.) Kernels wrap this in functions like `readl()`/`writel()` that also insert the needed memory barriers.

### Clocks and timers

Hardware timers provide the current time, elapsed time, and interrupts after a set interval. The OS uses a **programmable interval timer** (on x86, the legacy PIT, the HPET, and each core's **local APIC timer**) to drive time-slice preemption (← OS-1.4, OS-3.3), timekeeping, and `sleep()`/timeouts.

Traditionally the kernel took a timer interrupt at a fixed rate (`HZ`, for example 100 to 1,000 per second) even when idle. Modern Linux is **tickless** (`NO_HZ`): an idle CPU programs the timer for the next actual event only, which saves a lot of power, and `NO_HZ_FULL` can even stop ticks on a busy CPU running a single task (for low-jitter workloads).

### The IOMMU

Devices performing DMA (→ OS-10.2) access memory directly, bypassing the CPU's MMU. An **IOMMU** (Intel VT-d, AMD-Vi) gives devices their own page tables: device-visible addresses are translated and checked, so a device (or a malicious one plugged into Thunderbolt) can only reach the memory the OS has mapped for it (→ S10). IOMMUs also let a device be handed directly to a virtual machine (→ OS-12.1) and let devices limited to 32-bit addresses reach memory above 4 GB.

## OS-10.2 · Polling, Interrupts, and DMA

### Polling

The CPU repeatedly reads the device's status register until it indicates the operation is done (busy-waiting).

- **Cheap per check** (a few instructions) and **lowest latency**: the CPU notices completion immediately.
- **Wasteful** if the device is slow: all the time spent polling could have run other processes.

Polling is the right choice when the device is **very fast** (the operation completes within about the time an interrupt would take to handle) or when the CPU has nothing else to do.

### Interrupt-driven I/O

The CPU issues a command and moves on (the process blocks and another runs ← OS-2.2). When the device finishes, it raises an **interrupt**; the CPU runs the device's interrupt handler (← OS-1.3), which completes the operation and wakes the waiting process.

```
 CPU:   [ Process 1 issues I/O ][ Process 2 runs ....... ][ ISR ][ Process 1 continues ]
 Disk:                          [ ======= busy ======== ]
                                                        ^ interrupt
```

Hardware details:

- Devices signal an **interrupt controller** (on x86, the I/O APIC and each CPU's local APIC), which delivers interrupts to CPUs with a **vector** number and **priority**.
- Modern PCIe devices use **message-signaled interrupts (MSI / MSI-X)**: the device writes a special value to a special address instead of asserting a wire. Each device can have many vectors (for example, one per queue per CPU), and the OS can steer each to a chosen CPU (**interrupt affinity**; see `/proc/interrupts`).
- Handlers must be short; heavy work is deferred to a **bottom half** (softirq, tasklet, workqueue) running with interrupts enabled (← OS-1.3).

**Interrupts are not always better.** OSTEP's points:

- For a **fast device**, the interrupt costs (saving state, running the handler, waking a process, context switching) can exceed the time saved; polling is faster.
- For a device that is **sometimes fast and sometimes slow**, a **hybrid** works: poll briefly, then fall back to sleeping on an interrupt (a two-phase approach, like two-phase locks ← OS-4.4).
- **Interrupt livelock:** when interrupts arrive faster than the system can process them (a flood of network packets), the CPU spends all its time in interrupt handlers and never runs the code that consumes the data: throughput collapses to zero. The fix is to switch to **polling under load**. Linux's network stack does this with **NAPI**: on the first packet interrupt, the driver disables further interrupts and polls the device in batches until its queue is empty, then re-enables interrupts (N2, S5).
- **Interrupt coalescing:** the device waits a short time (or for several events) before raising one interrupt for all of them. Fewer interrupts, but higher latency for each event.

### Direct memory access (DMA)

With programmed I/O, the CPU copies every word between device and memory. For large transfers, that is a waste of CPU time. A **DMA engine** (built into modern device controllers: **bus mastering**; or a separate DMA controller in older systems) copies the data between the device and main memory **by itself**.

**Steps of a DMA read** (for example, a disk read into a memory buffer):

1. The driver allocates a buffer and tells the controller: source (device location), destination (**physical** or IOMMU-translated address of the buffer), byte count, and direction. In modern devices, this is done by writing a **descriptor** into a ring in memory and writing the controller's "doorbell" register.
2. The CPU goes on with other work.
3. The controller transfers the data directly into memory, competing with the CPU for memory bandwidth (historically called **cycle stealing**, since the DMA engine takes memory-bus cycles the CPU might have used).
4. When the whole transfer is complete, the controller raises **one interrupt**.
5. The driver's handler marks the request complete and wakes the waiting process.

```
  CPU  --(1) program descriptor-->  Device controller
  CPU  runs other processes           |
                                      | (3) data moved directly
                                      v
                                   Main memory
  CPU  <--(4) one interrupt when done--
```

Details worth knowing:

- **Scatter-gather:** a descriptor can list several memory fragments, so a transfer can fill non-contiguous physical pages (a virtually contiguous buffer is usually scattered physically ← OS-6.4) without an extra copy.
- **Pinning:** the buffer's pages must stay in memory (not be evicted or moved) until the transfer completes (← OS-7.7 I/O interlock).
- **Cache coherence:** the device writes memory behind the CPU caches' back. On systems without hardware-coherent DMA, the driver must **invalidate** cache lines before reading DMA'd data and **flush** them before a device reads memory, or someone sees stale data (→ S6). Kernel DMA-mapping APIs handle this.
- **Bounce buffers:** a device that can address only part of memory (for example, 32-bit DMA) may need data copied through a buffer in the addressable region, unless an IOMMU remaps it.

### Summary: moving data

| Method | CPU work per transfer | Latency | Best for |
|---|---|---|---|
| Programmed I/O + polling | CPU polls and copies everything | Lowest (if polling is dedicated) | Very fast or very simple devices; boot code |
| Programmed I/O + interrupts | Interrupt per word/byte; CPU copies | Moderate | Slow character devices (keyboard, serial) |
| DMA + interrupts | Setup + one interrupt per block | Moderate | Disks, network, anything bulk |
| DMA + polling | Setup + checking completion queues | Lowest | Ultra-fast NVMe and network in high-performance systems (SPDK, DPDK, io_uring polled mode) |

## OS-10.3 · The Kernel I/O Subsystem

### A uniform interface over diverse devices

The kernel hides device differences behind a small number of **device classes**, each with a standard interface, so applications (and most of the kernel) need not know details of particular hardware:

| Class | Access | Interface | Examples |
|---|---|---|---|
| **Block** | Random access to fixed-size blocks | `read`/`write`/`seek` on blocks, through the block layer and page cache; also `mmap` | Disks, SSDs, USB storage |
| **Character** | Stream of bytes, often sequential | `read`/`write` of bytes (`get`/`put`), with `ioctl` for extras | Keyboards, mice, serial ports, terminals, `/dev/null`, `/dev/random` |
| **Network** | Packets | **Sockets** (`socket`, `send`, `recv`, `select`/`epoll`) rather than files | Ethernet, Wi-Fi |
| **Clocks and timers** | Time | Get time, set alarms, interval timers | HPET, APIC timer |

Other ways devices differ: synchronous vs asynchronous, sharable vs dedicated (a tape drive, a printer), speed, read-only vs read-write.

The **`ioctl()`** system call is the escape hatch for everything that does not fit: it passes a device-specific command number and argument to the driver (eject a CD, set a terminal's baud rate, query a disk's geometry, configure a network interface).

### I/O scheduling

Reorder pending requests to improve overall performance and fairness: the disk schedulers of ← OS-9.2 are the main example. The kernel keeps a **wait queue** of requests per device, and may give priority to some requests (reads over writes, since a process usually waits for reads; interactive over background).

### Buffering

A **buffer** is memory holding data being transferred between two devices, or between a device and an application. Three reasons to buffer:

1. **Speed mismatch** between producer and consumer. A slow modem fills a buffer while the disk writes a previous one. **Double buffering:** while the device fills buffer 1, the consumer processes buffer 2; then they swap. This decouples the two sides so both work in parallel (N3).
2. **Transfer-size mismatch.** A network message is split into many small packets on the sender and reassembled from them in a buffer on the receiver.
3. **Copy semantics.** When a process calls `write(fd, buf, n)`, the data written must be the data in `buf` **at the time of the call**, even if the process modifies `buf` immediately after `write` returns. The kernel copies the data into a kernel buffer before returning. (Copy-on-write tricks can avoid the copy in some systems.)

A **circular buffer** (ring) generalizes double buffering to many slots: the producer–consumer bounded buffer from ← OS-4.7. Device descriptor rings, pipes, and terminal input queues are all circular buffers.

### Caching

A **cache** holds a **copy** of data for faster access; a buffer may hold the **only** copy of data in transit. The two are often combined: Linux's **page cache** holds file data read from disk (so later reads need no I/O ← OS-7.2) and also buffers writes, which are flushed later (**write-back** caching, ← OS-8.1). Caching I/O is extremely effective because of locality (N6).

### Spooling and device reservation

A **spool** is a buffer that holds output for a device that can serve only **one job at a time** and cannot interleave data streams, like a printer. Each application's output is spooled to a separate disk file; a **daemon** process sends the files to the printer one at a time (→ S9). The OS provides commands to view and cancel queued jobs. (Spooling is also the classic way to break the mutual-exclusion condition for printers ← OS-5.3.)

Some devices must be **reserved** for exclusive use (a tape drive during a backup): the OS provides open-for-exclusive-use or explicit allocate/release calls, with the risk of deadlock that entails (← OS-5).

### Error handling

Devices fail transiently (a network packet lost, a disk read that succeeds on retry) or permanently. The kernel **retries** transient errors, then reports failures to the process, on UNIX as a **−1 return value and `errno`** (`EIO`, `ENOSPC`, `ETIMEDOUT`...). Detailed device error information is available (for example, SCSI sense data), and hardware errors are logged by the kernel (`dmesg`).

### I/O protection

User processes must not perform I/O directly (← OS-1.4): **all I/O instructions are privileged**, device memory is not mapped into user address spaces, and every request goes through a system call where the kernel checks permissions and validates buffers (← OS-1.5). Exceptions are deliberate and controlled: a graphics driver may map part of a GPU's memory into a process for speed; user-space drivers get access to one specific device through the IOMMU (→ OS-10.5).

### Kernel data structures

The kernel tracks the state of all I/O: the open-file tables (← OS-8.1), network connection state, device queues, buffer and cache structures. UNIX makes this object-oriented: each kind of open "file" (regular file, pipe, socket, device) has a table of operations (← VFS, OS-8.3), so `read()` dispatches to the right code.

### Power management

The I/O subsystem also manages device power: spinning down idle disks, putting network and USB devices into low-power states, and runtime power management that suspends idle devices and wakes them on demand. On phones this is essential: Android aggressively powers down components not in use.

### Life cycle of a blocking read

A process calls `read()` on a file whose data is not in the page cache:

```
 1. Process issues read() -> system call trap into the kernel.
 2. Kernel checks parameters. Is the data already in the page cache?
        yes -> copy it to the user buffer, return. (Done: a few µs.)
 3. No: the file system maps the file offset to a disk block; the block layer
    queues a request (merging/scheduling), and the process is BLOCKED on a wait queue.
 4. The device driver takes the request, sets up DMA, and writes the controller's registers.
 5. The controller operates the device; DMA moves the data into a page-cache page.
 6. The controller raises an interrupt when done.
 7. The interrupt handler (and bottom half) marks the request complete and
    wakes the blocked process (Blocked -> Ready).
 8. When the scheduler runs the process, the kernel copies the data from the
    page cache to the user buffer and returns from read().
```

Every layer adds a few microseconds. For hard disks, this overhead is invisible next to milliseconds of device time; for fast SSDs it becomes a significant fraction, which is why kernels keep trimming this path (polled I/O, io_uring, N8).

## OS-10.4 · Blocking, Non-Blocking, and Asynchronous I/O

### Three styles of application interface

- **Blocking (synchronous):** the process is suspended until the I/O completes. `read()` returns only when data is available. This is the default, and the easiest to program: the code reads top to bottom.
- **Non-blocking:** the call returns immediately with whatever is available, possibly nothing. A socket or pipe opened with `O_NONBLOCK` returns −1 with `errno = EAGAIN` (or `EWOULDBLOCK`) if no data is ready. The program must try again later.
- **Asynchronous:** the call **starts** the I/O and returns immediately; the entire transfer happens in the background, and the process is **notified on completion** (a signal, a callback, or an entry in a completion queue). POSIX AIO (`aio_read`), Linux **io_uring**, and Windows I/O completion ports.

The distinction between non-blocking and asynchronous: a non-blocking `read` returns only what is **already** available (the process still does the transfer itself when data is ready); an asynchronous `read` returns immediately and the **whole** operation completes later.

| | Blocking | Non-blocking | Asynchronous |
|---|---|---|---|
| Call returns | When done | Immediately (partial or `EAGAIN`) | Immediately (operation in progress) |
| Who waits | The calling thread sleeps | Nobody; the program retries or multiplexes | Nobody; completion is reported later |
| Program structure | Simple, one thread per concurrent task | Event loop with readiness notification | Event loop with completion notification |

**Important Linux detail:** `O_NONBLOCK` has **no effect on regular files**. A `read()` of a file whose data is not in the page cache always blocks while the disk works (→ S4). Non-blocking readiness APIs are for pipes, sockets, and terminals. Truly asynchronous file I/O needs io_uring (or a thread pool, which is what libraries like libuv, used by Node.js, do for files).

### The problem: many connections

A server handling 10,000 clients with **one thread per connection** (blocking I/O) needs 10,000 threads: memory for their stacks, kernel structures, and constant context switching (N7). This was the famous **C10K problem** of the late 1990s. The alternative: a small number of threads, each handling many connections with **non-blocking I/O plus I/O multiplexing**, asking the kernel "which of these descriptors are ready?"

### select()

```c
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(sock1, &readfds);
FD_SET(sock2, &readfds);
int n = select(maxfd + 1, &readfds, NULL, NULL, &timeout);  // blocks until something is ready
if (FD_ISSET(sock1, &readfds)) { /* sock1 readable */ }
```

- Takes **bitmaps** (`fd_set`) of descriptors to watch for reading, writing, and exceptions, plus a timeout; on return, the bitmaps are **overwritten** with only the ready descriptors.
- Limited to descriptors below **FD_SETSIZE (1,024)** on Linux.
- Every call: the program rebuilds the sets, the kernel **copies** them in, **scans every** watched descriptor, and copies them back out. The program then scans the whole set again. **O(n)** per call in the number of descriptors watched, not the number ready.

### poll()

```c
struct pollfd fds[2] = {
    { .fd = sock1, .events = POLLIN },
    { .fd = sock2, .events = POLLIN },
};
int n = poll(fds, 2, 1000);          // timeout in ms
if (fds[0].revents & POLLIN) { /* sock1 readable */ }
```

- Takes an **array** of `pollfd` structures: no 1,024 limit, and input (`events`) is kept separate from output (`revents`), so the array need not be rebuilt.
- Still **O(n)** per call: the whole array is copied into the kernel and scanned every time.

### epoll (Linux)

```c
int ep = epoll_create1(0);

struct epoll_event ev = { .events = EPOLLIN, .data.fd = listen_sock };
epoll_ctl(ep, EPOLL_CTL_ADD, listen_sock, &ev);       // register ONCE

struct epoll_event ready[64];
for (;;) {
    int n = epoll_wait(ep, ready, 64, -1);            // returns only READY descriptors
    for (int i = 0; i < n; i++) {
        int fd = ready[i].data.fd;
        if (fd == listen_sock) {
            int c = accept(listen_sock, NULL, NULL);
            fcntl(c, F_SETFL, O_NONBLOCK);
            struct epoll_event cev = { .events = EPOLLIN, .data.fd = c };
            epoll_ctl(ep, EPOLL_CTL_ADD, c, &cev);
        } else {
            handle_client(fd);                        // read until EAGAIN, respond
        }
    }
}
```

- The **interest list** lives in the kernel: descriptors are registered once with `epoll_ctl`, not passed on every call.
- The kernel maintains a **ready list**: when a socket receives data, its callback adds it to the list. `epoll_wait` just returns the ready entries: cost **proportional to the number of ready descriptors**, not the number watched (N4).
- **Level-triggered** (default): `epoll_wait` keeps reporting a descriptor as long as it is readable (like `poll`).
- **Edge-triggered** (`EPOLLET`): reports only when the state **changes** (new data arrives). More efficient, but the program **must** read until `EAGAIN` each time, or leftover data will never be reported again (→ S3).
- Used by nginx, Redis, Node.js (libuv), Java NIO, Go's runtime network poller, and most high-performance Linux servers. BSD and macOS have the similar **kqueue**; Windows uses **I/O completion ports** (an asynchronous, completion-based model).

| | `select` | `poll` | `epoll` |
|---|---|---|---|
| Descriptor limit | 1,024 (FD_SETSIZE) | None | None |
| Registration | Every call | Every call | Once (`epoll_ctl`) |
| Cost per call | O(watched) | O(watched) | O(ready) |
| Kernel copy per call | All sets | Whole array | Only ready events |
| Portability | Everywhere (POSIX) | POSIX | Linux only |

### io_uring (Linux 5.1+, 2019)

epoll tells you **when** a socket is ready; you still make a system call for each `read`/`write`, and it does not help with regular files. **io_uring** is a general **asynchronous** interface built on two ring buffers **shared between the process and the kernel** (mapped into both address spaces with `mmap`):

```
 user space                         kernel
 +-----------------------+
 | Submission Queue (SQ) | ---->  kernel takes SQEs, performs the I/O
 |  [SQE][SQE][SQE] ...  |        (files, sockets, timers, opens, ...)
 +-----------------------+
 | Completion Queue (CQ) | <----  kernel posts CQEs with results
 |  [CQE][CQE] ...       |
 +-----------------------+
```

1. The program writes **submission queue entries** (SQEs: "read 4 KB from fd 7 at offset X into buffer B") into the SQ ring.
2. One `io_uring_enter()` system call submits **many** SQEs at once (batching), and can also wait for completions.
3. The kernel performs the operations asynchronously and places **completion queue entries** (CQEs, with result codes) into the CQ ring, which the program reads **without a system call**.
4. In **SQPOLL** mode, a kernel thread polls the SQ, so submitting I/O needs no system calls at all (at the cost of a core spinning).

It works uniformly for files (buffered and direct), sockets, and many other operations, and reduces system calls dramatically (N5). Because of its size and complexity, it has also been a notable source of kernel security bugs, and some environments (for example, many container platforms and Android) restrict or disable it.

### Reducing copies and calls

- **Vectored I/O:** `readv()`/`writev()` read into or write from several buffers in one system call (a header and a body, without assembling them).
- **Zero-copy:** `sendfile(out_sock, in_file, ...)` sends a file to a socket directly from the page cache, without copying data into user space and back. `splice()` moves data between a pipe and another descriptor inside the kernel. `mmap` avoids the read copy (← OS-7.2). Web servers serving static files use `sendfile`.
- **Direct I/O:** `O_DIRECT` makes transfers go straight between the device (DMA) and the user buffer, bypassing the page cache. Buffers and offsets must be aligned to the device's block size. Databases use it because they manage their own caches (→ S12).

## OS-10.5 · Device Drivers

### What a driver does

A **device driver** is kernel code that knows how to operate one kind of controller. It translates the kernel's generic requests ("read these 8 blocks," "send this packet") into the device's specific register accesses, command formats, and DMA descriptors, and it handles the device's interrupts.

```
   application:   read(fd, buf, n)
 --------------------------------------------------------- system call boundary
   VFS / file system  |  socket layer  |  tty layer
   block layer (queues, scheduling, merging)
   device driver  <-- device-specific code: registers, DMA rings, interrupts
 --------------------------------------------------------- hardware
   device controller -> device
```

Linux drivers are usually **loadable kernel modules** (← OS-1.6), loaded automatically when hardware is detected (by `udev`, based on the device's vendor and product IDs).

### Driver interfaces by device class

- **Block drivers** register with the block layer: they receive request queues of block reads and writes, which have already been merged and scheduled. They benefit from the page cache and are accessed through file systems or directly (`/dev/sda`, `/dev/nvme0n1`).
- **Character drivers** implement a `struct file_operations`, the same VFS operations table used by files (← OS-8.3):

```c
static const struct file_operations mydev_fops = {
    .owner          = THIS_MODULE,
    .open           = mydev_open,
    .release        = mydev_release,
    .read           = mydev_read,      // copy_to_user() from the device's buffer
    .write          = mydev_write,     // copy_from_user() then program the device
    .unlocked_ioctl = mydev_ioctl,     // device-specific commands
};
```

  When a program calls `read()` on `/dev/mydev`, the VFS calls `mydev_read`.
- **Network drivers** register a `net_device` with the networking stack. They do not appear in `/dev`; applications reach them through sockets.

### Device files, major and minor numbers

On UNIX, devices appear as **special files** in `/dev`. Each has a type (block `b` or character `c`) and a pair of numbers:

- **Major number:** which driver handles it.
- **Minor number:** which specific device (or partition) that driver manages.

```
$ ls -l /dev/sda /dev/sda1 /dev/null
brw-rw---- 1 root disk 8, 0  ... /dev/sda      (block, major 8, minor 0)
brw-rw---- 1 root disk 8, 1  ... /dev/sda1     (first partition)
crw-rw-rw- 1 root root 1, 3  ... /dev/null     (character, major 1, minor 3)
```

Opening a device file looks up the driver by major number, so the familiar `open`/`read`/`write`/`close` work on devices: the "everything is a file" design (← OS-1.5). `/dev` is populated dynamically by the kernel (devtmpfs) and `udev`.

### Top halves and bottom halves

As in ← OS-1.3: the interrupt handler (**top half**) does the minimum (acknowledge the device, grab status, maybe move a descriptor) with interrupts possibly disabled; the rest (processing received packets, completing requests, waking processes) runs in a **bottom half** (softirq, tasklet, threaded IRQ handler, or workqueue) where it can be preempted. Network drivers combine this with NAPI polling.

### Drivers and reliability

Drivers make up the **majority** of an OS kernel's code (roughly 70% of the Linux source tree) and are its biggest source of bugs. Studies found far higher error rates in driver code than in the rest of the kernel (Chou et al., 2001, cited in OSTEP, found drivers had up to several times more bugs than other kernel code), and driver failures were the leading cause of Windows crashes, which pushed Microsoft toward stricter driver verification and user-mode frameworks. Because a Linux driver runs in kernel mode, a bug in it can crash or compromise the entire system (← OS-1 S8).

Approaches to limit the damage:

- **User-space drivers:** run the driver as an ordinary process that talks to the device through a narrow kernel interface. Examples: **FUSE** (file systems in user space: a bug kills the FUSE process, not the kernel), **UIO** and **VFIO** (give a process safe, IOMMU-protected access to one device; used by DPDK for networking and SPDK for NVMe, which also **poll** instead of using interrupts for maximum speed), Windows' **UMDF**, and microkernels, where all drivers are user processes (← OS-1.6).
- Static analysis and verification of drivers, and stable, well-tested driver frameworks.
- In virtual machines, **virtio**: a standard, simple paravirtual device interface, so guests need only one well-tested driver per device type (→ OS-12.1).

### The xv6 IDE driver (IIT Bombay course)

xv6's disk driver (`ide.c`) shows the whole picture in about 150 lines, and Mythili Vutukuru's lectures use it:

- It uses **port-mapped I/O** (`inb`/`outb`/`insl`/`outsl` on ports 0x1F0 to 0x1F7) and **programmed I/O** for the data (no DMA).
- `iderw(b)` adds a buffer to a queue of pending requests (`idequeue`). If it is the only request, it starts it immediately (`idestart` writes the sector number and command into the registers). Then the calling process **sleeps** on the buffer (← OS-4.5 `sleep`/`wakeup`), holding no locks except those `sleep` handles.
- When the disk finishes, it raises an interrupt: `ideintr()` takes the first request off the queue, reads the data from the data port if it was a read, marks the buffer valid, **wakes** the sleeping process, and starts the next queued request.
- `idewait()` polls the status register for the "ready" bit: xv6 polls for short waits and uses interrupts for the long wait of the actual disk operation.

This is the canonical protocol from OS-10.1, a request queue, and the interrupt-driven sleep/wakeup pattern, all in one place.

## Quick Revision Sheet

- Port, bus (PCIe lanes, USB, SATA), controller. Device registers: status, command, data-in, data-out.
- Canonical protocol: poll until not busy, write data, write command, poll until done.
- Port-mapped I/O: separate address space, `in`/`out`, privileged. Memory-mapped I/O: registers at physical addresses, ordinary loads/stores, must be uncached and accessed via `volatile`.
- Timers drive preemption and timekeeping; tickless kernels save power.
- IOMMU: page tables for devices; protects memory from DMA; enables device passthrough.
- Polling: low latency, wastes CPU on slow devices. Interrupts: CPU free, overhead per event. Hybrid: poll briefly then sleep.
- Interrupt livelock under floods; NAPI switches to polling; interrupt coalescing trades latency for fewer interrupts.
- MSI/MSI-X: interrupts as memory writes, many vectors, per-CPU steering.
- DMA: driver programs descriptor, device moves data, one interrupt at the end. Scatter-gather, pinned pages, cache coherence, bounce buffers.
- Device classes: block, character, network (sockets), clocks. `ioctl` for device-specific commands.
- Buffering: speed mismatch (double buffering), size mismatch, copy semantics. Cache = copy; buffer may be the only copy.
- Spooling for printers; device reservation; errors reported via `errno`; all I/O privileged.
- Blocking read path: syscall → cache hit? → block layer → driver → DMA → interrupt → wake → copy → return.
- Blocking vs non-blocking (`EAGAIN`) vs asynchronous (completion notification). `O_NONBLOCK` does nothing for regular files.
- `select` (bitmaps, 1,024 limit, O(n)), `poll` (array, O(n)), `epoll` (register once, O(ready), level- or edge-triggered). kqueue on BSD, IOCP on Windows.
- Edge-triggered epoll: read until `EAGAIN`.
- io_uring: shared submission and completion rings, batching, SQPOLL; works for files and sockets.
- `readv`/`writev`, `sendfile`/`splice` (zero copy), `O_DIRECT` (bypass page cache; alignment).
- Drivers: block, character (`file_operations`), network (`net_device`). Major number = driver, minor = device.
- Drivers are most of the kernel and most of its bugs; user-space drivers (FUSE, VFIO) isolate faults.
- xv6 IDE driver: port I/O, request queue, sleep in `iderw`, wakeup in `ideintr`.

## Worked Numerical Problems

### N1 · Polling vs interrupts vs DMA (OS-10.2)

**Question.** A 1 GHz CPU. A poll (checking status and transferring data if ready) costs 400 cycles. (a) A mouse is polled 30 times per second. What fraction of CPU time is used? (b) A disk transfers data in 16-byte units at 4 MB/s and must be polled at least once per unit while transferring. CPU fraction? (c) The same disk with interrupts, where each interrupt (including handling and transfer of the 16 bytes) costs 500 cycles? (d) The same disk with DMA transferring 8 KB blocks, where setting up each DMA costs 1,000 cycles and the completion interrupt costs 500 cycles?

**Answer.**

(a) 30 × 400 = 12,000 cycles/s out of 10⁹: **0.0012%**. Polling a slow device occasionally is harmless.

(b) 4 MB/s ÷ 16 B = 250,000 polls/s (taking 4 MB as 4 × 10⁶ B). 250,000 × 400 = 10⁸ cycles/s: **10%** of the CPU while the disk is active.

(c) 250,000 interrupts/s × 500 = 1.25 × 10⁸ cycles/s: **12.5%**, even worse than polling while transferring (interrupts help only when the device is often idle).

(d) Blocks per second = 4 MB ÷ 8 KB ≈ 500 (512 with binary units). Each costs 1,000 + 500 = 1,500 cycles: about 750,000 to 768,000 cycles/s ≈ **0.08%**. DMA reduces overhead by more than 100×, because the per-event cost is paid once per 8 KB instead of once per 16 bytes.

### N2 · Interrupt livelock and NAPI (OS-10.2)

**Question.** A 10 Gb/s network card receives a stream of 1,500-byte packets at full line rate. Protocol processing costs 0.3 µs per packet. (a) How many packets arrive per second? (b) With one interrupt per packet, and 1.2 µs of interrupt overhead per interrupt, what fraction of one core is needed? (c) With NAPI-style polling that processes packets in batches of 64 (one interrupt or poll event per batch, same 1.2 µs overhead), what fraction? (d) What latency does batching add at this packet rate?

**Answer.**

(a) 10 × 10⁹ bits/s ÷ (1,500 × 8 bits) ≈ **833,333 packets/s**.

(b) 833,333 × (1.2 + 0.3) µs = 1.25 s of CPU per second: **125%** of a core. The core cannot keep up; it spends all its time in interrupt handling, packets are dropped, and useful throughput collapses: **receive livelock**.

(c) Batches: 833,333 ÷ 64 ≈ 13,021 per second × 1.2 µs ≈ 0.016 s. Processing: 833,333 × 0.3 µs = 0.25 s. Total ≈ **27%** of a core.

(d) Filling a batch of 64 packets takes 64 ÷ 833,333 s ≈ **77 µs**. At line rate that is fine (packets arrive continuously); at low rates, waiting for a full batch would be terrible, so NAPI and adaptive coalescing use interrupts when traffic is light and switch to polling only under load.

### N3 · Buffering and double buffering (OS-10.3)

**Question.** A device delivers data one block at a time; producing a block takes T = 10 ms. The application processes each block in C = 6 ms, and copying a block from the kernel buffer to the application takes M = 0.5 ms. For 100 blocks, estimate the total time with: (a) no buffering (the device reads directly into the user buffer, and the application must wait for each read); (b) single buffering in the kernel; (c) double buffering. (d) Repeat (b) and (c) if processing takes C = 12 ms.

**Answer.** (Following the standard model: with a single buffer, the device can read the next block while the application processes the current one, but the copy M cannot overlap with the device filling the same buffer.)

(a) Each block: read (10) then process (6) = 16 ms → **1.6 s**.

(b) Single buffer: time per block ≈ max(C, T) + M = max(6, 10) + 0.5 = 10.5 ms → **1.05 s**.

(c) Double buffer: the device fills one buffer while the application copies from the other and processes: time per block ≈ max(C + M, T) = max(6.5, 10) = 10 ms → **1.0 s**. The device is never idle; it is now the bottleneck.

(d) C = 12: single buffer = max(12, 10) + 0.5 = 12.5 ms → 1.25 s; double buffer = max(12.5, 10) = 12.5 ms → 1.25 s. When the **consumer** is the bottleneck, more buffering cannot help; the device simply waits. Buffering overlaps work, it does not create speed.

### N4 · select/poll vs epoll (OS-10.4)

**Question.** A server watches 10,000 connections; on each iteration of its event loop, about 20 are ready. The loop runs 5,000 times per second. With `poll`, the kernel spends about 50 ns per watched descriptor checking readiness, plus copying 8 bytes per descriptor into and out of the kernel at about 0.1 ns per byte. With `epoll`, each ready event costs about 100 ns. (a) Can `select` be used at all? (b) CPU per second spent inside `poll`? (c) Inside `epoll_wait`?

**Answer.**

(a) Not directly: `select` supports descriptors only below **1,024** (FD_SETSIZE) on Linux.

(b) Per call: scanning 10,000 × 50 ns = 500 µs; copying 10,000 × 8 B × 2 directions × 0.1 ns ≈ 16 µs. About 516 µs per call × 5,000 calls = **2.58 s per second**: impossible on one core. The loop could run only about 1,900 times per second at best, and all that time is spent checking the 9,980 idle connections.

(c) 20 ready × 100 ns = 2 µs per call × 5,000 = **10 ms per second (1%)**. The cost depends on activity, not on the number of connections, which is why epoll solved C10K.

### N5 · System-call batching with io_uring (OS-10.4)

**Question.** A program performs 1,000,000 random 4 KB reads from an NVMe SSD. A system call's fixed overhead (entry, exit, mitigations) is 1 µs. (a) CPU time spent on system-call overhead using one `pread` per read? (b) Using io_uring, submitting 32 reads per `io_uring_enter` call (each call costs 1.5 µs of fixed overhead) and reaping completions from the shared ring without extra calls? (c) With SQPOLL?

**Answer.**

(a) 1,000,000 × 1 µs = **1 s** of pure system-call overhead (plus, with blocking `pread`, the program needs many threads to keep the SSD busy, adding context switches).

(b) 1,000,000 ÷ 32 = 31,250 calls × 1.5 µs ≈ **47 ms**: about 21 times less. The program also keeps 32 or more reads in flight from a single thread, which is what an SSD needs for full throughput (← OS-9.3).

(c) Submission needs **no system calls**: a kernel thread polls the submission ring. The cost is a CPU core busy-polling while I/O is active (it sleeps after an idle timeout). It is worth it only when I/O rates are very high and a core can be dedicated.

### N6 · The value of the page cache (OS-10.3)

**Question.** Reading a 4 KB block costs 5 µs when it is in the page cache (system call plus copy) and an extra 8 ms when it must come from a hard disk. (a) Average read time at hit ratios of 90%, 99%, and 99.9%? (b) Repeat for 90% with an NVMe SSD (extra 80 µs on a miss).

**Answer.** Average = h × 5 µs + (1 − h) × (5 µs + miss penalty) = 5 µs + (1 − h) × penalty.

(a) HDD:
- 90%: 5 + 0.1 × 8,000 = **805 µs**
- 99%: 5 + 0.01 × 8,000 = **85 µs**
- 99.9%: 5 + 0.001 × 8,000 = **13 µs**

(b) NVMe at 90%: 5 + 0.1 × 80 = **13 µs**.

With a disk, each extra "9" in the hit ratio gives nearly a 10× improvement: the page cache is often more important than the disk itself. (The same EAT pattern as TLBs and page faults ← OS-6.5, OS-7.1.)

### N7 · Thread-per-connection vs event loop (OS-10.4)

**Question.** A server must handle 10,000 mostly idle connections that together generate 100,000 events per second. (a) Thread-per-connection: each thread uses about 64 KB of touched user stack plus a 16 KB kernel stack, and each event causes a context switch costing about 3 µs (including cache effects). Estimate memory and CPU overhead. (b) An epoll event loop on one thread: per-connection state of 4 KB, and dispatching each event costs 0.5 µs. Estimate memory and CPU overhead.

**Answer.**

(a) Memory: 10,000 × (64 + 16) KB = **800 MB** (and virtual address space of 8 MB per thread reserved by default, 80 GB in total, which is fine on 64-bit but not on 32-bit). CPU: 100,000 switches × 3 µs = **0.3 s per second (30% of a core)**, just for switching, before any real work. Scheduler run queues and lock contention grow with the thread count too.

(b) Memory: 10,000 × 4 KB = **40 MB**. CPU: 100,000 × 0.5 µs = **5%** of a core.

Event loops use about 20 times less memory and much less CPU overhead, at the cost of more complex code (state machines or callbacks instead of straight-line code). Modern languages hide this: Go's goroutines and async/await in Rust, C#, JavaScript, and Python let code look sequential while an event loop and epoll/io_uring run underneath.

### N8 · Where the time goes in one read (OS-10.3)

**Question.** A 4 KB read that misses the page cache passes through these software steps: system call entry/exit 0.5 µs, VFS and file system 2 µs, block layer 1.5 µs, driver submission 1 µs, interrupt handling 2 µs, waking the process and context switching 4 µs. What fraction of total time is software overhead if the device takes (a) 8 ms (HDD), (b) 80 µs (NVMe SSD), (c) 10 µs (a very low-latency SSD)? (d) With polled completion instead of interrupts (removing the interrupt, wakeup, and switch costs, but spinning during the device time), what changes for (c)?

**Answer.** Software total = 0.5 + 2 + 1.5 + 1 + 2 + 4 = **11 µs**.

(a) 11 / (8,000 + 11) ≈ **0.14%**: irrelevant.

(b) 11 / (80 + 11) ≈ **12%**.

(c) 11 / (10 + 11) ≈ **52%**: the OS is now slower than the device.

(d) Software drops to 0.5 + 2 + 1.5 + 1 = 5 µs; total 15 µs instead of 21 µs (about 29% lower latency), but the CPU is busy the whole time. This is why Linux added polled I/O for NVMe (`io_poll`, hybrid polling) and why io_uring and user-space drivers (SPDK) exist: as devices got 1,000× faster, the kernel's I/O path became the bottleneck.

## Scenario Questions (Test Your Understanding)

### S1 · The status register that never changes (OS-10.1)

A student writes a bare-metal driver:

```c
uint32_t *status = (uint32_t *)0xFE001000;   // memory-mapped status register
while ((*status & READY) == 0)
    ;                                        // wait for the device
```

With `-O0` it works. With `-O2` it spins forever, although the device sets READY. On another board, even the `-O0` version sometimes reads stale values. Explain both.

<details><summary>Answer</summary>

With optimization, the compiler assumes ordinary memory does not change by itself: nothing in the loop writes `*status`, so it loads the value once and loops forever on the register copy. The pointer must be declared **`volatile uint32_t *`**, which forces a real load on every iteration. (Kernel code uses `readl()`, which is volatile and includes barriers.)

The stale reads on the other board: the register's physical page is mapped **cacheable**, so the CPU keeps reading a cached copy instead of the device. Device register pages must be mapped **uncached** (for example, with `ioremap()` in Linux, which sets the cache-disable attributes ← OS-6.4).

</details>

### S2 · The chat server that fell over at 10,000 users (OS-10.4)

A chat server creates one thread per connected client, each blocking in `recv()`. It works for 1,000 users. At 10,000 users, memory use explodes, latency spikes, and `pthread_create` occasionally fails. Redesign it.

<details><summary>Answer</summary>

Each thread costs stack memory and kernel structures, and each message wakes a thread, causing a context switch; at 10,000 threads the switching and scheduler overhead dominate (N7), and per-user thread or memory limits (`ulimit -u`, address space) cause `pthread_create` to fail. This is the **C10K** problem.

Redesign as an **event-driven** server: set sockets non-blocking, register them with **epoll** (edge- or level-triggered), and run one event loop per CPU core (for example, with `SO_REUSEPORT` to spread incoming connections). Each loop reads available data, updates per-connection state, and writes responses. Slow work (disk, heavy computation) goes to a small worker thread pool. Frameworks such as nginx, Node.js, Netty, and Go's runtime do this internally.

</details>

### S3 · Edge-triggered and stuck (OS-10.4)

A server switched from level-triggered to **edge-triggered** epoll for performance. Now some clients occasionally hang: the server stops responding to them even though they have sent a request. The handler reads at most 4 KB per event. What is wrong?

<details><summary>Answer</summary>

Edge-triggered epoll reports a descriptor only when its state **changes** (new data arrives). If a client sends 6 KB, the server gets one event, reads 4 KB, and returns to `epoll_wait`. The remaining 2 KB is still in the socket buffer, but no new data arrives, so there is no new edge and no new event: the server never reads it, and the client waits forever.

Rule for edge-triggered mode: on each event, keep reading (and accepting, and writing) in a loop **until the call returns `EAGAIN`**, with the socket in non-blocking mode. Alternatively, use level-triggered mode, which keeps reporting the descriptor while data remains.

</details>

### S4 · Non-blocking, yet it blocks (OS-10.4)

A single-threaded event loop opens a large log file with `O_NONBLOCK` and reads it in chunks between handling network events, expecting reads never to stall. Under load, the whole server freezes for tens of milliseconds at a time. Why, and what are the correct approaches?

<details><summary>Answer</summary>

On Linux, `O_NONBLOCK` has **no effect on regular files**: a file is always considered "ready." If the requested data is not in the page cache, `read()` blocks while the disk fetches it (milliseconds on a hard disk), and since the event loop is single-threaded, every connection stalls. epoll also reports regular files as always ready.

Correct approaches: perform file I/O in a **thread pool** (what libuv/Node.js does), use **io_uring** for genuinely asynchronous file reads, or use `posix_fadvise(POSIX_FADV_WILLNEED)` / readahead to bring data into the cache ahead of time. `sendfile` does not fix it either, since it can also block on a cache miss.

</details>

### S5 · Under attack, the server stops answering (OS-10.2)

During a packet flood (millions of tiny packets per second), a server's CPU shows 100% time in interrupt and softirq context, and its applications receive almost nothing. Adding more flood traffic makes *useful* throughput drop further. Explain, and describe the kernel mechanisms that prevent it.

<details><summary>Answer</summary>

**Receive livelock.** Each packet triggers interrupt and protocol work at high priority. When packets arrive faster than they can be fully processed, the CPU spends all its time in the early stages (interrupts, softirq) and never gets to run the applications that consume the data; packets are dropped at the last stage after the most work has been done on them.

Prevention: **NAPI** (disable the device's interrupts on the first packet and poll it in bounded batches, re-enabling interrupts only when the queue is empty), a **budget** limiting how much softirq work runs before yielding to other tasks (Linux defers excess work to the `ksoftirqd` thread, which is scheduled like any other thread), interrupt coalescing, multi-queue NICs spreading load across cores (RSS), and dropping excess packets early in hardware or with XDP/eBPF filters before any expensive processing.

</details>

### S6 · Stale data after DMA (OS-10.2)

On an embedded ARM board without hardware cache coherence for DMA, a driver reads a network packet from its receive buffer right after the device's "DMA complete" interrupt, but sometimes sees old bytes from the previous packet. What is going on, and how should the driver be written?

<details><summary>Answer</summary>

The device wrote the new packet directly to **memory**, but the CPU's **data cache** still holds lines from the buffer's previous contents (from when the CPU last read it). The CPU reads the cached, stale lines instead of the new data in memory.

The driver must use the kernel's **DMA mapping API**: before handing the buffer to the device, and after the device finishes, the API **invalidates** the buffer's cache lines (for device-to-memory transfers) or **flushes** dirty lines to memory (for memory-to-device transfers). Alternatively, allocate the buffer as **coherent** (uncached) DMA memory. On x86, hardware keeps DMA coherent with caches, which is why such bugs often appear only when porting to other architectures.

</details>

### S7 · Two drivers, two crashes (OS-10.5)

On the same Linux machine, a bug in an experimental USB Wi-Fi driver (a kernel module) freezes the entire system, while a bug in a FUSE file system for a cloud drive only makes that one mount return errors. Explain the difference and the trade-off.

<details><summary>Answer</summary>

The Wi-Fi driver runs in **kernel mode**, in the kernel's address space. Its bug (corrupting memory, deadlocking with interrupts disabled, a NULL dereference) affects the kernel itself; there is no isolation between it and everything else (← OS-1 S8).

The FUSE file system runs as an ordinary **user process**; the kernel's FUSE module forwards file operations to it as messages. When the process crashes, the kernel simply returns errors (`ENOTCONN`) for that mount; everything else continues.

The trade-off is performance: every FUSE operation needs extra context switches and data copies between the kernel and the daemon (the microkernel argument ← OS-1.6), which is acceptable for a network-bound cloud drive but was historically too slow for disk file systems or high-speed NICs (although VFIO-based user-space drivers can be very fast by polling devices directly).

</details>

### S8 · What happens to the data in /dev/null? (OS-10.5)

A student asks what `cat bigfile > /dev/null` does at the hardware level, and why `head -c 16 /dev/urandom` returns random bytes although no disk file stores them. Explain using device files.

<details><summary>Answer</summary>

`/dev/null` and `/dev/urandom` are **character device files** (`c`, major 1, minors 3 and 9). Opening them finds the "memory devices" driver by major number. The data never touches any hardware.

- `/dev/null`'s `write` operation simply returns the requested byte count and discards the data; its `read` returns 0 (end of file). `cat bigfile > /dev/null` reads the file (through the page cache and the disk driver) and writes into a driver that throws it away, a common way to time reads or silence output.
- `/dev/urandom`'s `read` operation fills the user buffer with output from the kernel's cryptographic random number generator.

This is "everything is a file": the same `read`/`write` system calls dispatch through the driver's `file_operations` table.

</details>

### S9 · Interleaved pages from the printer (OS-10.3)

On an old system with no spooler, two users print long documents at the same time, and the printer produces pages mixing lines from both. Explain the problem and how spooling solves it.

<details><summary>Answer</summary>

A printer is a **non-sharable** device that handles one continuous stream. If two processes write to it directly, their writes interleave in whatever order the scheduler runs them, so lines from both documents mix.

**Spooling**: each process's output is written to its own **spool file** on disk (which can be written concurrently). A single **daemon** is the only process that ever accesses the printer, and sends one complete file at a time from its queue. Users can see and cancel queued jobs. As a bonus, applications finish "printing" at disk speed and don't wait for the slow printer, and the printer's mutual exclusion is enforced by design, not by locking (← OS-5.3).

</details>

### S10 · Port 0x60 and the malicious cable (OS-10.1)

(a) A user program on Linux tries to read the keyboard controller directly with `inb(0x60)` and is killed with a segmentation fault. Why? (b) A malicious Thunderbolt device plugged into a laptop tries to read the whole of physical memory using DMA. What stops it on a modern system?

<details><summary>Answer</summary>

(a) `in`/`out` are **privileged** instructions (← OS-1.4): in user mode they cause a general protection fault unless the kernel has explicitly granted access to specific ports (via `ioperm`/`iopl`, which require root). Otherwise any program could reprogram hardware, read keystrokes of other users, or crash the machine.

(b) DMA bypasses the CPU and its MMU, so without protection a device can read any physical memory (so-called DMA attacks). The **IOMMU** gives each device its own address translation: the device can only reach buffers the driver explicitly mapped for it, and any other access is blocked and reported. Modern OSes enable IOMMU protection for external ports (Windows "Kernel DMA Protection," Linux's Thunderbolt security levels) and may refuse to authorize unknown devices.

</details>

### S11 · Polling beats interrupts (OS-10.2)

A benchmark of 4 KB reads on a very fast NVMe drive shows lower latency with polled completion (the CPU spins checking the completion queue) than with interrupts, while on a SATA SSD polling gives almost no benefit and wastes CPU. Explain using the costs involved.

<details><summary>Answer</summary>

With interrupts, completion costs the interrupt delivery, the handler, waking the sleeping thread, and a context switch back to it: several microseconds (N8). If the device itself completes in about 10 µs, those costs are a large fraction of total latency, and spinning (which notices completion within nanoseconds) cuts latency substantially.

On a SATA SSD (~80 to 100 µs per read, plus the slower SATA path), the same few microseconds are a small fraction, and spinning for 100 µs wastes a whole core for little gain. So polling makes sense only when the device is faster than, or comparable to, the interrupt path, and when a CPU can be spared. Linux's hybrid polling sleeps for about half the expected completion time and then spins, getting most of the latency benefit at lower CPU cost (← OSTEP's hybrid approach).

</details>

### S12 · Why databases use O_DIRECT (OS-10.4, OS-7.3)

A database opens its data files with `O_DIRECT` and manages a 64 GB buffer pool itself, instead of relying on the Linux page cache. Give three reasons, and one cost.

<details><summary>Answer</summary>

Reasons: (1) **No double caching:** with buffered I/O, each page would be cached twice (in the database's buffer pool and in the page cache), wasting memory. (2) **Better replacement decisions:** the database knows its access patterns (a full-table scan should not evict hot index pages; some pages are pinned by transactions), which a general-purpose LRU cannot know (← OS-7 S7). (3) **Control over write ordering and durability:** it decides exactly when pages go to disk, coordinated with its write-ahead log, rather than having the kernel write back dirty pages at arbitrary times. Also, it avoids the extra copy between the page cache and user space.

Costs: buffers, offsets, and sizes must be **aligned** to the device's logical block size; the database must implement its own caching, readahead, and write scheduling well; and any read not served by its own pool goes straight to the device (there is no kernel cache behind it).

</details>
