# Unit 4: Process Synchronization

> **How to use this page.** Section IDs (`OS-4.5`) match the tags on practice questions. Arrows like **→ OS-5.1** point to where an idea is developed further; **← OS-2.4** points back to something this section depends on.

Unit 2 gave us threads that share memory and processes that can share memory regions. Unit 3 gave us preemption: the CPU can be taken away at *any* instruction. Put those together and a thread can be stopped halfway through updating shared data, while another thread reads or changes the same data. This unit is about the resulting bugs and the tools that prevent them: locks, semaphores, condition variables, and monitors. It carries the most interview weight of any unit, because concurrency bugs are subtle and every real system has them.

## OS-4.1 · Race Conditions and the Critical-Section Problem

### A counter that cannot count

OSTEP's first concurrency example: two threads each increment a shared counter 1,000,000 times.

```c
#include <pthread.h>
#include <stdio.h>

static volatile int counter = 0;

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        counter++;                 // looks like one operation. It is not.
    return NULL;
}

int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, worker, NULL);
    pthread_create(&b, NULL, worker, NULL);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("counter = %d\n", counter);   // expected 2000000
    return 0;
}
```

Typical runs print values like 1,143,012 or 1,378,550, different each time. The reason: `counter++` compiles to three machine instructions.

```
 mov  eax, [counter]    ; 1. load counter into a register
 add  eax, 1            ; 2. increment the register
 mov  [counter], eax    ; 3. store the register back
```

A timer interrupt (or another core) can intervene between any two of them:

| Time | Thread A | Thread B | eax (A) | eax (B) | counter |
|---|---|---|---|---|---|
| 1 | load → 50 | | 50 | | 50 |
| 2 | add → 51 | | 51 | | 50 |
| 3 | *interrupted* | load → 50 | 51 | 50 | 50 |
| 4 | | add → 51 | 51 | 51 | 50 |
| 5 | | store 51 | 51 | 51 | **51** |
| 6 | store 51 | | 51 | | **51** |

Two increments ran; the counter went up by one. One update was **lost**. (`volatile` does not help: it only stops the compiler from caching the variable in a register; the three steps still happen separately.)

### Terminology

- **Race condition:** the result depends on the relative timing (interleaving) of threads. The program is **indeterminate**: the same input gives different outputs.
- **Critical section (CS):** a piece of code that accesses a shared resource and must not be executed by more than one thread at a time.
- **Mutual exclusion:** the guarantee that if one thread is in its critical section, no other thread is in its critical section for the same resource.
- **Atomic:** happens as a single indivisible unit ("all or nothing"); no other thread can observe it half done.
- **Data race** (a stricter, language-level term): two threads access the same memory location concurrently, at least one access is a write, and there is no synchronization between them. In C and C++, a data race is **undefined behaviour**, so the compiler may transform your code in ways that assume it cannot happen.

### The critical-section problem

Each thread's code is structured as:

```
 do {
     [entry section]      // ask permission to enter
         critical section
     [exit section]       // announce leaving
         remainder section
 } while (true);
```

A solution must satisfy **three requirements**:

1. **Mutual exclusion:** at most one thread is in its critical section at a time.
2. **Progress:** if no thread is in its critical section and some threads want to enter, only threads that are *not* in their remainder sections take part in deciding who enters next, and this decision cannot be postponed indefinitely. (Informally: the CS must not stay empty when someone wants it, and a thread that is not interested cannot block others.)
3. **Bounded waiting:** after a thread requests entry, there is a limit on how many times other threads can enter before it gets in. (No starvation.)

And one assumption: **no assumptions** about relative speeds of threads or number of CPUs. A solution that works only "because the other thread is slow" is wrong.

Mutual exclusion is about **safety** (nothing bad happens). Progress and bounded waiting are about **liveness** (something good eventually happens). Deadlock violates progress; starvation violates bounded waiting.

### Races inside the kernel

The kernel has shared data too: the list of open files, the process table, memory allocation structures. Example: two processes calling `fork()` at the same time could both be given the same "next PID" if the PID counter update is not protected.

- On a **single CPU with a non-preemptive kernel**, kernel code runs until it blocks or returns, so races between kernel paths come only from interrupt handlers. Disabling interrupts briefly around shared updates is enough.
- On a **preemptive kernel or any multiprocessor**, kernel code in different threads runs truly concurrently, so the kernel needs proper locks. Linux has been SMP-safe since 2.0 (with one "Big Kernel Lock" at first, gradually replaced by fine-grained locks, and removed completely in 2011).

## OS-4.2 · Software Solutions

These use only ordinary loads and stores. They are mostly of historical and teaching value today, but interviewers love asking why the flawed attempts fail. All examples are for two threads, numbered 0 and 1; in thread `i`, `j = 1 − i`.

### Attempt 1: strict alternation (a `turn` variable)

```c
int turn = 0;               // whose turn is it

// Thread i
while (turn != i)
    ;                       // wait
/* critical section */
turn = j;                   // give the turn away
/* remainder section */
```

- **Mutual exclusion:** yes. `turn` has one value, so only one thread passes the loop.
- **Progress:** **violated.** Threads must alternate strictly. If thread 0 wants to enter twice in a row while thread 1 is busy in its long remainder section, thread 0 waits for thread 1, which is not even interested.

### Attempt 2: interest flags

```c
bool flag[2] = {false, false};   // flag[i]: thread i wants to enter

// Thread i
flag[i] = true;
while (flag[j])
    ;
/* critical section */
flag[i] = false;
```

- **Mutual exclusion:** yes.
- **Progress:** **violated.** If both set their flags at the same time, each waits for the other forever: a **deadlock** (livelock in some variants).

Swapping the order (check first, then set the flag) avoids that deadlock but breaks **mutual exclusion**: both check, both see `false`, both enter.

### Peterson's algorithm (1981)

Combine the two ideas: announce interest, then politely give the turn to the other thread.

```c
bool flag[2] = {false, false};
int turn;

// Thread i   (j = 1 - i)
flag[i] = true;              // I want to enter
turn = j;                    // but you go first if you want to
while (flag[j] && turn == j)
    ;                        // wait while you want in AND it is your turn
/* critical section */
flag[i] = false;             // I am done
/* remainder section */
```

**Why it works:**

1. **Mutual exclusion.** Suppose both threads are in the CS. Then each passed its loop, so for each thread either the other's flag was false or `turn` pointed to itself. Both flags are true (each set its own before looping), so `turn == 0` for thread 0 and `turn == 1` for thread 1 at those moments. But `turn` holds a single value, and whichever thread wrote `turn` *last* wrote the other thread's number and will wait. Contradiction.
2. **Progress.** If thread j is not interested, `flag[j]` is false and thread i enters immediately. If both are interested, `turn` decides; it cannot favour neither.
3. **Bounded waiting.** When thread j leaves the CS and tries to re-enter, it sets `turn = i`, so thread i (which is waiting) gets in next. Each thread waits for **at most one** entry of the other.

**Why it fails on modern hardware.** Peterson's correctness assumes every thread sees memory operations in program order (**sequential consistency**). Real CPUs do not guarantee this. On x86, each core has a **store buffer**: the write `flag[i] = true` may sit in the buffer while the core goes ahead and reads `flag[j]` from cache. Both threads can read the other's flag as `false` and both enter. Compilers may also reorder the statements. To make Peterson's correct in practice you need a **memory barrier** (fence) between the writes and the read (→ OS-4.3). This is a standard interview point: "Peterson's is correct in theory, broken on real hardware without fences."

### Dekker's algorithm

The first known correct software solution for two threads (attributed to Th. J. Dekker by Dijkstra, 1960s). It uses the same ingredients (two flags and a turn variable) but is more complicated: a thread that sees the other's flag set and finds it is not its turn temporarily **withdraws** its own flag until the turn comes back. It satisfies all three requirements. Peterson's algorithm is the simpler successor that textbooks now prefer.

### Lamport's Bakery algorithm (n threads)

Like taking a numbered ticket at a bakery counter: each arriving customer takes a number larger than any number currently held, and the smallest number is served first.

```c
bool choosing[N];            // thread i is picking a number
int  number[N];              // 0 = not interested

// Thread i
choosing[i] = true;
number[i] = 1 + max(number[0], ..., number[N-1]);
choosing[i] = false;

for (int j = 0; j < N; j++) {
    while (choosing[j])
        ;                                   // wait until j has its number
    while (number[j] != 0 &&
           (number[j] < number[i] ||
            (number[j] == number[i] && j < i)))
        ;                                   // wait while j has priority
}
/* critical section */
number[i] = 0;
```

Key points:

- Two threads can compute the **same number** (they read the array concurrently). Ties are broken by thread ID: compare pairs `(number, id)` lexicographically.
- **Why `choosing` is needed:** without it, thread i could look at `number[j]` while j is still computing its number (still 0), decide j is not interested, and enter. Then j finishes computing a number *equal* to i's, has a smaller ID, and also enters. Waiting for `choosing[j]` to become false closes that gap.
- Satisfies mutual exclusion, progress, and bounded waiting (FIFO order by ticket).
- Downsides: O(n) work per entry, ticket numbers grow without bound while contention persists, and it has the same memory-ordering caveat as Peterson's.

## OS-4.3 · Hardware Support for Synchronization

Software-only solutions are slow and fragile on real hardware. Modern systems rely on hardware support.

### Disabling interrupts

On a **single processor**, a thread can only lose the CPU through an interrupt. So:

```c
disable_interrupts();
/* critical section */
enable_interrupts();
```

Problems:

- **Privileged:** user programs cannot do it (← OS-1.4), and if they could, a buggy program could take over the machine.
- **Does not work on multiprocessors:** other CPUs keep running and can enter the same critical section.
- Interrupts disabled for long means lost or delayed I/O events.

The kernel does use it, **briefly**, to protect data shared with interrupt handlers on the local CPU (→ S6).

### Atomic instructions

Hardware provides instructions that read and modify a memory location **as one indivisible operation**, even with multiple CPUs (the hardware locks the cache line or bus during the operation).

**Test-and-set (TAS).** Set a location to true and return its **old** value, atomically:

```c
// What the hardware does atomically:
bool test_and_set(bool *target) {
    bool old = *target;
    *target = true;
    return old;
}
```

A spinlock built on it:

```c
bool lock = false;

void acquire(void) {
    while (test_and_set(&lock))
        ;                     // old value was true: someone holds it; spin
}
void release(void) {
    lock = false;
}
```

If the old value was `false`, the lock was free and this thread has now set it: it owns the lock. On x86, the `xchg` instruction (exchange register with memory) provides this.

**Compare-and-swap (CAS).** Write a new value only if the location still holds an expected value; return the old value (or success/failure):

```c
// Atomic in hardware:
int compare_and_swap(int *value, int expected, int new_value) {
    int old = *value;
    if (old == expected)
        *value = new_value;
    return old;
}
```

Lock with CAS: `while (compare_and_swap(&lock, 0, 1) != 0) ;`

CAS is more powerful than TAS: it enables **lock-free** updates. An atomic increment without a lock:

```c
void atomic_increment(int *p) {
    int old;
    do {
        old = *p;                                 // read current value
    } while (compare_and_swap(p, old, old + 1) != old);  // retry if someone changed it
}
```

If another thread changed `*p` between the read and the CAS, the CAS fails and we retry with the fresh value. No update is ever lost. On x86 this is `lock cmpxchg`.

**Fetch-and-add.** Atomically increment a value and return the old value (x86 `lock xadd`). OSTEP uses it to build a **ticket lock**:

```c
typedef struct { int ticket; int turn; } ticket_lock_t;   // both start at 0

void acquire(ticket_lock_t *l) {
    int my_turn = fetch_and_add(&l->ticket, 1);   // take the next ticket
    while (l->turn != my_turn)
        ;                                         // spin until called
}
void release(ticket_lock_t *l) {
    l->turn = l->turn + 1;                        // call the next ticket
}
```

Unlike the plain TAS spinlock, the ticket lock is **fair**: threads acquire in FIFO order of arrival, which gives bounded waiting. (It is the hardware version of the bakery idea.)

**Load-linked / store-conditional (LL/SC).** Used by ARM, RISC-V, MIPS, and PowerPC instead of CAS. `LL` reads a value and starts monitoring the address; `SC` writes only if no one else wrote that address since the `LL`, and reports success or failure. A CAS or fetch-and-add is built from an LL/SC retry loop.

### Bounded waiting with test-and-set

The simple TAS spinlock provides mutual exclusion and progress but **not bounded waiting**: an unlucky thread may lose the race every time. Silberschatz's fix hands the lock directly to the next waiting thread in circular order:

```c
bool waiting[N];   // all false
bool lock = false;

// Thread i
waiting[i] = true;
bool key = true;
while (waiting[i] && key)
    key = test_and_set(&lock);
waiting[i] = false;

/* critical section */

int j = (i + 1) % N;
while (j != i && !waiting[j])
    j = (j + 1) % N;          // find next waiting thread
if (j == i)
    lock = false;             // nobody waiting: release
else
    waiting[j] = false;       // pass the lock directly to thread j
```

A waiting thread enters either by winning TAS or by being handed the lock. Any waiting thread gets in within N − 1 turns.

### Atomic variables

Languages expose these instructions as atomic types. C11:

```c
#include <stdatomic.h>

atomic_int counter = 0;

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++)
        atomic_fetch_add(&counter, 1);     // one atomic read-modify-write
    return NULL;
}
```

This fixes the counter from OS-4.1. C++ has `std::atomic<int>`, Java has `AtomicInteger`. Atomic variables are right for **single variables** (counters, flags, pointers). They do not make a sequence of operations on several variables atomic; for that you need a lock.

### Memory models and barriers

For performance, CPUs and compilers **reorder** memory operations when the reordering is invisible to a single thread. Other threads, however, can see it.

- **Sequential consistency (SC):** the result is as if all threads' operations were interleaved in one global order that respects each thread's program order. Intuitive, but slow to guarantee; no mainstream CPU provides it by default.
- **x86 (TSO, total store order):** fairly strong. The only reordering visible to other cores is that a **store followed by a load** (to a different address) can appear reordered, because of the store buffer. That is exactly the reordering that breaks Peterson's.
- **ARM, POWER, RISC-V:** weaker; loads and stores can be reordered in more ways.

Example that breaks on weak hardware:

```c
int data = 0;
bool ready = false;

// Thread 1                    // Thread 2
data = 42;                     while (!ready) ;
ready = true;                  print(data);     // may print 0 on ARM!
```

Thread 1's two stores may become visible in the opposite order, or thread 2's loads may be satisfied out of order.

A **memory barrier (fence)** forces ordering: operations before it are completed and visible before operations after it (x86 `mfence`, ARM `dmb`). Modern code usually expresses this with **acquire/release** semantics:

- A **release** store (`ready = true` with release) guarantees all earlier writes are visible before the store.
- An **acquire** load (`while (!ready)` with acquire) guarantees later reads happen after the load.

```c
atomic_store_explicit(&ready, true, memory_order_release);     // thread 1
while (!atomic_load_explicit(&ready, memory_order_acquire)) ;  // thread 2
```

**Locks include the necessary barriers.** Acquiring a lock has acquire semantics and releasing has release semantics, so code that protects all shared data with locks does not need to think about reordering. You only need barriers explicitly when writing lock-free code or synchronization primitives yourself.

**`volatile` is not a synchronization tool in C/C++.** It prevents the compiler from caching a value in a register or removing accesses, but provides no atomicity and no CPU ordering guarantees. (In Java, `volatile` *does* give ordering and visibility guarantees; the keyword means different things in the two languages.)

## OS-4.4 · Mutex Locks and Spinlocks

### The lock API

A **mutex** (mutual exclusion lock) has two operations: `acquire()` (also `lock`) and `release()` (`unlock`). A thread that calls `acquire()` on a held lock does not return until it owns the lock.

```c
#include <pthread.h>

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
int counter = 0;

void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        pthread_mutex_lock(&m);
        counter++;                  // critical section
        pthread_mutex_unlock(&m);
    }
    return NULL;
}
```

OSTEP's criteria for evaluating a lock:

1. **Correctness:** does it provide mutual exclusion?
2. **Fairness:** does every waiting thread eventually get it (no starvation)?
3. **Performance:** overhead with no contention, with contention on one CPU, and with contention on many CPUs.

### Spinlocks vs blocking locks

A **spinlock** waits by looping (busy-waiting) until the lock is free. A **blocking (sleeping) lock** puts the waiting thread to sleep in a queue and wakes it when the lock is released.

| | Spinlock | Blocking lock |
|---|---|---|
| Waiting thread | Burns CPU in a loop | Sleeps; CPU runs other work |
| Cost of waiting | CPU time for the whole wait | Two context switches (sleep + wake) |
| Good when | Lock held very briefly (shorter than two context switches) **and** multiple CPUs | Lock may be held long, or single CPU |
| Can be used where sleeping is forbidden | **Yes** (interrupt handlers, scheduler code) | No |
| On a single CPU | Wasteful: the holder cannot run while the waiter spins until the waiter's quantum ends | Fine |

**Spinning on a uniprocessor.** If thread A holds a spinlock and is preempted, thread B spins for its whole quantum, because A cannot run to release the lock while B has the CPU. With N threads contending, N − 1 of them may each waste a full time slice. This is why OSTEP concludes that spinning needs help from the OS.

### Getting the OS involved

OSTEP walks through these improvements:

1. **Yield instead of spin:** if the lock is taken, call `yield()` to give up the CPU. Better on one CPU, but with many threads it still costs many context switches, and a thread can still starve.
2. **Queue + park/unpark:** keep an explicit queue of waiting threads; a waiter calls `park()` to sleep; `release()` calls `unpark()` on the next thread in the queue. Now waiters do not burn CPU and get the lock in FIFO order. A subtle **wakeup/waiting race** appears: a thread decides to sleep, but before it actually parks, the holder releases the lock and unparks it; the thread then parks forever. Solaris addresses this with `setpark()`, which announces "I am about to park"; if an unpark happens in between, the later park returns immediately. (xv6 and Linux solve the same problem differently → OS-4.5.)
3. **Two-phase locks:** spin for a short while (hoping the lock is released soon), and only then sleep. This combines the fast path of spinning with the efficiency of blocking.

### Linux futexes

Linux's pthread mutex uses a **futex** (fast userspace mutex):

- The lock is an integer in **user memory**. Acquiring an **uncontended** lock is a single atomic instruction (CAS) in user space: **no system call at all**.
- Only when the lock is contended does the thread call `futex(FUTEX_WAIT)` to sleep in the kernel; the releaser, seeing that there are waiters, calls `futex(FUTEX_WAKE)`.

The common case (no contention) is as cheap as an atomic instruction; the kernel is involved only when a thread must actually wait. glibc's mutex also spins briefly before sleeping in some configurations (two-phase behaviour).

### Spinlocks in the kernel

Kernel spinlocks are used for short critical sections, especially those reachable from interrupt context:

- `spin_lock()` also **disables preemption** on the local CPU. Otherwise the holder could be preempted and other threads would spin for a long time.
- If the same data is touched by an interrupt handler, use `spin_lock_irqsave()`, which also disables local interrupts (→ S6).
- **Rule:** never sleep (block, call a function that may sleep, touch user memory that may fault) while holding a spinlock.
- For longer critical sections where the holder may sleep, the kernel uses a sleeping `mutex` or a semaphore.

xv6 has exactly this split: `spinlock` (`acquire`/`release`, which disable interrupts on the current CPU and use `xchg`) and `sleeplock` (for things like disk buffers, where the holder may wait for I/O).

### Lock granularity and other variants

- **Coarse-grained locking:** one lock protects a large structure (or the whole kernel: the "Big Kernel Lock"). Simple and hard to get wrong, but limits parallelism, since threads touching unrelated parts still serialize.
- **Fine-grained locking:** separate locks for separate parts (one lock per hash bucket, per list node). More parallelism, more complexity, more risk of deadlock (→ OS-5).
- Start coarse, measure, then split locks only where contention is real.
- **Recursive (reentrant) mutex:** can be acquired again by the thread that already holds it (it keeps a count). Convenient, but often hides design problems. A normal mutex relocked by its holder deadlocks.
- **Reader-writer lock:** many readers or one writer (→ OS-4.7).
- **Trylock:** `pthread_mutex_trylock()` returns immediately with `EBUSY` instead of waiting. Useful for avoiding deadlock (→ OS-5.3).

**Lock discipline rules:**

- Every access to a shared variable, **reads included**, must hold the lock that protects it.
- Keep critical sections short; do no I/O or long computation while holding a lock.
- Only the thread that acquired a mutex may release it.

## OS-4.5 · Semaphores

### Definition

A **semaphore** (Dijkstra, 1965) is an integer variable `S` accessed only through two atomic operations:

- `wait(S)` (also `P`, from the Dutch *proberen*, "to test"; `down`; `sem_wait`)
- `signal(S)` (also `V`, *verhogen*, "to increment"; `up`; `sem_post`)

The classical busy-waiting definition:

```c
wait(S) {
    while (S <= 0)
        ;          // busy wait
    S--;
}

signal(S) {
    S++;
}
```

Both operations must be **atomic**: the test and the decrement in `wait` must happen without interruption.

### Blocking implementation

Busy waiting wastes CPU (such a semaphore is sometimes called a *spinlock semaphore*). The standard implementation blocks instead:

```c
typedef struct {
    int value;
    struct process *list;     // queue of waiting processes
} semaphore;

void wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        add this process to S->list;
        block();              // sleep: Running -> Blocked
    }
}

void signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        remove a process P from S->list;
        wakeup(P);            // Blocked -> Ready
    }
}
```

Key facts about this version:

- The value **can be negative**. If it is −k, exactly **k processes are waiting** on the semaphore. If it is positive, it counts available "permits."
- `wait` and `signal` themselves are short critical sections on the semaphore's own data. They are made atomic with a spinlock or by disabling interrupts. So busy waiting has not been eliminated completely; it has been moved from the application's critical section (possibly long) to the semaphore code (a few instructions), which is rarely contended.
- The order in which the list is served (FIFO or otherwise) determines whether waiting is bounded. A FIFO queue gives bounded waiting.

### Binary vs counting

- **Counting semaphore:** value ranges over an unrestricted domain. Controls access to a resource with N identical instances.
- **Binary semaphore:** value is 0 or 1. Behaves much like a mutex lock.

### Three uses

**1. Mutual exclusion** (initial value 1):

```c
semaphore mutex = 1;
wait(mutex);
/* critical section */
signal(mutex);
```

**2. Ordering / signalling** (initial value 0). Statement S1 in thread A must run before statement S2 in thread B:

```c
semaphore synch = 0;

// Thread A          // Thread B
S1;                  wait(synch);
signal(synch);       S2;
```

If B arrives first, it blocks until A signals. If A signals first, the value becomes 1, and B passes straight through. The semaphore **remembers** the signal. OSTEP uses this for a parent waiting for a child thread (`sem_wait` in the parent, `sem_post` at the end of the child).

**3. Resource counting** (initial value N): at most N threads can use a pool of N resources (database connections, buffer slots) at once. Each thread calls `wait` before using one and `signal` after.

A useful rule from OSTEP for choosing the initial value: **the number of resources you are willing to give away immediately after initialization.** One for a lock, zero for ordering, N for a pool.

### Semaphore vs mutex

| | Mutex | Semaphore |
|---|---|---|
| Value | Locked / unlocked | Integer count |
| Ownership | Yes: only the locking thread may unlock | No: any thread may signal |
| Main use | Mutual exclusion | Signalling, counting, and mutual exclusion |
| Priority inheritance | Commonly supported (holder is known) | Generally impossible (no owner) |
| Misuse detection | Can detect unlock by non-owner, relock by owner | Cannot |

A binary semaphore can be used as a lock, but a mutex is clearer and safer for that purpose. A semaphore is the right tool when one thread waits for an event produced by another.

### POSIX semaphores

```c
#include <semaphore.h>

sem_t s;
sem_init(&s, 0, 1);    // 0 = shared between threads of this process
                       // (nonzero = shared between processes, in shared memory)
sem_wait(&s);          // P
sem_post(&s);          // V  (async-signal-safe, so usable from a signal handler)
sem_destroy(&s);

sem_t *n = sem_open("/mysem", O_CREAT, 0644, 1);  // named semaphore for unrelated processes
```

### Pitfalls

Semaphores are powerful but unstructured. A single mistake gives bugs that are hard to find:

- `signal(mutex) ... wait(mutex)` (swapped): mutual exclusion is violated.
- `wait(mutex) ... wait(mutex)`: the thread blocks on itself forever.
- Forgetting a `wait` or `signal`: violated exclusion or permanent blocking.
- Two semaphores acquired in different orders by two threads:

```c
// Thread 0          // Thread 1
wait(S);             wait(Q);
wait(Q);             wait(S);     // deadlock if each got its first one
```

This is a deadlock (→ OS-5.1). Monitors (→ OS-4.6) were invented to make such mistakes harder.

### Sleep and wakeup in xv6: the lost-wakeup problem

Mythili Vutukuru's course spends time on how xv6 lets a thread sleep until a condition becomes true. The naive approach has a race:

```
 Consumer                              Producer
 --------                              --------
 if (queue is empty)                   
     /* about to sleep... */           add item to queue
                                       wakeup(queue)    <- nobody is sleeping yet
     sleep(queue)                      <- sleeps forever: the wakeup was lost
```

The consumer checked the condition, then the producer changed it and sent a wakeup **before** the consumer actually went to sleep. This is the **lost wakeup** problem (the same race as park/unpark in OS-4.4).

xv6's solution: `sleep(chan, lk)` takes the lock `lk` that protects the condition. The caller holds `lk` while checking the condition and calling sleep. Inside, `sleep` acquires the process-table lock **before** releasing `lk`, marks the process `SLEEPING` on `chan`, and then switches away. `wakeup(chan)` must acquire the process-table lock too, so it cannot run in the gap between "decided to sleep" and "asleep." And callers always re-check the condition in a loop after waking:

```c
acquire(&q->lock);
while (q->count == 0)
    sleep(q, &q->lock);     // atomically release lock and sleep; reacquire on wakeup
item = remove(q);
release(&q->lock);
```

This "hold the lock, check in a loop, atomically release and sleep" pattern is exactly what condition variables provide.

## OS-4.6 · Monitors and Condition Variables

### Condition variables

A **condition variable (CV)** is a queue that threads can wait on until some condition becomes true. It is always used together with a mutex that protects the condition's state.

POSIX API:

| Call | Meaning |
|---|---|
| `pthread_cond_wait(&cv, &m)` | **Atomically** release mutex `m` and sleep on `cv`. When woken, reacquire `m` before returning. Caller must hold `m`. |
| `pthread_cond_signal(&cv)` | Wake **one** thread waiting on `cv` (if any). |
| `pthread_cond_broadcast(&cv)` | Wake **all** threads waiting on `cv`. |

The canonical pattern (OSTEP: join with a CV):

```c
int done = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;

void thr_exit(void) {                 // child, when finished
    pthread_mutex_lock(&m);
    done = 1;                         // change the state
    pthread_cond_signal(&c);          // then signal
    pthread_mutex_unlock(&m);
}

void thr_join(void) {                 // parent
    pthread_mutex_lock(&m);
    while (done == 0)                 // check the state in a loop
        pthread_cond_wait(&c, &m);
    pthread_mutex_unlock(&m);
}
```

Why each piece is needed:

- **Why the state variable `done`?** A CV has **no memory**. If the child signals before the parent waits, the signal is lost, and the parent would wait forever. The state variable records that the event happened; the parent checks it first and never waits.
- **Why the lock?** Without it, the parent could check `done == 0`, get preempted, the child sets `done = 1` and signals (nobody is waiting yet), and then the parent sleeps forever: the lost-wakeup race again. Holding the lock while checking and having `wait` release it atomically closes the gap.
- **Why `while` instead of `if`?** See Mesa semantics below.

### Signal on a CV vs signal on a semaphore

| | Condition variable `signal` | Semaphore `signal` |
|---|---|---|
| No thread waiting | **Nothing happens**; the signal is lost | Value is incremented; a later `wait` passes immediately |
| Has a value | No | Yes |
| Needs a separate state variable | Yes, always | No (the count is the state) |

### Monitors

A **monitor** is a language construct (Brinch Hansen, Hoare, early 1970s) that bundles shared data with the procedures that operate on it, and guarantees that **only one thread is active inside the monitor at a time**. The compiler inserts the lock acquire/release automatically, so the programmer cannot forget them.

```
 monitor BoundedBuffer {
     item buffer[N];  int count = 0;
     condition not_full, not_empty;

     procedure insert(item x) {
         while (count == N) not_full.wait();
         add x; count++;
         not_empty.signal();
     }
     procedure remove() { ... symmetric ... }
 }
```

Monitors provide mutual exclusion automatically; condition variables inside them provide waiting for conditions. **Java** gives every object a monitor: `synchronized` methods/blocks for exclusion, and `wait()`, `notify()`, `notifyAll()` as its single built-in condition variable. C# has `lock` and `Monitor`. In C, a mutex plus condition variables is the "manual" monitor.

### Hoare vs Mesa semantics

When thread T1 signals a CV that T2 is waiting on, both are now eligible to run inside the monitor, but only one may. Who goes first?

- **Hoare semantics (signal-and-wait):** T2 runs **immediately**, and T1 waits until T2 leaves or waits again. The condition T1 made true is **guaranteed** still true when T2 resumes. Theoretically neat, harder to implement, more context switches.
- **Mesa semantics (signal-and-continue):** T1 keeps running; T2 is merely moved to the ready queue and will reacquire the lock **later**. By then another thread may have run and made the condition false again. The signal is only a **hint** that the state may have changed. (Named after the Mesa language at Xerox PARC, 1980.)

Virtually every real system (pthreads, Java, C#, Linux kernel wait queues) uses **Mesa semantics**. Therefore:

> **Always wait in a `while` loop that re-checks the condition, never an `if`.**

The loop also handles **spurious wakeups**: POSIX allows `pthread_cond_wait` to return even when nobody signalled (it simplifies implementations on some platforms). With a `while` loop, a spurious wakeup is harmless.

### Covering conditions and broadcast

OSTEP's example: a memory allocator where threads wait for memory of different sizes. One thread frees 50 bytes and signals. If it wakes a thread waiting for 100 bytes, that thread re-checks, goes back to sleep, and a thread waiting for 10 bytes stays asleep even though it could proceed. The fix is `broadcast`: wake everyone and let each re-check. A CV used this way is a **covering condition**. It costs extra wakeups but is correct. Use `broadcast` when waiters wait for different conditions on the same CV, or when a state change may allow several waiters to proceed.

### Rules for CVs

1. Always associate a CV with a mutex and some shared **state**.
2. Hold the mutex when checking or changing the state, when waiting (required by the API), and preferably when signalling.
3. Always wait in a `while` loop.
4. Use separate CVs for separate conditions (see producer-consumer below), or broadcast.

## OS-4.7 · Classic Synchronization Problems

These problems appear in every course and many interviews. Each represents a common real-world pattern.

### Bounded buffer (producer–consumer)

Producers put items into a buffer of N slots; consumers take them out. Producers must wait when the buffer is full, consumers when it is empty, and the buffer's internal state must not be corrupted. (This finishes the job started in ← OS-2.4.)

**Semaphore solution:**

```c
semaphore mutex = 1;     // protects the buffer's internals
semaphore empty = N;     // counts empty slots
semaphore full  = 0;     // counts filled slots

// Producer                       // Consumer
while (true) {                    while (true) {
    item = produce();                 wait(full);
    wait(empty);                      wait(mutex);
    wait(mutex);                      item = remove_from_buffer();
    add_to_buffer(item);              signal(mutex);
    signal(mutex);                    signal(empty);
    signal(full);                     consume(item);
}                                 }
```

- At all times `empty + full = N` (ignoring operations in progress). The buffer can hold all N items, unlike the lock-free version in OS-2.4, which held N − 1.
- **Order of `wait` matters.** If the producer did `wait(mutex)` before `wait(empty)` and the buffer was full, it would sleep **holding the mutex**; the consumer could never get the mutex to make space: **deadlock** (→ S3). Rule: acquire the counting semaphore first, the mutex second. The order of `signal`s does not matter for correctness.
- `produce()` and `consume()` stay **outside** the mutex so that producers and consumers can do their slow work in parallel.

**Condition variable solution (OSTEP's progression).** OSTEP builds it in steps, each fixing a bug:

1. One CV, `if` checks. Breaks with **two consumers**: consumer C1 is woken by the producer, but before it runs, consumer C2 sneaks in and takes the item. C1 then wakes, does not re-check (it used `if`), and tries to consume from an empty buffer. Fix: `while`.
2. One CV, `while` checks. Still breaks: with one CV, a consumer that empties the buffer may signal and wake **another consumer** instead of the producer. All three threads can end up asleep. Fix: two CVs, so consumers only wake producers and vice versa.
3. Correct version:

```c
int buffer[MAX];
int fill_ptr = 0, use_ptr = 0, count = 0;
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  empty = PTHREAD_COND_INITIALIZER;   // signalled when a slot frees
pthread_cond_t  fill  = PTHREAD_COND_INITIALIZER;   // signalled when an item arrives

void put(int v) { buffer[fill_ptr] = v; fill_ptr = (fill_ptr + 1) % MAX; count++; }
int  get(void)  { int v = buffer[use_ptr]; use_ptr = (use_ptr + 1) % MAX; count--; return v; }

void *producer(void *arg) {
    for (int i = 0; i < LOOPS; i++) {
        pthread_mutex_lock(&mutex);
        while (count == MAX)
            pthread_cond_wait(&empty, &mutex);
        put(i);
        pthread_cond_signal(&fill);
        pthread_mutex_unlock(&mutex);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < LOOPS; i++) {
        pthread_mutex_lock(&mutex);
        while (count == 0)
            pthread_cond_wait(&fill, &mutex);
        int v = get();
        pthread_cond_signal(&empty);
        pthread_mutex_unlock(&mutex);
        consume(v);
    }
    return NULL;
}
```

Real-world instances: pipes (← OS-2.4), a thread pool's task queue, a disk driver's request queue, Unix pipelines, message queues between services.

### Readers–writers

A shared database: **readers** only read, **writers** modify. Any number of readers may read at the same time, but a writer needs **exclusive** access (no other writers and no readers).

**First readers–writers problem (reader preference):** no reader waits unless a writer already holds the lock.

```c
semaphore rw_mutex = 1;   // exclusive access for writers (and for "the readers as a group")
semaphore mutex    = 1;   // protects read_count
int read_count = 0;

// Writer
wait(rw_mutex);
/* writing */
signal(rw_mutex);

// Reader
wait(mutex);
read_count++;
if (read_count == 1)
    wait(rw_mutex);       // first reader locks writers out
signal(mutex);

/* reading */

wait(mutex);
read_count--;
if (read_count == 0)
    signal(rw_mutex);     // last reader lets writers in
signal(mutex);
```

How it behaves:

- The first reader acquires `rw_mutex` on behalf of all readers; later readers just increment the count and walk in.
- If a writer is writing, the first reader blocks on `rw_mutex` (while holding `mutex`), so other arriving readers block on `mutex`.
- **Writer starvation:** if readers keep arriving so that `read_count` never drops to 0, a waiting writer never gets in.

**Second readers–writers problem (writer preference):** once a writer is waiting, no **new** reader may start. Readers can now starve.

**Fair version:** add a "turnstile" semaphore that every reader and writer passes through in arrival order; a waiting writer holds the turnstile, stopping new readers until it has written. Neither side starves.

Reader-writer locks in practice: `pthread_rwlock_rdlock / wrlock / unlock`, Java's `ReentrantReadWriteLock`, Linux kernel `rwlock_t` and `rw_semaphore`. They only pay off when reads greatly outnumber writes and read sections are not tiny; otherwise the extra bookkeeping makes them slower than a plain mutex. For very read-heavy data, the kernel uses **RCU** instead (→ OS-4.8).

### Dining philosophers

Five philosophers sit around a table, alternately thinking and eating. There is one chopstick between each pair (five in total). To eat, a philosopher needs **both** the left and right chopsticks. (Dijkstra, 1965.) The problem models allocating several resources among several processes without deadlock or starvation.

**Naive solution: deadlocks.**

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};

// Philosopher i
while (true) {
    wait(chopstick[i]);             // left
    wait(chopstick[(i + 1) % 5]);   // right
    eat();
    signal(chopstick[i]);
    signal(chopstick[(i + 1) % 5]);
    think();
}
```

If all five get hungry at once and each picks up their left chopstick, every chopstick is held and everyone waits for their right one forever: all four deadlock conditions hold (→ OS-5.1).

**Deadlock-free fixes:**

1. **Limit diners:** allow at most **four** philosophers at the table at once (a counting semaphore initialized to 4). With five chopsticks and at most four competitors, at least one philosopher can get both (pigeonhole principle).
2. **Asymmetry / resource ordering:** odd-numbered philosophers pick up left then right; even-numbered pick up right then left. Or equivalently, number the chopsticks and always pick the **lower-numbered** first (so the last philosopher reverses the order). This breaks the circular wait (→ OS-5.3). Dijkstra's original fix.
3. **Pick up both or neither:** check both chopsticks inside a critical section and take them only if both are free. The monitor solution below does this.

**Monitor solution (Silberschatz):**

```
 monitor DiningPhilosophers {
     enum { THINKING, HUNGRY, EATING } state[5];
     condition self[5];

     void pickup(int i) {
         state[i] = HUNGRY;
         test(i);                          // try to start eating
         if (state[i] != EATING)
             self[i].wait();               // wait until a neighbour lets us eat
     }

     void putdown(int i) {
         state[i] = THINKING;
         test((i + 4) % 5);                // left neighbour may now eat
         test((i + 1) % 5);                // right neighbour may now eat
     }

     void test(int i) {
         if (state[(i + 4) % 5] != EATING &&
             state[i] == HUNGRY &&
             state[(i + 1) % 5] != EATING) {
             state[i] = EATING;
             self[i].signal();
         }
     }

     initialization_code() {
         for (int i = 0; i < 5; i++) state[i] = THINKING;
     }
 }
```

A philosopher eats only when neither neighbour is eating, so it is deadlock-free. It is **not starvation-free**: two neighbours can alternate eating so that the philosopher between them never finds both free. (The `if` in `pickup` is safe even under Mesa semantics, because `test()` sets `state[i] = EATING` before signalling and only philosopher i changes it back. With a pthreads implementation, where spurious wakeups are possible, write `while (state[i] != EATING)` anyway.)

With five philosophers, at most **two** can eat at the same time.

### Sleeping barber

A barbershop has one barber, one barber chair, and N waiting chairs. If there are no customers, the barber sleeps. An arriving customer wakes the barber if he is asleep; sits in a waiting chair if the barber is busy; or **leaves** if all waiting chairs are taken. (Dijkstra.) It models a server process with a bounded request queue, where excess requests are dropped.

```c
#define CHAIRS 5
semaphore customers = 0;   // number of waiting customers (barber sleeps on this)
semaphore barbers   = 0;   // barber ready to cut (customer waits on this)
semaphore mutex     = 1;   // protects 'waiting'
int waiting = 0;           // customers in waiting chairs

// Barber
while (true) {
    wait(customers);       // sleep if no customers
    wait(mutex);
    waiting--;
    signal(barbers);       // barber is ready for one customer
    signal(mutex);
    cut_hair();
}

// Customer
wait(mutex);
if (waiting < CHAIRS) {
    waiting++;
    signal(customers);     // wake the barber if needed
    signal(mutex);
    wait(barbers);         // wait for the barber
    get_haircut();
} else {
    signal(mutex);         // shop full: leave
}
```

The separate `waiting` counter is needed because a customer must be able to **check** how many are waiting without blocking, and semaphores cannot be read.

### Other patterns worth knowing

- **Barrier:** N threads each must reach a point before any continues (for example, between phases of a parallel computation). `pthread_barrier_wait`, or build it from a counter, a mutex, and a CV with broadcast.
- **Rendezvous:** two threads each wait for the other to reach a point: two semaphores initialized to 0, each thread signals its own and waits on the other's.
- **Strict alternation between threads** ("print ping and pong alternately," "print odd numbers from one thread and even from another"): two semaphores, one initialized to 1 and one to 0, passed back and forth (→ S8).

## OS-4.8 · Liveness, Priority Inversion, and Lock-Free Synchronization

### Liveness failures

Locks guarantee safety but can break liveness:

| Failure | What happens | Example |
|---|---|---|
| **Deadlock** | A set of threads each wait for a resource held by another in the set; none can proceed | Two threads acquiring two locks in opposite orders (→ OS-5) |
| **Starvation** | A thread waits indefinitely while others keep proceeding | A writer under reader-preference locking; unfair TAS spinlock |
| **Livelock** | Threads are not blocked; they keep changing state in response to each other but make no progress | Two threads that each `trylock` the second lock, fail, release the first, and retry in lockstep forever. Like two people stepping aside in a corridor in the same direction repeatedly. Fixed with random backoff. |

### Priority inversion

**Setup:** three tasks with priorities H > M > L, and a lock shared by H and L.

```
 time -->
 L: [lock R]---preempted----------------------------------[unlock R]
 H:        [wants R: BLOCKED ...................................][runs]
 M:              [runs ......... runs ......... runs ....]
```

1. L acquires lock R.
2. H becomes ready, preempts L, and tries to acquire R: it blocks (fine so far; L will release R soon).
3. M becomes ready. It has higher priority than L, so it preempts L. M does not need R at all.
4. Now **H (highest priority) waits for M (medium priority)**, indirectly, for as long as M runs. The priorities have been inverted. With many medium tasks, H's wait is **unbounded**.

**Priority inheritance protocol:** while a low-priority task holds a lock that a higher-priority task is waiting for, the holder temporarily **inherits** the waiter's priority. In the example, L runs at H's priority, so M cannot preempt it; L finishes its critical section quickly, releases R, drops back to its own priority, and H runs. H's blocking time is bounded by the length of L's critical section.

**Priority ceiling protocol:** each lock is given a *ceiling* equal to the highest priority of any task that may use it; a task holding the lock runs at the ceiling priority. This also prevents chains of blocking and certain deadlocks, but needs to know in advance which tasks use which locks.

**Mars Pathfinder (1997):** a few days after landing, the lander began resetting itself repeatedly. It ran the VxWorks RTOS. A low-priority meteorological task held a mutex on a shared information bus; a high-priority bus-management task blocked on that mutex; medium-priority communication tasks preempted the low-priority one. The high-priority task missed its deadline, a watchdog timer noticed and reset the whole system. Engineers reproduced it on an identical copy on Earth and fixed it by uploading a change that **enabled priority inheritance** on that mutex, an option VxWorks supported but had been turned off.

Linux supports priority inheritance for pthread mutexes created with the `PTHREAD_PRIO_INHERIT` protocol attribute, and internally through "rt-mutexes."

### Lock-free and wait-free data structures

Locks have costs: contention, convoys, deadlock, priority inversion, and a preempted lock holder blocking everyone. **Non-blocking** algorithms avoid locks by using atomic instructions (usually CAS) directly.

- **Lock-free:** at every step, **some** thread makes progress. Individual threads can starve (retry forever), but the system as a whole never stalls, even if a thread is suspended mid-operation.
- **Wait-free:** **every** thread completes its operation in a bounded number of its own steps. Strongest guarantee, hardest to design.
- (**Obstruction-free:** a thread completes if it eventually runs alone. Weaker than lock-free.)

**Treiber's lock-free stack:**

```c
typedef struct node { int value; struct node *next; } node_t;
_Atomic(node_t *) top = NULL;

void push(int v) {
    node_t *n = malloc(sizeof *n);
    n->value = v;
    node_t *old;
    do {
        old = atomic_load(&top);
        n->next = old;
    } while (!atomic_compare_exchange_weak(&top, &old, n));   // retry if top changed
}

int pop(int *out) {
    node_t *old, *next;
    do {
        old = atomic_load(&top);
        if (old == NULL) return 0;          // empty
        next = old->next;                   // (!) old may already be freed: see below
    } while (!atomic_compare_exchange_weak(&top, &old, next));
    *out = old->value;
    /* when is it safe to free(old)? */
    return 1;
}
```

**The ABA problem.** CAS checks only that the value is the **same**, not that it was **unchanged**:

1. Thread 1 in `pop` reads `top = A` and `next = B`, then is preempted.
2. Thread 2 pops A, pops B, and pushes A back (A's memory was reused). Now `top = A`, but `A->next` is no longer B.
3. Thread 1 resumes: CAS sees `top == A` and succeeds, setting `top = B`, a node that has been **removed** (and perhaps freed). The stack is corrupted.

Fixes:

- **Tagged pointers / version counters:** store a counter next to the pointer and CAS both together (double-width CAS, such as x86 `cmpxchg16b`); every update increments the counter, so A-with-version-5 differs from A-with-version-7.
- **Safe memory reclamation:** never reuse a node while another thread may still hold a pointer to it: **hazard pointers**, **epoch-based reclamation**, or RCU-style grace periods. Garbage-collected languages (Java) largely avoid ABA for this reason.

Lock-free code is very hard to get right and not automatically faster. Use well-tested libraries (such as Java's `ConcurrentLinkedQueue`, or `liburcu`) rather than writing your own in production.

### Read-Copy-Update (RCU) basics

RCU is a Linux kernel technique for data that is **read very often and updated rarely** (routing tables, the list of loaded modules, security policies).

- **Readers** take no locks at all. They mark a read-side critical section (`rcu_read_lock()` / `rcu_read_unlock()`, which in many configurations just disable preemption) and follow pointers normally. Reading is almost free and scales perfectly across CPUs.
- **Writers** never modify data in place. To update, they:
  1. **Copy** the element and modify the copy.
  2. **Publish** the new version by atomically switching the pointer (`rcu_assign_pointer`, which includes a release barrier). New readers now see the new version; readers already in progress still see the old one, which remains valid.
  3. **Wait for a grace period** (`synchronize_rcu()`): until every CPU has passed through a point where it cannot be in an old read-side section (for example, a context switch). After that, no reader can hold a pointer to the old version.
  4. **Free** the old version.
- Writers still serialize among themselves using an ordinary lock.

RCU trades memory (two versions exist briefly) and writer latency for extremely fast readers. It solves the reclamation problem from the ABA discussion by making it safe to free only after all readers are done.

### What real concurrency bugs look like

OSTEP Chapter 32 summarizes a study of bugs in MySQL, Apache, Mozilla, and OpenOffice (Lu et al., 2008). Most were **not** deadlocks:

- **Atomicity violation:** code assumed a sequence of operations was atomic, but it was not enforced. Example: `if (p->info != NULL) fputs(p->info, ...)` in one thread while another sets `p->info = NULL` between the check and the use. Fix: a lock around both.
- **Order violation:** code assumed A happens before B, but it was not enforced. Example: a thread uses a pointer that another thread has not initialized yet. Fix: a condition variable or semaphore enforcing the order.

These two categories made up about 97% of the non-deadlock bugs in that study. When debugging, ask: "which operations here are assumed to be atomic?" and "which events are assumed to happen in order?"

## Quick Revision Sheet

- `x++` = load, add, store: three steps that can interleave → lost updates.
- Race condition: result depends on timing. Critical section: code touching shared data.
- CS requirements: mutual exclusion, progress, bounded waiting; no speed assumptions.
- Strict alternation violates progress. Flag-only attempt can deadlock.
- Peterson's: `flag[i] = true; turn = j; while (flag[j] && turn == j);` Correct in theory; needs a fence on real CPUs (store buffer reorders store→load).
- Bakery: n threads, ticket numbers, ties by ID, `choosing[]` needed.
- Disabling interrupts: uniprocessor kernel only.
- TAS, CAS, fetch-and-add, LL/SC are atomic read-modify-write instructions. Ticket lock (fetch-and-add) is FIFO-fair.
- Locks include acquire/release barriers. `volatile` (C/C++) is not synchronization.
- Spinlock: short CS, multicore, cannot sleep. Blocking lock: longer CS or single CPU. Futex: user-space fast path, kernel only on contention.
- Kernel: never sleep holding a spinlock; use `spin_lock_irqsave` if interrupt handlers share the data.
- Semaphore: `wait` decrements (blocks if negative), `signal` increments (wakes one). Negative value −k = k waiters.
- Initial value: 1 for a lock, 0 for ordering, N for a pool.
- Mutex has an owner; semaphore does not.
- CV: no memory; always pair with state + mutex; `wait` atomically releases the mutex; always use `while` (Mesa semantics, spurious wakeups).
- Producer-consumer: `wait(empty)` before `wait(mutex)`; two CVs with while loops.
- Readers-writers: first version starves writers.
- Dining philosophers: naive deadlocks; fix with ≤ 4 diners, resource ordering, or both-or-none.
- Priority inversion: fix with priority inheritance (Mars Pathfinder).
- Lock-free: CAS loops; beware ABA (fix: tagged pointers, hazard pointers).
- RCU: lock-free readers, copy-update-publish, wait for grace period, then free.

## Worked Numerical Problems

### N1 · Possible final values of a shared counter (OS-4.1)

**Question.** `x` is initially 0. Two threads each run `x = x + 1` implemented as load, add, store. (a) What final values are possible if each thread does this once? (b) If each thread does it 10 times in a loop, what are the minimum and maximum possible final values?

**Answer.**

(a) **1 or 2.** 2 if one thread's store happens before the other's load; 1 if both load 0 before either stores.

(b) Maximum **20** (no overlap). Minimum is **2**, not 10. The schedule that achieves it:

1. T1 loads 0 (and is preempted before storing).
2. T2 runs 9 complete iterations: x = 9.
3. T1 stores 1 (overwriting 9). x = 1.
4. T2 loads 1 for its 10th iteration (and is preempted before storing).
5. T1 runs its remaining 9 iterations: x = 10.
6. T2 stores 2. x = **2**.

Every value from 2 to 20 is possible. This is a favourite interview question because most people guess 10.

### N2 · Counting interleavings (OS-4.1)

**Question.** Thread A executes 3 atomic instructions a1, a2, a3 in order; thread B executes b1, b2, b3. (a) How many distinct interleavings are there? (b) If the instructions are `load, add, store` for `x++` in each thread (x starts at 0), in how many interleavings is the final value 2? (c) Generalize (a) to m and n instructions.

**Answer.**

(a) Choose which 3 of the 6 positions belong to A: C(6, 3) = **20**.

(b) The result is 2 only if one thread's store comes before the other thread's load. Since each thread's load is its first instruction and its store is its last, this means one thread runs **entirely** before the other: only a1 a2 a3 b1 b2 b3 or b1 b2 b3 a1 a2 a3. So **2 of 20** give 2; the other **18** lose an update.

(c) C(m + n, m) = (m + n)! / (m! n!). With 3 threads of k instructions each: (3k)! / (k!)³.

The lesson: among all orderings, the race is the *common* case. It is rare in practice only because time slices are long compared with three instructions, which is exactly why it slips through testing.

### N3 · Semaphore bookkeeping (OS-4.5)

**Question.** A counting semaphore (blocking implementation, value may go negative) is initialized to 7. (a) 20 `wait` and 15 `signal` operations are performed, in some order. What is the final value? (b) Starting again from 7, suppose all 20 waits happen first (by different processes), then 15 signals. How many processes are blocked after the waits, and after the signals? (c) Starting from 3, five processes call `wait`. What is the value, and how many are blocked?

**Answer.**

(a) 7 − 20 + 15 = **2**, whatever the order (each operation changes the value by exactly 1).

(b) After 20 waits: 7 − 20 = −13, so **13 processes are blocked** (7 got through). After 15 signals: −13 + 15 = 2, so **0 blocked**, and 2 permits remain.

(c) 3 − 5 = **−2**: 3 processes passed, **2 are blocked**.

(With the busy-waiting definition, the value never goes below 0: it would be 0 in (c), with 2 processes spinning.)

### N4 · Bounded buffer state (OS-4.7)

**Question.** Producer–consumer with semaphores, N = 5 (`empty = 5`, `full = 0`, `mutex = 1` initially). The producer has completed 7 items and the consumer has completed 3. (a) What are `empty` and `full`? (b) The producer tries to produce 2 more with no consumption. What happens? (c) Could `full` ever be 6?

**Answer.**

(a) Items in buffer = 7 − 3 = 4. `full = 4`, `empty = 1`.

(b) The first item: `wait(empty)` takes empty to 0, item added, `full = 5`. The second: `wait(empty)` with empty = 0: the producer **blocks** (value −1 in the blocking implementation) until the consumer takes an item and signals `empty`.

(c) No. Every increment of `full` is preceded by a successful `wait(empty)`, so `full + empty ≤ N` always. That invariant is what makes the solution correct.

### N5 · Minimum resources to avoid deadlock (OS-4.7, OS-5.1)

**Question.** (a) 5 philosophers each need 2 chopsticks. What is the minimum number of chopsticks (in a shared pool, any chopstick usable by anyone) that guarantees no deadlock? (b) Generalize: n processes each need at most k instances of a resource. (c) With 5 philosophers and 5 chopsticks arranged normally, what is the maximum number eating simultaneously? With n philosophers?

**Answer.**

(a) Worst case: every philosopher holds 1 and waits for 1 more. With 5 chopsticks, all 5 are held: deadlock. With **6**, at least one philosopher can get a second chopstick, eat, and release both. Answer: **6**.

(b) Worst case: each process holds k − 1 and waits. That uses n(k − 1). One more instance lets someone finish: **n(k − 1) + 1** guarantees no deadlock. (For 5 and 2: 5 × 1 + 1 = 6.) This reasoning returns in Unit 5.

(c) Eating philosophers cannot be neighbours: **2** out of 5. In general, **⌊n / 2⌋**.

### N6 · Lock contention limits throughput (OS-4.4)

**Question.** Each request spends 2 ms inside a critical section protected by one global lock, and 8 ms of work that needs no lock. Ignore lock overhead. (a) What is the maximum throughput on 1, 4, and 8 cores? (b) The data is split so that requests are spread evenly over 4 independent locks. What is the maximum throughput on 8 cores now?

**Answer.**

(a) The lock can be held by one request at a time for 2 ms, so the lock alone allows at most 1000 / 2 = **500 requests/s**, however many cores there are. Each request takes 10 ms of CPU.

- 1 core: 1000 / 10 = **100 req/s** (CPU-bound).
- 4 cores: 400 req/s of CPU capacity < 500: **400 req/s**.
- 8 cores: 800 req/s of CPU capacity, but the lock caps it at **500 req/s**. Adding cores beyond 5 gives nothing.

(b) With 4 independent locks the lock limit becomes 4 × 500 = 2000 req/s. CPU capacity is 800 req/s, so throughput = **800 req/s**. This is Amdahl's law (← OS-2.7) in the form of a lock: the critical section is the serial fraction.

### N7 · Spin or sleep? (OS-4.4)

**Question.** On a multicore machine, a context switch (sleep plus later wakeup) costs 10 µs of CPU in total. The lock's critical section lasts on average 2 µs. When a thread finds the lock held, on average about half the critical section remains. (a) Expected CPU cost of waiting by spinning vs by sleeping? (b) At what remaining hold time does sleeping become better? (c) Why is a two-phase lock a good compromise?

**Answer.**

(a) Spinning: about **1 µs** (the remaining half of the 2 µs section). Sleeping: **10 µs**. Spinning is 10× cheaper.

(b) Sleeping wins when the expected remaining wait exceeds the switch cost: roughly **> 10 µs**. So spin for short critical sections, sleep for long ones.

(c) A two-phase lock spins for up to about the cost of a context switch, then sleeps. If the lock is released quickly (the common case), it pays only for the spin. If not, it wastes at most about one context switch worth of spinning before sleeping, so its cost is at most about twice the optimal choice, without having to know the hold time in advance. (This is the classic "ski rental" argument.)

### N8 · Priority inversion timing (OS-4.8)

**Question.** Priorities H > M > L on one CPU. At t = 0, L acquires a mutex for a critical section needing 3 ms. At t = 1, H arrives and requests the mutex. At t = 1.5, M arrives and needs 40 ms of CPU (no mutex). (a) When does H get the mutex without priority inheritance? (b) With priority inheritance? (c) What is H's blocking time in each case?

**Answer.**

(a) L runs 0–1 (1 ms done). H preempts at 1, blocks on the mutex at about 1, L resumes. At 1.5, M preempts L (M > L). M runs 1.5–41.5. L resumes and finishes its remaining 1.5 ms at **43**. H gets the mutex at t = 43.

(b) At t = 1 H blocks, and L inherits H's priority. At 1.5, M arrives but has lower priority than L's inherited priority, so L keeps running, finishing its 2 remaining ms at **t = 3**. L releases the mutex, drops back to low priority, and H runs.

(c) Without inheritance: 43 − 1 = **42 ms**, dominated by M, which is unrelated to the mutex, and unbounded in general. With inheritance: 3 − 1 = **2 ms**, bounded by L's critical section.

## Scenario Questions (Test Your Understanding)

### S1 · Works in debug, hangs in release (OS-4.3)

```c
int ready = 0;          // shared
// Thread A: spins
while (!ready) ;
printf("go\n");
// Thread B (later):
ready = 1;
```

Compiled with `-O0` it works. With `-O2`, thread A spins forever. Why? Would adding `volatile` be a proper fix?

<details><summary>Answer</summary>

With optimization, the compiler sees that nothing in the loop changes `ready` (it assumes no data races, since they are undefined behaviour), loads it once into a register, and turns the loop into `if (!ready) for (;;);`. The store from thread B is never re-read.

`volatile` forces a memory read each iteration, so the program appears to work on x86, but it gives no ordering guarantees: any data written before `ready = 1` may not be visible to A on weaker hardware. The proper fix is an atomic with release/acquire (`atomic_store_explicit(&ready, 1, memory_order_release)` and an acquire load), or a condition variable so A sleeps instead of spinning.

</details>

### S2 · The consumer that crashed on an empty queue (OS-4.6)

A work queue uses one mutex and one condition variable. The consumer code is `if (queue_empty()) pthread_cond_wait(&cv, &m); item = dequeue();`. With one consumer thread it has worked for months. After adding a second consumer, `dequeue()` occasionally fails with the queue empty. Explain the exact interleaving.

<details><summary>Answer</summary>

Mesa semantics. Consumer C1 is waiting. The producer adds one item and signals, moving C1 to the ready queue, but C1 must reacquire the mutex before it can run. Meanwhile consumer C2, which was running and just arrived at the check, acquires the mutex first, finds the queue non-empty, and takes the item. When C1 finally reacquires the mutex, it returns from `wait` and, because it used `if`, does not re-check. It calls `dequeue()` on an empty queue.

Fix: `while (queue_empty()) pthread_cond_wait(&cv, &m);`. The loop also covers spurious wakeups.

</details>

### S3 · A harmless-looking reordering (OS-4.7)

A developer "tidies up" the producer so that it acquires `mutex` first, then `empty`:

```c
wait(mutex); wait(empty); add(item); signal(full); signal(mutex);
```

Under light load it works. Under heavy load, the system freezes. Why?

<details><summary>Answer</summary>

When the buffer is full, the producer acquires `mutex`, then blocks on `wait(empty)` **while holding `mutex`**. The consumer, which would free a slot and signal `empty`, first needs `mutex`, which it can never get. The producer waits for the consumer and the consumer waits for the producer: a **deadlock**. Under light load the buffer is never full, so the problem never shows. Rule: wait on the counting semaphore before taking the mutex.

</details>

### S4 · The broken singleton (OS-4.3)

```c
Config *get_config(void) {
    if (instance == NULL) {                 // first check, no lock
        pthread_mutex_lock(&m);
        if (instance == NULL)
            instance = create_config();      // allocate and initialize
        pthread_mutex_unlock(&m);
    }
    return instance;
}
```

This "double-checked locking" occasionally returns a config whose fields are garbage. How?

<details><summary>Answer</summary>

`instance = create_config()` involves writing the object's fields and then writing the pointer. The compiler or CPU may make the **pointer** visible to other threads before the **fields** (the pointer store is not ordered after the field stores, and the first check reads `instance` with no lock and no acquire). Another thread passes the unlocked check, sees a non-NULL pointer, and reads uninitialized fields.

Fixes: make `instance` an atomic pointer, written with release and read with acquire; or use `pthread_once()` (C) / a function-local static (C++11 guarantees thread-safe initialization); or simply always take the lock.

</details>

### S5 · Spinlocks on one core (OS-4.4)

A spinlock-based library performs well on a 16-core server. Deployed on a single-core embedded board with preemptive scheduling, the same program becomes extremely slow under contention. Why?

<details><summary>Answer</summary>

On one core, when a thread that holds the lock is preempted, a waiting thread spins for its **entire time slice**: the holder cannot run to release the lock while the spinner has the only CPU. Each contended acquisition can waste a full quantum (or several, with more threads). On 16 cores, the holder keeps running on its own core and releases the lock within microseconds.

Fix: use blocking locks (a pthread mutex, which sleeps via futex) or at least yield after a few spins. Kernel spinlocks avoid the problem by disabling preemption while held.

</details>

### S6 · Deadlock with yourself (OS-4.4)

A driver protects a packet list with `spin_lock(&list_lock)`. Both normal kernel code (a system call) and the network card's interrupt handler add to the list. Occasionally one CPU locks up completely, spinning forever. No other CPU holds the lock. How is that possible, and what is the fix?

<details><summary>Answer</summary>

The system call path acquires `list_lock` on CPU 0. While it holds the lock, the network card interrupts **CPU 0**. The interrupt handler tries to acquire `list_lock` and spins. But the holder is the code the handler interrupted, and it cannot resume until the handler returns. The handler waits for the holder, the holder waits for the handler: a single-CPU deadlock.

Fix: in process context, use `spin_lock_irqsave(&list_lock, flags)` (and `spin_unlock_irqrestore`), which disables local interrupts while the lock is held, so the handler cannot run on this CPU at that moment. Other CPUs can still take the interrupt and simply spin briefly until the lock is released.

</details>

### S7 · The thread that never woke up (OS-4.5, OS-4.6)

A thread does:

```c
if (!data_ready)            // checked without holding a lock
    sleep_on(&wq);          // go to sleep until woken
```

and another thread does `data_ready = 1; wake_up(&wq);`. Rarely, the first thread sleeps forever even though `data_ready` is 1. Explain, and describe how xv6 or pthreads prevent it.

<details><summary>Answer</summary>

**Lost wakeup.** Thread 1 checks `data_ready` (0) and decides to sleep, but is preempted before it actually sleeps. Thread 2 sets `data_ready = 1` and calls `wake_up`, which finds no sleeper. Thread 1 then sleeps, and no further wakeup will come.

The check and the transition to sleeping must be atomic with respect to the waker. xv6's `sleep(chan, lk)` is called holding the lock that protects the condition, and it releases that lock only after acquiring the process-table lock that `wakeup` also needs. `pthread_cond_wait(&cv, &m)` atomically releases `m` and blocks. In both, the waker sets the condition while holding the same lock, and the waiter re-checks the condition in a `while` loop after waking.

</details>

### S8 · Ping, pong (OS-4.5)

Two threads must print `ping` and `pong` strictly alternately, forever, starting with `ping`. Design it with semaphores, and state the initial values.

<details><summary>Answer</summary>

```c
sem_t ping_turn, pong_turn;
sem_init(&ping_turn, 0, 1);   // ping goes first
sem_init(&pong_turn, 0, 0);

void *ping(void *a) { for (;;) { sem_wait(&ping_turn); puts("ping"); sem_post(&pong_turn); } }
void *pong(void *a) { for (;;) { sem_wait(&pong_turn); puts("pong"); sem_post(&ping_turn); } }
```

Each thread waits for its own turn and hands the turn to the other. At any time the sum of the two semaphore values is at most 1, so only one thread prints. The same pattern prints odd/even numbers from two threads, or extends to N threads in a ring with N semaphores (one initialized to 1).

</details>

### S9 · The writer that never writes (OS-4.7)

A caching service uses a reader-preference readers-writers lock. Monitoring shows reads served fine, but configuration updates (writes) sometimes wait for minutes during peak traffic. Explain and give two fixes.

<details><summary>Answer</summary>

With reader preference, a writer can acquire the lock only when `read_count` reaches 0. At peak traffic, new readers keep arriving before the last one leaves, so the count never drops to 0 and the writer **starves**.

Fixes: a **writer-preference** or **fair** lock (a turnstile, so that once a writer is waiting, new readers queue behind it; `pthread_rwlock` implementations can be configured to prefer writers); or, for read-mostly data, **RCU**-style or copy-on-write updates: build a new configuration and swap a pointer atomically, so writers never wait for readers at all.

</details>

### S10 · ABA in a free list (OS-4.8)

A lock-free free-list of memory blocks uses CAS on the head pointer for `pop`. Under heavy load, the same block is occasionally handed to two threads at once. Describe the sequence of events.

<details><summary>Answer</summary>

Thread 1 in `pop` reads `head = A` and `A->next = B`, then is preempted before its CAS. Thread 2 pops A (and uses it), pops B (and uses it), then frees A back onto the list: now `head = A` again, but `A->next` is C (or whatever was below B). Thread 1 resumes: `CAS(&head, A, B)` succeeds, because head is A again. Head now points to B, which is **in use by thread 2**. The next `pop` hands out B a second time.

Fix: pair the head pointer with a version counter updated on every change and CAS both together (double-width CAS), or use hazard pointers / epoch-based reclamation so that A cannot be recycled while thread 1 may still use it.

</details>

### S11 · Signal before wait (OS-4.5, OS-4.6)

Thread A must wait for thread B's initialization. In version 1, B calls `sem_post(&s)` (s initialized to 0) and A calls `sem_wait(&s)`. In version 2, B calls `pthread_cond_signal(&cv)` and A calls `pthread_cond_wait(&cv, &m)`, with no other state variable. In a run where B finishes before A starts waiting, what happens in each version?

<details><summary>Answer</summary>

**Version 1 works.** The post raises `s` to 1; the semaphore remembers it, and A's later `sem_wait` returns immediately.

**Version 2 hangs.** A condition variable has no memory: signalling with no waiter does nothing. A then waits forever. The fix is a state variable protected by the mutex (`initialized = 1` in B before signalling; A does `while (!initialized) pthread_cond_wait(...)`). The CV is only the waiting mechanism; the state is the truth.

</details>

### S12 · Resets on Mars (OS-4.8)

A spacecraft's flight computer keeps resetting. Logs show the high-priority bus-management task missing its deadline, which trips a watchdog. That task only waits on one mutex, held for very short periods by a low-priority weather task. The CPU is not overloaded. Diagnose and fix.

<details><summary>Answer</summary>

**Unbounded priority inversion.** The weather task (low) holds the mutex; the bus task (high) blocks on it; medium-priority tasks (communications) preempt the weather task, which therefore cannot finish its tiny critical section. The high-priority task waits for all the medium work, misses its deadline, and the watchdog resets the system. This is the Mars Pathfinder incident (1997).

Fix: enable **priority inheritance** on the mutex (the actual fix, uploaded remotely), so the weather task runs at high priority while holding it and releases it quickly; or use a priority ceiling; or redesign so tasks of very different priorities do not share a lock.

</details>
