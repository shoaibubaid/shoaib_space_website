# Unit 6: Memory Management

> **How to use this page.** Section IDs (`OS-6.4`) match the tags on practice questions. Arrows like **→ OS-7.1** point to where an idea is developed further; **← OS-2.1** points back to something this section depends on.

Every process believes it has a large, private, contiguous memory starting at address 0 (← OS-2.1). In reality, dozens of processes share one physical RAM, scattered in pieces. This unit explains how the OS and hardware create that illusion: translating every address a program uses into a physical address, protecting processes from each other, and doing it fast enough that programs barely notice. OSTEP calls this **virtualizing memory**. Unit 7 then extends it so that the total memory in use can exceed physical RAM.

---

## OS-6.1 · Address Binding, Logical vs Physical Addresses, and the MMU

### Goals of memory virtualization

OSTEP lists three goals:

1. **Transparency:** programs should not notice that memory is virtualized; each behaves as if it owns private memory.
2. **Efficiency:** in time (translation must not slow programs much, which requires hardware support such as TLBs) and in space (the bookkeeping must not use too much memory).
3. **Protection (isolation):** a process must not be able to read or modify the memory of another process or of the kernel.

### Address binding

A program refers to memory symbolically in source code (`count`, `buffer`). These references must eventually become physical addresses. **Binding** can happen at three stages:

| Binding time | How | Consequence |
|---|---|---|
| **Compile time** | Compiler generates **absolute** addresses, knowing where the program will be placed | Must recompile if the location changes. MS-DOS `.COM` programs. |
| **Load time** | Compiler generates **relocatable** code; the loader adds the start address when loading | Program cannot be moved once it is running |
| **Execution time** | Binding delayed until each memory access; the hardware translates every address as it is used | Process can be **moved** in memory during execution. Requires hardware (MMU). All modern general-purpose OSes. |

### Logical vs physical addresses

- **Logical (virtual) address:** generated by the CPU while executing the program: the address in an instruction, the value of a pointer.
- **Physical address:** the address actually sent to the memory hardware.
- With compile-time and load-time binding, logical and physical addresses are identical. With execution-time binding, they differ, and the set of all logical addresses a process can use is its **logical (virtual) address space**.

When a C program prints a pointer (`printf("%p", &x)`), it prints a **virtual** address. It never sees a physical address.

### The memory-management unit (MMU)

The **MMU** is the hardware that translates virtual addresses into physical addresses on every memory access (instruction fetches, loads, stores). It sits between the CPU core and memory, and is part of the CPU chip on modern processors.

### Dynamic relocation: base and limit registers

The simplest MMU (OSTEP's "base and bounds") has two registers per CPU:

- **Base (relocation) register:** the physical address where the process's memory starts.
- **Limit (bounds) register:** the size of the process's address space.

For every memory reference:

```
                 +---------+
 virtual addr -->| < limit?|--- no ---> trap: addressing error (protection fault)
                 +---------+
                      | yes
                      v
                   (+ base) -----> physical address
```

```
 physical = virtual + base,   valid only if 0 <= virtual < limit
```

Example: base = 32 KB, limit = 16 KB. Virtual address 3,000 → physical 32,768 + 3,000 = **35,768**. Virtual address 20,000 → exceeds the limit → **trap**.

Properties:

- **Protection:** a process cannot generate an address outside its region.
- **Relocation:** the OS can move a process by copying its memory and changing the base register.
- The base and limit registers can be changed **only in kernel mode** (← OS-1.4). Otherwise any program could point its base at another process.

**OS responsibilities** with dynamic relocation (OSTEP):

- On process creation, find free physical space (using a **free list**) for its address space.
- On termination, return the space to the free list.
- On every **context switch**, save the old process's base/limit into its PCB and load the new one's.
- Install exception handlers for out-of-bounds accesses (typically: kill the process).

**Problem:** the whole address space must be contiguous in physical memory, including the large unused gap between heap and stack (← OS-2.1). That wastes memory and causes fragmentation (→ OS-6.3). Segmentation (→ OS-6.7) and paging (→ OS-6.4) solve this.

## OS-6.2 · Linking, Loading, Shared Libraries, and Swapping

### From source to running program

```
 source.c --compiler--> source.o (relocatable object) --linker--> a.out (executable) --loader--> process in memory
                                  ^
                          other .o files, libraries
```

- The **compiler/assembler** produces **object files** with code, data, a symbol table, and **relocation entries** (places whose addresses are not yet known).
- The **linker** combines object files and libraries into an executable, resolving symbol references (a call to `printf` in `main.o` is connected to the definition of `printf`).
- The **loader** (part of `execve` ← OS-2.3) maps the executable into memory and starts it.

### Static vs dynamic linking

**Static linking:** library code is copied into the executable at link time (`gcc -static`).

- Self-contained executable; no dependencies at run time; slightly faster startup.
- Every program carries its own copy of the library, on disk and in memory. A security fix to the library requires relinking every program.

**Dynamic linking:** the executable records only which **shared libraries** it needs (Linux `.so`, Windows `.dll`, macOS `.dylib`). At run time, the **dynamic linker/loader** (`ld-linux.so` on Linux) maps them into the process and resolves references.

- **One copy of library code in physical memory**, shared by all processes using it (→ OS-6.4 shared pages). With 200 processes using `libc`, its code occupies RAM only once.
- Libraries can be updated (for example, a security patch) without relinking programs.
- Costs: slower startup, a dependency on the correct library version being present ("DLL hell"), and an indirection on calls.

How it works on Linux (TLPI Chapters 41 and 42):

- Shared libraries are compiled as **position-independent code (PIC)**: code that works at any address, because the library may be mapped at different addresses in different processes.
- Calls to library functions go through the **PLT** (procedure linkage table), and addresses of external data and functions are kept in the **GOT** (global offset table), which is per-process writable data. The code pages stay read-only and shareable; only the small GOT differs between processes.
- **Lazy binding:** by default a function's address is resolved the first time it is called, not at startup.
- `ldd ./prog` lists the libraries a program needs.

### Dynamic loading

A routine is not loaded until the program explicitly asks for it at run time, using `dlopen()` / `dlsym()` (Windows `LoadLibrary`). This is how programs load **plugins**. Unlike dynamic linking, it is controlled by the program itself, not required at startup.

### Swapping

A process's memory can be temporarily moved out to a **backing store** (a fast disk or SSD area), and brought back later to continue.

- **Standard swapping** moves **entire processes**. It lets the total memory of all processes exceed physical memory, and is managed by the medium-term scheduler (← OS-2.2).
- Cost is dominated by transfer time: swapping a 100 MB process out and another in at 50 MB/s takes 2 s + 2 s = **4 s**. Too slow for interactive use.
- A process with **pending I/O** into its memory cannot be swapped out (the device would write into memory that now belongs to someone else), unless I/O goes through kernel buffers.

Modern systems swap **pages**, not whole processes (**paging with swapping** → OS-7.1), which is much finer-grained. On Linux, "swap" means page-level swap. **Mobile systems** generally avoid swapping to flash storage (limited write endurance, limited space): iOS asks applications to free memory and terminates them if needed; Android kills background processes (after saving their state) and uses **zram**, a compressed swap area in RAM.

## OS-6.3 · Contiguous Memory Allocation and Fragmentation

With base-and-limit relocation, each process occupies **one contiguous block** of physical memory. The OS must decide where to put each process.

### Fixed partitions

Divide memory into a fixed number of partitions (possibly different sizes) at boot. Each holds one process; the number of partitions bounds the degree of multiprogramming. Early IBM OS/360 (MFT) worked like this.

Problem: a process smaller than its partition wastes the rest of the partition: **internal fragmentation**.

### Variable partitions

Allocate exactly as much memory as each process needs. The OS keeps a list of free blocks (**holes**). Initially all user memory is one big hole. When processes leave, their blocks become holes; adjacent holes are **merged (coalesced)**.

```
 time 1: | OS | P1        | P2    | P3          |      free       |
 time 2: | OS | P1        | hole  | P3          |      free       |   P2 exited
 time 3: | OS | P1        | P4| h | P3          | P5   |  free    |   P4 fits in P2's hole
```

### Placement strategies

Given a request of size n and a list of holes:

| Strategy | Rule | Notes |
|---|---|---|
| **First fit** | Allocate the **first** hole big enough | Fast (stops early). Tends to leave small fragments near the start of the list. |
| **Next fit** | Like first fit, but start searching where the last search ended | Spreads allocations; slightly worse fragmentation than first fit in studies. |
| **Best fit** | Allocate the **smallest** hole big enough | Must search the whole list (unless sorted by size). Leaves the smallest leftover, which is often too small to be useful. |
| **Worst fit** | Allocate the **largest** hole | Must search the whole list. Leaves the largest leftover, hoping it stays useful. In practice usually worst. |

Simulations show **first fit and best fit are better than worst fit** in both speed and storage use; first fit is generally faster, and neither clearly beats the other in storage use. See N6 for a worked example.

### External vs internal fragmentation

- **External fragmentation:** there is enough total free memory for a request, but it is split into holes that are each too small. The waste is *outside* allocated blocks.
- **Internal fragmentation:** an allocated block is larger than what was requested (because allocations are rounded up to a fixed unit, or a whole partition or page is given out). The waste is *inside* allocated blocks.

| | External | Internal |
|---|---|---|
| Where is the waste? | Between allocations | Inside allocations |
| Caused by | Variable-size allocation | Fixed-size allocation units |
| Occurs in | Variable partitions, segmentation, `malloc` heaps | Fixed partitions, paging (last page), buddy allocator |

**50-percent rule** (Knuth): with first fit, statistically, for every N allocated blocks, about 0.5 N blocks are lost to fragmentation. So about **one third** of memory (0.5N out of 1.5N) may be unusable.

### Fixing external fragmentation

1. **Compaction:** shuffle allocated blocks together so all free memory forms one large hole. Possible only with **execution-time binding** (relocate by changing the base register). It is expensive: all moved memory must be copied, and processes with pending I/O must not be moved.
2. **Allow non-contiguous allocation:** let a process's memory be scattered across physical memory. That is exactly what **paging** does (→ OS-6.4), and it eliminates external fragmentation entirely.

### The same problem in user space: `malloc`

OSTEP Chapter 17 (free-space management) shows the same issues inside a process's heap. `malloc` manages variable-size blocks and faces the same placement choices and external fragmentation. Techniques:

- A **header** before each allocated block records its size, so `free(ptr)` knows how much to release (this is why `free` does not take a size).
- **Splitting** a large free block to satisfy a small request, and **coalescing** adjacent free blocks on free.
- **Segregated lists:** separate free lists for common sizes (fast, little fragmentation for those sizes); the **slab allocator** (→ OS-7.7) is the kernel version.
- **Buddy allocation:** power-of-two sizes, fast coalescing, internal fragmentation (→ OS-7.7).
- glibc `malloc` gets memory from the kernel with `brk()` (growing the heap) for small allocations and `mmap()` for large ones (≥ 128 KB by default), which can be returned to the kernel individually.

## OS-6.4 · Paging

### The idea

Paging divides memory into **fixed-size** pieces so that a process's memory does not need to be contiguous:

- Physical memory is divided into **frames**.
- Each process's logical address space is divided into **pages** of the **same size** as frames.
- Any page can be placed in **any** free frame. A per-process **page table** records which frame holds each page.

```
 Logical memory             Page table            Physical memory
 (process A)                page -> frame          frame
 +---------+               +---+-----+            +-----------+
 | page 0  |               | 0 |  1  |          0 |           |
 +---------+               | 1 |  4  |            +-----------+
 | page 1  |               | 2 |  3  |          1 | A: page 0 |
 +---------+               | 3 |  7  |            +-----------+
 | page 2  |               +---+-----+          2 |           |
 +---------+                                      +-----------+
 | page 3  |                                    3 | A: page 2 |
 +---------+                                      +-----------+
                                                4 | A: page 1 |
                                                  +-----------+
                                                5 |           |
                                                  |    ...    |
                                                7 | A: page 3 |
                                                  +-----------+
```

Benefits:

- **No external fragmentation:** any free frame can be used for any page.
- Easy allocation: the OS keeps a list of free frames; a process needing n pages needs any n free frames.
- **Internal fragmentation** is limited to the last page of each region: on average **half a page** per region.
- Makes sharing, copy-on-write, and demand paging possible (→ OS-7).

### Address translation

Page size is always a **power of two**, so a virtual address splits cleanly into two fields:

```
 virtual address:   |   page number  p   |   page offset  d   |
                     (m − n) bits              n bits
 (virtual address space = 2^m bytes, page size = 2^n bytes)
```

- **Page number p:** index into the page table.
- **Offset d:** position within the page; it is copied unchanged, because a page and its frame have the same size.

```
 physical address = (frame number f) × page size + d
                  = | f | d |      (just replace the p bits with f)
```

Steps for every memory access:

1. Extract p and d from the virtual address.
2. Look up entry p in the page table to get frame number f (checking validity and permissions).
3. Form the physical address by concatenating f and d.

**Worked example.** 16-bit virtual addresses, page size 1 KB (2¹⁰), so 6 bits of page number and 10 bits of offset (64 pages). Page table: page 5 → frame 1.

- Virtual address `0x1432` = binary `000101 0000110010`. Page = `000101` = 5; offset = `0000110010` = 0x032 = 50.
- Frame 1: physical = 1 × 1024 + 50 = **1074 = 0x0432**.

In decimal: page = ⌊address / page size⌋, offset = address mod page size. (More in N1.)

### The page table and PTE contents

The page table is an array in memory, indexed by page number. Each **page table entry (PTE)** contains the frame number plus control bits:

| Bit | Meaning |
|---|---|
| **Valid / present** | Is this page mapped (and currently in memory)? If not, access causes a **page fault** trap (→ OS-7.1) |
| **Protection** (R/W, and execute / NX) | Allowed operations. Writing a read-only page, or executing from a non-executable page, traps. |
| **User / supervisor** | May user-mode code access it? Kernel pages are mapped in every process but marked supervisor-only (→ S12). |
| **Dirty (modified)** | Set by hardware when the page is written. A clean page need not be written back to disk before being evicted (→ OS-7.3). |
| **Accessed (referenced)** | Set by hardware when the page is read or written. Used by page-replacement algorithms (→ OS-7.3). |
| **Cache disabled** | For pages mapped to device registers (memory-mapped I/O → OS-10.1) |

On **x86-64**, a PTE is 64 bits: bit 0 present, bit 1 read/write, bit 2 user/supervisor, bit 5 accessed, bit 6 dirty, bit 7 page size (huge page), bit 63 no-execute, and bits 12 to 51 the physical frame number.

**Where the page table lives:** in main memory. The **page-table base register** (PTBR; `CR3` on x86) points to the current process's table. On a context switch, the kernel changes PTBR (← OS-2.2), which instantly switches the whole address space.

The kernel also keeps a **frame table**: one entry per physical frame, recording whether it is free and, if not, which process and page use it.

### Protection

- Access beyond the process's mapped pages: the PTE is invalid, so the hardware traps. (A separate page-table length register can also bound the table size.)
- Invalid pages include the large unused gap between heap and stack: nothing is mapped there, so accidental accesses trap.
- **Page 0 is deliberately left unmapped** in user processes, so dereferencing a NULL pointer traps instead of silently reading memory (→ S1).

### Shared pages

Two processes can map **the same physical frame** into their page tables. Uses:

- **Shared code:** code that is **reentrant** (never modifies itself) can be shared. 40 users running the same editor need only one copy of its code in RAM, plus 40 private copies of its data. Shared libraries (← OS-6.2) work the same way.
- **Shared memory IPC** (← OS-2.4): `shm_open` + `mmap` map the same frames into both processes.
- **Copy-on-write** after `fork()` (← OS-2.3, → OS-7.2).

### Page size trade-offs

| Smaller pages | Larger pages |
|---|---|
| Less internal fragmentation (average half a page per region) | Smaller page tables (fewer entries) |
| Finer-grained memory use and protection | Fewer TLB misses (more memory covered per TLB entry → OS-6.5) |
| More page-table entries; more page faults | More efficient disk I/O per page transfer |

The common page size is **4 KB** (x86, ARM, most Linux systems); ARM64 also supports 16 KB and 64 KB (Apple silicon uses 16 KB). **Huge pages** of 2 MB and 1 GB on x86-64 reduce TLB pressure for large-memory programs (→ OS-7.7). `getconf PAGESIZE` shows the size on Linux.

A classic exam formula: with average process size s, PTE size e, and page size p, the overhead per process is `s·e/p` (page table) + `p/2` (internal fragmentation), minimized when **p = √(2se)** (N8).

### The two problems with simple paging

1. **Speed:** every memory access now needs **two** memory accesses: one to read the PTE, one for the actual data. That would halve performance. Solution: the **TLB** (→ OS-6.5).
2. **Size:** a linear page table for a 32-bit address space with 4 KB pages has 2²⁰ entries; at 4 bytes each that is **4 MB per process**, mostly describing unused pages. For 64-bit address spaces it is impossibly large. Solution: **multilevel and other page-table structures** (→ OS-6.6).

## OS-6.5 · The Translation Lookaside Buffer (TLB)

### What it is

The **TLB** is a small, fast hardware cache inside the MMU that stores **recent virtual-to-physical translations** (page number → frame number plus protection bits). It is sometimes called an address-translation cache.

- Very small: typically 32 to 128 entries in the first-level TLB, plus a second-level TLB of about 1,000 to 2,000 entries on modern x86 cores.
- **Fully associative** or highly set-associative: all entries are compared with the page number in parallel, so a lookup takes a fraction of a clock cycle to a cycle, fast enough to be part of the instruction pipeline.

### Translation with a TLB

```
 CPU generates virtual address (p, d)
        |
        v
   +-----------+   hit    frame f
   |    TLB    | --------------------------------> physical address (f, d)
   +-----------+
        | miss
        v
   walk the page table in memory (1 or more memory accesses)
   -> if the PTE is invalid: page fault (-> OS-7.1)
   -> otherwise insert (p -> f) into the TLB (evicting an entry), retry
```

On a hit, translation costs almost nothing. On a miss, the page table must be read from memory (and possibly the cache).

**Who handles a miss?**

- **Hardware-managed TLB** (x86, ARM): the MMU contains a **page-table walker** that reads the page table itself, using the format the hardware defines. The OS only maintains the tables.
- **Software-managed TLB** (MIPS, older SPARC): a miss raises an exception; an OS handler looks up the page table (in any format the OS likes) and loads the entry with special privileged instructions. Flexible, but the handler must be carefully placed so that it cannot itself cause a TLB miss (MIPS keeps kernel code in an unmapped region; entries can also be "wired" so they are never evicted). OSTEP describes both.

### Why TLBs work: locality

OSTEP's example: an array of 10 four-byte integers starting at virtual address 100, with tiny 16-byte pages. The array spans three pages: a[0] to a[2] on the first, a[3] to a[6] on the second, a[7] to a[9] on the third. Summing it in a loop, the TLB misses on the first access to each page and hits on the others:

```
 a[0] miss, a[1] hit, a[2] hit, a[3] miss, a[4] hit, a[5] hit, a[6] hit, a[7] miss, a[8] hit, a[9] hit
```

Hit rate 70%, from **spatial locality** (elements on the same page). With realistic 4 KB pages, a sequential scan of an int array misses only once per 1,024 elements. **Temporal locality** (running the loop again soon) makes the second pass hit 100%.

### Effective access time (EAT)

Let:

- `h` = TLB hit ratio
- `t` = TLB lookup time
- `m` = memory access time

With a single-level page table:

```
 EAT = h (t + m) + (1 − h) (t + 2m)
```

- Hit: TLB lookup, then one memory access for the data.
- Miss: TLB lookup, one access to read the PTE, one access for the data.

Many textbook problems ignore `t` (treating it as negligible): `EAT = h·m + (1 − h)·2m`. Some add the TLB time only once, as above. **Read carefully which convention a question uses.**

With a **k-level** page table, a miss costs `t + k·m + m = t + (k + 1)m` (one access per level, plus the data).

Example: t = 20 ns, m = 100 ns, h = 80%: EAT = 0.8 × 120 + 0.2 × 220 = **140 ns** (40% slower than raw memory). At h = 98%: 0.98 × 120 + 0.02 × 220 = **122 ns**. Real hit ratios are typically above 99% for most workloads. See N4.

### TLBs and context switches

TLB entries belong to one address space: page 5 of process A and page 5 of process B are different. On a context switch, options:

1. **Flush the TLB** (invalidate all entries). Simple, but the new process starts with a cold TLB and suffers many misses (part of the indirect cost of a context switch ← OS-2.2).
2. **Address-space identifiers (ASIDs):** each TLB entry is tagged with the ID of its address space. The TLB matches only entries whose ASID equals the current one, so entries from several processes coexist and no flush is needed. On x86 these are called **PCIDs** (process-context identifiers).

Kernel pages, which are identical in every address space, can be marked **global** so they are not flushed.

Switching between **threads of the same process** changes neither the page table nor the TLB contents (← OS-2.5).

### TLB reach

**TLB reach** = number of entries × page size: the amount of memory that can be accessed without TLB misses.

- 64 entries × 4 KB = **256 KB**
- 64 entries × 2 MB huge pages = **128 MB**

A program whose working set is much larger than the TLB reach, and which accesses it randomly (hash tables, graph traversal, databases), suffers constant TLB misses. Remedies: **huge pages** (2 MB / 1 GB on x86-64; Linux transparent huge pages → OS-7.7), larger or multi-level TLBs, and better locality in the program.

### Keeping TLBs consistent

When the OS changes a PTE (unmaps a page, changes its permissions, evicts it), any cached TLB copy becomes stale and must be invalidated (x86 `invlpg` for one entry). On a multiprocessor, other CPUs may have cached the same entry, so the OS must send **inter-processor interrupts** asking them to invalidate it too. This is a **TLB shootdown**, and it is expensive on large machines (→ S11).

## OS-6.6 · Page Table Structures

### The size problem

A single linear page table needs one entry for **every page in the address space**, used or not:

- 32-bit address space, 4 KB pages → 2²⁰ pages × 4-byte PTE = **4 MB per process**.
- 48-bit address space, 4 KB pages → 2³⁶ pages × 8-byte PTE = **512 GB per process**. Impossible.

Most of the address space is unused (the gap between heap and stack), so most entries would be invalid. The structures below avoid storing them.

(A naive alternative is simply using larger pages: 16 KB pages cut the table by 4×, but increase internal fragmentation. OSTEP also discusses a hybrid of paging and segmentation with one page table per segment; it helps, but brings back external fragmentation for the page tables themselves.)

### Hierarchical (multilevel) page tables

**Page the page table.** Split the linear page table into page-sized pieces, and keep an **outer page table** (page directory) that points to them. If an entire piece would contain only invalid entries, it is **not allocated at all**, and the directory entry is marked invalid.

**Two-level paging for 32-bit x86** (4 KB pages, 4-byte entries, so one page holds 1,024 entries):

```
 virtual address (32 bits):  | p1 (10 bits) | p2 (10 bits) | d (12 bits) |

 CR3 --> page directory [p1] --> page table [p2] --> frame f  -->  physical = f | d
         (1024 entries)           (1024 entries)
```

1. `p1` indexes the page directory to find the page table.
2. `p2` indexes that page table to find the frame.
3. Combine the frame with offset `d`.

A process using only a little memory at the bottom (code, heap) and at the top (stack) needs the directory plus a few inner tables: kilobytes instead of 4 MB (N2).

**x86-64 (four-level paging):** 48-bit virtual addresses (256 TB), 4 KB pages, 8-byte entries, so each table has 512 entries (9 bits of index):

```
 | unused (16) | PML4 (9) | PDPT (9) | PD (9) | PT (9) | offset (12) |
```

- Each table is exactly one 4 KB page.
- **Huge pages** end the walk early: a PD entry with the "page size" bit maps a **2 MB** page directly (offset = 21 bits), and a PDPT entry can map **1 GB**.
- Newer CPUs support **five-level paging** (57-bit addresses, 128 PB). Linux abstracts these levels as `pgd → p4d → pud → pmd → pte`.
- The top 16 bits must be copies of bit 47 ("canonical addresses"); the lower half of the space is user space and the upper half kernel space.

**Cost:** a TLB miss now requires one memory access **per level** (4 or 5 on x86-64) before the data access. CPUs reduce this with caches of intermediate page-table entries (page-walk caches) and normal data caches holding page-table lines. This is a classic **time-space trade-off**: smaller tables, slower misses, which makes a high TLB hit rate even more important.

**How many levels?** Each level's table fits in one page. With page size P and entry size E, each level resolves log₂(P/E) bits. Levels = ⌈(virtual page-number bits) / log₂(P/E)⌉ (N3).

### Hashed page tables

Common for address spaces larger than 32 bits in some architectures. The virtual page number is **hashed** into a table; each bucket holds a linked list of entries `(virtual page number, frame number, next)`. Translation hashes the page number and walks the chain looking for a match.

Variant: **clustered page tables**, where each entry maps several consecutive pages (for example 16), which suits sparse address spaces where used memory comes in clusters.

### Inverted page tables

Instead of one table per process with one entry per **virtual page**, keep **one table for the whole system** with one entry per **physical frame**:

```
 entry i  =  (process id, virtual page number)   stored in frame i
```

Translation of `(pid, p, d)`: search the table for an entry matching `(pid, p)`. If it is at index i, the physical address is `(i, d)`. If none matches, it is a page fault (or illegal access).

- **Pro:** table size is proportional to **physical memory**, independent of the number of processes and the size of their address spaces (N2).
- **Con:** searching is slow, so a **hash table** is used to find the entry (plus the TLB for speed).
- **Con:** **sharing** is awkward: each frame has exactly one entry, so it can hold only one (pid, page) mapping at a time. Shared memory needs extra mechanisms.
- The OS still needs per-process information about pages that are not in memory (for demand paging), stored separately.
- Used by IBM PowerPC (hashed), IA-64 (as an option), and UltraSPARC.

### Comparison

| Structure | Size depends on | TLB-miss cost | Sharing | Examples |
|---|---|---|---|---|
| Linear (single-level) | Virtual address space | 1 access | Easy | 16/32-bit small systems |
| Multilevel | Pages actually used | 1 per level | Easy | x86, x86-64, ARM |
| Hashed | Pages actually used | Hash + chain walk | Easy | Some 64-bit systems |
| Inverted | Physical memory | Hash search | Hard | PowerPC, IA-64 |

## OS-6.7 · Segmentation

### The programmer's view

Programmers think of a program not as a flat array of bytes but as a collection of logical units: code, global data, heap, stack, each library, each large array. **Segmentation** supports that view: the address space is a collection of **variable-size segments**, each with a name (number) and a length.

A logical address is a pair: **(segment number s, offset d)**.

### Hardware: the segment table

Each process has a **segment table**; each entry has:

- **Base:** starting physical address of the segment
- **Limit:** length of the segment
- Protection bits (read, write, execute), and optionally a direction bit (does the segment grow up or down?)

The **segment-table base register (STBR)** points to the table, and a **segment-table length register (STLR)** holds the number of segments.

```
 (s, d) --> is s < STLR?  --no--> trap
               |yes
               v
           entry = table[s]
               |
           is d < limit? --no--> trap (segmentation fault)
               |yes
               v
           physical = base + d
```

Example: segment 2 has base 4300, limit 400. Address (2, 53) → 4353. Address (2, 500) → trap. (More in N7.)

Segmentation is base-and-limit relocation (← OS-6.1) with **one pair per segment** instead of one per process.

### OSTEP's version: segments selected by address bits

OSTEP shows segmentation with a normal flat virtual address whose **top bits select the segment**. With a 14-bit address and 3 segments (code `00`, heap `01`, stack `11`), the top 2 bits choose the segment and the remaining 12 bits are the offset (up to 4 KB per segment).

The **stack grows downward**, so the hardware also needs a direction bit. For a stack segment with base 28 KB (the highest address plus one) and current size 2 KB, virtual address 15 KB (binary `11 1100 0000 0000`) has segment `11` and offset 3 KB. For a negative-growing segment, the effective offset is 3 KB − 4 KB (the maximum segment size) = **−1 KB**, so the physical address is 28 KB − 1 KB = **27 KB**. The bounds check requires |−1 KB| ≤ 2 KB (the current size): valid.

### Advantages

- **Sparse address spaces:** only segments that exist take physical memory; the huge gap between heap and stack costs nothing (unlike base and bounds).
- **Protection per segment:** code read-only and executable, data non-executable, matching the program's structure.
- **Sharing whole segments:** a code segment of a shared program or library can be shared by pointing several processes' segment tables at the same base.

### Disadvantages

- Segments have **variable sizes**, so physical memory develops **external fragmentation**, exactly like variable partitions (← OS-6.3), requiring compaction or clever allocation.
- A large, sparsely used segment (such as a big heap with few live objects) must still be entirely in memory.
- Programmers or compilers must deal with segment numbers (unless the top-bits scheme is used).

### Segmentation with paging

To get segmentation's logical structure and paging's freedom from external fragmentation, **page each segment**: the segment table points to a page table for that segment, not to a contiguous region.

- **Multics** (1960s): segmentation with paging, a direct ancestor of many ideas in UNIX.
- **Intel IA-32 (x86, 32-bit):** a logical address (segment selector + offset) goes through the **segmentation unit** to produce a **linear address**, which then goes through the **paging unit** to produce a physical address.
  - A **segment selector** (16 bits: 13-bit index, 1 bit choosing the global or local descriptor table (GDT/LDT), 2-bit requested privilege level) chooses a **segment descriptor** holding base, limit, and access rights.
- **x86-64 in 64-bit mode** essentially disables segmentation: segment bases are treated as 0 and limits are not checked (a **flat** address space), except for the FS and GS registers, which Linux and Windows use to point at **thread-local storage** and per-CPU kernel data (← OS-2.6). Memory protection is done entirely with paging.

So on modern x86-64 Linux, a "segmentation fault" (`SIGSEGV`) is really a **page-level** protection violation; the name survives from systems where segments did the checking (→ S8).

### Comparison of memory-management schemes

| | Contiguous (base/limit) | Segmentation | Paging | Segmented paging |
|---|---|---|---|---|
| Unit | Whole process | Variable-size segments | Fixed-size pages | Pages within segments |
| External fragmentation | Yes | Yes | **No** | No |
| Internal fragmentation | With fixed partitions | No | Last page of each region | Last page of each segment |
| Sparse address space | No | Yes | Yes | Yes |
| Sharing | Hard | Per segment | Per page | Both |
| Hardware | Base + limit registers | Segment table | Page table + TLB | Both |
| Examples | Early systems | Burroughs, 8086 (segments without protection) | Modern x86-64, ARM | Multics, 32-bit x86 |

## Quick Revision Sheet

- Goals: transparency, efficiency, protection.
- Binding: compile time (absolute), load time (relocatable), execution time (MMU; allows moving processes).
- Logical/virtual address generated by the CPU; physical address seen by memory. Pointers in C are virtual.
- Base/limit: physical = virtual + base, trap if virtual ≥ limit. Registers changed only in kernel mode, saved/restored on context switch.
- Static linking copies libraries into the executable; dynamic linking shares one copy of library code (PIC, PLT/GOT, lazy binding). `dlopen` = dynamic loading.
- Swapping whole processes is slow; modern systems swap pages; mobile OSes kill apps instead.
- Placement: first fit (fast), best fit, worst fit (usually worst), next fit.
- External fragmentation: free memory in unusable holes (variable-size allocation). Internal: waste inside allocated blocks (fixed-size units). 50-percent rule: ~1/3 lost.
- Compaction needs execution-time binding.
- Paging: frames and pages same size; address = page number | offset; physical = frame | offset. No external fragmentation; half a page internal on average.
- PTE: frame number, valid, protection (R/W/NX), user/supervisor, dirty, accessed.
- PTBR (CR3) switched on context switch. Shared pages: reentrant code, shared libraries, shared memory, COW.
- TLB: cache of translations; EAT = h(t + m) + (1 − h)(t + 2m); k-level miss costs (k + 1) memory accesses.
- ASID/PCID avoids TLB flushes; TLB reach = entries × page size; huge pages increase reach; TLB shootdown on multiprocessors.
- 32-bit linear page table = 4 MB. Multilevel tables allocate only used parts; x86-64 has 4 levels of 9 bits + 12-bit offset.
- Levels = ⌈page-number bits / log₂(page size / PTE size)⌉.
- Inverted page table: one entry per frame (pid, page); size ∝ physical memory; sharing is hard.
- Segmentation: (segment, offset), base + limit per segment; logical view, per-segment protection, external fragmentation.
- x86-64 is flat (paging only, FS/GS for TLS); "segfault" is a historical name.

## Worked Numerical Problems

### N1 · Paging address translation (OS-6.4)

**Question.** A system uses 16-bit virtual addresses and 1 KB pages. A process's page table is:

| Page | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| Frame | 5 | 2 | 7 | invalid | 9 | 1 |

(a) How many bits are used for page number and offset, and how many pages can the address space have? (b) Translate virtual addresses 2500, 0x0C2F, and 0x1432. (c) What physical address does virtual address 4095 map to?

**Answer.**

(a) Page size 2¹⁰ → **10 offset bits**; 16 − 10 = **6 page-number bits**; 2⁶ = **64 pages**.

(b)
- **2500:** page = ⌊2500 / 1024⌋ = 2, offset = 2500 − 2048 = 452. Frame 7 → 7 × 1024 + 452 = 7168 + 452 = **7620**.
- **0x0C2F** = 3119: page = 3, offset = 3119 − 3072 = 47. Page 3 is **invalid → trap** (page fault or segmentation fault, depending on whether the page is on disk or simply not part of the address space).
- **0x1432** = `0001 0100 0011 0010`. Top 6 bits `000101` = page 5; low 10 bits `00 0011 0010` = 0x032 = 50. Frame 1 → 1024 + 50 = 1074 = **0x0432**. (In hex, only the page bits change.)

(c) 4095: page 3 (3072 to 4095), offset 1023. Page 3 is invalid: **trap**.

### N2 · Page table sizes (OS-6.4, OS-6.6)

**Question.** (a) 32-bit virtual addresses, 4 KB pages, 4-byte PTEs: size of a single-level page table? (b) 48-bit virtual addresses, 4 KB pages, 8-byte PTEs, single level? (c) Using two-level paging for (a) (10 | 10 | 12), a process uses 8 MB of code and data starting at address 0, and a 4 MB stack at the top of the address space. How much memory do its page tables take? (d) A machine with 16 GB of physical memory and 4 KB frames uses an inverted page table with 8-byte entries. How big is it, and how does it change with 500 processes instead of 50?

**Answer.**

(a) 2³² / 2¹² = 2²⁰ entries × 4 B = **4 MB** per process.

(b) 2⁴⁸ / 2¹² = 2³⁶ entries × 8 B = 2³⁹ B = **512 GB** per process. Hence multilevel tables.

(c) Each inner page table (1,024 entries × 4 B = 4 KB) maps 1,024 × 4 KB = **4 MB**.
- 8 MB of code/data → 2 inner tables. 4 MB of stack → 1 inner table.
- Plus the outer page directory: 4 KB.
- Total = 4 KB + 3 × 4 KB = **16 KB**, versus 4 MB for a linear table (256× smaller).

(d) 16 GB / 4 KB = 2³⁴ / 2¹² = 2²² frames = 4,194,304 entries × 8 B = **32 MB** for the whole system. It does **not change** with the number of processes: its size depends only on physical memory.

### N3 · How many levels? (OS-6.6)

**Question.** (a) Virtual addresses are 46 bits, the page size is 8 KB, and a PTE is 4 bytes. If each page-table level must fit in one page, how many levels are needed? (b) Verify that x86-64's 48-bit addresses with 4 KB pages and 8-byte PTEs need 4 levels. (c) For (b), how many memory accesses does a TLB miss cost, and what about with 2 MB pages?

**Answer.**

(a) Offset = log₂(8 KB) = 13 bits. Page-number bits = 46 − 13 = 33. Entries per page = 8 KB / 4 B = 2,048 = 2¹¹, so each level resolves 11 bits. Levels = ⌈33 / 11⌉ = **3**.

(b) Offset 12 bits; page-number bits 36. Entries per page = 4 KB / 8 B = 512 = 2⁹, so 9 bits per level. Levels = 36 / 9 = **4** ✓.

(c) 4 accesses for the walk + 1 for the data = **5 memory accesses** (without page-walk caches). With 2 MB pages, the walk stops at the PD level: **3 + 1 = 4** accesses, and each TLB entry covers 512× more memory.

### N4 · Effective access time (OS-6.5)

**Question.** Memory access time is 100 ns and TLB lookup is 20 ns. (a) Single-level page table, hit ratio 80%: EAT? (b) Hit ratio 98%? (c) Four-level page table, hit ratio 98%? (d) Ignoring TLB time (a common exam convention), what hit ratio gives an EAT of 110 ns with a single-level table?

**Answer.**

(a) 0.80 × (20 + 100) + 0.20 × (20 + 200) = 96 + 44 = **140 ns**.

(b) 0.98 × 120 + 0.02 × 220 = 117.6 + 4.4 = **122 ns**.

(c) A miss costs 20 + 4 × 100 + 100 = 520 ns. EAT = 0.98 × 120 + 0.02 × 520 = 117.6 + 10.4 = **128 ns**.

(d) h × 100 + (1 − h) × 200 = 110 → 200 − 100h = 110 → **h = 0.9** (90%).

A deeper page table barely matters **if** the hit rate is high; at low hit rates, every extra level hurts a lot.

### N5 · TLB reach and hit rate (OS-6.5)

**Question.** (a) A TLB has 64 entries. What is its reach with 4 KB pages and with 2 MB pages? (b) A program sums a 4 MB array of 4-byte integers sequentially, once. With 4 KB pages and an empty TLB at the start, how many TLB misses occur and what is the hit rate? (c) The program instead reads 1 million random elements of a 1 GB array. Estimate the hit rate with 4 KB pages and with 2 MB pages.

**Answer.**

(a) 64 × 4 KB = **256 KB**. 64 × 2 MB = **128 MB**.

(b) 4 MB / 4 KB = 1,024 pages, so **1,024 misses** (one per page). Accesses = 4 MB / 4 B = 1,048,576. Hit rate = 1 − 1,024 / 1,048,576 ≈ **99.9%** (one miss per 1,024 accesses).

(c) With 4 KB pages, the TLB covers 256 KB of the 1 GB array, about 0.024%; a random access almost always misses: hit rate ≈ **0%**. With 2 MB pages, reach = 128 MB = 1/8 of the array: hit rate ≈ **12.5%** (at best, if the TLB holds 64 of the 512 huge pages). Random access over a large working set defeats the TLB; huge pages reduce the damage (and each miss is cheaper, with one fewer level).

### N6 · Placement strategies (OS-6.3)

**Question.** Memory holes, in address order: 100 KB, 500 KB, 200 KB, 300 KB, 600 KB. Requests arrive in order: 212 KB, 417 KB, 112 KB, 426 KB. Show where each goes under first fit, best fit, worst fit, and next fit.

**Answer.**

**First fit:**
- 212 → 500 (leaves 288). Holes: 100, 288, 200, 300, 600.
- 417 → 600 (leaves 183). Holes: 100, 288, 200, 300, 183.
- 112 → 288 (leaves 176). Holes: 100, 176, 200, 300, 183.
- 426 → **no hole large enough: must wait.**

**Best fit:**
- 212 → 300 (leaves 88). Holes: 100, 500, 200, 88, 600.
- 417 → 500 (leaves 83). Holes: 100, 83, 200, 88, 600.
- 112 → 200 (leaves 88). Holes: 100, 83, 88, 88, 600.
- 426 → 600 (leaves 174). **All four placed.**

**Worst fit:**
- 212 → 600 (leaves 388). Holes: 100, 500, 200, 300, 388.
- 417 → 500 (leaves 83). Holes: 100, 83, 200, 300, 388.
- 112 → 388 (leaves 276). Holes: 100, 83, 200, 300, 276.
- 426 → **must wait.**

**Next fit** (search continues from the last allocation):
- 212 → 500 (leaves 288); pointer stays at this hole.
- 417 → 288 no, 200 no, 300 no, 600 yes (leaves 183).
- 112 → continue from there: 183 yes (leaves 71).
- 426 → wrap around: 100, 288, 200, 300, 71: **must wait.**

Here best fit is the only strategy that satisfies all requests, because it preserved the 600 KB hole. With other request sequences, first fit can win; neither dominates.

### N7 · Segmentation translation (OS-6.7)

**Question.** A segment table:

| Segment | Base | Limit |
|---|---|---|
| 0 | 219 | 600 |
| 1 | 2300 | 14 |
| 2 | 90 | 100 |
| 3 | 1327 | 580 |
| 4 | 1952 | 96 |

Translate: (a) (0, 430) (b) (1, 10) (c) (2, 500) (d) (3, 400) (e) (4, 112).

**Answer.**

(a) 430 < 600 → 219 + 430 = **649**.
(b) 10 < 14 → 2300 + 10 = **2310**.
(c) 500 ≥ 100 → **trap** (segmentation fault).
(d) 400 < 580 → 1327 + 400 = **1727**.
(e) 112 ≥ 96 → **trap**.

Note the check is offset < limit (strictly): offset 96 would also trap for segment 4, because valid offsets are 0 to 95.

### N8 · Internal fragmentation and page size (OS-6.4)

**Question.** (a) A process of 72,766 bytes is loaded with 2,048-byte pages. How many frames does it need, and how much internal fragmentation results? (b) Average process size is 1 MB and PTEs are 8 bytes. Using overhead = s·e/p + p/2, find the page size that minimizes overhead per process. (c) What is the overhead at that page size?

**Answer.**

(a) 72,766 / 2,048 = 35 full pages (71,680 bytes) plus 1,086 bytes. So **36 frames**; internal fragmentation = 2,048 − 1,086 = **962 bytes**. Worst case would be a process of 35 pages + 1 byte, wasting 2,047 bytes.

(b) Differentiate: −s·e/p² + 1/2 = 0 → p = √(2se) = √(2 × 2²⁰ × 8) = √(2²⁴) = 2¹² = **4,096 bytes** (4 KB).

(c) Page-table overhead = 2²⁰ × 8 / 4,096 = 2,048 B; fragmentation = 4,096 / 2 = 2,048 B. Total ≈ **4 KB** per process: tiny relative to 1 MB, which is part of why 4 KB pages became standard. (The formula ignores TLB effects, which favour larger pages today.)

## Scenario Questions (Test Your Understanding)

### S1 · Why NULL crashes (OS-6.4)

`int *p = NULL; *p = 5;` crashes immediately with a segmentation fault on Linux. Physical address 0 exists in RAM. Why does the access fail, and what would happen on a system without memory protection?

<details><summary>Answer</summary>

`p` holds **virtual** address 0, on virtual page 0. The OS deliberately leaves the lowest pages of every user address space **unmapped** (Linux refuses user mappings below `vm.mmap_min_addr`, typically 64 KB). The MMU finds an invalid PTE, raises a page fault; the kernel sees the address is not part of any mapping and sends `SIGSEGV`.

Without protection (MS-DOS in real mode), address 0 is a real location (the interrupt vector table on x86 real mode). The write would silently corrupt it, and the machine would misbehave later, far from the bug. Leaving page 0 unmapped turns a silent corruption into an immediate, debuggable crash. Keeping it unmapped also blocks a class of kernel exploits that tricked the kernel into dereferencing NULL while an attacker controlled page 0.

</details>

### S2 · The overflow that did not crash (OS-6.4)

A program allocates `char *buf = malloc(100)` and writes 200 bytes into it. It does not crash. Writing 100,000 bytes does crash. Why the difference, and why do tools like AddressSanitizer exist?

<details><summary>Answer</summary>

Protection is enforced at **page granularity**. `buf` lies somewhere inside a heap page (4 KB) that is mapped and writable, together with other heap blocks and `malloc`'s bookkeeping. Writing 100 bytes past the end stays inside mapped, writable pages: the MMU sees nothing wrong, but the program silently corrupts neighbouring objects or allocator headers, which may cause a crash much later (or a security hole). Writing 100,000 bytes eventually runs past the end of the mapped heap into an unmapped page, and faults.

AddressSanitizer (and similar tools) add **byte-granularity** checks in software, using shadow memory and "red zones" around allocations, so overflows are caught at the faulting instruction.

</details>

### S3 · Compaction needs the right binding (OS-6.1, OS-6.3)

An old system uses load-time binding: the loader patches every address in the program with its actual location. The system has plenty of free memory in total but cannot start a new program because of fragmentation. Why can it not compact memory? What hardware feature would allow it?

<details><summary>Answer</summary>

With load-time binding, the running program contains **absolute physical addresses** everywhere: in instructions, in pointers stored in its data, on its stack, in registers. Moving it would require finding and fixing every such address, including pointer values computed at run time, which is not possible reliably.

With **execution-time binding** (a relocation/base register in the MMU), the program only ever uses addresses relative to its base. Compaction copies its memory elsewhere and changes one register value. (With paging, compaction is unnecessary: any free frame can be used.)

</details>

### S4 · Same work, very different speed (OS-6.5)

Two programs sum all elements of the same 2 GB array. Program A reads it sequentially. Program B reads the elements in a random order. Both do the same number of additions, but B is about 10 to 20 times slower. Explain the role of the TLB (and caches), and suggest an OS-level change that helps B.

<details><summary>Answer</summary>

A has perfect spatial locality: each 4 KB page's TLB entry serves 1,024 consecutive integer reads, so TLB misses are about 0.1% of accesses, and hardware prefetching keeps the caches full.

B touches a random page on almost every access. 2 GB is 524,288 pages, far beyond TLB reach (a few MB even with a large second-level TLB), so nearly every access is a TLB miss requiring a multi-level page walk, and a data cache miss as well.

Using **huge pages** (2 MB: the whole array is only 1,024 pages, and 1 GB pages would need just 2) makes TLB misses far rarer and each walk one level shorter. On Linux, via transparent huge pages or `madvise(MADV_HUGEPAGE)`/`hugetlbfs` (→ OS-7.7). Cache misses remain, so B is still slower than A, but much less so.

</details>

### S5 · Threads switch faster than processes (OS-6.5, OS-2.5)

Explain precisely, in terms of the MMU, why a context switch between two threads of the same process is cheaper than one between two processes, and how PCIDs change the comparison.

<details><summary>Answer</summary>

Between threads of one process, the page table does not change: CR3 is not reloaded, and every TLB entry stays valid. The incoming thread finds translations for shared code and data already cached.

Between processes, CR3 must point to a new page table. Without tagging, the TLB must be **flushed** (except global kernel entries), so the new process starts with a cold TLB and pays many page walks.

With **PCIDs** (ASIDs), TLB entries are tagged with their address space, so switching processes does not require a flush; if the process ran recently, some of its entries may still be there. The gap shrinks, but threads still win: they share one set of entries, and caches hold the same code and data.

</details>

### S6 · Fifty copies of libc? (OS-6.2, OS-6.4)

A server runs 50 processes, all dynamically linked against the C library (about 2 MB of code and 50 KB of writable data). Roughly how much physical memory does libc use, and how do page tables make that possible? What would change with static linking?

<details><summary>Answer</summary>

The **code pages** of libc are read-only and position-independent, so every process's page table maps them to the **same physical frames**: about 2 MB total. The **writable data** (globals, GOT) is private: each process gets its own copy, initially shared copy-on-write and copied only when written, up to about 50 × 50 KB = 2.5 MB. Total roughly 4.5 MB instead of 50 × 2 MB = 100 MB.

With static linking, each executable contains its own copy of the needed libc code. Processes running the **same** executable still share its code pages, but 50 **different** static programs would each have their own copy in RAM.

</details>

### S7 · 16 GB of RAM, 3 GB usable (OS-6.1, OS-6.6)

A 32-bit program on a 16 GB machine fails to allocate more memory after about 3 GB, while plenty of physical memory remains free. Why? Would running a 32-bit Linux kernel with PAE fix it?

<details><summary>Answer</summary>

The limit is the program's **virtual address space**: 32-bit addresses give 4 GB, and a 32-bit Linux kernel traditionally reserves the top 1 GB for itself (the 3 GB / 1 GB split), leaving about 3 GB for code, heap, stack, and libraries. Physical memory does not matter; the process has run out of addresses.

**PAE** (Physical Address Extension) lets a 32-bit kernel use up to 64 GB of **physical** memory by using wider page-table entries (36-bit frame addresses, three-level tables). But each process's virtual address space is still 32 bits, so a single process still cannot exceed about 3 GB; PAE only helps many processes together use more RAM. The real fix is a 64-bit build.

</details>

### S8 · Where are the segments? (OS-6.7)

A student asks: "On my x86-64 Linux laptop, why is the error called a *segmentation* fault, if Linux uses paging and not segmentation?" Answer, and name the one place x86-64 Linux still uses segment registers.

<details><summary>Answer</summary>

The name is historical. On early UNIX machines (like the PDP-11) and on systems with real segmentation, accesses outside a segment's limit caused the fault. The signal kept its name (`SIGSEGV`). On x86-64 in 64-bit mode, segment bases are treated as 0 and limits are not checked, so all protection comes from **page tables**; today the signal means "access to a virtual address that is unmapped or not permitted."

The exception is **FS and GS**, whose bases can still be set. Linux user space uses FS to point at the current thread's **thread-local storage** (so `errno` is per-thread ← OS-2.6), and the kernel uses GS for per-CPU data.

</details>

### S9 · Inverted tables and shared memory (OS-6.6)

A system uses an inverted page table. Two processes want to share one page of memory through `shm_open` and `mmap`. Why is this harder than with per-process page tables, and how can a system handle it?

<details><summary>Answer</summary>

In an inverted table, frame i has exactly **one** entry holding one (pid, virtual page) pair. With per-process tables, sharing is trivial: both processes' PTEs simply contain the same frame number. With an inverted table, only one of the two mappings can be recorded for that frame at a time.

Workarounds: when the other process touches the page, fault and temporarily re-map the frame's entry to it (costly if both use it constantly); or add a separate structure (a chain of alias entries, or a global segment identifier, as PowerPC does by translating through a shared "virtual segment ID" first, so both processes map to the same system-wide virtual address before the inverted lookup).

</details>

### S10 · A million tiny allocations (OS-6.3)

A program calls `malloc(1)` one million times on 64-bit Linux, expecting to use about 1 MB. `ps` shows about 32 MB of heap. Where did the memory go? Which kind of fragmentation is this?

<details><summary>Answer</summary>

Each `malloc` block has a **header** (the allocator must record its size for `free`) and must be **aligned** (16 bytes on 64-bit systems), so glibc's smallest chunk is **32 bytes**: 8 bytes of header plus 24 usable bytes, of which the program uses 1. One million allocations therefore consume about 32 MB. This is **internal fragmentation** (waste inside allocated blocks) plus bookkeeping overhead.

Fixes: allocate one array of a million bytes, or use a pool / arena allocator for many small objects.

</details>

### S11 · Unmapping is slow on the big machine (OS-6.5)

A multithreaded program that frequently calls `munmap` runs fine on a 4-core laptop, but on a 128-core server `munmap` becomes a major bottleneck, with many inter-processor interrupts shown in profiling. Explain.

<details><summary>Answer</summary>

Removing a mapping changes PTEs. Any CPU running a thread of this process may have those translations cached in its **TLB**, and the hardware does not keep TLBs coherent automatically. Before the memory can be reused, the kernel must perform a **TLB shootdown**: send an inter-processor interrupt to every CPU that might hold stale entries, have each invalidate them, and wait for all acknowledgements. With 128 cores running the process's threads, each `munmap` interrupts many CPUs and waits for the slowest.

Fixes: unmap less often (reuse memory, batch frees, as `malloc` arenas do), keep the process's threads on fewer cores, or rely on kernel optimizations (batched and lazy shootdowns).

</details>

### S12 · Why the kernel lives in every address space (OS-6.4, OS-1.4)

Traditionally, Linux maps the entire kernel into the upper part of **every** process's virtual address space, marked supervisor-only. Why do this instead of giving the kernel its own separate address space? What changed after the Meltdown vulnerability (2018)?

<details><summary>Answer</summary>

On a system call or interrupt, the CPU switches to kernel mode but keeps the **same page table**, so the kernel's code and data are immediately accessible with no CR3 switch and no TLB flush. The kernel can also directly access the calling process's user memory (for `copy_from_user`). The user/supervisor bit prevents user code from touching those pages.

**Meltdown** showed that on many Intel CPUs, speculative execution could read supervisor-only memory before the permission check took effect, leaking kernel data through cache timing. The fix, **KPTI** (kernel page-table isolation), gives each process two page tables: the user-mode one maps almost none of the kernel, and every entry to and exit from the kernel switches CR3. This made system calls noticeably more expensive (← OS-1.5), with PCIDs used to limit the TLB-flush cost. CPUs designed after Meltdown do not need KPTI.

</details>
