# Unit 7: Virtual Memory

> **How to use this page.** Section IDs (`OS-7.3`) match the tags on practice questions. Arrows like **→ OS-9.6** point to where an idea is developed further; **← OS-6.4** points back to something this section depends on.

Unit 6 gave each process a private address space made of pages that can live in any physical frame. This unit takes the last step: a page does not have to be in physical memory **at all** until the process touches it. Pages can sit on disk and be brought in on demand. The result is **virtual memory**: programs can be larger than physical RAM, many more processes fit in memory at once, and process creation becomes cheap. The price is a new set of questions: which page to throw out when memory is full, how many frames each process should get, and what happens when the system runs out.

---

## OS-7.1 · Demand Paging

### The idea

Most of a program is not needed at any given moment: error-handling code, rarely used features, the unused part of a large array. **Demand paging** loads a page into memory **only when it is first accessed**. OSTEP describes it as the OS using disk (swap space) to give the illusion of a memory much larger than physical RAM.

Benefits:

- A program can be **larger than physical memory**.
- Each process uses less physical memory, so **more processes** fit, raising CPU utilization and throughput (← OS-1 N1).
- Less I/O to start a program: only the pages actually used are read.

The PTE's **valid (present) bit** now has a second meaning (← OS-6.4):

- `valid = 1`: the page is legal **and** in memory.
- `valid = 0`: the page is either not part of the address space, **or** legal but currently on disk. The OS records which one, and where on disk the page lives (often in the PTE itself or in its own data structures).

With **pure demand paging**, a process starts with **no** pages in memory: even its first instruction causes a fault.

### Handling a page fault

When the CPU accesses a page whose PTE is invalid, the MMU raises a **page-fault** exception (← OS-1.3: a *fault*, so the faulting instruction will be re-executed).

```
  1. reference ---------------------> page table: invalid
  2. trap to OS (page fault)
  3. OS: is the reference legal?  -- no --> SIGSEGV (terminate)
             | yes: page is on disk
  4. find a free frame (if none: run page replacement -> OS-7.3)
  5. schedule disk read of the page into the frame
     (process blocks; CPU runs someone else)
  6. disk interrupt: read done
  7. update PTE: frame number, valid = 1
  8. restart the faulting instruction
```

In more detail, the full sequence (Silberschatz lists these steps):

1. Trap to the OS; save user registers and process state.
2. Determine that the interrupt was a page fault; check that the reference was legal and find the page's location on disk.
3. Issue a read from disk into a free frame: wait in the device queue, wait for seek and rotational latency, then the transfer (→ OS-9.1).
4. While waiting, give the CPU to another process (a context switch).
5. Receive the disk interrupt; save the registers of whichever process was running; determine that the interrupt came from the disk.
6. Update the page table to show the page is now in memory.
7. Wait for the CPU to be allocated to this process again.
8. Restore registers and process state, and **re-execute the faulting instruction**.

The three big costs are servicing the interrupt (microseconds), **reading the page** (milliseconds on an HDD, tens to hundreds of microseconds on an SSD), and restarting the process. The disk read dominates everything else by far.

### Instruction restart

The hardware must be able to **restart any instruction** after a fault, as if it had never started. For most instructions this is easy: re-fetch and re-execute. It is harder for instructions that modify several locations, such as a block-move instruction (IBM System/360 `MVC`, which moves up to 256 bytes) whose source or destination crosses a page boundary. If it faults halfway, part of the destination has been overwritten, and if source and destination overlap, the source may have been modified too. Solutions: the microcode touches both ends of both blocks **before** modifying anything (so any fault happens before changes), or it saves the overwritten values in temporary registers so they can be restored.

### Minor and major faults

Linux distinguishes:

- **Major (hard) fault:** the page must be read from disk.
- **Minor (soft) fault:** the page is already in memory but not mapped in this process's page table. Examples: a shared library page already loaded by another process, a page still in the page cache, a newly allocated zero-filled page, a copy-on-write copy. It costs a trap and some kernel work, but no I/O.

`/usr/bin/time -v ./prog` reports both counts; `ps -o min_flt,maj_flt` shows them per process.

### Why demand paging works: locality

If processes touched pages randomly, every access might fault. They do not: programs exhibit **locality of reference** (← OS-1.3). At any time a process actively uses a small set of pages (the current function, its data, the stack top), and this set changes slowly. That set is its **locality**, and it is the foundation of the working-set model (→ OS-7.6).

### Effective access time with page faults

Let `ma` be the memory access time and `p` the probability that an access causes a page fault (0 ≤ p ≤ 1):

```
 EAT = (1 − p) × ma  +  p × (page-fault service time)
```

With ma = 200 ns and a fault service time of 8 ms:

```
 EAT = (1 − p) × 200 + p × 8,000,000   (ns)
     ≈ 200 + 7,999,800 × p
```

- If p = 1/1,000, EAT ≈ **8.2 µs**: the computer runs **40 times slower** because of paging.
- To keep the slowdown under 10% (EAT < 220 ns): 7,999,800 p < 20 → **p < 0.0000025**, fewer than one fault per 400,000 accesses.

The page-fault rate must be **extremely** low. That is why page replacement policy matters so much, and why a system that starts faulting frequently (thrashing → OS-7.6) collapses rather than slowing down gracefully. See N1.

### Swap space and backing store

Pages that are not in memory live on the **backing store**:

- **File-backed pages** (program code, memory-mapped files) can simply be re-read from their file. A clean code page can be discarded and read again from the executable.
- **Anonymous pages** (heap, stack, which have no file) must be written to **swap space** before their frame is reused (→ OS-9.6).

### Lazy allocation and overcommit

Demand paging also applies to newly allocated memory. When a program calls `malloc(1 GB)` (which uses `mmap`), Linux only reserves **virtual** address space; physical frames are allocated one page at a time when first written (**zero-fill-on-demand**: a new page is filled with zeros, never with another process's old data).

As a result, Linux allows processes to reserve more memory in total than RAM plus swap (**overcommit**, controlled by `vm.overcommit_memory`). This is usually fine because programs rarely touch everything they allocate. When memory actually runs out and nothing more can be reclaimed, the kernel's **OOM killer** picks a process (based on memory use and an adjustable score, `oom_score_adj`) and kills it to free memory (→ S1).

## OS-7.2 · Copy-on-Write and Memory-Mapped Files

### Copy-on-write (COW)

As mentioned in ← OS-2.3, `fork()` would be slow if it copied the entire address space, especially since the child usually calls `exec()` immediately. With **copy-on-write**:

1. `fork()` copies only the **page tables**. Parent and child PTEs point to the **same frames**, and all writable pages are marked **read-only** in both.
2. When either process **writes** to such a page, the MMU raises a protection fault.
3. The kernel sees that this is a COW page (the region is logically writable), allocates a new frame, copies the page, maps the copy (writable) into the faulting process, and restarts the instruction. If the other process is now the only user of the original frame, its mapping can simply be made writable again.

```
 After fork():                      After child writes page B:
 parent PT --> [A][B][C] <-- child PT   parent PT --> [A][B][C]
               (all read-only)          child PT  --> [A][B'][C]   B' = private copy
```

Consequences:

- `fork()` cost is proportional to the page-table size, not the memory size.
- Only pages that are actually modified are ever copied. Read-only pages (code) are never copied.
- The kernel needs a pool of free frames to allocate on COW faults; Linux fills new pages from this pool.
- **`vfork()`**: an older optimization in which the child uses the parent's address space directly (no copying at all) and the parent is suspended until the child calls `exec()` or `_exit()`. Dangerous if the child modifies memory, and largely unnecessary now that fork uses COW.

COW is used elsewhere too: `MAP_PRIVATE` file mappings (below), and copy-on-write file systems (→ OS-8.6).

### Memory-mapped files

`mmap()` maps a file into a process's address space, so the file's contents can be accessed with ordinary loads and stores instead of `read()` and `write()`.

```c
int fd = open("data.bin", O_RDWR);
struct stat st;
fstat(fd, &st);
char *p = mmap(NULL, st.st_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
p[100] = 'x';             // modifies the file (through the page cache)
msync(p, st.st_size, MS_SYNC);   // force changes to disk now (optional)
munmap(p, st.st_size);
close(fd);
```

How it works:

- `mmap` only sets up the mapping. Pages are loaded by **demand paging**: the first access to each page causes a page fault, and the kernel reads that page of the file.
- The file's pages are in the kernel's **page cache**; the process's page table points directly at those frames. There is no copy between a kernel buffer and a user buffer, unlike `read()`.
- Modified pages are written back to the file eventually (by the kernel's writeback threads), on `msync()`, or when unmapped.

**`MAP_SHARED` vs `MAP_PRIVATE`:**

| | `MAP_SHARED` | `MAP_PRIVATE` |
|---|---|---|
| Writes visible to other processes mapping the file | Yes | No |
| Writes reach the underlying file | Yes | No (copy-on-write: a private copy is made on first write) |
| Typical use | Shared memory IPC, editing files in place | Loading executables and shared libraries (data pages) |

**Anonymous mappings** (`MAP_ANONYMOUS`) are backed by no file: zero-filled memory. `malloc` uses them for large allocations. With `MAP_SHARED | MAP_ANONYMOUS` before `fork()`, parent and child share the region: a simple shared-memory IPC method (← OS-2.4). POSIX shared memory (`shm_open`) is an `mmap` of a file in the memory-backed file system `/dev/shm`.

**mmap vs read/write:**

| | `mmap` | `read` / `write` |
|---|---|---|
| Copies | None (maps the page cache) | Copy between kernel and user buffer |
| System calls | One setup call; then plain memory accesses | One per call |
| Random access to large files | Convenient (pointer arithmetic) | Needs `lseek`/`pread` |
| Errors | I/O errors appear as `SIGBUS` on access, awkward to handle | Returned as error codes |
| Small or sequential I/O | Page faults and TLB setup may cost more | Often faster |
| File size changes | Must re-map | Natural |

Programs are loaded this way: `execve` maps the executable's code segment with `MAP_PRIVATE` and read/execute permission; code pages are faulted in from the file as they execute. That is why starting a large program does not read all of it.

## OS-7.3 · Page Replacement

### The need

When a page fault occurs and **no frame is free**, the OS must choose a **victim** page to evict. Memory is over-allocated deliberately (that is the point of virtual memory), so this happens constantly on a busy system.

**Basic page replacement:**

1. Find the location of the desired page on disk.
2. Find a free frame. If none exists, choose a **victim frame** with a page-replacement algorithm. If the victim page is **dirty** (modified since it was loaded, ← OS-6.4 dirty bit), write it to disk first; update its PTE to invalid.
3. Read the desired page into the frame; update the page table.
4. Restart the faulting instruction.

If the victim is dirty, the fault needs **two** page transfers (write out, read in), doubling the service time. The dirty bit avoids unnecessary writes: a clean page's copy on disk is already up to date, so it is simply discarded. (Code pages are never dirty.)

In practice, the OS does not wait for a fault to find a free frame. OSTEP describes a background **swap daemon** (page daemon, Linux `kswapd`) with two watermarks: when free memory falls below the **low watermark**, the daemon evicts pages until free memory reaches the **high watermark**. This keeps a pool of free frames ready, and it lets the OS write out many dirty pages in one batch (→ page buffering below).

### Evaluating algorithms: reference strings

Algorithms are compared by counting page faults on a **reference string**: the sequence of pages a process accesses. Only page numbers matter (consecutive accesses to the same page count once, since the second cannot fault).

The goal: the **lowest page-fault rate**. As frames increase, faults should generally decrease (but see Belady's anomaly, → OS-7.4).

Throughout this section we use Silberschatz's reference string with **3 frames**:

```
 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1
```

Full traces are in N2.

### FIFO

Replace the page that has been in memory **longest** (the oldest loaded). Implemented with a queue.

- On the string above: **15 faults**.
- Simple, but the oldest page may be heavily used (such as a variable initialized at the start and used throughout), and evicting it causes an immediate fault.
- Suffers from **Belady's anomaly** (→ OS-7.4).

### Optimal (OPT, MIN)

Replace the page that **will not be used for the longest time** in the future (Belady, 1966).

- On the string above: **9 faults**, the minimum possible for 3 frames.
- **Provably optimal:** no algorithm can have fewer faults on any reference string.
- **Not implementable** in general: it needs knowledge of future references (like SJF needs future burst lengths ← OS-3.3). It is used as a **benchmark**: "within 10% of optimal" is a meaningful statement about a real algorithm.

### Least Recently Used (LRU)

Use the recent past as an approximation of the near future: replace the page that has **not been used for the longest time**. It is OPT looking backward in time instead of forward.

- On the string above: **12 faults**: better than FIFO, worse than OPT.
- It works well because of **temporal locality**: a page used recently is likely to be used again soon.
- LRU does **not** suffer from Belady's anomaly.

**Implementing exact LRU** is the problem. It needs to know the order of **every** memory access:

- **Counters (timestamps):** add a logical clock to the CPU; on every access, copy the clock into the PTE's "time of use" field. Replace the page with the smallest time. Requires a memory write on every access and a search on every replacement.
- **Stack:** keep a doubly linked stack of page numbers; on every access, move the page to the top. The bottom is the LRU page. Each access updates several pointers.

Either way, the hardware would need to do extra work on **every memory reference**; no real hardware does this (a software update on every access would slow memory down by 10× or more). So real systems use **approximations of LRU**.

### LRU approximations using the reference bit

Most hardware provides a **reference (accessed) bit** per PTE, set to 1 by the MMU whenever the page is read or written (← OS-6.4). The OS can clear it and later check whether it was set again. That tells us which pages were used *recently*, but not the order.

**Additional-reference-bits (aging).** Keep an 8-bit history byte per page. At regular intervals (say every 100 ms, on a timer interrupt), the OS shifts each page's byte right by one and moves the reference bit into the highest-order bit, then clears the reference bit.

```
 history 11000100  -> used in the last two intervals and 6 intervals ago
 history 01110111  -> not used in the last interval
 Interpreted as unsigned integers, the page with the SMALLEST value is the LRU approximation.
 11000100 (196) was used more recently than 01110111 (119).
```

**Second-chance (clock) algorithm.** A FIFO queue with a twist: when a page is selected for replacement, look at its reference bit.

- If 0: replace it.
- If 1: give it a **second chance**: clear the bit, and move on to the next page.

Implemented as a **circular list** of frames with a "clock hand" pointer:

```
 frames arranged in a circle; the hand points at the next candidate

      A(1)   B(1)   C(0)   D(1)   E(0)
       ^
      hand

 Need a victim: A has ref=1 -> clear to 0, advance
                B has ref=1 -> clear to 0, advance
                C has ref=0 -> evict C, load the new page there (ref=1),
                               hand moves to D
```

- A page that is used frequently keeps getting its bit set and is never replaced.
- **Worst case:** if every bit is set, the hand goes all the way around, clearing them all, and then replaces the page it started at: it degenerates to **FIFO** (N4).
- This is the basis of most real page-replacement implementations.

**Enhanced second-chance (reference bit, dirty bit).** Consider both bits as a pair and replace from the lowest nonempty class:

| Class | (ref, dirty) | Meaning | Replace? |
|---|---|---|---|
| 1 | (0, 0) | Neither recently used nor modified | **Best** victim: no write needed |
| 2 | (0, 1) | Not recently used, but dirty | Must be written first |
| 3 | (1, 0) | Recently used, clean | Probably needed again soon |
| 4 | (1, 1) | Recently used and dirty | Worst victim |

The clock may need to sweep several times to find a victim in the lowest class. Preferring clean pages saves I/O. Classic Mac OS used this scheme.

### Counting-based algorithms

Keep a count of references to each page:

- **LFU (least frequently used):** replace the page with the smallest count. Problem: a page heavily used early (for example during initialization) keeps a high count and is never evicted. Fix: periodically shift counts right (exponential decay).
- **MFU (most frequently used):** replace the page with the largest count, on the argument that a page with a small count was probably just brought in and has yet to be used.

Neither is common: they are expensive to implement and do not approximate OPT well.

### Page buffering

Refinements used alongside any algorithm:

- Keep a **pool of free frames**. On a fault, read the new page into a free frame immediately, then write out the victim later, so the process does not wait for the write.
- When the paging device is idle, **write dirty pages to disk in the background** (clearing their dirty bits), so that when they are later chosen as victims, they can be discarded without a write.
- Remember **which page was in each free frame**. If that page is referenced again before the frame is reused, it can be taken back without any I/O (a minor fault). VAX/VMS used this to compensate for its simple FIFO replacement.

### What real systems do

- **Linux** keeps pages on two LRU lists, **active** and **inactive**, per memory zone (separately for anonymous and file-backed pages). New pages go on the inactive list; a page referenced again while inactive is promoted to active; the kernel moves unreferenced pages from active to inactive and reclaims from the tail of inactive. This is a clock-like approximation that also resists **scan pollution**: a single sequential scan of a huge file touches each page once, so those pages never leave the inactive list and do not push out the frequently used working set (→ S7). Since Linux 6.1, **MGLRU** (multi-generational LRU) generalizes this to several generations.
- **Windows** uses a working-set model with per-process working sets that are trimmed when memory is short, plus standby (clean) and modified (dirty) page lists that act as page buffering.
- **Applications with special knowledge** (databases) often manage their own buffer pools, because they know their access patterns better than any general-purpose policy.

## OS-7.4 · Belady's Anomaly and Stack Algorithms

### Belady's anomaly

Intuitively, giving a process **more frames** should never cause **more** page faults. For FIFO, it can. With the reference string

```
 1 2 3 4 1 2 5 1 2 3 4 5
```

FIFO causes **9 faults with 3 frames** but **10 faults with 4 frames** (N3). This was discovered by Belady, Nelson, and Shedler in 1969.

Why FIFO misbehaves: the set of pages FIFO keeps with 4 frames is **not** a superset of the set it keeps with 3 frames. The eviction order depends on load order, and adding a frame can shift which page is oldest at a critical moment.

### Stack algorithms

A **stack algorithm** is one for which the set of pages in memory with n frames is **always a subset** of the set in memory with n + 1 frames, at every point in the reference string (the **inclusion property**).

- If a page is in memory with n frames, it is also in memory with n + 1 frames, so every hit with n frames is also a hit with n + 1. Therefore a stack algorithm **can never** have more faults with more frames: **no Belady's anomaly**.
- **LRU** is a stack algorithm: with n frames it holds the n most recently used pages; with n + 1 it holds the n + 1 most recently used, which includes those n.
- **OPT** is a stack algorithm: it holds the pages whose next uses are soonest.
- **FIFO** is not a stack algorithm (it holds the most recently *loaded* pages, and load history differs with different frame counts).
- **Clock / second chance** can also exhibit the anomaly, since it degenerates to FIFO. LFU, when ties are broken by FIFO, can too.

Stack algorithms have a useful practical property: a single pass over a reference string can compute the fault count for **every** memory size at once (by tracking each reference's "stack distance"), which is how memory-sizing studies are done.

| Algorithm | Stack algorithm? | Belady's anomaly possible? | Implementable? |
|---|---|---|---|
| OPT | Yes | No | No (needs future) |
| LRU | Yes | No | Only approximately |
| FIFO | No | Yes | Yes |
| Clock | No | Yes | Yes (common) |
| Random | No | Yes (on some strings) | Yes |

## OS-7.5 · Allocation of Frames

How many of the available frames should each process get?

### Minimum and maximum

- **Maximum:** the total number of free frames (a process cannot have more than exist).
- **Minimum:** set by the **architecture**. A single instruction must be able to complete, so the process needs at least as many frames as the pages one instruction can touch at once. An instruction that spans a page boundary, with an operand on another page, fetched through an indirect pointer on yet another page, may need several frames simultaneously. With too few frames, the instruction faults, one page is replaced to bring in another, and the instruction faults again forever.

As frames per process decrease, the fault rate increases and execution slows.

### Allocation algorithms

With m frames and n processes:

- **Equal allocation:** each process gets m / n frames. Simple, but a small process wastes frames while a large one faults constantly.
- **Proportional allocation:** give each process frames in proportion to its size. If process i has virtual size sᵢ and S = Σ sᵢ:

```
 aᵢ = (sᵢ / S) × m          (rounded to an integer, and at least the minimum)
```

Example: 62 frames, processes of 10 pages and 127 pages. S = 137. Process 1 gets 10/137 × 62 ≈ **4**; process 2 gets 127/137 × 62 ≈ **57**. (Equal allocation would give both 31, most of them wasted on the small process.)

- **Priority-based allocation:** use priority, or a combination of size and priority, instead of size alone, so high-priority processes fault less.

Allocations change as processes arrive and leave, and as the multiprogramming level changes.

### Global vs local replacement

When a process faults and needs a frame:

- **Local replacement:** the victim must be one of the process's **own** frames. Its number of frames stays fixed.
- **Global replacement:** the victim may be **any** frame in the system, even one belonging to another process. A process's number of frames grows and shrinks.

| | Local | Global |
|---|---|---|
| A process's fault rate depends on | Only its own behaviour | Also on other processes' behaviour |
| Unused frames of one process | Cannot be used by others | Taken by those who need them |
| System throughput | Often lower | Usually **higher** |
| Isolation | Good | Poor (a "noisy neighbour" can steal memory) |

**Global replacement is used by most systems** (including Linux) because it gives better throughput. To limit its downsides, Linux also supports per-group limits with **cgroups** (`memory.max`, `memory.high`), which make a container reclaim from its own pages first: effectively local replacement for a group (→ S12, OS-12.2).

### NUMA

On NUMA machines (← OS-3.5), memory attached to the local CPU socket is faster. The allocator tries to give a process frames from the node where it runs ("first-touch" policy), and the scheduler tries to keep the process on that node. Linux can also migrate pages toward the node that uses them (automatic NUMA balancing).

## OS-7.6 · Thrashing, the Working-Set Model, and Page-Fault Frequency

### Thrashing

If a process does not have enough frames to hold the pages it is actively using, it faults, replaces a page it will need again almost immediately, faults on that page, and so on. It spends more time **paging than executing**. This is **thrashing**.

**How a whole system slides into thrashing** (the classic story):

1. Processes start faulting more (for example, because a new process started or one entered a phase needing more memory).
2. With global replacement, faulting processes take frames from other processes, which then also start faulting.
3. Processes queue up for the paging device; the ready queue empties; **CPU utilization drops**.
4. The long-term scheduler (in older batch systems) sees low CPU utilization and **admits more processes** to raise it.
5. The new processes take frames away from existing ones, causing even more faults; CPU utilization drops further.

```
 CPU
 utilization
   ^
   |            ____
   |          /      \
   |        /          \
   |      /              \      <- thrashing
   |    /                  \
   |  /                      \___
   +-------------------------------->  degree of multiprogramming
```

Throughput plummets while the disk is saturated. The fix is the opposite of step 4: **reduce** the degree of multiprogramming (swap out or suspend processes) until the rest have enough memory. Local replacement limits the spread (one thrashing process cannot steal others' frames) but does not cure the thrashing process, and it still slows everyone by occupying the paging device.

### The locality model

As a process executes, it moves from **locality to locality**: a set of pages actively used together (a function, its data, its callees). Localities can overlap. If a process is given enough frames for its current locality, it faults only while moving to a new one. If it gets fewer frames than its locality needs, it thrashes.

### The working-set model

Denning (1968) made the locality model precise. Choose a **working-set window Δ** (a number of recent page references). The **working set** WS(t, Δ) is the set of distinct pages referenced in the most recent Δ references.

```
 ... 2 6 1 5 7 7 7 7 5 1 6 2 3 4 1 2 3 4 4 4 3 4 3 4 4 4 1 3 2 3 4 4 4 3 4 4 4 ...
     |<------- Δ = 10 ------->|                 |<------- Δ = 10 ------->|
                             t1                                        t2
 WS(t1) = {1, 2, 5, 6, 7}                        WS(t2) = {3, 4}
```

- If Δ is **too small**, it does not cover the whole locality.
- If Δ is **too large**, it spans several localities.
- If Δ = ∞, the working set is every page the process has ever touched.

Let WSSᵢ be the working-set size of process i. Total demand for frames:

```
 D = Σ WSSᵢ
```

- If **D > m** (total frames), thrashing will occur, because some process will not have its working set in memory.
- **Policy:** the OS monitors each working set and gives each process enough frames for it. If D exceeds m, it **suspends** a process (swapping out its pages) and gives its frames to the others. If there are spare frames, it can start another process.

This keeps the degree of multiprogramming as high as possible while preventing thrashing.

**Approximating the working set.** Tracking the exact window is expensive. Approximation with a timer and reference bits: for Δ = 10,000 references, interrupt every 5,000 references; on each interrupt, copy each page's reference bit into one of two in-memory history bits and clear it. A page is in the working set if its reference bit or either history bit is 1. More history bits and more frequent interrupts give more accuracy at higher cost.

### Page-fault frequency (PFF)

A more direct approach: control the **fault rate** itself.

```
 page-fault
 rate
   ^
   |  \
   |   \        ---------------------------  upper bound: give the process more frames
   |    \
   |     \___
   |         \______
   |                \____________
   |        ---------------------------  lower bound: take frames away
   +-------------------------------------->  number of frames
```

- If a process's fault rate exceeds the **upper bound**, it needs more frames: allocate more.
- If its fault rate falls below the **lower bound**, it has more than it needs: take some away.
- If the fault rate is too high and **no free frames** are available, suspend a process.

PFF is simpler to implement than the working-set model (count faults over time) and responds directly to the quantity we care about. Note that at the start of a new locality, the fault rate naturally spikes; the working set of the new locality is being loaded.

### Thrashing today

On modern desktops and servers, memory is large relative to typical working sets, and the practical answer to sustained thrashing is usually **more RAM** (or smaller workloads). Linux reports memory pressure through **PSI** (pressure stall information, `/proc/pressure/memory`), which tools like `systemd-oomd` use to kill processes **before** the system thrashes for minutes, rather than waiting for the kernel's last-resort OOM killer.

## OS-7.7 · Kernel Memory Allocation, and Other Considerations

### Why kernel memory is different

The kernel allocates memory for its own data structures (PCBs, inodes, network buffers, page tables) differently from user memory:

- Many requests are for **small objects of various sizes**, often less than a page; wasting a page on each would be very costly.
- Some memory must be **physically contiguous**: hardware devices doing DMA (← OS-1.3) often work with physical addresses and cannot follow page tables.
- Kernel memory is usually not paged out.

Two classic allocators:

### Buddy system

Memory is managed in blocks whose sizes are **powers of two**. A request is rounded up to the next power of two.

- **Allocation:** if no free block of the needed size exists, take a larger block and **split** it in half repeatedly (each pair of halves are **buddies**) until a block of the right size is obtained.
- **Freeing:** when a block is freed, check whether its buddy is also free. If so, **coalesce** them into a block of twice the size, and repeat upward.

Example: a 256 KB segment, and a request for 21 KB (rounded to 32 KB):

```
 256 -> split -> 128 | 128
        128 -> split -> 64 | 64
                        64 -> split -> 32 | 32
                                       ^^
                                  allocated (21 KB used, 11 KB wasted)
```

- **Fast coalescing:** a block of size 2ᵏ at address A has its buddy at `A XOR 2ᵏ`, so finding the buddy is one computation.
- **Drawback: internal fragmentation.** A 33 KB request gets 64 KB, wasting almost half. On average about 25% is wasted.

Linux's page allocator is a buddy system managing **physical pages**, with orders 0 to 10 (1 page = 4 KB up to 1,024 pages = 4 MB) per memory zone. `/proc/buddyinfo` shows how many free blocks of each order exist; few high-order blocks mean physical memory is fragmented. See N8.

### Slab allocation

Introduced by Jeff Bonwick for SunOS 5.4 (1994). Designed for kernel objects that are allocated and freed very frequently.

- A **cache** exists for each kernel **object type** (one for inodes, one for process descriptors, one for file objects, and so on).
- Each cache consists of **slabs**: one or more physically contiguous pages, carved into equal-size slots exactly fitting that object.
- Each slab is **full**, **partial**, or **empty**. Allocation takes a free slot from a partial slab if possible, then an empty one, and only then gets a new slab from the page allocator.

```
  cache: task_struct        slabs (contiguous pages)
  +----------------+       +----+----+----+----+
  |  full slabs    | ----> |obj |obj |obj |obj |
  |  partial slabs | ----> |obj |free|obj |free|
  |  empty slabs   | ----> |free|free|free|free|
  +----------------+       +----+----+----+----+
```

Benefits:

- **No fragmentation waste** for these objects: each slot fits the object exactly.
- **Fast:** allocation and freeing are simple list operations; objects can even be kept **pre-initialized** (constructed), since freed objects are returned to the cache in a known state.
- Good cache behaviour (and per-CPU caches avoid locking).

Linux history: the original **SLAB** allocator, **SLOB** for tiny embedded systems, and **SLUB** (the default since 2.6.23, simpler with less metadata). SLOB was removed in 6.4 and SLAB in 6.8, leaving SLUB. `/proc/slabinfo` and `slabtop` show the caches. `kmalloc()` serves general small allocations from size-class caches (`kmalloc-64`, `kmalloc-128`, ...), and returns physically contiguous memory; `vmalloc()` returns memory that is only **virtually** contiguous (built from scattered pages) for large allocations that do not need physical contiguity.

### Prepaging

Pure demand paging causes a burst of faults when a process starts, or when a swapped-out process resumes. **Prepaging** loads some pages **before** they are referenced (for example, the whole remembered working set of a process being swapped back in; or the next few pages of a file being read sequentially, which is Linux's **readahead**).

Is it worth it? Suppose s pages are prepaged and a fraction α of them is actually used. Prepaging saves s·α faults and wastes the cost of loading s·(1 − α) unneeded pages. If α is close to 0, prepaging loses; if close to 1, it wins.

### Page size, TLB reach, and huge pages

Revisit the trade-off from ← OS-6.4 in the context of virtual memory:

- **Smaller pages:** less internal fragmentation; better **resolution** (only needed data is brought in); but more faults and larger page tables.
- **Larger pages:** fewer faults for the same data, cheaper I/O per byte (a disk seek costs the same whether you read 4 KB or 64 KB), and larger **TLB reach** (← OS-6.5).

Modern systems use 4 KB base pages and support **huge pages** for large-memory workloads:

- **hugetlbfs:** explicitly reserved 2 MB or 1 GB pages (databases, virtual machines).
- **Transparent huge pages (THP):** the kernel automatically backs suitable anonymous memory with 2 MB pages and a background thread (`khugepaged`) merges 4 KB pages into huge pages. It can cause latency spikes (compaction to find contiguous memory) and memory bloat, so some databases recommend disabling it.

### Program structure

The programmer's choices of data layout and loop order matter a great deal. Example: `int data[128][128];` stored row by row (C is row-major), pages of 128 integers, so each **row is one page**. Suppose the process has fewer than 128 frames.

```c
// Program 1: column-by-column
for (j = 0; j < 128; j++)
    for (i = 0; i < 128; i++)
        data[i][j] = 0;       // touches a different row (page) on every access

// Program 2: row-by-row
for (i = 0; i < 128; i++)
    for (j = 0; j < 128; j++)
        data[i][j] = 0;       // finishes one page before moving on
```

Program 1 causes 128 × 128 = **16,384** page faults; Program 2 causes **128** (N7). The same effect, at a smaller scale, applies to caches and the TLB. Other factors: stacks have good locality, hash tables deliberately scatter accesses (poor locality), and pointer-heavy structures like linked lists scatter objects across pages. Compilers and loaders help by placing routines that call each other on the same page.

### I/O interlock and page locking

Suppose a process issues a read into a buffer in its memory, then blocks. While it waits, another process faults, and global replacement picks the buffer's frame as a victim and gives it to that process. When the device's DMA transfer completes, it writes into the frame, which now belongs to someone else.

Solutions:

- Never do I/O directly into user memory: copy through kernel buffers (costs a copy).
- **Lock (pin)** pages in memory while I/O is pending: a **lock bit** per frame prevents it from being selected for replacement.

Pinning is used for other purposes too:

- Kernel code and many kernel data structures are never paged out.
- A newly loaded page for a low-priority process can be locked until it has been used once, so a high-priority process's fault does not immediately steal it (which would waste the I/O).
- User programs can lock pages with **`mlock()` / `mlockall()`**: real-time programs (avoid unpredictable fault delays → S9) and security software (keep keys out of swap). Locked memory is limited by `RLIMIT_MEMLOCK` because pinning too much starves the system.

## Quick Revision Sheet

- Demand paging: load pages only when accessed; invalid PTE → page fault → OS reads page → restart instruction.
- Page fault steps: trap, check legality, find frame (maybe evict), disk read (process blocks), update PTE, restart.
- Minor fault: page in memory, just needs mapping. Major fault: disk I/O.
- EAT = (1 − p)·ma + p·fault time. With 200 ns / 8 ms, p must be below ~1 in 400,000 for <10% slowdown.
- Overcommit + zero-fill-on-demand; OOM killer when memory truly runs out.
- COW: fork shares frames read-only; copy a page on first write.
- `mmap`: file pages mapped from the page cache; `MAP_SHARED` writes reach the file, `MAP_PRIVATE` is COW.
- Dirty victim needs a write-back (two transfers). Swap daemon keeps free frames between watermarks.
- FIFO (Belady's anomaly), OPT (optimal, needs future), LRU (good, expensive exactly).
- Silberschatz string with 3 frames: FIFO 15, OPT 9, LRU 12.
- Clock/second chance: ref bit 1 → clear and skip; 0 → evict. All bits set → FIFO.
- Enhanced second chance: prefer (0,0), then (0,1), (1,0), (1,1).
- Aging: 8-bit shift register; smallest value = least recently used.
- Stack algorithms (LRU, OPT) have the inclusion property → no Belady's anomaly. FIFO, clock can have it. Example: 1 2 3 4 1 2 5 1 2 3 4 5 → FIFO 9 faults with 3 frames, 10 with 4.
- Proportional allocation: aᵢ = sᵢ / S × m. Global replacement: better throughput, less isolation.
- Thrashing: paging more than executing; CPU utilization collapses; fix by reducing multiprogramming.
- Working set WS(t, Δ); if Σ WSSᵢ > m, suspend a process. PFF: keep fault rate between bounds.
- Buddy: power-of-two blocks, split and coalesce; buddy at A XOR size; internal fragmentation.
- Slab: per-object-type caches of pre-sized slots; no fragmentation, fast; Linux uses SLUB.
- Prepaging/readahead, huge pages (TLB reach), loop order (row vs column), `mlock` for I/O and real time.

## Worked Numerical Problems

### N1 · Effective access time with page faults (OS-7.1)

**Question.** (a) Memory access takes 200 ns and servicing a page fault takes 8 ms. What is EAT if 1 access in 1,000 faults? What maximum fault rate keeps the slowdown under 10%? (b) A different system: memory access 100 ns; a fault takes 8 ms if the victim is clean (or a free frame exists) and 20 ms if the victim is dirty; victims are dirty 70% of the time. What is the maximum fault rate for an EAT of at most 200 ns?

**Answer.**

(a) EAT = 0.999 × 200 + 0.001 × 8,000,000 = 199.8 + 8,000 ≈ **8,200 ns = 8.2 µs** (41× slower than memory).

For EAT ≤ 220 ns: 200 + 7,999,800 p ≤ 220 → p ≤ 20 / 7,999,800 ≈ **2.5 × 10⁻⁶**, about **one fault per 400,000 accesses**.

(b) Average fault service time = 0.3 × 8 + 0.7 × 20 = 2.4 + 14 = **16.4 ms** = 16,400,000 ns.

EAT = (1 − p) × 100 + p × 16,400,000 ≤ 200 → 100 + 16,399,900 p ≤ 200 → p ≤ 100 / 16,399,900 ≈ **6.1 × 10⁻⁶**.

### N2 · FIFO, OPT, and LRU traces (OS-7.3)

**Question.** Reference string `7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1`, 3 frames, initially empty. Count page faults for FIFO, OPT, and LRU.

**Answer.** Frame contents after each reference (F = fault; the page evicted is shown in parentheses):

```
 ref |  FIFO          |  OPT           |  LRU
 ----+----------------+----------------+----------------
  7  | 7 - -   F      | 7 - -   F      | 7 - -   F
  0  | 7 0 -   F      | 7 0 -   F      | 7 0 -   F
  1  | 7 0 1   F      | 7 0 1   F      | 7 0 1   F
  2  | 2 0 1   F (7)  | 2 0 1   F (7)  | 2 0 1   F (7)
  0  | 2 0 1          | 2 0 1          | 2 0 1
  3  | 2 3 1   F (0)  | 2 0 3   F (1)  | 2 0 3   F (1)
  0  | 2 3 0   F (1)  | 2 0 3          | 2 0 3
  4  | 4 3 0   F (2)  | 2 4 3   F (0)  | 4 0 3   F (2)
  2  | 4 2 0   F (3)  | 2 4 3          | 4 0 2   F (3)
  3  | 4 2 3   F (0)  | 2 4 3          | 4 3 2   F (0)
  0  | 0 2 3   F (4)  | 2 0 3   F (4)  | 0 3 2   F (4)
  3  | 0 2 3          | 2 0 3          | 0 3 2
  2  | 0 2 3          | 2 0 3          | 0 3 2
  1  | 0 1 3   F (2)  | 2 0 1   F (3)  | 1 3 2   F (0)
  2  | 0 1 2   F (3)  | 2 0 1          | 1 3 2
  0  | 0 1 2          | 2 0 1          | 1 0 2   F (3)
  1  | 0 1 2          | 2 0 1          | 1 0 2
  7  | 7 1 2   F (0)  | 7 0 1   F (2)  | 1 0 7   F (2)
  0  | 7 0 2   F (1)  | 7 0 1          | 1 0 7
  1  | 7 0 1   F (2)  | 7 0 1          | 1 0 7
 ----+----------------+----------------+----------------
     | 15 faults      |  9 faults      | 12 faults
```

How OPT chose, for example, at the reference to 3 (position 6): pages in memory are 2, 0, 1. Next uses: 0 at position 7, 2 at position 9, 1 at position 14. Evict **1**, used farthest in the future. At the reference to 0 (position 11), pages 2, 4, 3: 4 is never used again, so evict **4**.

How LRU chose, for example, at the reference to 4 (position 8): pages 2 (last used at position 4), 0 (position 7), 3 (position 6). Evict **2**, the least recently used.

The first 3 faults are **compulsory** (cold-start) misses that every algorithm incurs.

### N3 · Belady's anomaly (OS-7.4)

**Question.** Reference string `1 2 3 4 1 2 5 1 2 3 4 5`. Count faults for FIFO with 3 and 4 frames, and for LRU with 3 and 4 frames.

**Answer.**

**FIFO, 3 frames:**
```
 1 F [1 - -]   2 F [1 2 -]   3 F [1 2 3]   4 F [4 2 3]   1 F [4 1 3]   2 F [4 1 2]
 5 F [5 1 2]   1   [5 1 2]   2   [5 1 2]   3 F [5 3 2]   4 F [5 3 4]   5   [5 3 4]
```
**9 faults.**

**FIFO, 4 frames:**
```
 1 F  2 F  3 F  4 F  [1 2 3 4]   1  2 (hits)
 5 F [5 2 3 4]   1 F [5 1 3 4]   2 F [5 1 2 4]   3 F [5 1 2 3]
 4 F [4 1 2 3]   5 F [4 5 2 3]
```
**10 faults.** More frames, more faults.

**LRU, 3 frames:** faults on 1, 2, 3, 4, 1, 2, 5 (7 so far; 1 and 2 then hit), then 3 (evicts 5), 4 (evicts 1), 5 (evicts 2): **10 faults**.

**LRU, 4 frames:** faults on 1, 2, 3, 4; 1 and 2 hit; 5 evicts 3; 1 and 2 hit; 3 evicts 4; 4 evicts 5; 5 evicts 1: **8 faults**.

LRU improves from 10 to 8 with the extra frame, as a stack algorithm must.

### N4 · Clock (second chance) trace (OS-7.3)

**Question.** Run the clock algorithm with 3 frames on `1 2 3 4 1 2 5 1 2 3 4 5`. A newly loaded page gets reference bit 1; a hit sets the bit to 1; the hand starts at frame 0 and advances past a page after loading it. How many faults? Compare with FIFO.

**Answer.** Frames f0, f1, f2; `*` marks reference bit = 1. "Hand" is where the hand points after the step.

```
 ref | f0   f1   f2  | hand | action
 ----+---------------+------+-----------------------------------------------------
  1  | 1*   -    -   |  f1  | fault: free frame f0
  2  | 1*   2*   -   |  f2  | fault: free frame f1
  3  | 1*   2*   3*  |  f0  | fault: free frame f2
  4  | 4*   2    3   |  f1  | fault: f0, f1, f2 all 1 -> cleared; f0 now 0 -> evict 1
  1  | 4*   1*   3   |  f2  | fault: f1 bit 0 -> evict 2
  2  | 4*   1*   2*  |  f0  | fault: f2 bit 0 -> evict 3
  5  | 5*   1    2   |  f1  | fault: all bits 1 -> cleared; f0 -> evict 4
  1  | 5*   1*   2   |  f1  | hit: set bit
  2  | 5*   1*   2*  |  f1  | hit: set bit
  3  | 5    3*   2   |  f2  | fault: f1, f2, f0 cleared; f1 now 0 -> evict 1
  4  | 5    3*   4*  |  f0  | fault: f2 bit 0 -> evict 2
  5  | 5*   3*   4*  |  f0  | hit: set bit
```

**9 faults**, the same as FIFO. Whenever all reference bits are set, the clock sweeps around once, clears them, and evicts the page at its starting position: exactly the FIFO choice. Clock beats FIFO only when some pages have not been referenced since the last sweep.

### N5 · Working set and thrashing check (OS-7.6)

**Question.** A process has the reference string `1 2 3 2 1 4 4 4 5 4 4 5 5 4 6` (positions 1 to 15). With Δ = 5: (a) find WS at t = 5, t = 10, and t = 15. (b) Three processes currently have working-set sizes 3, 2, and 3, and there are 7 free frames. What should the OS do? (c) What if Δ were 15 for this process at t = 15?

**Answer.**

(a)
- t = 5 (references 1 to 5: 1 2 3 2 1): WS = **{1, 2, 3}**, size 3.
- t = 10 (references 6 to 10: 4 4 4 5 4): WS = **{4, 5}**, size 2.
- t = 15 (references 11 to 15: 4 5 5 4 6): WS = **{4, 5, 6}**, size 3.

The working set shrank when the process moved from locality {1, 2, 3} to {4, 5}.

(b) D = 3 + 2 + 3 = 8 > 7 frames. The OS cannot give every process its working set, so thrashing is likely. It should **suspend one process** (swap it out), then give the remaining two their 3 + 2 or 3 + 3 frames.

(c) With Δ = 15, WS at t = 15 = {1, 2, 3, 4, 5, 6}, size 6: the window spans two localities and overestimates what the process currently needs.

### N6 · Frame allocation (OS-7.5)

**Question.** A system has 62 free frames and two processes of 10 and 127 pages. (a) Allocation under equal and proportional schemes? (b) A third process of 63 pages arrives; recompute the proportional allocation. (c) In (b), what happens if the architecture requires a minimum of 8 frames per process?

**Answer.**

(a) Equal: **31 and 31**. Proportional: S = 137; 10/137 × 62 = 4.53 → **4**; 127/137 × 62 = 57.47 → **57** (61 used; 1 frame left for the pool).

(b) S = 200. 10/200 × 62 = 3.1 → **3**; 127/200 × 62 = 39.4 → **39**; 63/200 × 62 = 19.5 → **19** (61 used).

(c) The small process gets 3 < 8: it must be raised to **8**, and the 5 extra frames are taken from the others (for example, proportionally: 39 → about 36, 19 → about 17). Below the minimum, the process could fault forever on a single instruction.

### N7 · Loop order and page faults (OS-7.7)

**Question.** `int A[128][128]` (4-byte ints) is stored in row-major order, with a page size of 512 bytes. The process has only 64 frames available for the array, all initially empty. Count page faults for (a) row-by-row initialization and (b) column-by-column initialization (LRU replacement). (c) What if the page size is 1 KB and there are 100 frames?

**Answer.** Each row is 128 × 4 = 512 bytes = exactly **one page**. The array occupies 128 pages.

(a) Row by row: all 128 elements of row 0 are written (1 fault), then row 1 (1 fault), and so on: **128 faults** (the minimum: each page must be loaded once).

(b) Column by column: each access `A[i][j]` for i = 0..127 touches all 128 rows (pages), but only 64 fit. With LRU, by the time the next column starts at row 0, row 0's page was evicted (it is the least recently used). Every access faults: 128 × 128 = **16,384 faults**.

(c) Now each page holds 2 rows, so the array is 64 pages. Row by row: **64 faults**. Column by column: 100 frames ≥ 64 pages, so after the first column loads all 64 pages, nothing is evicted: also **64 faults**. Loop order stops mattering (for paging) once the whole array fits; it still matters for caches and the TLB.

### N8 · Buddy system (OS-7.7)

**Question.** A buddy allocator manages 1 MB (1,024 KB), initially free. Show the state after each step: (1) A requests 70 KB, (2) B requests 35 KB, (3) C requests 80 KB, (4) A is freed, (5) D requests 60 KB, (6) B is freed, (7) D is freed, (8) C is freed. Also compute the internal fragmentation of each allocation.

**Answer.** (Addresses in KB.)

1. **A 70 → 128.** Split 1024 → 512 + 512; 512 → 256 + 256; 256 → 128 + 128. A at 0–128. Free: 128@128, 256@256, 512@512.
2. **B 35 → 64.** Split 128@128 → 64@128 + 64@192. B at 128–192. Free: 64@192, 256@256, 512@512.
3. **C 80 → 128.** Split 256@256 → 128@256 + 128@384. C at 256–384. Free: 64@192, 128@384, 512@512.
4. **Free A** (128@0). Its buddy is 128@128 (0 XOR 128), which is split and partly used: no merge. Free: 128@0, 64@192, 128@384, 512@512.
5. **D 60 → 64.** Use 64@192. Free: 128@0, 128@384, 512@512.
6. **Free B** (64@128). Buddy 64@192 holds D: no merge.
7. **Free D** (64@192). Buddy 64@128 free → merge into 128@128. Its buddy 128@0 free → merge into 256@0. Its buddy 256@256 contains C: stop. Free: 256@0, 128@384, 512@512.
8. **Free C** (128@256). Buddy 128@384 free → 256@256. Buddy 256@0 free → 512@0. Buddy 512@512 free → **1024@0**. Memory is whole again.

Internal fragmentation: A 128 − 70 = **58 KB**, B 64 − 35 = **29 KB**, C 128 − 80 = **48 KB**, D 64 − 60 = **4 KB**.

## Scenario Questions (Test Your Understanding)

### S1 · Allocating more memory than exists (OS-7.1)

On a Linux machine with 8 GB of RAM and no swap, `char *p = malloc(10UL << 30);` (10 GB) returns a valid pointer. The program then writes to every byte, and partway through it is killed with no error message from `malloc`. Explain both events.

<details><summary>Answer</summary>

`malloc` of this size calls `mmap`, which only reserves **virtual** address space; with Linux's default heuristic **overcommit**, a request like this can succeed without any physical memory being committed. Physical frames are allocated one page at a time on first write (zero-fill-on-demand page faults).

As the program writes, it consumes real frames. When RAM is exhausted and nothing can be reclaimed (no swap, file-backed pages already dropped), a page fault cannot be satisfied, and the kernel's **OOM killer** chooses a victim (likely this process, the largest) and sends `SIGKILL`. `dmesg` shows an "Out of memory: Killed process" message. With `vm.overcommit_memory = 2` (strict accounting), the `malloc` itself would fail instead.

</details>

### S2 · Faster the second time (OS-7.1, OS-7.2)

A large program takes 4 seconds to start the first time after boot and 0.4 seconds the second time. `/usr/bin/time -v` shows about 12,000 major faults on the first run and almost none on the second, though both have many minor faults. Explain.

<details><summary>Answer</summary>

The executable and its shared libraries are mapped, and their pages are loaded by demand paging. On the first run, those file pages are not yet in the **page cache**, so each first touch is a **major fault** requiring disk I/O. After the program exits, the pages stay in the page cache. On the second run, the page-table entries are new (so faults still occur), but the kernel finds the pages already in memory and simply maps them: **minor faults**, with no I/O. Readahead and prepaging reduce the first-run cost further.

</details>

### S3 · More processes, less work (OS-7.6)

A batch system shows 30% CPU utilization. The operator raises the number of concurrently running jobs from 8 to 16 to use the CPU better. CPU utilization falls to 5%, the disk is 100% busy, and jobs finish much later. What happened, and what should the operator do?

<details><summary>Answer</summary>

**Thrashing.** With 16 jobs, the sum of their working sets exceeds physical memory. Jobs constantly fault out each other's pages (global replacement), so almost all time is spent waiting for the paging disk; the CPU sits idle. Raising multiprogramming because CPU utilization is low is exactly the feedback loop that causes the collapse.

Reduce the number of concurrent jobs until their combined working sets fit in memory (the working-set or page-fault-frequency policy does this automatically by suspending jobs), or add RAM. The initial 30% was probably due to I/O-bound jobs, not a lack of jobs.

</details>

### S4 · The snapshot that doubled memory (OS-7.2)

A 20 GB in-memory database takes a snapshot by calling `fork()`; the child writes the data to disk while the parent keeps serving requests. `fork()` returns in milliseconds. During snapshots under a write-heavy workload, memory usage climbs toward 40 GB and the machine sometimes runs out of memory. Explain with copy-on-write.

<details><summary>Answer</summary>

`fork()` is fast because it copies only page tables; parent and child share all 20 GB of frames read-only. The child only reads, so it causes no copies. But every time the **parent** writes to a page that is still shared, a COW fault copies that page (4 KB, or 2 MB with transparent huge pages, which makes it much worse). Under heavy writes spread across the dataset, a large fraction of pages gets modified during the snapshot, so up to 20 GB of copies accumulate until the child exits and the old versions are freed.

Mitigations: keep enough free memory headroom, disable transparent huge pages (to copy 4 KB instead of 2 MB per write), and avoid snapshots during peak writes. (Redis documents exactly this behaviour.)

</details>

### S5 · More memory, more faults (OS-7.4)

A student simulates a system using FIFO replacement. Increasing the frames from 3 to 4 increases the fault count on their test trace. They assume their simulator is buggy. Is it? What would happen with LRU?

<details><summary>Answer</summary>

Not necessarily a bug: it may be **Belady's anomaly**. FIFO is not a stack algorithm: the pages it keeps with 4 frames are not always a superset of those it keeps with 3, so a hit with 3 frames can become a miss with 4. The classic trace `1 2 3 4 1 2 5 1 2 3 4 5` gives 9 and 10 faults.

LRU (and OPT) are stack algorithms: the pages held with n frames are always a subset of those held with n + 1 frames, so adding frames can never increase faults. On that trace LRU goes from 10 to 8.

</details>

### S6 · Why not true LRU? (OS-7.3)

A hardware designer asks why OSes approximate LRU with clock instead of just implementing LRU exactly. Explain what exact LRU would require and why clock is "good enough."

<details><summary>Answer</summary>

Exact LRU needs the full order of recency, updated on **every memory access**: writing a timestamp into the PTE on each load/store, or moving the page to the top of a linked stack. That means extra memory writes for every instruction's data access, and a search or list manipulation on replacement. It would slow every memory access far more than paging saves.

Clock needs only the **reference bit**, which the MMU already sets when it walks or caches a translation, and the OS scans lazily only when it needs a victim. It approximates "not used recently" with one bit of history (aging adds a few more bits). Since fault costs are dominated by disk I/O and the difference between LRU and a good approximation is small in practice, clock is the standard choice.

</details>

### S7 · The nightly scan (OS-7.3)

Every night a backup job reads a 500 GB archive once, sequentially. With a naive LRU page cache, users find the system sluggish every morning, because their frequently used files and program pages have to be reloaded. Why? How does Linux's two-list design help, and what can the backup program do itself?

<details><summary>Answer</summary>

Under plain LRU, every newly read page of the archive becomes the "most recently used," so the scan pushes out the entire working set of useful pages, even though each archive page is used exactly **once** (**cache pollution** by a scan).

Linux places new pages on the **inactive** list and promotes them to the active list only if they are referenced **again**. Archive pages are touched once, stay inactive, and are reclaimed first; the active list (users' frequently used pages) survives. MGLRU and scan-resistant algorithms (like 2Q and ARC) follow the same idea.

The backup program can help with `posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED)` after reading (or `POSIX_FADV_NOREUSE`), or with `O_DIRECT`, which bypasses the page cache entirely.

</details>

### S8 · mmap and a crash (OS-7.2)

A program maps a file with `mmap(... MAP_SHARED ...)`, modifies it through the pointer, and then crashes with a segfault before calling `msync` or `munmap`. Is the modification lost? What if it had used `MAP_PRIVATE`? What if the whole machine lost power instead?

<details><summary>Answer</summary>

**Process crash, `MAP_SHARED`:** the changes were made directly to page-cache pages belonging to the file. The pages are simply marked dirty; the kernel writes them back to the file eventually, regardless of whether the process is still alive. **Not lost.**

**`MAP_PRIVATE`:** the first write to each page created a private copy-on-write copy. Those copies belong only to the process and are discarded when it dies. The file was never changed.

**Power loss:** dirty page-cache pages not yet written to disk are lost, whether they came from `mmap` or `write()`. Only `msync(MS_SYNC)` (or `fsync`) before the failure guarantees durability (→ OS-8.6).

</details>

### S9 · Glitches in the audio (OS-7.7)

A real-time audio program occasionally produces clicks. Profiling shows its audio thread sometimes stalls for 5 to 20 ms inside ordinary memory accesses. The machine has plenty of free RAM. What could cause this, and how is it prevented?

<details><summary>Answer</summary>

**Page faults** in the audio thread. Even with free RAM, a page of its code, data, or a buffer may never have been touched (demand paging), may have been reclaimed (clean code pages can be discarded and re-read from disk), or may hit a COW or zero-fill fault. A major fault means disk I/O: milliseconds, far beyond a few-millisecond audio deadline.

Prevention: call **`mlockall(MCL_CURRENT | MCL_FUTURE)`** to lock all pages in memory, **pre-fault** buffers and the stack at startup (touch every page once), avoid `malloc` in the real-time path, and run the thread with a real-time scheduling policy (← OS-3.6).

</details>

### S10 · No swap, still paging (OS-7.1, OS-7.3)

A server is configured with no swap space "so it can never page." Under memory pressure it becomes extremely slow for minutes, with heavy disk **reads**, before the OOM killer finally acts. How can a system without swap be paging?

<details><summary>Answer</summary>

Without swap, **anonymous** pages (heap, stack) cannot be evicted. But **file-backed** pages can still be reclaimed: page-cache data and, crucially, the **code pages** of every running program and library, which are clean copies of files and can be re-read on demand. Under pressure, the kernel keeps evicting code pages, and running programs immediately fault them back in from disk. This is thrashing on executable pages. It continues until reclaim truly fails, and only then does the OOM killer run.

Remedies: a small amount of swap (so cold anonymous pages can be moved out instead of hot code), memory limits per service (cgroups), and a userspace OOM daemon driven by PSI pressure metrics that acts earlier.

</details>

### S11 · A fault in the middle of an instruction (OS-7.1)

An instruction copies 200 bytes from one buffer to another in a single operation. The destination buffer crosses a page boundary, and the second page is not in memory. The fault happens after 120 bytes were copied. Why is this a problem for "restart the instruction," and how can hardware handle it?

<details><summary>Answer</summary>

Restarting the instruction assumes it had no effect before the fault. Here 120 bytes of the destination are already overwritten. If the source and destination **overlap**, the source has also been partly modified, so re-executing from the beginning would copy corrupted data.

Hardware solutions: (1) before modifying anything, the microcode **probes** both ends of the source and destination ranges, so any page fault happens before the first byte is written; (2) keep temporary registers holding the overwritten values and undo them before the fault is taken; or (3) make the instruction **resumable**, keeping its progress in registers (as x86 `rep movsb` does: the count and pointer registers are updated after each element, so restarting simply continues where it stopped).

</details>

### S12 · The noisy neighbour (OS-7.5)

On a shared host, one container runs a job that streams through a huge dataset. Latency-sensitive services in other containers get much slower whenever it runs, even though they use little memory. Explain in terms of global replacement, and describe a fix.

<details><summary>Answer</summary>

With **global replacement**, the streaming job's page faults can take frames from any process. It pulls in data continuously, so the reclaim path evicts pages of the other services (their code, their data, their cached files), which then fault them back in and wait for disk. One process's behaviour sets everyone's fault rate.

Fix: **cgroup memory limits** (`memory.max` / `memory.high`) on the streaming container, so it must reclaim from its own pages first (local replacement for the group), and `memory.low`/`memory.min` protections for the latency-sensitive services. The streaming job should also avoid polluting the cache (`O_DIRECT`, `posix_fadvise`).

</details>
