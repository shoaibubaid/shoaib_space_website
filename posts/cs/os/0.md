# The Story of an Operating System

> **How to use this page.** This is the trailer, not a unit. It tells the story of the whole subject in one pass: each unit exists because the previous one left a problem unsolved. Read it once before starting, or come back to it whenever you lose track of how the pieces connect. Every unit is linked by its ID (**→ OS-4**), the same IDs used to tag practice questions.

---

## Act I: Taking control of the machine

### The problem: a computer that trusts everyone

Picture a bare computer: a CPU fetching instructions, some memory, a disk, a keyboard. You want to run programs on it. The simplest idea is to load a program into memory and jump to it.

That works for exactly one program. The moment a second program exists, or the first one has a bug, everything falls apart. A program can overwrite another's memory. It can talk to the disk directly and corrupt everyone's files. It can loop forever, and there is no way to take the CPU back, because while the program is running, *nothing else is*. The "operating system" is just more code sitting in memory, waiting for a turn it will never get.

So the very first question is not about files or processes. It is:

**How can software stay in charge of a machine while letting other programs run at full speed on it?**

### Unit 1 · Introduction and OS Structure (→ OS-1)

The answer needs help from the hardware. Unit 1 introduces the bargain that every modern OS is built on, **limited direct execution**: programs run directly on the CPU (fast), but the CPU has a **user mode** in which dangerous instructions are forbidden, a **timer** that interrupts any program after a few milliseconds, and **traps** that let programs ask the kernel for help through a fixed, checked doorway: the **system call**. Along the way you meet interrupts and faults, the storage hierarchy, kernel architectures (monolithic, microkernel, and everything in between), and how a machine boots from nothing into an OS.

Unit 1 ends with the OS in control. But in control of *what*? It can stop a program and start another, yet it has no concept of "a program in the middle of running" that it could pause and resume.

## Act II: Sharing the CPU

### Unit 2 · Processes and Threads (→ OS-2)

**What exactly is a running program, and how does the OS juggle many of them?**

Unit 2 invents the **process**: a program plus everything needed to pause it and resume it later (registers, memory, open files), recorded in a **PCB**. The kernel switches between processes with a **context switch**. Processes are born through `fork()` and `exec()`, reaped with `wait()`, and if nobody reaps them, they linger as zombies. They talk through pipes, shared memory, and signals. Then a lighter unit appears: the **thread**, several flows of execution sharing one address space.

Now there are dozens of processes, all ready to run, and only a few CPUs. Unit 2 describes how to switch; it says nothing about **who should go next**.

### Unit 3 · CPU Scheduling (→ OS-3)

**Which ready process should run next, and for how long?**

This is policy, and every choice trades something. FCFS is fair but lets one long job stall everyone (the convoy effect). SJF is provably optimal for waiting time but needs to see the future. Round robin gives fast response but slows completion. MLFQ learns each process's behaviour from its history, without needing to know it in advance. Then come multiple cores, real-time deadlines (RMS and EDF), and the schedulers actually running on your laptop (Linux's CFS and EEVDF).

Scheduling brings a new danger with it. **Preemption** means a thread can be stopped at *any* instruction, including halfway through `counter++`. Two threads sharing data are now a race waiting to happen.

### Unit 4 · Process Synchronization (→ OS-4)

**How do threads share data safely when they can be interrupted at any moment?**

Unit 4 starts with a counter that cannot count and builds the whole toolbox: the critical-section problem and its three requirements, Peterson's algorithm (and why real CPUs break it), atomic instructions, locks, semaphores, condition variables, and monitors. Then it applies them to the classic puzzles: producer–consumer, readers–writers, dining philosophers, sleeping barber. It ends with the subtle failures: priority inversion (which nearly lost a Mars mission), lock-free data structures and the ABA problem, and RCU.

But the cure has a side effect. Locks make threads **wait for each other**, and a set of threads can end up waiting in a circle, forever.

### Unit 5 · Deadlocks (→ OS-5)

**When can waiting become permanent, and what can the OS do about it?**

Unit 5 pins down exactly when deadlock is possible (the four Coffman conditions), how to see it (resource-allocation and wait-for graphs), and the four responses: **prevent** it by breaking a condition (lock ordering is the one that works in practice), **avoid** it by staying in safe states (the banker's algorithm), **detect and recover**, or **ignore** it, which is what Linux and Windows actually do for user programs.

With the CPU shared safely, the story turns to the second great resource. Every process in Acts I and II assumed it had memory of its own. None of them does.

## Act III: Sharing memory

### Unit 6 · Memory Management (→ OS-6)

**How can every process have its own private memory, starting at address 0, when they all share one physical RAM?**

The answer is **address translation**: every address a program uses is virtual, and hardware (the MMU) translates it on every access. Unit 6 goes from the simplest scheme (base and limit registers) through contiguous allocation and its fragmentation, to **paging**: fixed-size pages placed in any free frame. Paging raises two new problems, and Unit 6 solves both: translation is too slow (so the **TLB** caches it) and page tables are too big (so they become multilevel, hashed, or inverted). Segmentation is covered as the alternative and historical companion.

Paging frees pages from needing to sit next to each other. Why stop there? A page could also be somewhere other than RAM entirely.

### Unit 7 · Virtual Memory (→ OS-7)

**Can programs use more memory than the machine physically has?**

Yes, with **demand paging**: load a page only when it is touched, and keep the rest on disk. Unit 7 follows a page fault step by step, computes why the fault rate must be astonishingly low, and shows how copy-on-write makes `fork()` cheap and how `mmap` turns files into memory. Then the hard part: when memory is full, **which page goes?** FIFO, OPT, LRU, and the clock algorithm; Belady's anomaly; how many frames each process deserves; and **thrashing**, the collapse that happens when working sets don't fit. The unit ends with how the kernel allocates its own memory (the buddy and slab allocators).

Everything so far disappears when the power goes out. Processes end, memory is wiped. Data that must outlive them needs somewhere else to live.

## Act IV: Making data last

### Unit 8 · File Systems (→ OS-8)

**How do we turn a disk, which is just a huge array of numbered blocks, into named, organized, protected files that survive crashes?**

Unit 8 builds the abstraction layer by layer: files and their metadata (inodes), the three-level tables behind every file descriptor, directories, hard and symbolic links, mounting, and the VFS that lets one set of system calls work on every file system. Then the implementation: contiguous, linked (FAT), and indexed allocation, the inode's multilevel index, extents, and free-space tracking. The final challenge is **crash consistency**: an update that needs three writes, a power failure after one. The answers are fsck, journaling, log-structured, and copy-on-write file systems, compared through FAT32, ext4, and NTFS.

The file system treats the disk as a perfect array of blocks. The real device is anything but.

### Unit 9 · Disk and Storage (→ OS-9)

**What is the storage device really like, and how do we get speed and reliability out of it?**

A hard disk is mechanical: reaching a block means moving an arm and waiting for a platter to spin, so random access is hundreds of times slower than sequential, and **disk scheduling** (SSTF, SCAN, C-LOOK) matters. An SSD has no moving parts but cannot overwrite in place, so a hidden flash translation layer rewrites, garbage-collects, and levels wear behind the OS's back. Then Unit 9 combines many devices with **RAID** for speed and survival, computes exactly how much redundancy costs and how likely a rebuild is to fail, and connects storage back to Act III through swap space.

Disks are only one kind of device among many: keyboards, network cards, GPUs, timers. The OS must talk to all of them.

### Unit 10 · I/O Systems (→ OS-10)

**How does the OS communicate with every kind of device, efficiently and uniformly?**

Unit 10 goes down to device registers (port-mapped and memory-mapped) and the three ways of moving data: **polling**, **interrupts**, and **DMA**, each best in a different situation (and interrupts can even livelock a machine). It then climbs back up through the kernel's I/O subsystem (buffering, caching, spooling), the life of a single `read()`, and the programming models for thousands of simultaneous connections: blocking, non-blocking, `select`, `poll`, `epoll`, and `io_uring`. It ends with device drivers, the largest and buggiest part of any kernel.

By now, protection has appeared everywhere in the story: user mode, page permissions, file modes, privileged I/O. It is time to face the people those mechanisms are meant to stop.

## Act V: Trust and isolation

### Unit 11 · Protection and Security (→ OS-11)

**Who may do what to which resources, and how do attackers get around the rules?**

Unit 11 starts with the model (protection domains and the access matrix), its two real forms (ACLs and capabilities), and UNIX as it actually works: permission bits, setuid, the sticky bit, real and effective user IDs. It covers authentication and why passwords are stored salted and slow-hashed. Then the attacker's side: buffer overflows, TOCTOU races, privilege escalation. Finally the layered defenses that make modern systems hard to break: NX, stack canaries, ASLR, control-flow integrity, sandboxing with seccomp, and encryption.

Throughout this course, the OS has isolated **processes** from each other. The last question pushes isolation one level further.

### Unit 12 · Virtualization and Modern OS (→ OS-12)

**Can we run entire operating systems side by side on one machine, or isolate applications without a whole OS each?**

Unit 12 virtualizes the machine itself. It covers why classic x86 resisted it, and the four ways around that: trap-and-emulate, binary translation, paravirtualization, and hardware support. Memory needs two levels of translation, I/O uses virtio, and running VMs can live-migrate between hosts. Then **containers**: namespaces, cgroups, and layered images, the lighter alternative that shares one kernel. The course closes with real-time and distributed systems, and with Linux, Windows, and Android as case studies. Each of them turns out to be every unit of this course, assembled one particular way.

The story comes full circle. In Unit 1, the OS learned to stay in control of a machine while letting programs run directly on it. In Unit 12, a hypervisor does exactly the same thing to the OS.

### The three pillars

OSTEP organizes operating systems into three ideas. Here is where each lives in these notes:

| Pillar | Idea | Units |
|---|---|---|
| **Virtualization** | Make one physical resource look like many private ones | CPU: 2, 3. Memory: 6, 7. Whole machines: 12 |
| **Concurrency** | Make many things happening at once behave correctly | 2 (threads), 4, 5 |
| **Persistence** | Keep data safe across crashes and power loss | 8, 9, 10 |

Protection (Unit 11) runs underneath all three, and Unit 1 provides the hardware foundation for everything.

## How These Notes Are Built

- **Section IDs** like `OS-4.5` appear on every section heading. Every practice question is tagged with one, so a wrong answer links straight to the section that explains it. The same scheme extends to other subjects (`CN-3.2`, `DBMS-5.1`).
- **Arrows:** **←** points back to a concept this section builds on; **→** points forward to where an idea is developed further.
- **Each unit** contains detailed sections, a **Quick Revision Sheet** for the night before an exam, **Worked Numerical Problems** with full solutions, and **Scenario Questions** that test understanding through realistic situations, with collapsible answers so you can try first.
- **Sources:** the explanations follow the approach of *Operating Systems: Three Easy Pieces* (OSTEP), *The Linux Programming Interface* (TLPI), and Mythili Vutukuru's IIT Bombay OS lectures with the xv6 teaching OS, with Silberschatz's *Operating System Concepts* for the standard exam problems.

### Suggested paths

**Interview preparation (highest yield first):** OS-2 (processes, fork, threads) → OS-4 (synchronization) → OS-6 and OS-7 (paging, TLB, page replacement) → OS-5 (deadlock) → OS-3 (scheduling) → OS-10.4 (epoll, blocking vs non-blocking) → OS-12.2 (containers) → OS-8 (inodes, links, journaling).

**Course exam (numericals first):** OS-3.8 and OS-3 N1 to N8 (Gantt charts) → OS-5 N1 (banker's algorithm) → OS-6 N1 to N4 (translation, page tables, EAT) → OS-7 N2 to N4 (replacement traces) → OS-8 N1 and N2 (inode sizes) → OS-9 N3 and N4 (disk scheduling) → OS-9 N7 (RAID parity).

**Working from practice questions (the intended way):** attempt questions first, and when one goes wrong, follow its tag to the section, read that section and its ← prerequisites, then try the scenario questions at the end of that unit.
