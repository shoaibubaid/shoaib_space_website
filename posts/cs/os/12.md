# Unit 12: Virtualization and Modern OS

> **How to use this page.** Section IDs (`OS-12.2`) match the tags on practice questions. Arrows like **→ OS-0** point to the course introduction; **← OS-1.4** points back to something this section depends on.

The OS virtualizes the CPU (Units 2 and 3), memory (Units 6 and 7), and storage (Units 8 and 9) for processes. This unit applies the same idea one level down: virtualizing an **entire machine**, so several operating systems run side by side on one computer, each believing it owns the hardware. Then it looks at **containers**, which isolate applications while sharing one kernel, and closes with real-time and distributed systems and case studies of Linux, Windows, and Android that tie the whole course together.

## OS-12.1 · Virtual Machines and Hypervisors

### Terminology and motivation

- **Host:** the physical machine.
- **Virtual machine (VM):** a software-created copy of a machine: virtual CPUs, memory, disks, network cards.
- **Guest OS:** the operating system running inside a VM.
- **Hypervisor** or **virtual machine monitor (VMM):** the software that creates and runs VMs, multiplexing the real hardware among them, just as an OS multiplexes it among processes.

Why virtualize:

- **Consolidation:** many lightly loaded servers become VMs on a few hosts, saving hardware, power, and space (N5).
- **Isolation:** a crash or compromise in one VM does not affect others; a much stronger boundary than processes or containers.
- **Running different OSes** side by side (Linux and Windows), or old OSes on new hardware.
- **Snapshots and cloning:** save a VM's complete state, roll back, or copy it.
- **Live migration:** move a running VM to another host with almost no downtime (N4).
- **Testing and development:** try kernels and configurations safely.
- **Cloud computing:** AWS, Azure, and GCP rent out VMs; virtualization is their foundation.

History: IBM's VM/370 (1972) virtualized mainframes; VMware (1999) virtualized x86 with binary translation; Xen (2003) popularized paravirtualization; Intel VT-x and AMD-V (2005 to 2006) added hardware support, which is now universal.

### Type 1 vs type 2 hypervisors

```
 Type 1 (bare metal)                     Type 2 (hosted)
 +-------+ +-------+ +-------+           +-------+ +-------+
 | Guest | | Guest | | Guest |           | Guest | | Guest |   +-----------+
 |  OS   | |  OS   | |  OS   |           |  OS   | |  OS   |   | host apps |
 +-------+ +-------+ +-------+           +-------+ +-------+   +-----------+
 +----------------------------+          +------------------+
 |        Hypervisor          |          | Hypervisor (app) |
 +----------------------------+          +------------------+-------------+
 |         Hardware           |          |           Host OS              |
 +----------------------------+          +--------------------------------+
                                         |           Hardware             |
                                         +--------------------------------+
```

| | Type 1 (native, bare metal) | Type 2 (hosted) |
|---|---|---|
| Runs on | Directly on hardware | As an application on a host OS |
| Examples | VMware ESXi, Xen, Microsoft Hyper-V, KVM (Linux kernel acting as the hypervisor) | VirtualBox, VMware Workstation/Fusion, Parallels |
| Performance | Best; controls hardware directly | Extra overhead from the host OS |
| Use | Data centers, clouds | Desktops, development |
| Device drivers | Its own, or a privileged management VM (Xen's dom0) | Uses the host OS's drivers |

The line blurs: **KVM** is a Linux kernel module that turns Linux itself into a type 1 hypervisor (each VM is a Linux process, with **QEMU** in user space emulating devices), and Hyper-V runs Windows itself as a privileged partition above the hypervisor.

### Popek and Goldberg's requirements (1974)

A VMM should provide:

1. **Equivalence (fidelity):** a program runs in the VM exactly as on real hardware, except for timing and resource availability.
2. **Resource control (safety):** the VMM stays in complete control of the real resources; guests cannot escape or affect each other.
3. **Efficiency:** the vast majority of guest instructions run **directly** on the CPU without VMM intervention.

They classified instructions:

- **Privileged:** trap if executed in user mode (← OS-1.4).
- **Sensitive:** read or change privileged machine state (the mode, page table base, interrupt state), or behave differently depending on the mode.

**Theorem:** a machine can be virtualized with trap-and-emulate if **every sensitive instruction is privileged**. Then the VMM can run the guest kernel in user mode, and every sensitive operation traps to the VMM.

**Classic x86 violated this.** About 17 instructions were sensitive but **not** privileged. The famous example is **`POPF`**: in kernel mode it can change the interrupt-enable flag; in user mode it silently **ignores** that change instead of trapping. A guest kernel running in user mode that tried to disable interrupts with `POPF` would fail silently, and the VMM would never know. Similarly, `SGDT`/`SIDT` let user code read the location of descriptor tables, revealing that it runs in a VM (→ S1).

### Technique 1: trap-and-emulate

On a virtualizable architecture: run the guest OS kernel in **user mode** (or a less privileged ring). The VMM runs in kernel mode.

- Ordinary guest instructions (arithmetic, loads, stores) run **directly** on the CPU at full speed.
- When the guest kernel executes a privileged instruction (load a page table base, disable interrupts), the CPU **traps** to the VMM, which **emulates** its effect on the VM's **virtual** state (for example, recording "this VM's virtual interrupts are disabled"), then resumes the guest.

System calls get more expensive. OSTEP traces a guest application's system call:

```
 guest app:     syscall  --trap-->  VMM (real kernel mode)
 VMM:           "this belongs to the guest OS": jump to the guest OS's trap handler
                (which the guest registered with the VMM when it tried to set up its trap table)
 guest OS:      handles the system call (in user mode!); privileged instructions
                inside it trap to the VMM again
 guest OS:      return-from-trap  --trap-->  VMM
 VMM:           performs the real return to the guest app
```

One system call now costs several traps instead of one.

### Technique 2: binary translation

VMware's solution for classic x86 (1999): run guest **user** code directly, but **scan and rewrite guest kernel code** on the fly, just before it executes. Problematic instructions (like `POPF`) are replaced with calls into the VMM or with safe equivalents; translated blocks are cached, so each piece is translated once. It gave good performance on unmodified guests before hardware support existed.

### Technique 3: paravirtualization

**Modify the guest OS** to know it runs on a hypervisor. Instead of executing sensitive instructions, the guest makes explicit **hypercalls** (like system calls to the hypervisor): "update this page table entry," "block until the next event." Xen introduced this for x86 in 2003.

- Efficient: the guest batches work and avoids expensive traps and emulation.
- Requires changing the guest kernel (easy for Linux, impossible for closed-source OSes at the time).
- Today, full paravirtualization of the CPU is rare (hardware support replaced it), but **paravirtual devices** (virtio, below) and paravirtual clocks are everywhere.

### Technique 4: hardware-assisted virtualization

Intel **VT-x** and AMD **AMD-V** add a new CPU mode:

- **VMX root mode** for the hypervisor and **VMX non-root mode** for guests. Each has its own rings 0 to 3, so the guest kernel runs in **ring 0 of non-root mode**: it believes it is in kernel mode, and most privileged instructions work directly on its virtual state.
- Sensitive operations that the VMM must handle cause a **VM exit** to root mode; the hypervisor handles it and performs a **VM entry** back. Which events cause exits is configurable.
- A per-vCPU **VMCS** (virtual machine control structure) holds the guest's and host's saved state and the exit controls.
- Guest system calls and most interrupt-flag changes no longer involve the VMM at all.

VM exits are still expensive (hundreds to thousands of cycles, ~1 µs), so performance depends on **avoiding exits** (N1). ARM has an equivalent (EL2), as does RISC-V (the H extension).

### Memory virtualization

A guest OS manages page tables that map **guest virtual** addresses to what it believes are physical addresses: **guest physical** addresses. The hypervisor must map those to real **host physical** addresses. Two levels of translation:

```
 guest virtual  --(guest page tables)-->  guest physical  --(VMM's mapping)-->  host physical
```

**Shadow page tables (software):** the VMM builds, for each guest page table, a **shadow** table mapping guest virtual → host physical directly, and points the real MMU at the shadow. It write-protects the guest's page tables so that every guest update traps (a VM exit), letting the VMM keep the shadow in sync. TLB misses cost the same as native, but guest page-table updates (process creation, fork, page faults) cause many expensive exits (N3).

**Nested / extended page tables (hardware):** Intel **EPT** and AMD **NPT/RVI** let the MMU walk **both** levels in hardware: the guest's page tables (guest virtual → guest physical) and the VMM's EPT (guest physical → host physical). Guest page-table updates need no exits at all. The cost moves to **TLB misses**: each of the guest's page-table accesses itself needs a translation through the EPT, so with 4-level tables at both levels a worst-case walk takes up to **24 memory references** instead of 4 (N2). TLBs, page-walk caches, and **huge pages** in the host (← OS-7.7) keep this manageable. Nearly all modern hypervisors use EPT/NPT.

**Memory overcommitment:** the total memory assigned to VMs may exceed physical RAM (← OS-7.1). Techniques:

- **Ballooning:** a driver inside the guest (the balloon) allocates guest memory on request from the hypervisor, "inflating" so the guest's own memory manager decides which pages to give up (it knows which are least useful), and hands those frames back to the hypervisor. Better than the hypervisor swapping guest pages blindly, since it cannot tell which guest pages matter (N8).
- **Page sharing / deduplication:** identical pages across VMs (the same OS code, zero pages) are merged into one read-only copy with copy-on-write (← OS-7.2). Linux **KSM** (kernel samepage merging) does this for KVM. (It has side-channel risks, so clouds often disable it between customers.)
- **Hypervisor swapping** as a last resort, and memory compression.

### I/O virtualization

- **Full emulation:** the hypervisor emulates a real, well-known device (an Intel e1000 network card, an IDE disk). Unmodified guests use their normal drivers, but **every register access** by the guest driver causes a VM exit and emulation: slow (S9).
- **Paravirtual devices: virtio.** A standard, simple device interface designed for VMs: the guest driver and the hypervisor share rings of buffer descriptors in memory (like io_uring ← OS-10.4) and notify each other in batches, so many I/Os need one exit. Linux, Windows (with drivers), and most hypervisors support it.
- **Device passthrough:** give a VM direct, exclusive access to a physical device, with the **IOMMU** (← OS-10.1) remapping and restricting its DMA to the VM's memory (Linux VFIO). Near-native performance, but the device cannot be shared, and live migration is hard.
- **SR-IOV:** one physical device (typically a network card or NVMe drive) presents many **virtual functions**, each passed through to a different VM: sharing with native performance.

### CPU scheduling, time, and migration

- Each VM has **virtual CPUs (vCPUs)**, which the hypervisor schedules on physical CPUs like threads (in KVM, each vCPU literally is a Linux thread scheduled by CFS/EEVDF ← OS-3.7). With overcommitted CPUs, a guest sees **steal time**: time when its vCPU was ready but the hypervisor ran something else (S7).
- **Lock-holder preemption:** if the hypervisor deschedules a vCPU holding a spinlock, the guest's other vCPUs spin uselessly (← OS-4 S5). Hypervisors detect spinning (pause-loop exiting) and guests use paravirtual spinlocks.
- **Time:** a descheduled guest misses timer interrupts, so guest clocks drift unless the guest uses a paravirtual clock (kvm-clock, Hyper-V TSC page) that reads host-provided time (S3).
- **Live migration** (**pre-copy**): copy all memory to the destination while the VM keeps running; then repeatedly re-copy pages dirtied during the previous round (tracked with write protection or dirty bits); when the remaining dirty set is small, pause the VM briefly, copy the last pages and CPU state, and resume it on the destination. Downtime is typically tens of milliseconds. If the VM dirties memory faster than the network can copy it, pre-copy never converges; hypervisors then throttle the VM or use **post-copy** (resume at the destination first, fetch pages on demand) (N4).

### Related forms of virtualization

- **Emulation:** running code for a **different** CPU architecture by interpreting or translating every instruction (QEMU's TCG, Apple's Rosetta 2 translating x86 to ARM). Much slower than virtualization, where guest instructions run natively.
- **Application virtual machines:** the JVM or .NET CLR run a portable bytecode, with just-in-time compilation. They virtualize a language runtime, not a machine.
- **Nested virtualization:** running a hypervisor inside a VM (used for testing and in some clouds), supported by hardware extensions.
- **Unikernels** and **microVMs:** minimal VMs for single applications (← OS-1.6); **Firecracker** (used by AWS Lambda) boots a microVM in about 125 ms with a tiny device model.

## OS-12.2 · Containers

### OS-level virtualization

A **container** is a group of processes that share the host's **single kernel** but are isolated so that they see their own file system, process tree, network, and host name, and are limited in the resources they can use. Instead of virtualizing hardware, the kernel virtualizes its own **interfaces**.

```
 Virtual machines                            Containers
 +--------+ +--------+ +--------+            +--------+ +--------+ +--------+
 |  App   | |  App   | |  App   |            |  App   | |  App   | |  App   |
 |  libs  | |  libs  | |  libs  |            |  libs  | |  libs  | |  libs  |
 |Guest OS| |Guest OS| |Guest OS|            +--------+ +--------+ +--------+
 +--------+ +--------+ +--------+            +------------------------------+
 +------------------------------+            |   Host OS kernel (shared)    |
 |          Hypervisor          |            |  namespaces, cgroups, ...    |
 +------------------------------+            +------------------------------+
 |           Hardware           |            |           Hardware           |
 +------------------------------+            +------------------------------+
```

Earlier forms: `chroot` (1979; ← OS-11 S10), FreeBSD **jails** (2000), Solaris **zones** (2004). On Linux, containers are not a single kernel feature; they are assembled from several mechanisms.

### Namespaces: what a process can see

A **namespace** wraps a global resource so that processes inside it see their own isolated instance. Linux has:

| Namespace | Isolates | Effect inside the container |
|---|---|---|
| **PID** | Process IDs | The container has its own PID numbering; its first process is **PID 1**; it cannot see or signal host processes |
| **Mount (mnt)** | Mount table | Its own root file system (set up with `pivot_root`) and mounts |
| **Network (net)** | Network stack | Its own interfaces, IP addresses, routing tables, ports, firewall rules |
| **UTS** | Host name and domain name | Its own host name |
| **IPC** | System V IPC, POSIX message queues | Separate shared-memory segments and queues (← OS-2.4) |
| **User** | UIDs and GIDs | UID 0 inside can map to an unprivileged UID outside ("rootless" containers) |
| **Cgroup** | View of the cgroup hierarchy | Sees only its own cgroup subtree |
| **Time** | Some clocks | Its own offsets for monotonic and boot-time clocks |

Created with `clone()` flags (`CLONE_NEWPID`, `CLONE_NEWNET`, ... ← OS-2.5), `unshare()`, and joined with `setns()`. `lsns` lists them; `/proc/<pid>/ns/` shows a process's namespaces.

### cgroups: what a process can use

**Control groups** organize processes into a hierarchy and apply **resource limits and accounting** to each group (cgroup v2 has a single unified hierarchy under `/sys/fs/cgroup`):

- **cpu:** `cpu.weight` (proportional share, implemented by the fair scheduler ← OS-3.7) and `cpu.max` (hard quota: at most *quota* µs per *period* µs → N7).
- **memory:** `memory.max` (hard limit: exceeding it triggers reclaim and then the OOM killer **within the group** ← OS-7.1), `memory.high` (throttling threshold), `memory.low`/`min` (protection) (← OS-7.5).
- **io:** weights and bandwidth/IOPS limits per device (← OS-9.2).
- **pids:** `pids.max` limits the number of processes (stops fork bombs ← OS-11 N8).
- **cpuset:** which CPUs and NUMA nodes the group may use.

systemd places every service and user session in its own cgroup; Kubernetes resource requests and limits become cgroup settings.

### Images and union file systems

A container **image** packages an application with its libraries and a minimal user-space file tree (but **no kernel**). Images are built from **layers**: each layer is a set of file changes on top of the previous one (a base OS layer, a language runtime layer, the application layer). At run time, an **overlay** (union) file system (Linux **overlayfs**) stacks the read-only image layers and adds a thin writable layer on top for the container:

- Many containers share the same read-only layers on disk and in the page cache.
- Modifying a file from a lower layer copies it up into the writable layer (**copy-on-write** at file granularity ← OS-7.2).
- When the container is deleted, its writable layer disappears; persistent data goes into **volumes** (bind-mounted host directories).

### Security layers

Because containers share the kernel, isolation relies on restricting what container processes can ask of it (← OS-11.5):

- **Capabilities:** containers start with a reduced capability set (no `CAP_SYS_ADMIN`, no module loading).
- **seccomp:** a default filter blocks dozens of risky system calls (`mount`, `kexec_load`, `bpf`, `reboot`...).
- **User namespaces:** root inside is not root outside.
- **MAC:** SELinux or AppArmor profiles confine containers.
- **Read-only root file systems**, no-new-privileges flags (setuid binaries cannot gain privileges).

### The ecosystem

- **OCI** (Open Container Initiative) standardizes image and runtime formats.
- **runc** is the low-level runtime that actually creates the namespaces and cgroups and starts the process; **containerd** manages images and container lifecycles; **Docker** and **Podman** provide the user-facing tools.
- **Kubernetes** orchestrates containers across many machines: scheduling (bin-packing containers onto nodes by requested CPU and memory, a distributed version of ← OS-3), restarting failed containers, networking, and scaling.

### Containers vs VMs

| | Virtual machines | Containers |
|---|---|---|
| What is virtualized | Hardware | Kernel interfaces (OS-level) |
| Kernel | One per VM (any OS) | Shared host kernel (Linux containers run Linux) |
| Isolation strength | Strong: small hypervisor interface | Weaker: the whole kernel system-call interface is the boundary |
| Start time | Seconds (microVMs ~0.1 s) | Milliseconds to under a second |
| Memory overhead | A whole guest OS per VM (hundreds of MB) | Just the application's processes (N6) |
| Density per host | Tens | Hundreds to thousands |
| Image size | GBs (full OS disk) | MBs (layers, shared) |
| Performance | Near native (with VT-x/EPT/virtio) | Native (they are ordinary processes) |
| Typical use | Multi-tenant clouds, different OSes, strong isolation | Packaging and deploying applications, microservices, CI |

A **kernel vulnerability** can let a process escape any container on the host, which is why clouds running untrusted code combine both: containers inside lightweight VMs (**Kata Containers**, **Firecracker**), or a user-space kernel that intercepts system calls (**gVisor**) (S4).

## OS-12.3 · Real-Time and Distributed Operating Systems

### Real-time operating systems (RTOS)

Recall the requirements (← OS-1.2, OS-3.6): correctness depends on **meeting deadlines**; the key property is **predictability** (bounded worst-case latency), not throughput.

Typical RTOS characteristics:

- **Preemptive, priority-based scheduling** with fixed priorities (rate-monotonic) or EDF (← OS-3.6); the highest-priority ready task always runs.
- **Bounded interrupt and dispatch latency:** short, non-preemptible sections; interrupts disabled only briefly (← OS-3.6).
- **Priority inheritance** or ceiling protocols on mutexes, to bound priority inversion (← OS-4.8, Mars Pathfinder).
- **No demand paging** (or all memory locked), since a page fault's delay is unpredictable (← OS-1 S10, OS-7 S9); often static memory allocation, no swapping.
- **Small footprint:** kernels of kilobytes, suitable for microcontrollers; often a single address space with no MMU, and tasks are threads.
- Deterministic system-call timing; minimal features.

Examples: **FreeRTOS** and **Zephyr** (microcontrollers, IoT), **VxWorks** (aerospace, Mars rovers), **QNX** (a microkernel used in cars and medical devices ← OS-1.6), **RTEMS**. **Linux with PREEMPT_RT** (merged into mainline in 6.12) makes almost the entire kernel preemptible, turns interrupt handlers into schedulable threads, and replaces most spinlocks with priority-inheriting sleeping locks, giving soft to firm real-time latencies of tens of microseconds on suitable hardware.

### Distributed systems and distributed OS

A **distributed system** is a set of independent computers, each with its own memory and OS, communicating over a network, that appears to users as a single coherent system (← OS-1.2).

- **Network operating system:** each machine runs its own OS; users are aware of the multiple machines and access remote resources explicitly (SSH, file sharing, remote login).
- **Distributed operating system:** a single OS spanning machines, managing them as one system, with **transparency**: users need not know where resources are (location transparency), whether they moved (migration transparency), whether they are replicated (replication transparency), or whether something failed (failure transparency). Research systems: Amoeba, Sprite, Plan 9. In practice, this role is played today by middleware and cluster managers (Kubernetes, Hadoop/YARN, distributed file systems) running on ordinary OSes.

Fundamental problems (each a course of its own):

- **Partial failure:** some machines or links fail while others continue; a node cannot distinguish a slow peer from a dead one.
- **No shared memory, no global clock:** processes communicate only by messages (← OS-2.4) with unpredictable delays. **Lamport logical clocks** order events consistently (if a happens before b, then C(a) < C(b)); vector clocks capture causality exactly.
- **Remote procedure calls** (← OS-2.4) and their semantics under failure (at-most-once, at-least-once).
- **Distributed file systems:** NFS, AFS, and their consistency semantics (← OS-8.3); large-scale systems like GFS/HDFS store replicated chunks across thousands of disks.
- **Mutual exclusion and deadlock** without shared memory (← OS-4, OS-5): token passing, central coordinators, distributed deadlock detection (a global wait-for graph no single node sees).
- **Consensus:** getting nodes to agree on one value despite failures: **Paxos** and **Raft**, used for replicated configuration stores such as etcd (which Kubernetes relies on) and ZooKeeper.
- **CAP theorem:** in the presence of a network **partition**, a system must choose between **consistency** (every read sees the latest write) and **availability** (every request gets a response).

## OS-12.4 · Case Studies: Linux, Windows, and Android

### Linux

A monolithic, modular kernel (← OS-1.6) first released by Linus Torvalds in 1991, now the kernel of servers, supercomputers, Android phones, and most embedded devices.

| Area | Design (with links to the units) |
|---|---|
| Structure | Monolithic, loadable modules; runs on dozens of architectures |
| Processes and threads | Everything is a **task** (`task_struct`), created by `clone()` with sharing flags; threads share an address space (← OS-2.5) |
| Scheduling | Classes: deadline, real-time (FIFO/RR), fair (CFS → EEVDF since 6.6), idle; `sched_ext` for BPF schedulers (← OS-3.7) |
| Synchronization | Spinlocks, mutexes, RCU, futexes for user space; lockdep (← OS-4, OS-5.1) |
| Memory | 4/5-level paging, demand paging, COW, page cache, active/inactive lists and MGLRU, buddy + SLUB, THP, overcommit + OOM killer (← OS-6, OS-7) |
| File systems | VFS with ext4, XFS, Btrfs, and many more; dentry and inode caches (← OS-8) |
| Block and I/O | blk-mq with none/mq-deadline/bfq/kyber; NVMe; epoll; io_uring (← OS-9, OS-10) |
| Security | UNIX permissions, POSIX ACLs, capabilities, LSMs (SELinux, AppArmor), seccomp, namespaces (← OS-11) |
| Virtualization | KVM, namespaces + cgroups for containers (← OS-12.1, OS-12.2) |
| Extensibility | **eBPF:** small programs loaded into the kernel at run time, checked by a **verifier** for safety (bounded loops, valid memory access), then JIT-compiled; used for tracing, networking (XDP), security policies, and schedulers, without writing kernel modules |

Philosophy: "everything is a file" (devices, pipes, sockets, `/proc`, `/sys`), small composable tools, and a stable user-space ABI ("we do not break user space").

### Windows (NT family)

Designed by Dave Cutler's team (formerly of VMS) and released as Windows NT in 1993; the basis of every Windows since XP. It is usually called a **hybrid** kernel (← OS-1.6):

```
 user mode:    applications | Win32 subsystem (csrss) | services | WSL2 (Linux in a VM)
               ntdll.dll (system call stubs)
 ---------------------------------------------------------------------------
 kernel mode:  Executive: I/O manager, object manager, memory manager,
               process/thread manager, security reference monitor,
               cache manager, configuration manager (registry), ALPC
               Kernel (ntoskrnl): scheduling, interrupts, synchronization
               Device drivers (layered)       |   Win32k (windowing, graphics)
               HAL (hardware abstraction layer)
 ---------------------------------------------------------------------------
               Hardware (and optionally the Hyper-V hypervisor below everything)
```

Key features:

- **Object manager:** kernel resources (processes, threads, files, events, semaphores, sections) are **objects** accessed through **handles**, a per-process table much like UNIX file descriptors (and, like them, capabilities ← OS-11.2). Every object has a security descriptor.
- **Processes and threads:** the thread is the unit of scheduling; 32 priority levels with dynamic boosts for interactive threads (← OS-3.7); no `fork`, only `CreateProcess` (← OS-2.3).
- **Memory manager:** demand paging with per-process **working sets** trimmed under pressure, standby and modified page lists (← OS-7.3), memory-mapped **section** objects, and large pages.
- **I/O manager:** asynchronous I/O throughout, using **I/O request packets (IRPs)** passed through stacks of layered drivers; **I/O completion ports** for scalable servers (← OS-10.4).
- **NTFS** with the MFT, journaling, and ACLs (← OS-8.7); the **registry** as a hierarchical configuration database.
- **Security:** access tokens, SIDs, ACLs, integrity levels, User Account Control, and virtualization-based security (running sensitive parts of the OS in a separate hypervisor-protected environment).
- **WSL:** WSL 1 translated Linux system calls into NT kernel calls; **WSL 2** runs a real Linux kernel in a lightweight Hyper-V VM (S11).

### Android

The world's most widely used OS, built on the Linux kernel with a very different user space:

- **Linux kernel** (← everything above), with additions, notably **Binder**, a fast capability-based IPC mechanism through which apps call system services (← OS-2.4, OS-11.2).
- **App sandbox:** each app runs as its **own Linux UID** (← OS-11.2) in its own process, confined by **SELinux** policies and seccomp; permissions (camera, contacts) are granted by the user.
- **ART** (Android Runtime): apps are compiled from Dalvik bytecode, ahead of time and just-in-time. New app processes are forked from a pre-initialized process called **zygote**, so they share its already-loaded runtime and framework pages via **copy-on-write** (← OS-7.2), making startup fast and saving memory.
- **Memory management without swap to flash:** **zram** compressed swap in RAM, and the **low-memory killer** (now `lmkd`, driven by PSI pressure metrics ← OS-7.6), which kills background apps according to their importance; apps must save state and expect to be killed (S12).
- Power management is central: aggressive suspend, wakelocks, and restrictions on background work.

### Comparison

| | Linux | Windows | Android |
|---|---|---|---|
| Kernel type | Monolithic + modules | Hybrid (NT) | Linux (monolithic) |
| Process creation | `fork` + `exec`, `clone` | `CreateProcess` | fork from zygote |
| Scheduler | EEVDF (fair) + RT classes | Priority-based, 32 levels, boosts | Linux scheduler, tuned for UI and power |
| IPC | Pipes, sockets, shared memory, signals | ALPC, named pipes, sections | Binder |
| File system | ext4, XFS, Btrfs | NTFS, ReFS | ext4 / F2FS |
| Access control | UNIX permissions + ACLs, capabilities, SELinux/AppArmor | ACLs on all objects, tokens, integrity levels | UID per app + SELinux + permissions |
| Low-memory policy | Page reclaim, swap, OOM killer | Working-set trimming, page file | zram + low-memory killer |

## Quick Revision Sheet

- Hypervisor/VMM multiplexes hardware among guest OSes. Type 1: on hardware (ESXi, Xen, Hyper-V, KVM). Type 2: on a host OS (VirtualBox, Workstation).
- Popek–Goldberg: equivalence, resource control, efficiency. Virtualizable with trap-and-emulate iff every sensitive instruction is privileged. Classic x86 was not (POPF).
- Techniques: trap-and-emulate, binary translation (VMware), paravirtualization (Xen hypercalls), hardware assist (VT-x/AMD-V: root/non-root modes, VMCS, VM exits).
- Performance = avoid VM exits.
- Memory: guest virtual → guest physical → host physical. Shadow page tables (exits on guest PT writes) vs EPT/NPT (hardware 2D walk: up to 24 references per TLB miss with 4+4 levels; huge pages help).
- Overcommit: ballooning (guest chooses what to give up), page sharing/KSM (COW), hypervisor swapping.
- I/O: emulation (exit per register access), virtio (shared rings, batching), passthrough with IOMMU, SR-IOV.
- vCPUs are scheduled like threads (steal time, lock-holder preemption); paravirtual clocks; live migration by iterative pre-copy (or post-copy).
- Emulation (other ISA) ≠ virtualization; JVM = application VM; microVMs (Firecracker).
- Containers: shared kernel + namespaces (pid, mnt, net, uts, ipc, user, cgroup, time) + cgroups (cpu, memory, io, pids, cpuset) + overlay file systems + capabilities/seccomp/MAC.
- Container PID 1 must reap zombies and handle signals.
- Containers: fast, dense, weaker isolation; VMs: strong isolation, heavier. Combine with Kata/Firecracker/gVisor for untrusted code.
- RTOS: priority preemption, bounded latency, priority inheritance, no demand paging, small (FreeRTOS, VxWorks, QNX, Zephyr, PREEMPT_RT Linux).
- Distributed: partial failure, no global clock (Lamport clocks), RPC, consensus (Paxos, Raft), CAP.
- Linux: tasks, EEVDF, SLUB, VFS, blk-mq, io_uring, LSMs, KVM, eBPF. Windows NT: hybrid, HAL, executive, objects and handles, IRPs, NTFS, tokens. Android: Linux + Binder + UID per app + zygote + lmkd/zram.

## Worked Numerical Problems

### N1 · The cost of VM exits (OS-12.1)

**Question.** A VM exit plus re-entry costs 1.5 µs of CPU time. (a) A CPU-bound guest causes 1,000 exits per second (timer and interrupt handling). Overhead? (b) A guest uses an **emulated** network card; each packet requires about 5 device-register accesses, each causing an exit, at 100,000 packets per second. Overhead? (c) The same traffic through **virtio**, with one notification exit and one interrupt injection per batch of 64 packets (count both as exits)?

**Answer.**

(a) 1,000 × 1.5 µs = 1.5 ms per second: **0.15%**. Hardware virtualization makes CPU-bound guests nearly native.

(b) 100,000 × 5 = 500,000 exits/s × 1.5 µs = 0.75 s per second: **75%** of a vCPU spent on exits alone, before the hypervisor even emulates the device.

(c) 100,000 ÷ 64 ≈ 1,563 batches × 2 exits = 3,125 exits/s × 1.5 µs ≈ 4.7 ms: **≈ 0.5%**. Paravirtual I/O is about 160 times cheaper here, which is why virtio (or passthrough) is standard.

### N2 · Two-dimensional page walks (OS-12.1)

**Question.** A guest uses 4-level page tables, and the host uses 4-level extended page tables. (a) On a TLB miss, what is the worst-case number of memory references for the page walk? (b) Including the data access, compare the effective access time with native execution, for a 99% TLB hit rate and 100 ns per memory reference. (c) What if the host uses 2 MB pages (3-level EPT walk)?

**Answer.**

(a) Each of the guest's 4 page-table entries is at a **guest physical** address, which must be translated through the 4-level EPT (4 references) and then read (1 reference): 4 × 5 = 20. The final guest physical address of the data must also be translated through the EPT: 4 more. Total **24** references (formula: (n + 1)(m + 1) − 1 with n = m = 4), versus **4** natively.

(b) Native miss: 4 + 1 = 5 references = 500 ns. Virtualized miss: 24 + 1 = 25 references = 2,500 ns.
- Native EAT = 0.99 × 100 + 0.01 × 500 = **104 ns**.
- Virtualized EAT = 0.99 × 100 + 0.01 × 2,500 = **124 ns** (about 19% slower).

(c) m = 3: walk = (4 + 1)(3 + 1) − 1 = 19 references; miss = 20 × 100 = 2,000 ns. EAT = 99 + 20 = **119 ns**. Huge pages in the guest shorten n as well. (In practice, page-walk caches make actual walks much shorter than the worst case.)

### N3 · Shadow page tables vs EPT (OS-12.1)

**Question.** A guest runs a build workload that creates 200 processes per second; setting up each process writes about 500 page-table entries, and there are 10,000 guest context switches per second. With shadow page tables, each guest page-table write and each guest CR3 load causes an exit costing 2 µs (including updating the shadow). (a) Overhead per second with shadow paging? (b) With EPT? (c) What does EPT pay instead?

**Answer.**

(a) PTE writes: 200 × 500 = 100,000 exits. CR3 loads: 10,000 exits. Total 110,000 × 2 µs = **0.22 s per second (22% of a vCPU)**.

(b) With EPT, the guest updates its own page tables and loads CR3 directly: **no exits** for these.

(c) Longer **TLB-miss** walks (N2). For workloads with frequent page-table changes (process creation, fork, memory-mapping churn), EPT wins decisively; for a workload with rare page-table changes but terrible TLB locality, shadow paging could be faster. Hardware vendors added EPT precisely because process-heavy workloads suffered so much under shadow paging.

### N4 · Live migration (OS-12.1)

**Question.** A VM with 8 GB of memory is migrated over a link that copies 1 GB/s. While running, it dirties memory at 200 MB/s. Pre-copy stops iterating when the remaining dirty memory is below 50 MB, then pauses the VM and copies the rest. (a) Trace the rounds: data sent, time, and pages dirtied. (b) Total migration time, total data sent, and downtime? (c) What if the VM dirties 1.2 GB/s?

**Answer.**

(a)
| Round | Sent | Time | Dirtied during the round |
|---|---|---|---|
| 1 | 8 GB | 8 s | 200 MB/s × 8 s = 1.6 GB |
| 2 | 1.6 GB | 1.6 s | 320 MB |
| 3 | 320 MB | 0.32 s | 64 MB |
| 4 | 64 MB | 0.064 s | 12.8 MB (< 50 MB: stop iterating) |
| Stop-and-copy | 12.8 MB + CPU state | ≈ 13 ms | VM paused |

(b) Total time ≈ 8 + 1.6 + 0.32 + 0.064 + 0.013 ≈ **10 s**. Data sent ≈ 8 + 1.6 + 0.32 + 0.064 + 0.013 ≈ **10 GB** (25% more than the VM's memory). **Downtime ≈ 13 ms**: users barely notice.

(c) The VM dirties memory **faster** than the link can copy it, so each round leaves **more** to send than the previous one: pre-copy **never converges**. Hypervisors respond by throttling the VM's vCPUs (auto-converge) to reduce its dirty rate, by compressing pages, or by switching to **post-copy** (move execution first, then pull pages on demand over the network, which risks the VM failing if the source dies mid-migration).

### N5 · Server consolidation (OS-12.1)

**Question.** A company has 40 physical servers, each with 8 cores averaging 10% utilization and using 12 GB of RAM. It wants to consolidate onto hosts with 32 cores and 256 GB each, keeping hosts below 70% CPU and 90% memory, plus one spare host for failover. (a) How many hosts? (b) If each old server draws 300 W and each new host 800 W, what is the power saving?

**Answer.**

(a) CPU demand: 40 × 8 × 0.10 = **32 cores**. Usable per host: 32 × 0.7 = 22.4 cores → ⌈32 / 22.4⌉ = **2 hosts**. Memory demand: 40 × 12 = **480 GB**; usable per host 256 × 0.9 ≈ 230 GB → ⌈480 / 230⌉ = **3 hosts**. Memory is the binding constraint: 3 hosts + 1 spare = **4 hosts**. (Page sharing and ballooning could reduce the memory need.)

(b) Before: 40 × 300 W = 12 kW. After: 4 × 800 W = 3.2 kW. Saving ≈ **8.8 kW (73%)**, plus cooling, space, and hardware maintenance.

### N6 · VM vs container density (OS-12.2)

**Question.** A host has 128 GB of RAM, 8 GB reserved for the host itself. An application needs 250 MB of memory. Running it in a VM adds about 600 MB for the guest kernel and base OS services; running it in a container adds about 10 MB. (a) How many instances fit either way? (b) Startup takes about 20 s for a full VM, 0.15 s for a Firecracker microVM, and 0.3 s for a container. Why the differences? (c) What does the VM buy in exchange?

**Answer.**

(a) Available 120 GB = 122,880 MB. VMs: 122,880 / 850 ≈ **144**. Containers: 122,880 / 260 ≈ **472**. (Containers also share read-only image layers and library pages in the page cache.)

(b) A full VM must run firmware, boot a guest kernel, initialize emulated devices, and start an init system and services (← OS-1.7). A microVM has a minimal device model and a stripped-down kernel, cutting boot to a fraction of a second. A container is just `clone()` with new namespaces, joining cgroups, mounting the overlay, and `exec` of the application: no kernel to boot.

(c) **Isolation.** Each VM has its own kernel behind a small hardware-enforced interface, so a kernel exploit inside one VM does not compromise the others. All containers share one kernel with a large system-call interface. VMs can also run different OSes and kernel versions.

### N7 · CPU quotas and throttling in cgroups (OS-12.2)

**Question.** A container has `cpu.max = "50000 100000"` (quota 50 ms per 100 ms period) on an 8-core host. (a) How much CPU is it allowed? (b) Its service runs 4 CPU-bound threads in parallel. What happens within each period, and what latency can a request see? (c) With a single CPU-bound thread? (d) How would `cpu.weight` behave differently?

**Answer.**

(a) 50 / 100 = **0.5 CPU** on average, however many cores it uses.

(b) The 4 threads together consume 4 ms of quota per ms of wall time, so the 50 ms quota is used up after **12.5 ms**; the whole group is then **throttled** (not scheduled at all) for the remaining **87.5 ms** of the period. A request arriving just after throttling starts waits up to about 87.5 ms, even though the host may have idle cores: the classic cause of mysterious tail-latency spikes in containers. (Fixes: raise the quota, reduce the thread count to match it, or use a shorter period.)

(c) One thread runs 50 ms, then is throttled for 50 ms: requests can still wait up to 50 ms.

(d) `cpu.weight` sets a **proportional share** used only under contention (CFS/EEVDF weights ← OS-3.7): if the host is idle, the container may use all 8 cores; when busy, it gets its share. No hard cap, so no throttling pauses, but also no guaranteed ceiling.

### N8 · Memory overcommit with ballooning and sharing (OS-12.1)

**Question.** A host has 64 GB, of which 4 GB is used by the hypervisor. It runs 4 VMs, each configured with 24 GB. (a) What is the overcommit ratio? (b) Each VM's working set grows to 20 GB. How much must be reclaimed? (c) Each VM contains 3 GB of pages identical across all four (same OS image). How much does page sharing save? (d) How should the remainder be reclaimed, and what happens if the working sets really need it?

**Answer.**

(a) Configured 4 × 24 = 96 GB for 60 GB usable: **1.6×** overcommit.

(b) Demand 4 × 20 = 80 GB vs 60 GB available: **20 GB** must be reclaimed.

(c) 4 copies of 3 GB become 1 shared copy: saves **9 GB**. 11 GB remain to reclaim.

(d) **Balloon** each VM by about 2.75 GB: each guest's memory manager gives up its least valuable pages (clean page cache first, then its own swap), making informed choices. If the guests' working sets genuinely need 20 GB each, reclaiming them causes **thrashing** (← OS-7.6) inside the guests, or, if the hypervisor swaps guest memory itself, **double paging** (the host swaps out a page, then the guest decides to evict the same page and must first fault it back in). The only real fix is fewer VMs per host or more RAM: overcommit relies on VMs not all needing their maximum at once.

## Scenario Questions (Test Your Understanding)

### S1 · Why x86 needed tricks (OS-12.1)

Before 2005, why couldn't a VMM simply run an x86 guest kernel in ring 3 and rely on traps (trap-and-emulate)? How did VMware and Xen work around it, and what finally solved it?

<details><summary>Answer</summary>

x86 had **sensitive instructions that were not privileged**, violating Popek and Goldberg's condition. The guest kernel, run in ring 3, would execute them without trapping, and they would behave differently from ring 0: `POPF` silently ignored changes to the interrupt flag (so the guest thought it had disabled interrupts but had not), and instructions like `SGDT` and `SMSW` revealed real machine state. The VMM never got the chance to emulate them, breaking equivalence and control.

**VMware** used **binary translation**: rewrite guest kernel code on the fly, replacing problematic instructions with safe sequences or calls into the VMM. **Xen** used **paravirtualization**: modify the guest kernel to call the hypervisor explicitly (hypercalls) instead of executing those instructions. **Intel VT-x / AMD-V** solved it in hardware: a separate non-root mode where the guest kernel runs in ring 0, and the hardware forces exits to the VMM for configured sensitive operations.

</details>

### S2 · System calls inside a VM (OS-12.1)

Describe the path of a guest application's `read()` system call under pure trap-and-emulate (guest kernel in user mode), and explain why hardware virtualization makes it cheaper.

<details><summary>Answer</summary>

Under trap-and-emulate: the app's `syscall` traps to the **VMM** (the only code in real kernel mode). The VMM recognizes that it belongs to the guest, looks up the trap handler the guest registered (the guest's attempt to install its trap table was itself trapped and recorded), and transfers control to the guest kernel's handler, which runs in user mode. As the guest kernel works, each privileged instruction traps to the VMM again. Its return-from-trap also traps, and the VMM performs the real return to the application. One system call becomes several traps and switches (OSTEP's appendix traces this).

With VT-x, the guest kernel runs in **non-root ring 0**: the application's `syscall` goes **directly** to the guest kernel, which returns directly. The VMM is involved only if the system call needs something that causes a VM exit (for example, touching an emulated device). Most system calls run at native speed.

</details>

### S3 · The clock that runs slow (OS-12.1)

On an overloaded virtualization host, a guest's clock falls several seconds behind real time per hour, and timeouts inside the guest behave strangely. Why? How do modern hypervisors and guests prevent this?

<details><summary>Answer</summary>

A guest traditionally keeps time by **counting timer interrupts** (← OS-10.1). When the host is busy, the guest's vCPU is descheduled for long stretches, and the virtual timer interrupts are delayed or coalesced, so the guest counts fewer ticks than actually elapsed. Its clock drifts, and time-based logic (timeouts, rate limiting) breaks.

Fixes: **paravirtual clocks** (kvm-clock, Xen pvclock, Hyper-V's reference TSC page), where the hypervisor exposes shared memory from which the guest reads accurate host time and scaling factors; stable, invariant TSC counters virtualized by the hardware; tickless guests; and NTP or chrony inside the guest to correct residual drift.

</details>

### S4 · Untrusted code in containers (OS-12.2)

A company wants to let customers upload arbitrary code and run it on shared servers. An engineer proposes Docker containers with default settings. Why is that risky, and what would you use instead?

<details><summary>Answer</summary>

All containers on a host share **one kernel**, and their isolation boundary is the kernel's entire system-call interface: hundreds of system calls and many subsystems (file systems, networking, eBPF, io_uring). Any exploitable kernel bug lets a malicious container gain host root and reach every other customer's data (container escapes have happened repeatedly). Misconfigurations (privileged containers, mounted Docker sockets, extra capabilities) make it worse.

For untrusted, multi-tenant code, add a stronger boundary: run each tenant's containers inside a **lightweight VM** (Kata Containers, **Firecracker** microVMs as used by AWS Lambda and Fargate), or use **gVisor**, which intercepts the container's system calls in a user-space kernel so few reach the host kernel. Keep strict seccomp profiles, user namespaces, no extra capabilities, and fast kernel patching.

</details>

### S5 · The container that ignores Ctrl+C (OS-12.2)

A containerized app runs directly as the container's PID 1. `docker stop` always waits 10 seconds and then kills it forcibly, and over time the container accumulates zombie processes from the shell commands the app runs. Explain both, and give the standard fix.

<details><summary>Answer</summary>

In a PID namespace, the first process has **PID 1** and takes on init's special roles (← OS-2.3):

- The kernel does **not** apply the default action (terminate) for signals sent to PID 1 from within its namespace unless it has installed a handler. `docker stop` sends `SIGTERM`; an app that never installed a `SIGTERM` handler (because normally the default action would kill it) simply ignores it. After the timeout, Docker sends `SIGKILL`, which is always delivered (from the parent namespace), killing it with no cleanup.
- Orphaned processes inside the container are re-parented to PID 1, which is expected to **reap** them with `wait()`. The app does not, so they become **zombies** (← OS-2.3).

Fix: run a tiny init as PID 1, such as **tini** or `docker run --init`, which forwards signals to the app and reaps orphans; or make the app handle `SIGTERM` and reap children itself.

</details>

### S6 · The JVM that got OOM-killed (OS-12.2)

A Java service runs in a container limited to 2 GB (`memory.max`) on a 64 GB host. Older JVMs would size their heap from the machine's total memory and get killed by the OOM killer under load, with no Java `OutOfMemoryError`. Explain.

<details><summary>Answer</summary>

Inside a container, `/proc/meminfo` and `sysconf` report the **host's** memory (64 GB), not the cgroup limit, and the number of CPUs similarly reflects the host. An old JVM sized its default maximum heap as a fraction of 64 GB (for example, 16 GB). As the heap grew past 2 GB, the **cgroup memory controller** hit `memory.max`, could not reclaim enough, and invoked the OOM killer **within the cgroup**, sending `SIGKILL` to the process: the JVM never got a chance to throw `OutOfMemoryError`.

Modern JVMs (Java 10+, backported to 8u191) are **container-aware**: they read cgroup limits and size the heap accordingly (and `-XX:MaxRAMPercentage` tunes it). The general lesson applies to any runtime that auto-sizes thread pools or caches: read the cgroup limits, not the host totals.

</details>

### S7 · Slow for no visible reason (OS-12.1)

A web server in a cloud VM becomes slow at certain times of day. Inside the guest, `top` shows only 40% CPU utilization for the server, but a high `st` (steal) value of 30%. What is steal time, what does it indicate, and what can be done?

<details><summary>Answer</summary>

**Steal time** is time during which the guest's vCPU was **ready to run but the hypervisor was running something else**: another VM on the same physical CPU (a noisy neighbour), or hypervisor work. From the guest's point of view, time passes but its code does not execute; requests take longer although the guest's own CPU usage looks moderate.

It indicates CPU **overcommitment** on the host at those times. Remedies: move to an instance type with **dedicated** cores (no overcommit), resize, migrate to a less loaded host, or spread load. Burstable instance types that exhaust their CPU credits show similar symptoms.

</details>

### S8 · Clones with the same secrets (OS-12.1)

An administrator creates 20 VMs by cloning a snapshot of one configured VM, taken while it was running. Later, security scans find that all 20 have identical SSH host keys, and a cryptographic library in two of them generated the same random numbers after resume. Why, and how are these problems avoided?

<details><summary>Answer</summary>

A snapshot captures the **entire state**: disk contents (including SSH host keys generated at first boot) and, for a running snapshot, **RAM**, including the kernel's random-number generator state and user-space RNG buffers. Every clone resumes with identical state, so any randomness drawn afterwards can be identical across clones until enough new entropy is mixed in. Identical keys and nonces break cryptography (for example, a repeated nonce can reveal a private key).

Avoidance: generalize images before cloning (`cloud-init` or `sysprep` regenerates host keys and machine IDs on first boot); prefer cloning from a powered-off template; hypervisors expose a **VM generation ID** that changes on snapshot restore or clone, which the guest kernel uses to reseed its RNG; and provide `virtio-rng` for fresh entropy from the host.

</details>

### S9 · Emulated vs virtio network (OS-12.1)

After migrating an old VM to a new host, network throughput drops from about 9 Gb/s to under 1 Gb/s and the host's CPU usage for that VM is very high. The VM's configuration shows its network card as "e1000." Explain and fix.

<details><summary>Answer</summary>

"e1000" is a **fully emulated** Intel NIC. The guest's standard e1000 driver programs it by reading and writing device registers; each access causes a **VM exit** into the hypervisor, which emulates the hardware's behaviour, often several exits per packet (N1). At high packet rates, the exits dominate: CPU usage soars and throughput collapses.

Switch the VM to a **virtio-net** device (installing virtio drivers in the guest if needed): the guest and host exchange packets through shared memory rings and notify each other in batches, with very few exits; with vhost-net, packet processing even happens in the host kernel. For the highest performance, use SR-IOV or device passthrough.

</details>

### S10 · Linux for the flight controller? (OS-12.3)

A drone startup plans to run the flight-stabilization loop (which must run every 1 ms, with deadlines strictly met) as a normal process on the same stock Linux that runs the camera and Wi-Fi software. What could go wrong, and what architectures are used instead?

<details><summary>Answer</summary>

Stock Linux optimizes for throughput and fairness, not bounded worst-case latency: a page fault (← OS-7 S9), a long non-preemptible kernel section, an interrupt storm from Wi-Fi, memory reclaim, or a higher-priority kernel thread can delay the loop by milliseconds occasionally. A missed control deadline in flight can mean a crash. Averages look fine in testing, but the rare worst case matters (← OS-1 S10).

Common designs: run the control loop on a separate **microcontroller with an RTOS** (FreeRTOS, NuttX, or similar, as in PX4-based flight controllers) and keep Linux on a companion computer for the camera and networking; or use **PREEMPT_RT** Linux with the loop as a `SCHED_FIFO` thread, memory locked (`mlockall`), CPU isolation for that core, and measured worst-case latencies; or a hypervisor/partitioning system that runs an RTOS and Linux side by side on separate cores.

</details>

### S11 · WSL 1 vs WSL 2 (OS-12.4, OS-12.1)

Microsoft's WSL 1 ran Linux programs on Windows by translating Linux system calls into NT kernel operations. WSL 2 instead runs a real Linux kernel inside a lightweight Hyper-V VM. Why the change, and what trade-off did users notice?

<details><summary>Answer</summary>

Translating system calls requires re-implementing Linux semantics on top of the NT kernel: `fork` (which NT does not have ← OS-12.4), Linux file permissions and case-sensitive names on NTFS, `epoll`, `/proc`, and so on. Many features were incomplete or slow (file-heavy workloads like `git` and package managers were notoriously slow), and some programs (Docker, which needs namespaces and cgroups) could not work at all. A real Linux kernel in a VM gives **full compatibility** and native Linux file-system performance, and thanks to hardware virtualization the overhead is small.

The trade-off: files are now inside the VM's virtual disk (ext4), so accessing **Windows files from Linux** (or Linux files from Windows) crosses the VM boundary through a network file protocol and is slower than with WSL 1, and networking and memory are those of a separate VM (the VM's memory must be reclaimed from it).

</details>

### S12 · Why the app restarted (OS-12.4, OS-7.6)

A user switches from a game to a camera app and back; the game restarts from its title screen. The phone has 8 GB of RAM and no disk swap. Explain what Android did, and what the game's developers should do.

<details><summary>Answer</summary>

While the camera (a memory-hungry foreground app) ran, memory pressure rose. Android does not swap to flash; it compresses some pages into **zram**, and when pressure persists, its **low-memory killer** (`lmkd`, reacting to PSI pressure signals) kills processes starting with the least important: cached and background apps. The game's process was killed (like the OOM killer ← OS-7.1, but proactive and by importance). Returning to it started a new process.

Android expects this: apps must save their state when moved to the background (`onSaveInstanceState`, `onStop`, or persisting to storage) and restore it when recreated, so a killed-and-restarted app resumes where the user left it. Games should also keep their memory footprint small to reduce the chance of being chosen.

</details>
